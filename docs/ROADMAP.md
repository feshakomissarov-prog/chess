## Порядок работы

Не строить сразу всё приложение. Каждый инкремент должен запускаться, иметь проверяемые критерии готовности и не ломать предыдущие функции. Для крупных изменений Codex работает в отдельной ветке/PR, а не бесконтрольно переписывает main.

## Следующий большой блок: M4.5 (решение от 2026-11-01)

**Единое большое ТЗ для десктопного Codex:** [M4_5_BATCH_ANALYSIS_PERSONAL_DIAGNOSTICS.md](specs/M4_5_BATCH_ANALYSIS_PERSONAL_DIAGNOSTICS.md). Codex выполняет блоки последовательно в отдельных проверяемых PR; каждый блок оставляет работоспособный клиент. Исходная база и аналитический код уже есть — не начинать проект с нуля.

1. **Аудит покрытия:** сколько завершённых партий, какие имеют Lichess evaluations/Stockfish runs, на каких позициях пробелы; один профиль/источник и валидная ревизия линии.
2. **Пополнение Lichess:** по официальному API забирать *уже существующие* оценки при инкрементальном импорте и целевой проверке неоценённых старых игр; никакого недокументированного POST/скрейпинга для массового заказа серверного анализа. Если Lichess не анализировал партию — это нормально.
3. **Массовый локальный Stockfish:** очередь с resume/cancel/pause, стабильными настройками движка и ограничением CPU; один раз запустить обработку всего недостающего архива и возобновлять позже без повторных расчётов. Независимый поток загрузки готовых данных Lichess, не смешивать разные оценки в одну.
4. **Метрики качества:** собственные ходы, зевки/ошибки/неточности, подтверждённые лучшие ходы, CPL/мат, результаты, отдельно дебют/миттельшпиль/эндшпиль, контроль, цвет, период, rating band. Явные определения и версии классификатора, знаменатель *оценённых собственных ходов* и покрытие данных.
5. **Личный профиль и дебюты:** ECO/название/семейство, типовые позиции потери оценки, сегментация по цвету и рейтингу соперника, повторяющиеся проблемы с минимальной выборкой и кликабельными примерами из партий; не выдавать малые выборки за «слабость».
6. **Рабочие экраны и доказательная приёмка:** фоновая очередь + дашборд прогресса, переход из показателя в партию/ход, регрессии на 10k+ партий, восстановление после прерывания, сохранность SQLite и Fair Play.

**Почему M4.5, а не перенумерация:** ранее согласованные M5 (голос) и M6 (ИИ-тренер) сохраняются, но стартуют после завершения аналитической платформы. Старые документы M3/M4 остаются историей реализации; новые требования имеют приоритет только в части *следующего* блока.

**Ограничение Lichess:** документированный публичный API предоставляет экспорт игр с готовыми evaluations и кэш отдельных cloud-positions, но не гарантирует публичную возможность массово заказать серверный анализ. Поэтому основной гарантируемый механизм полного покрытия — **локальный Stockfish**. Соблюдать один сетевой запрос за раз, HTTP 429 и ограничения Lichess, не обходить лимиты. См. [официальные API](https://lichess-org.github.io/api/) и [API tips](https://lichess.org/page/api-tips).

**Технический долг:** [Issue #5](https://github.com/feshakomissarov-prog/chess/issues/5) содержит отложенные локальное обновление/QA новой UX-версии, реальный Stockfish E2E и резервную копию перед миграцией. Он не препятствует *проектированию* M4.5, но релизный запуск анализа на пользовательской SQLite должен проходить с защитой данных.

## Технические правила на старте

- Отделять шахматные правила от отображения.
- Не хранить в git токены, пароли, персональные партии и базы данных.
- Не включать в онлайн-игре стороннюю шахматную помощь, включая численные оценки позиции.
- Сохранять простую возможность локального запуска и тестов.
- Корневой `AGENTS.md` уже подготовлен по мотивам других репозиториев владельца; Codex обязан соблюдать его и не переписывать без отдельной задачи.
