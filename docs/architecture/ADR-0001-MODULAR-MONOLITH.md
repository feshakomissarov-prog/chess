# ADR-0001 — модульный монолит с контролируемым асинхронным I/O

**Дата решения:** 2026-11-03  
**Статус:** архитектурный выбор принят 03.11.2026; **реализован в draft PR #44** (SHA 9a59b21, Windows CI 604 PASS), **не слит**. Под новый согласованный UX он адаптируется в одном следующем цикле [ARCH-UX-01 v1.1](../specs/ARCH_UX_01_UNIFIED_EXECUTION_SPEC.md), без перехода на микросервисы.

## Контекст

Chess Coach поставляется как одно настольное Windows приложение на Python 3.12 / PySide6. В проекте есть большие связанные классы `MainWindow`, `GameRepository`, `LichessService`; сложные online-game event streams, durable SQLite state, Stockfish UCI и fail-closed Fair Play. Цель следующего этапа — уменьшить связанность и вероятность регрессий, не менять функциональность и не создавать сеть микросервисов.

## Решение

**Один развертываемый модульный монолит**, один основной Qt процесс и отдельный дочерний Stockfish (когда это разрешено). Доменные данные/показатели отделены от UI, application coordinators от DB/network adapters, Qt signal bridge от worker threads. Один владелец Fair Play leases; один управляемый transactional writer policy; отдельные приоритетные execution lanes для interactive game, safety control, background Lichess и UCI.

Выполнение — отдельный большой draft PR ARCH-01 с внутренними проверяемыми коммитами по [ТЗ](ARCHITECTURE_REFACTOR_EXECUTION_SPEC.md) и [целевой карте](CHESS_COACH_TARGET_ARCHITECTURE.md), после того как код и продуктовые решения M4.6 объединены в main.

## Чего НЕ делаем

- Не переписываем проект целиком на Rust, C++ или иной GUI framework, не добавляем микросервисы или Python plugin framework.
- Не создаём новый engine: Stockfish уже native.
- Не включаем обязательные p95/latency benchmark checks или нагрузочные 3k/10k/50k test suites на текущем этапе **по решению владельца**.
- Не меняем PGN, метрики, сохранённые пользовательские данные, SQLite schema или Fair Play поведение ради «чистой архитектуры».
- Не делаем product features дебютов, глубокого обучения, GPT, ML, голоса одновременно с рефакторингом.

## Оптимизация без преждевременной миграции языка

Целевое оборудование — обычный Windows-ноутбук 4 ядра / 8 ГБ RAM / SSD. Изоляция UI event loop от HTTP/долгих SQLite запросов, короткие транзакции, правильные индексы/кэш, отменяемые фоновые операции и отсутствие блокировок game stream важнее гипотетической скорости Python.

Можно позже заменить **отдельный доказанно узкий CPU-bound** вычислительный компонент Rust/PyO3/C++ при выполнении *всех* условий: воспроизводимый профиль узкого места, неудача алгоритмической оптимизации, стабильный Python-level контракт, сохранённые Windows package/CI, лицензии, изоляция ошибок/памяти, прежняя методология аналитики/Fair Play, возможность отката. Никакого Rust toolchain в ARCH-01.

## Последствия и риски

**Плюсы:** предсказуемая ответственность, удобнее тестировать гонки, быстрее делать новые аналитические модули, данные не привязаны к Qt, проще отлаживать проблемы параллельных задач.

**Цена:** временные совместимые фасады, дополнительные интерфейсы, отдельные тесты границ, риск ошибок при переносе сигналов/транзакций. Задача не считается успешной, если «папок стало больше», но взаимодействия всё ещё скрытые.

**Контроль:** полный Windows CI exact SHA и функциональные/сafety тесты без ослабления; затем независимое ревью и физическая Windows-проверка владельца до merge. Реальные токены/пользовательские SQLite запрещены в CI.

## Дополнение 04.11.2026 — архитектура согласована с шестью UX-маршрутами

Решение **остаётся в силе**: один Windows Python/PySide6 процесс, одна SQLite, управляемый Stockfish, единственный источник состояния активной игры/учётной записи и единый fail-closed Fair Play. Новая оболочка содержит Главная/Играть/Мои партии/Анализ/Обучение/Прогресс и Настройки, но **не создаёт отдельные backend services под каждую страницу**. Отдельные UI pages обращаются к application coordinators/read models, которые переиспользуют существующие SQLite/Lichess/UCI adapters.

Для принятого UX критичны: одна BoardView active→finished, сохранение final-sync/SQLite после исчезновения старого ResultPage; видимые команды takeback/draw/resign, stable route selection; общий score/provenance для Home/Details/Review/Progress и единый inspector/background lanes. Локальные исследования PGN/FEN не изменяют исходные партии. Не вводить микросервисные RPC, отдельные account/session state или новые SQLite tables ради пользовательской навигации.

Нормативные требования, приоритеты и тестовые gates — [ARCH-UX-01 v1.1](../specs/ARCH_UX_01_UNIFIED_EXECUTION_SPEC.md), [source-backed аудит](../reviews/ARCH_UX_01_PRE_FLIGHT_AUDIT.md). Существующие W0–W9/ARCH-FIX в draft PR #44 являются базой, не поводом переписывать всё. **No merge** без отдельного разрешения владельца.
