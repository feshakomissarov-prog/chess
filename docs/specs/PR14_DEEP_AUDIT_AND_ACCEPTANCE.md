## Оценка проверки

Прежние P0 по коду действительно исправлены: `GET /api/games/user/{username}` использует официальный `until` (не `before`), `division=true`, `finished=true`, `ongoing=false`; запись `games`, normalized revision, `raw_pgn`, Lichess metadata, mapping и backfill checkpoint идёт атомарно в одной SQLite-транзакции и async worker ждёт commit; инкрементальная пагинация `puzzle/activity` обходит DESC-страницы через `before`; в статистике исключены неопределённые результаты из ничьих; Stockfish блокируется при переданном непустом наборе active human games; после 429 предусмотрено повторное восстановление OAuth.

Это **не** доказательство сохранности всего живого архива или корректной работы настоящего Stockfish. Моки не заменяют E2E. В работе остаются нижеуказанные **конкретные ошибки и пробелы**. Их нужно исправить одним большим заданием, но по последовательным подблокам и с минимально необходимыми новыми тестами. **Не менять интерфейс правых стрелок, не делать голос/ИИ, не сливать PR и не запускать реальный импорт без разрешения владельца.**

## A. P0 — не открывать raw-only варианты как standard chess

**Подтверждённый дефект:** `GameRepository._import_unsupported_archive_record_sync` создаёт строку `games` с `initial_fen='' `, `moves=''`, `import_error='Unsupported variant...'`, `raw_pgn`, но без `game_revisions`. При этом `MainWindow.show_saved_games() -> open_selected() -> _open_saved_game()` без проверки variant и `import_error` присваивает `session.initial_fen=''` и вызывает `session._rebuild_board()`. Последний делает `chess.Board('')` и бросает ValueError. Достаточно одного импортированного Crazyhouse/Antichess game: пользователь выбирает «Открыть для просмотра», получает ошибку Qt/Python. Ссылка на код: `repository.py::_import_unsupported_archive_record_sync`, `window.py::_open_saved_game`, `session.py::_rebuild_board`.

**Исправить:** в библиотеке такие партии явно помечать как «Вариант X — просмотр доски/анализ не поддерживается»; разрешать PGN export/метаданные, не пытаться строить standard Board, не запускать Stockfish; открытия из графика и истории тоже проверяют поддержку. При желании выводить raw PGN в read-only окне. `chess960` — отдельно поддержать правильно или маркировать unsupported; не объявлять все варианты работающими, когда нет доски.

**Тест:** импорт raw-only Crazyhouse → открыть через библиотеку (Qt offscreen) → нет исключения, вывод понятного статуса, `export_pgn` побайтно сохраняет оригинал. Отдельно PGN с неуспешным парсингом, но доступными ID и raw text: не пропускать весь последующий архив без recovery/явной ошибки, разрешить quarantine.

## B. P0 — корректное закрытие приложения во время архивной синхронизации

**Подтверждённый риск гонки:** `MainWindow.closeEvent()` вызывает `self.lichess.close()`, затем `self.game_repository.shutdown()`. Однако `LichessService.close()` не выставляет `self._archive_stop` и `self._puzzle_stop`. В фоне остаются import worker и OAuth puzzle callback/потоки. `close()` join'ит daemon threads не более 1.5 сек на поток, после чего repository закрывает writer. Рабочий импорт может вызвать `_writer.submit(...)` **после** `executor.shutdown()`, получить `RuntimeError`, либо не завершиться до выхода. В тесте быстрых 2501 fake-записей это не проверяется.

**Исправить:** при shutdown выставить stop обоим импортам, отменить OAuth puzzle callback, безопасно и ограниченно дождаться их завершения **до** shutdown SQLite writer; соединение stream корректно закрыть; при закрытии GUI без зависания показать, если операция ещё сворачивается, и не утверждать successful. Как корректно избежать гонки между закрытием очереди и задачей writer — отдельный lifecycle протокол (accepting_work flag/join workers/flush) без `sleep` и без грубого `os._exit`.

**Тест:** закрыть `MainWindow` с запущенным fake NDJSON worker, медленным SQLite commit и puzzle worker; после выхода все импорты stopped, нет submit-after-shutdown/необработанных исключений/незакрытых sqlite handles, cursor не продвинут дальше сохранённых строк, быстрый повторный запуск позволяет продолжить. Windows WinError 32 не воспроизводится.

## C. P0 — owner-specific соперник/результат при нескольких аккаунтах

**Подтверждённая модельная ошибка:** `repository.import_archive_record` сохраняет `color` и rating в `account_games` (хорошо), но `_save_snapshot_sync` при повторном импорте того же `game_id` другим аккаунтом делает `opponent=excluded.opponent`. В `account_games` **не хранится opponent**. Например A играет с B: импорт A пишет `games.opponent=B`; импорт B переписывает `games.opponent=A`; после этого поиск и фильтр статистики по сопернику для A возвращают неверный результат. `StatisticsService.summary(opponent=... , account_id=...)` по-прежнему использует `g.opponent`.

**Исправить:** нормализовать аккаунт-специфичные `opponent/name/rating/color` в `account_games` и использовать их при `account_id` фильтрах, в списке библиотеки и статистике. Общие нейтральные поля `white_player/black_player` остаются в `games`. Не переименовывать текущие game_id и не ломать старые PGN.

**Тест:** одна игра (A белые, B чёрные) импортируется двумя аккаунтами в обоих порядках; для A соперник B и цвет белый, для B соперник A и цвет чёрный; фильтр по opponent, W/L, rating и заметки корректны независимо от порядка. Проверить миграцию с `user_version=5`.

## D. P1 — полнота backfill при длительной синхронизации и запоздалом окончании игр

**Конкретная логическая дыра:** `ArchiveSync._run()` сначала делает backfill по `until_ms` на момент старта, но `repository.finish_archive_backfill()` устанавливает `incremental_since = now` **на момент окончания** backfill. Incremental перезапрашивает только `now-24h`. Если начальный импорт занял >24 ч (пауза/выключение/медленный архив) и за это время завершились партии, созданные после initial `until` либо уже старые активные игры завершились позднее, некоторые записи могут не попасть ни в backfill, ни в 24-часовое перекрытие. Даже при быстрой синхронизации старый начатый correspondence game, завершившийся сегодня, может иметь `createdAt` намного раньше overlap. То есть обещание «все игры + позже изменившиеся» сейчас шире действительных гарантий.

**Исправить:** хранить **отдельную фиксированную дату начала backfill** и после него догружать диапазон `since=backfill_started_at - overlap`, не пропуская игры, возникшие за время импорта; для длинных correspondence/позднего Lichess анализа предусмотреть **ограниченный явный refresh** завершённой игры по id или последних изменённых без повторного full archive. Честно описать предел API: если endpoint выбирает по дате создания, изменения старых игр нельзя автоматически обнаружить только по «новым датам» без повторной проверки части старого архива. No-progress/10k boundary ограничение и checkpoint сохранить.

**Тест:** заморозить часы: backfill старт 2025-01-01, пауза/возобновление 2025-01-04; новая игра создана 2025-01-02 и завершена 2025-01-03; после синхронизации игра присутствует. Correspondence началась за месяц до backfill, завершилась во время него; отдельный targeted refresh обновляет историю/результат. Replay без дублей.

## E. P1 — реальная версия Stockfish и честный cache key

**Факт:** `CompletedGameAnalyzer.analyze` читает `engine_version = str(engine.id.get('version', 'unknown'))`. Стандартный UCI-ответ `id` содержит обычно `name` и `author`, **отдельного `version` может не быть**. После обновления бинарника многие Stockfish run будут иметь `engine_version='unknown'`, а кэш ключуется по этой строке + nodes/ply. Получится cache hit чужой версии движка для той же партии.

**Исправить:** включить в engine identity фактическое `id name` (часто включает версию), по необходимости fingerprint/path/executable SHA256, версию параметров/классификатора; не хэшировать движок на каждом открытии GUI, вычислять один раз при выборе бинарника. Для кэша с 'unknown' не давать ложный collision между разными бинарниками. Повторный анализ одинакового binary+settings должен попадать в кэш, обновлённый engine — нет. Также локально ограничивать запуск движка **когда активная человеческая игра начинается**, включая event `gameStart`; остановку запущенного анализа выполнить своевременно (сейчас stop_event проверяется только между positions, но не прерывает текущий `engine.analyse`).

**Тест:** fake UCI id `{"name":"Stockfish 16.1"}` и `{"name":"Stockfish 17"}` без version → разный run/cache; одна версия → cache hit; запуск human `gameStart` во время анализа → stop and engine quit, не ждать следующей партии.

## F. P1 — кнопки Lichess и минимальная UX-диагностика

- `--offline` — **ожидаемо неактивная** кнопка Lichess, без OAuth/запросов. «Подключено» — кнопка connect выключена и есть disconnect.
- В `_lichess_status` статус `Ограничение Lichess (429)` всё ещё попадает в `connected=True`, включая 429 при **неудачном первичном restore**, когда `_lichess_connected=False`; из-за этого кнопки игры могут ошибочно стать активными, хотя запросы будут отклоняться global cooldown. Привязать разрешение онлайн-действий к подтверждённой авторизации + cooldown, а не только к текстовому префиксу. После паузы — контролируемый «Повторить подключение». Не создавать дубли streams при повторе и смене аккаунта.
- На экране архива и puzzle:read показывать **последнюю успешную синхронизацию, число реально новых записей и error/resume state**, а не только число обработанных (из-за overlap их больше). Не выдавать «синхронизировано» на сетевом обрыве.

**Тест:** restore 429 до authenticated → AI/friend/archive/active games disabled; после паузы однократный retry → enabled; offline всегда disabled. При закрытии окна с import — без активных controls.

## G. Важные проверки, которые недостаточно покрыты нынешним CI

1. **2501 партий** в PR#14 тестируется с **in-memory fake Repository**, не с настоящим SQLite + нормализованными строками/файлом backup; **1005 same timestamp** тоже проверены через fake Repository. Дополнить меньшим, но настоящим integration test на SQLite (например 200 партий, 2 аккаунта, crash at DB commit) и перезапуск процесса. 2501 SQLite integration можно делать nightly/slow, не обязательно в каждом CI, но утверждение «2501 записаны в реальную SQLite» пока недоказано.
2. Сравнение фактического числа уникальных завершённых игр с ожидаемым fake API count, сырых PGN/ходов, более сложного PGN с setup FEN, неполной eval/clock, повторных импортов и ошибочной записи на середине страницы.
3. Для `puzzle/activity`: воспроизвести 2501 **DESC-страницу** и restart **на настоящем SQLite** (отдельно backfill и incremental); одинаковые timestamps; не выдумывать точный timestamp решения при отсутствии поля. High watermark не прыгать при retry.
4. UI обычного Windows запуска (не `--offline`) проверить отдельно **только владельцу**; Codex не инициирует OAuth/массовый import. Видимый оконный smoke и библиотека с unsupported games — offscreen тесты.
5. Актуализировать Windows Actions версии `checkout/setup-python` после проверки совместимости с Node 24; устранение warning не даёт права менять защиту Windows. Не изменять Dr.Web или execution policy.
