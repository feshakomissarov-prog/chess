## 1. Продуктовая цель, важное уточнение терминов

У владельца Chess Coach должны быть **два ясно различимых намерения**:
- **«Тренировка»**: отработка избранной темы (например, `mateIn1`, `mateIn2`, `mateIn3`, `mateIn4`, `mateIn5`, вилка, связка, эндшпиль), подбор сложности, подсказки, повтор, локальная история и серия; **НЕ изменять ни официальный рейтинг Lichess, ни новый локальный рейтинг Chess Coach**. Старые исторические CC rating events оставить без изменений и не выдавать их за актуальный официальный рейтинг.
- **«На рейтинг Lichess»**: задачи с официальной фиксацией результата через Lichess `puzzle:write`, сервер сам рассчитывает изменение рейтинга и присылает `ratingDiff` / `glicko`. Приложение показывает **только подтверждённый официальный результат**, не вычисляет его локальной Elo-псевдоформулой. По мере роста рейтинга задачи **в среднем** становятся сильнее благодаря подбору относительно рейтинга; гарантии «каждая следующая сложнее предыдущей» нет.

**Важно:** режим «На рейтинг» — это изменение реального аккаунта Lichess, **не рейтинг локальной тренировки CC** и не рейтинг партий Blitz/Rapid. Приложение обязано обозначать различие на Home, внутри тренажёра, в истории и в ошибках сети. Не добавлять третий дублирующий режим «проверка», тренерскую игру против Lichess, отдельную базу или полный redesign.

### 1.1. Сверено с официальными источниками Lichess

| Источник | Подтверждённые факты | Следствие для Chess Coach |
| --- | --- | --- |
| [Batch GET и POST, официальная схема API](https://github.com/lichess-org/api/blob/master/doc/specs/tags/puzzles/api-puzzle-batch-angle.yaml) | `GET /api/puzzle/batch/{angle}` требует `puzzle:read`, `nb` 1…50, `difficulty` = easiest/easier/normal/harder/hardest; `POST` того же маршрута требует **отдельный** `puzzle:write` и сообщает результаты для обновления рейтинга. Ответ POST может также вернуть следующие задачи при `nb > 0`. | Одна доска, одна общая логика задач, разные **действия с сервером**. Не изобретать недокументированные endpoints или большие выгрузки. |
| [PuzzleBatchSolveRequest](https://github.com/lichess-org/api/blob/master/doc/specs/schemas/PuzzleBatchSolveRequest.yaml) | У каждого элемента `solutions[]` есть `id`, `win`, `rated`. | Явный и проверяемый `rated:true` **только для рейтинговой попытки**; в тренировке **вообще не POST**. |
| [PuzzleBatchSolveResponse](https://github.com/lichess-org/api/blob/master/doc/specs/schemas/PuzzleBatchSolveResponse.yaml) | `rounds[]` включает `id`, `win`, `ratingDiff`; `glicko.rating/deviation/provisional` может быть в ответе; `puzzles[]` — новые позиции. | Изменение официальных очков брать из ответа Lichess по **тому же ID**. Отсутствующие данные не выдумывать. |
| [GET Puzzle Activity](https://github.com/lichess-org/api/blob/master/doc/specs/tags/puzzles/api-puzzle-activity.yaml), [схема](https://github.com/lichess-org/api/blob/master/doc/specs/schemas/PuzzleActivity.yaml) | Серверная история содержит timestamp, puzzle ID, win, но **не обещает ratingDiff** в каждой записи. | При сетевой неопределённости можно сверить факт/результат, но нельзя из истории вывести точное Δ. |
| [Lichess Themes](https://lichess.org/ru/training/themes) | Темы `mateIn1`, `mateIn2`, `mateIn3`, `mateIn4`, `mateIn5` и другие действительно существуют. | Дать знакомый выбор по теме, не обещать, что «Мат в 3» означает точно три пользовательских щелчка: шахматная линия включает ответы соперника. |
| [Lichess Puzzle Storm](https://lichess.org/page/storm) | Альтернативный режим Storm — нерейтинговый, задачи усложняются внутри серии. | Не смешивать «тренировочные темы» с отдельным Storm: **таймер, гонка, отдельный стрик-режим вне scope**. |

**Важное различие факта и продуктового решения:** официальная схема подтверждает возможность отправить `win/rated`, но **не устанавливает, в какой момент наша кнопка «Подсказка», «Показать решение» или переключение режимов считается проигрышем**. Ниже это **предлагаемая и согласованная для Chess Coach семантика**, а не цитата из поведения сайта. Если реальный Lichess API противоречит этому после тестового sandbox/fake исследования, Codex документирует конкретный конфликт до отправки реальной записи и не выдумывает серверную политику.

## 2. UX: два входа, один экран, без смены существующей темы

### 2.1. Главная страница — та же карточка с шахматной доской

Карточку Home назвать **«Задачи»** (вместо двусмысленного «Следующая задача»); маленькую доску и preview существующей сохранённой задачи **оставить**. Под заголовком компактно показывать: «Lichess: 1917» (лишь если есть проверенное серверное значение; иначе «Рейтинг Lichess: не загружен»). Ниже — две **рядом расположенные доступные** CTA:
- **[Тренировка]** — вторичный визуальный стиль; всегда доступна при действующем `puzzle:read`, без права на запись.
- **[На рейтинг]** — акцентная; если `puzzle:write` ещё не предоставлен — **явно открывает разрешение** только после нажатия, а не скрыто. До согласия пояснение «Изменяет официальный рейтинг Lichess» видно рядом/в tooltip и доступно клавиатуре.
- **[Повторить эту]** — маленькая текстовая ссылка в карточке **только если есть сохранённая задача**, не третья конкурирующая большая кнопка. Replay всегда unrated, никогда не списывает очки. Нажатие на доску Home открывает **именно этот повтор**, а не неизвестный режим; accessible description явно говорит об этом.
- Нет сохранённого preview → нейтральный placeholder, обе основные кнопки видны; ошибка preview не ломает NEW. Не рисовать стартовую расстановку за настоящую задачу.

Иллюстрация информационной иерархии, **не требование ASCII-отрисовки**:

~~~
┌──────────────────── ЗАДАЧИ ─────────────────────┐
│ [МАЛЕНЬКАЯ ДОСКА]   Рейтинг Lichess: 1917      │
│                      Сохранённая задача ...    │
│                      Повторить эту             │
│                                                │
│ [       Тренировка       ] [   На рейтинг   ]  │
└────────────────────────────────────────────────┘
~~~

Не увеличивать высоту существующей карточки сверх доступного Home layout: при узкой левой колонке кнопки можно **сделать в две строки**, сохранить размеры доски и отступы, не вытеснять важные KPI/недавние партии, не добавлять общий scroll trap.

### 2.2. Экран «Обучение → Решение задач»

Оставить знакомые **три зоны**: слева список тем, по центру большая доска + лента красных/зелёных результатов + **одна** «Следующая задача», справа профиль, текущая задача, история и статус сохранения. **Над доской**, рядом с уже существующими фильтрами, добавить визуальный **двухпозиционный выбор**:

~~~
Решение задач
[  ТРЕНИРОВКА  ] [  НА РЕЙТИНГ LICHESS  ]
  Профиль: ad_fesha        Тема: Смешанная       Сложность: Обычная
  [ ] Автопереход после чистого решения

       Ваш ход · белые                     Рейтинг Lichess: 1917
              [ ДОСКА ]                    ID: ...
        ✓  ✓  ×  !  ✓                     Серия: 2
  [Подсказка] [Показать решение] [Повторить] [Следующая задача →]
~~~

Использовать `QButtonGroup`/checkable buttons/radios как **настоящую одну взаимоисключающую настройку**, с явным активным состоянием, доступным названием и клавиатурной навигацией. Не создавать два экземпляра страницы/доски или два независимых набора Qt workers. Смена режима всегда **сознательная и видимая**, состояние профиля/доски/сессии принадлежит одному controller.

**В тренировке:** слева открыты «Темы», «Мат в 1/2/3/4/5+», «Вилка», «Связка», «Жертва» и другие поддерживаемые API; справа «Тренировка · не влияет на рейтинг Lichess», локальные успехи/ошибки, streak; можно подсказки, reveal, replay, ручная NEXT/автопереход. Фильтры `mix` и относительная сложность остаются. Начальная сложность «Обычная».

**На рейтинг:** заголовок «Официальный рейтинг Lichess: 1917» без «CC: 1498» как альтернативы; при подтверждении ответа появляется «+N / −N · подтверждено Lichess» с новой серверной оценкой. Смешанная + обычная — **дефолт**, чтобы заранее не подсказывать мотив; пользователь всё же может выбрать тематический рейтинг, поскольку официальный API принимает `angle`. В этом случае показывать заметную метку «Тема: Мат в 3» — не обещать равную информативность рейтинга смешанных и тематических задач. Сложность относительна **серверному рейтингу**, не должна автоматически прыгать после каждого правильного ответа: подбор Lichess сам учитывает уровень.

Смысл цветов: зелёный — чистое решение, красный — первая ошибка, жёлтый — с подсказкой (в тренировке), серый — раскрыто/пропущено/повтор, нейтральный — ещё решается. **В рейтинговом** статус отправки выделяется текстом/иконкой отдельно от цвета решения (сервер не обязан мгновенно подтвердить результат). Любой цвет дублирован символом и accessible label. Никакой новой навязчивой анимации или modal QMessageBox при обычной подсказке/решении/Next.

### 2.3. Настройки, память, клавиатура, адаптивность

- У нового профиля режим по умолчанию **«Тренировка»**. На Home две отдельные CTA явно определяют стартовый режим. Запоминать **последний сознательный выбор режима отдельно по Lichess account ID** в QSettings, но **не включать запись рейтинга скрыто при автоматическом открытии**. Если последнее значение rated, обычный вход через sidebar «Обучение» показывает выбранный режим и **ожидает явного пользовательского действия для новой рейтинговой попытки**, а не запускает POST/сессию сам.
- Текущая тема и сложность можно помнить раздельно по режимам; от старого `puzzles/theme` перенести в тренировку, не сбрасывая старые настройки. Тема rated по умолчанию `mix`.
- У автоперехода видимая ✓ при ON; подписать «Автопереход после чистого решения»; в rated он запускается **только после серверного подтверждения результата**, в тренировке после локального CLEAN. Сохранённый флажок — per-account и per-mode, без непреднамеренного наследования.
- `Tab` проходит «режим → профиль → тема/сложность → доска → кнопки» в понятном порядке; `Space/Enter` переключают режим; фокус не пропадает после перерисовки. Толтип и AccessibleName помогают понять, влияет ли действие на рейтинг. Обычные ПКМ-стрелки/ЛКМ/колесо/повтор работают как в PUZ-UX-05.
- Референсные размеры Windows native: широкий 1672×941 / 100%; 1280×720 / 125%; 1120×640 / 150%. При компактном размере переключатель и основной CTA остаются доступны без обрезания доски; горизонтальная лента результатов с короткой видимой историей; правая панель прокручивается независимо. Не менять основную палитру, фигуры и плотность UI произвольно.

## 3. Формальная модель режимов — правило «никакой ретроактивной оценки»

**Модель:** `PuzzleMode = TRAINING | LICHESS_RATED`. Поле `mode_at_attempt_start` фиксируется в момент загрузки **конкретной новой задачи**; оно неизменно до завершения этой попытки. `Puzzle source` (new/replay/local) и `mode` — **разные оси**; replay всегда `unrated` независимо от вкладки.

| Событие | Тренировка (TRAINING) | На рейтинг (LICHESS_RATED) |
| --- | --- | --- |
| Получить задачу | GET batch/read-only, небольшая уникальная очередь из PUZ-UX-05 | GET с разрешением рейтингового профиля, по 1 задаче или следующий элемент из подтверждённого POST; без массового скачивания |
| Первый правильный ход | Продолжить линию, локальная индикация | Продолжить линию, результат ещё НЕ отправлен до завершения |
| Чистый успех | ✓, локальная история/серия; **никакой рейтинг не меняется** | Один POST `rated:true, win:true` после успешного завершения всей линии; ждать ACK |
| Первый неверный легальный ход | ✕, серия 0; можно повторить попытку, без POST | Сразу зафиксировать локально rated-loss intent; **один** POST `rated:true, win:false`, после чего продолжать разбор без новой рейтинговой отправки |
| Подсказка | Мгновенно показать, жёлтая плитка, без POST/попапов | Предварительно видимое пояснение «Подсказка засчитывает эту рейтинговую попытку как ошибку»; при первом запросе подсказки — один rated-loss, затем мгновенная подсказка без модального подтверждения |
| «Показать решение» | Показать сразу, отметить локально, без POST | Аналогично подсказке: rated-loss один раз, сразу показать линию. Не открывать неожиданное окно подтверждения |
| «Повторить» | Старую позицию unrated, без нового счётчика/рейтинга | Любой replay unrated, даже если исходная задача была scored; не отправлять повторный POST |
| «Следующая» после завершения | Быстро выбрать уникальную из очереди, иначе GET | После подтверждённого сервером результата открыть следующую предложенную сервером задачу/GET |
| Авторизация / история | `puzzle:read`; локальные результаты | `puzzle:read puzzle:write`; сервер подтверждает официальный результат |

**Исключение:** неправильный первый ход делает рейтинговую попытку проигранной, но пользователь может продолжать решение/видеть подсказки **без второго POST**. Отметка «Ошибка» остаётся красной. Если серверное сообщение ещё не дошло, UI не пишет «−15» заранее.

### 3.1. Переключение в любой момент — без обмана и случайных штрафов

У пользователя всегда есть **видимый переключатель**. Это не обещание «сменить оценку у уже начатой головоломки», потому что так можно злоупотреблять рейтингом и потерять смысл результатов.

- **До загрузки задачи / между задачами:** сразу переключить mode. При выборе ranked показать auth CTA при необходимости; никакого POST.
- **Из TRAINING во время незавершённой задачи:** предложить **«Завершить текущую тренировку / Перейти к рейтинговой задаче»**. Если пользователь выбирает переключиться сейчас — локально фиксировать текущую как пропуск (без рейтинга) **один раз**, затем загружать совершенно новую рейтинговую задачу; старую тренировочную НЕ засчитывать как ranked.
- **Из RATED до первого действия пользователя на ещё не начатой задаче:** разрешить отказаться и переключиться без POST; в локальной истории отметить `discarded_before_attempt`. Не выдавать это за результат сервера.
- **Из RATED после первого правильного частичного хода, но до завершения:** явный лаконичный диалог: «Попытка уже начата. Прервать и отправить поражение на Lichess?» Кнопки **«Продолжить»** (default) / **«Прервать и перейти к тренировке»**; только после подтверждения записать `win:false rated:true`. Никаких автоматических рейтинговых штрафов только из-за простого переключения вкладки/закрытия окна.
- **Из RATED после ошибки или подсказки:** результат уже является поражением независимо от дальнейшего разбора. Можно перейти к тренировке, но не удалять pending/unknown серверную запись.
- **При неопределённом ответе сервера на уже отправленный scored result:** переключение в TRAINING разрешено, но **новую RATED задачу не начинать**, пока состояние результата не выяснено/разрешено вручную. Показывать честную причину и действие «Проверить результат», не выдавать ещё один rated attempt.

По умолчанию **никакого modal confirmation** при обычных подсказках; единственный необходимый диалог — осознанное прерывание **уже начатой** рейтинговой попытки или активной тренировки перед уходом, когда это действительно меняет судьбу попытки. При закрытии приложения с ещё не начатой rated задачей серверу ничего не писать. При закрытии с частичной активной rated задачей без подтверждения **не делать скрытый POST**, сохранить locally paused state/abort reason, а при возобновлении предложить продолжить или явно завершить. Не требовать вечной фоновой работы после закрытия окна.

### 3.2. Автопереход в обоих режимах

- OFF — пользователь увидит вердикт и сам нажмёт единственную NEXT.
- TRAINING ON — после чистого завершения не менее 1,5 с видимого ✓ и локального учёта.
- RATED ON — **только после явного server ACK** с результатом именно текущей задачи, затем показать ✓ и официальный Δ не менее 1,5 с, затем автоматом NEXT. Пока сервер отвечает — статус «Подтверждаю результат Lichess…», не silent redirect; при error/timeout — нет автоперехода.
- Если пользователь выключил флажок после завершения и до перехода — таймер отменяется. Если включил после уже законченной задачи — старую задачу неожиданно не пролистывать.
- Wrong/hinted/revealed/skipped/replay — автопереход не запускается.
- Если сервер возвращает ту же задачу, не считать её новой; применить **ограниченную** стратегию PUZ-UX-05. Не отправлять повторный rated POST только чтобы получить новую задачу.

## 4. Нативный официальный OAuth: явное согласие, два permission gate

Текущий main имеет отдельный keyring `ChessCoach.Lichess.Puzzles / puzzle-activity-token` для `puzzle:read`; обычные игровые `board:play` credentials должны оставаться **отдельными**. Новый режим требует `puzzle:write`. Предлагаемое решение без хранения секретов в SQLite/QSettings:

1. TRAINING продолжает использовать существующий строго read-only credential; при входе не запрашивает лишних разрешений. Если read-only не подключён — **«Подключить задачи Lichess»** с обычным `puzzle:read`.
2. При **первом сознательном нажатии** «На рейтинг» показать краткий native информационный экран/строку: «Chess Coach сможет отправлять ваши результаты головоломок и менять **официальный рейтинг Lichess**. Разрешение предоставляется отдельно; обычные партии не затрагиваются.» Кнопки **«Разрешить на Lichess» / «Отмена»**. После «Разрешить» запустить имеющийся PKCE OAuth с scopes **`puzzle:read puzzle:write`** в отдельном credential slot, например `ChessCoach.Lichess.Puzzles / puzzle-rated-token`. Не использовать password или PAT в логах.
3. После callback проверить аккаунт через официальный GET /api/account и соответствие выбранному `lichess:<username>`, validate scope/response где API это поддерживает; токен режима только для этого аккаунта. При отмене/ошибке/несовпадении не портить старый `puzzle:read` token и не запускать scored attempt.
4. При наличии rated-token не открывать OAuth заново каждый сеанс: безопасно проверить его пригодность перед RATED POST, без синхронной keyring операции на GUI thread. Невалидный / 401/403 → понятный «Разрешение на запись задач не действует · подключить заново» и fallback TRAINING, **не сбрасывать** pending ranked result, не выдавать учёт за подтверждённый.
5. Отключение/смена профиля: account-scoped refs; не использовать чужой токен, не привязывать server result к активному на момент ACK другому пользователю. Не удалять и **не отзывать** обычный OAuth board:play, PAT, read-only credentials; revoke отдельного rated token — только по явной команде с capture текущего слота/identity. Без нового глобального auth-refactor по историческому issue #40.
6. Запрещено использовать реальные токены в CI, писать grant, scope, token hash или raw puzzle activity пользователя в публичный GitHub. Можно писать безопасные поля: mode, account alias anonymized, puzzle id из фикстуры, status, HTTP status, timings; запрещены bearer/raw OAuth callback URL.

**Безопасность/правила:** рейтинговая головоломка — это разрешённый публичный puzzle training, **не подсказки при live партии с человеком**. Существующий Fair Play guard для онлайн-партий не менять. Нельзя отправлять шахматные ходы в `board:play` или на Lichess puzzle POST из «Тренировки».

## 5. Серверная оценка: надёжный ACK без двойных штрафов

### 5.1. Чистый контракт транспорта

В `src/chess_coach/lichess/api.py` добавить **отдельный** типизированный метод `submit_puzzle_round(token, angle, puzzle_id, win, rated=True, next_count=1)`, использующий только документированный `POST /api/puzzle/batch/{angle}` с JSON:

~~~json
{"solutions":[{"id":"0haqU","win":true,"rated":true}]}
~~~

Пример `0haqU` — **публичный ID из документации**. `rated:true` **никогда** не выводить из текущего чекбокса после нажатия: frozen mode у попытки. Проверять форму `rounds` и именно `id` результата; `glicko` и optional `puzzles` валидировать отдельно. Никаких неизвестных POST endpoints, server calculations локально, массовой отправки исторических попыток. `nb=0/1` как минимальная норма; можно взять из ответа `puzzles[]` для ускорения NEXT, если валидно. TRAINING ничего через POST не отправляет.

При серверном успешном ACK:
- локальный transaction/correlation ID из неизменяемой попытки → server round с тем же puzzle ID и account; status=`confirmed`.
- официальный Δ берём **только** из `ratingDiff`; текущее значение — `glicko.rating` при наличии или отдельная read-only подтверждённая сводка. При отсутствии поля вместо числа показать «Результат принят Lichess, уточняю рейтинг». Не суммировать вслепую с устаревшим cached Home рейтингом.
- обновить Home official rating и виджет в тренировке **для того же аккаунта**, не менять чужую карточку; не обновлять тренировочный CC local Elo.
- результаты/плитки отображают одновременно свой verdict и статус **«Lichess ✓ подтверждено / отправляется / неизвестно»** без смешения.

### 5.2. Реальная неопределённость сети

У POST результата **нет документированного idempotency key**. Поэтому обычное «HTTP timeout → бесконечно повторю POST» **не допускается**, иначе возможен двойной учёт/расхождение.

Минимально достаточная SQLite запись (аддитивная, без изменения существующих данных): `attempt_id, account_id, puzzle_id, mode, win, rated, created_at_ms, transport_status, server_confirmed_at_ms, server_rating_diff nullable, server_rating nullable`. Ключевое: один scored outcome на `account + puzzle + session_id` в Chess Coach, сохранённый **до отправки**; существующий local outbox переиспользовать при возможности, не создавать вторую несогласованную очередь без причины. Состояния `prepared → sending → confirmed / rejected / unknown`, причём `unknown` означает «возможно принят сервером», а не «можно спокойно повторить».

- HTTP 2xx + соответствующий `rounds[].id` = **confirmed**.
- Очевидная ошибка ещё до отправки (нет сети/разрешения) = **not_sent**, можно предложить повтор после проверки пользователя; **не делать rated POST тайно при startup**.
- Timeout/оборванный ответ после возможной отправки = **unknown**; **не повторять автоматически**. Кнопка «Проверить результат» делает read-only GET activity/ dashboard, сверяет пользователя, puzzle ID, result и время попытки. Схема activity не содержит guaranteed ratingDiff; точный Δ оставить «неизвестен», пока не подтверждён сервером.
- Если read-only сверка не может **однозначно** установить результат (например, ранее играл ту же задачу, сеть недоступна), показать «Не удалось подтвердить результат Lichess. Повторный POST не выполнялся.»; разрешить продолжить в TRAINING, но не делать новые RATED отправки до устранения неясности. Поддержать безопасное восстановление при следующем открытии.
- 401/403 → предложить обновить **отдельное puzzle:write** разрешение, сохранив prepared/unknown и local history; 429 → уважать Retry-After, никакого spam; явная 4xx без обработки сервером → rejected с описанием.
- Не заявлять, что сам сервер обязательно применяет один и тот же puzzle ID дважды или наоборот: **именно отсутствие задокументированной идемпотентности** является причиной запрета автоматической слепой повторной отправки.

**Доказательство:** tests с «server committed then client timeout», «server rejects before send», «duplicate UI click», «switch profile after send» и restart of temporary SQLite. Ровно одна rated отправка на одну попытку **по нашему клиентскому алгоритму**; отдельная server activity reconciliation вместо второго POST. Это реалистичная проблема потери рейтинга, а не искусственная race-hunt.

## 6. Данные, совместимость и метрики

**Источник истины:**
- official Lichess puzzle rating и ratingDiff — только server read/ACK;
- training outcome, streak, count, hints — local SQLite;
- исторический Chess Coach practice rating (1500/1498 на старых скриншотах) — **legacy preserved**; после введения двух режимов **заморозить новые локальные Elo-события** при TRAINING/RATED, не удалять прошлые строки. Показывать при необходимости в разделе «Прогресс → История Chess Coach» с пометкой «историческая локальная оценка», не смешивать с официальной.

**Ожидаемая модель хранения:** у каждой локальной попытки хранится `mode` (TRAINING/RATED/LEGACY/REPLAY), `account_id`, `puzzle_id`, `session_id`, исход, первая ошибка, подсказки, длительность, `server_status`, опциональное `ratingDiff`. Старые строки имеют `LEGACY_LOCAL`/отсутствующий mode и **не мигрируют автоматически в rated**; старые исходы/рейтинги остаются воспроизводимыми. Миграция **аддитивная** с тестами на копии старой fixture; не трогать оригинальную SQLite владельца.

Home и правая панель должны показывать **официальный Lichess рейтинг** с временем источника; при отсутствии интернета — «Последнее подтверждение: …», а не выдуманные значения. Лента результатов относится к **текущему режиму и профилю**: при переключении режимов показывать соответствующие результаты, отдельно длительная общая история с пометкой TRAINING/RATED/REPLAY; результаты другого аккаунта сразу скрываются. Не считать replay в rated stats. При частичной ошибке сети не списывать/начислять локальную альтернативную оценку.

**Производительность:** при уже подготовленной задаче переход мгновенно на GUI, GET/POST в existing worker/coordinator, не читать keyring, не ждать SQLite и не делать requests в GUI thread. Home показывает сохранённый текущий рейтинг/metadata без повторного тяжелого расчёта 3327 партий. Никакой отдельной cloud DB.

## 8. Конкретная матрица человеческих действий и ошибок

### Сценарий A. Home → два понятных режима

1. Открыть Home с cached saved puzzle: мини-доска, два CTA «Тренировка»/«На рейтинг», понятная подпись рейтинга, «Повторить эту» только при preview.
2. Нажать **«Тренировка»**: загрузилась новая голова (не replay из Home) выбранной темы, кнопки работают, рейтинг не изменился.
3. Вернуться Home → нажать **«На рейтинг»**: если токена rated нет, понятное consent **до** открытия браузера; отказ оставляет пользователя в рабочем TRAINING, без POST. Разрешение затем открывает **новую** rated задачу.
4. Replay по мини-доске/ссылке — unrated. Повтор не затрагивает scoreboard, даже если исходный puzzle ранее был ranked.

### Сценарий B. Тренировка темы и практические привычки

Выбрать «Мат в 2», затем «Мат в 3», «Мат в 5+», «Вилка», «Эндшпиль»; темы соответствуют IDs API, профиль сохранён. Пройти 5 разных задач, вручную NEXT или включив автопереход. Сделать неправильный ход и исправить, взять подсказку, показать решение без popup; цветные плитки/серия корректны. После 5 задач **официальный рейтинг и legacy CC rating events не изменились**, локальная статистика выросла. ПКМ-стрелки исчезают при выборе своей фигуры, колесо просмотра и возврат работают.

### Сценарий C. Рейтинг — правильно, неправильно, просмотр

1. Выбрать rated `mix/normal` и зафиксированный account; GET puzzle.
2. Сделать несколько правильных пользовательских ходов (с ответами соперника); **пока не закончено, POST нет**.
3. Завершить чисто → **ровно один POST** с `rated:true win:true`, дождаться сервера, увидеть «✓ подтверждено Lichess, +N»; официальный рейтинг и Home обновились с источником, местный CC Elo без изменений.
4. На следующей ошибиться первым ходом → **ровно один POST win:false`**, немедленно красный статус; затем исправить/взять hint — **никакого второго POST и превращения в победу**.
5. Нажать «Следующая», увидеть новый ID, не тот же как NEW. Если auto ON — дождаться server ACK и видимого результата, потом следующий puzzle.

### Сценарий D. Переключение посреди задачи

TRAINING→RATED после двух ходов: текущая TRAINING попытка либо честно завершена локальным пропуском, либо пользователь продолжает её; завершённые ходы **не становятся rated задним числом**. RATED→TRAINING до первого хода: без POST; после первого правильного частичного хода: **предупреждение о поражении**, при «Продолжить» ничего не меняется, при подтверждении один POST failure. После первой ошибки/подсказки результат и так зафиксирован: переключение не отменяет серверную оценку. При отзыве puzzle:write не откатывать уже отправленные результаты.

### Сценарий E. Настоящая ошибка сети

Fake HTTP transport воспроизводит: 200 + matching round; 200 без matching round (не считать успехом); timeout **до отправки**; timeout **после возможного COMMIT на сервере**; 401/403; 429 Retry-After; отмена OAuth; смена профиля. При unknown второй POST **не происходит автоматически**, пользователь видит «Проверить результат», сверка activity подтверждает там, где возможно; новая rated сессия не маскирует pending. TRAINING остаётся доступной. Restart временной SQLite восстанавливает запись и её status.

### Сценарий F. Accessibility и реальный Windows

QTest.mouseClick на Home двух CTA, реальная Qt keyboard navigation, действия мыши на BoardView, hover/tooltip, checkbox ✓, mode switch, реальные native screenshots READY TRAINING, AUTH CONSENT, READY RATED, RATED SENDING, RATED CONFIRMED (+/−), RATED UNKNOWN, review, tape и компактные состояния. Пройти при 100/125/150% DPI из §2.3. Никакой программы с неактивной доской без восстановления. На Home с 3300 synthetic games графики остаются видны.

**Нельзя зачесть** fake server `ratingDiff: +15` как **настоящий** официальный рейтинг владельца. Safe production write возможно проверить **только владельцу** с его разрешения после независимого теста fake transport. Принцип необратимости: тесты GitHub NEVER POST на реальный Lichess.

Это понятный и достижимый человеческий путь при медленном интернете: человек нажимает кнопку, ожидая ускорить отправку. Кодовая причинная цепочка:

- `src/chess_coach/ui/pages/puzzle_training.py:_request_rated_result` (1533+) выставляет `_rated_pending_attempt.status='prepared'` и сразу начинает первый worker через `rated_result_requested`. `_render_rated_pending_attempt` (612+, ветка `prepared`) **показывает CTA повтора**, не отличая ещё исполняемый первый запрос от возобновления после рестарта. `_rated_recovery_clicked` (1619+) может эмитить `rated_retry_requested`.
- `window.py` (6075–6080) связывает кнопку с **ещё одним** `_submit_rated_puzzle_result(..., retry=True)` и новым фонoвым worker. Внутри worker (6256–6305) повтору разрешено продолжать, когда SQLite уже хранит `prepared`; оба worker имеют независимые `get_account` и затем без условной атомарной проверки переводят запись в `sending` и доходят до mutating `submit_puzzle_round`. `puzzles.py:update_rated_puzzle_attempt` (125+) делает unconditional UPDATE. `_start_registered_work` (3117+) прямо не сериализует worker. Поэтому при двух ответах `get_account` возможны **две попытки официального POST с одним puzzle ID**. На сервере дополнительное начисление может быть отклонено — **не утверждать, что рейтинг обязательно удвоится**, но двойная отправка запрещена как риск сохранности рейтингового исхода. Также поздний callback второго worker не должен возвращать GUI из confirmed в pending.
