## 1. Проблема пользователя и реальные границы

Владелец вручную сыграл в Chess Coach с Lichess AI, использовал premove и потерял ферзя: компьютер ответил неожиданным ходом, но **очередной предход всё равно выполнился**. Это ожидаемое свойство обычного premove (он выполняется по легальности, **не по угаданному ответу соперника**), а не автоматическое доказательство ошибки шахматных правил. Пользователю нужен **ясный способ запросить возврат уже сделанного хода**, отдельный от отмены ещё не исполненного предхода.

**Три разных действия, которые нельзя смешивать:**
1. `Отменить предход` — локально удалить **ещё не отправленный** queued premove: немедленно, без запроса Lichess.
2. `Вернуть ход` во время **партии с Lichess AI** — запросить takeback через официальный Board API; **не откатывать серверную позицию локально**. Официальное руководство Lichess описывает мгновенный возврат против AI, но нужно проверить на реальном Board API, а не предполагать, что он обязательно сработает: https://lichess.org/page/blind-mode-tutorial.
3. `Предложить вернуть ход` с **человеком** — отправить предложение по Lichess; дождаться согласия соперника. В рейтинговых и иных ограниченных режимах следовать ответу сервера, не обходить запреты.

Board API: `POST /api/board/game/{gameId}/takeback/yes` (предложить/принять), `POST /api/board/game/{gameId}/takeback/no` (отклонить), OAuth `board:play`. Спецификация: https://github.com/lichess-org/api/blob/master/doc/specs/tags/board/api-board-game-gameId-takeback-accept.yaml.

## 2. P0 — ясный и работающий возврат хода

- Для активной AI-партии сделать **заметную кнопку «Вернуть ход»** в игровом экране, отдельно от «Отменить предход». Для человека — «Предложить вернуть ход».
- Сохранить существующий `LichessService.takeback` и `LichessGameSession`; использовать документированный `takeback/yes` и существующую логику подтверждённого укорочения `gameState.moves`. Никакого несанкционированного изменения локальной онлайн-партии.
- При нажатии: проверить, что игра активна, ход(ы) существуют, нет конфликтующих pending move/takeback; отправить **один** запрос и показать состояние «Ожидаем возврата от Lichess». Если API отклонил запрос 400/403 — понятное сообщение, не фальшивый откат.
- При подтверждённом Lichess takeback обновить доску, очередь хода, SAN, часы, SQLite, PGN и перемещение в истории; сбросить predmove и optimistic overlay, связанные со старой веткой.
- Против AI проверить фактическое количество возвращаемых полуходов, особенно когда AI **уже ответил** после ошибочного предхода. Не зашивать «обязательно один ход» либо «обязательно два хода» без подтверждения. Если Lichess возвращает только ход компьютера, предусмотреть повторное явное действие владельца, но **не циклические автоматические takeback-запросы**.
- В незавершённой локальной offline-доске добавить отдельно **«Отменить последний ход»** (через `GameController` с корректным изменением `move_stack`/SAN/premove), если поддерживается исходными границами M0. Это не заменяет онлайн-takeback.
- Отмена уже **исполненного** предхода — это только takeback, не кнопка `Отменить предход`. Явно объяснить в UI.
- По желанию добавить настройку **«Разрешить предходы»** (включена по умолчанию, можно выключить, особенно при обучении с AI); выключение снимает queued intent. Не делать условную «догадку ответа соперника» частью простого premove.

**Обязательные тесты:** AI-request `yes` единожды; укорочение 1/2 ply; AI 400 и 429; human-offer/accept/decline; offline undo; уже отправленный предход нельзя удалить как queued; граничные случаи promotion/castling/en-passant и history.

## 3. P1 — исследовать и убрать подлагивания шахматной доски

**Подтверждённые кодовые места, требующие профилирования:**
- `BoardView.set_position()` вызывает `super().set_board(board.copy(stack=True))` **даже при неизменной позиции**. Вероятно лишний reset выбора/перерисовки. Изменить на дифференциальное обновление: если позиция, ходовая история и настройки отрисовки не поменялись, **не делать set_board**, но корректно обновлять сообщения, подсветку, premove и часы. Не сломать поддержку специального положения/одинакового FEN с разной историей.
- `MainWindow._refresh_online()` с нуля воспроизводит список полуходов и создаёт `QListWidgetItem` для каждого SAN при каждом refresh; может сбрасывать прокрутку/выделение и создавать ощущение подлагивания. Инкрементально изменять только новый хвост, а при takeback/истории делать контролируемую пересборку; сохранять выбранный ply и scroll.
- `LichessGameSession.apply_event()` синхронно вызывает `_save()`, а `GameRepository.save_snapshot()` в GUI-потоке восстанавливает целую `chess.Board`, строит PGN и выполняет SQLite-запросы при получении потоковых событий. Это потенциальная причина фризов на длинных партиях. **Измерить**, затем минимально устранить дорогую работу из Qt GUI-потока/исключить повторное сохранение без изменения подтверждённого state. Сохранить durable commits, сериализацию записей, порядок событий, корректный финальный PGN и recovery; нельзя терять ходы ради быстрого интерфейса.
- Проверить повторный `refresh()` при вызове `on_move_intent`, `on_premove_intent`, `_lichess_game_event`, `_lichess_status`, `_update_clock`; не перезапускать network streams/Qt controls от ненужных paint/refresh.
- Оценить реакцию GUI в партиях с короткой (5 ply) и длинной (100–200 ply) историей, 50 быстрыми fake-событиями; измерять Qt-loop latency и длительность refresh без реального Lichess.

**Регрессионные интерактивные проверки:**
- Click-click: выделение фигуры остаётся после безвредного обновления часов/статуса и повторного `refresh`; корректная отмена при другой позиции; невозможный ход не отправляется.
- Drag: ghost follows cursor; release outside; loss of focus; приход gameState во время drag; поворот доски; координаты HiDPI; ручная правая стрелка одновременно не создаёт шахматный ход.
- Premove: постановка, отмена, недопустимый; неожиданный ход соперника, который **делает premove легальным**, приводит к штатной отправке (не отменять его «из соображений безопасности»), но пользователь видит предупреждение и может отключить premove на будущее.
- Promotion: **обычный ход** предлагает Q/R/B/N; в текущем `BoardView._emit_premove` для пешки на последнюю горизонталь автоматически выбран Q. Проверить соответствие ТЗ и при необходимости дать выбор underpromotion Q/R/B/N для premove либо чётко документировать «автоферзь» с согласованием владельца. Без самовольного удаления поддержки всех четырёх фигур.
- Verify no UI freezes when SQLite busy/permission denied, no silent loss of server-authoritative moves. Background writes must be thread-safe and orderly; avoid SQLite connection reuse across threads.

## 4. P1 — тесты и окна Windows

Пожелание владельца: во время тестирования **не всплывают десятки чёрных и шахматных окон**.

**Не использовать одну и ту же `MainWindow` для всей автоматической тестовой базы**: тесты обязаны быть изолированы, иначе будут маскироваться дефекты. Вместо этого:
1. **Все unit/integration/pytest-qt проверки запускать headless:** `QT_QPA_PLATFORM=offscreen` (устанавливать в тестовом запуске; не переносить эту настройку на обычный запуск приложения). `window.show()` в тесте допустим в Qt offscreen, но реальное окно не отображается.
2. По возможности один экземпляр `QApplication` на сеанс pytest (стандартная модель `pytest-qt`), **новый изолированный тестовый widget на каждый тест** с корректной очисткой. Не слить состояния тестов ради «одного окна».
3. **Отдельный ручной Windows GUI smoke:** один раз открывать настоящий Chess Coach, делать короткий список действий, потом закрывать; не запускать его 10–20 раз.
4. Для CLI использовать **один уже открытый PowerShell/терминал**, а не множество отдельных `cmd.exe`/PowerShell процессов. Разделить источник мелькания: консоль инструментов Codex или Qt test windows. Не запускать реальный Lichess в автоматических тестах и не повторять HTTP 429 ради теста.
5. В Windows проверить `pytest`, `compileall` и `git diff --check`; заявлена `requires-python>=3.12` — нужно CI/проверка Python 3.12+, либо явно `NOT RUN`. Windows Python 3.11.5 — фактически использованная Codex тестовая среда, **не доказанная поддерживаемая конфигурация проекта**.

В отчёте показать количество тестов, команду, наличие/отсутствие видимых окон, число ручных запусков GUI; если окно всё равно мелькает, записать **имя и путь процесса**, а не просто предположить причину.

## 5. P1 — ярлык Chess Coach на рабочем столе

**Цель:** владелец нажимает на ярлык «Chess Coach» и получает одно окно приложения, без PowerShell, командных строк, запросов прав администратора или пересоздания .venv.

- Подготовить **добровольно запускаемый, идемпотентный** `scripts/create_desktop_shortcut.ps1` (или `scripts/create_desktop_shortcut.py` через штатные Windows API/COM), который находит `repo_root` относительно самого файла, Windows Desktop через штатный механизм/известные папки Windows (учитывать OneDrive Desktop), проверяет `.venv\Scripts\pythonw.exe`, корректно устанавливает `.lnk` с TargetPath `pythonw.exe`, Arguments `-m chess_coach`, WorkingDirectory = project root и понятным названием.
- Без скачивания иконок с интернета. Можно использовать существующий системный значок Python, либо добавить **собственную** `.ico` из разрешённых ресурсов в отдельном небольшом PR. Не использовать чужой бренд Lichess/Chess.com как свой значок без разрешения.
- Отдельно обеспечить сохранение ошибок запуска: при `pythonw.exe` нет консоли, поэтому настроить минимальный crash/exception log в разрешённом каталоге приложения (например `%LOCALAPPDATA%\ChessCoach\logs`) **без паролей, OAuth-токенов и текстов приватных партий**, с ограничением размера/ротацией; либо безопасный диагностический запуск из PowerShell. Никакого скрытого сетевого доступа сверх прежнего штатного OAuth restore.
- Скрипт по умолчанию **только создаёт ярлык**, приложение сам не запускает, не регистрируется в автозапуске и не создаёт задачи Планировщика.
- Не требовать админ-прав, не отключать Defender/Dr.Web, не просить исключения, не использовать `-ExecutionPolicy Bypass`, скрытые `cmd.exe`, bat-цепочки/процессы или упаковку сомнительного EXE ради ярлыка.
- Если .venv отсутствует или версия Python не соответствует требованиям — понятная диагностическая инструкция, без молчаливой установки пакетов/изменения системы.
- Отдельный `scripts/remove_desktop_shortcut.ps1` необязателен; достаточно документировать безопасное удаление ярлыка.
- В README описать один раз создание ярлыка; затем запуск — двойной щелчок. Проверить корректность пробелов в пути, Windows 10/11 и OneDrive Desktop.

## 6. Безопасность и Dr.Web

Владелец ранее показал **Dr.Web**, запись 2026-10-31 20:06: поведенческий анализ заблокировал доступ к защищаемому объекту. Точный путь и процесс по скриншоту неизвестны. **Windows Defender — другой антивирус; пустой журнал Defender не подтверждает отсутствие события Dr.Web.**

- Не отключать защиту, не добавлять исключений, не обходить блокировки, не менять настройки безопасности ОС.
- Не скрывать в фоне массовые запуски процессов. Не делать побочных файловых изменений вне репозитория, штатного AppData и запрошенного ярлыка на Desktop.
- Если снова сработает Dr.Web, запросить у владельца **только подробности события**: защищаемый объект, путь процесса, название обнаружения и действие. Не передавать токены/личные пути сверх необходимого.
- Использовать один постоянный терминал при проверках; не объяснять каждое окно без подтверждённых данных.
