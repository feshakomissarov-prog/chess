## 1. Источники и независимые факты: что реально есть у Lichess

Изучены публичные пользовательские страницы и **официальный API OpenAPI**, а не только внешний скриншот:

1. **Официальный пользовательский раздел:** https://lichess.org/training ; каталог https://lichess.org/training/themes . Есть «Healthy mix», фазы opening/middlegame/endgame, специальные эндшпили, мотивы `pin`, `fork`, `sacrifice`, `skewer`, матовые шаблоны и длины решения. Это реальные идентификаторы, не произвольные названия.
2. **История и диагностика:** разделы Puzzle Dashboard, Strengths, Improvement areas и Puzzle History, видимые в https://lichess.org/training/themes и https://lichess.org/training/history (последний требует входа). Это образец работы с предыдущими попытками; мы должны показывать *свои реальные данные*, а не «копию статистики Lichess».
3. **Новые задачи:** в https://github.com/lichess-org/api/blob/master/doc/specs/tags/puzzles/api-puzzle-next.yaml официальный `GET /api/puzzle/next?angle=&difficulty=&color=`, OAuth scope `puzzle:read`; в https://github.com/lichess-org/api/blob/master/doc/specs/tags/puzzles/api-puzzle-batch-angle.yaml есть `GET /api/puzzle/batch/{angle}?difficulty=&nb=`, 1–50 за запрос и также `puzzle:read`. Использовать **малый bounded batch**, не выкачивать все задачи. Lichess прямо запрещает использовать endpoint для массового перечисления.
4. **Разделение чтения и записи:** в том же batch-API `POST /api/puzzle/batch/{angle}` с `puzzle:write` может отправлять результаты и обновлять официальный рейтинг Lichess. **ЭТО НЕ РАЗРЕШЕНО ЭТИМ ТЗ**: не запрашивать `puzzle:write` и ничего не POST без отдельного решения владельца. Текущие новые решения в Chess Coach — **локальная практика**; официальный Lichess puzzle rating/история не изменяются автоматически.
5. **Текущая история пользователя:** `GET /api/puzzle/activity` (https://github.com/lichess-org/api/blob/master/doc/specs/tags/puzzles/api-puzzle-activity.yaml) отдаёт authenticated NDJSON с `puzzle:read` и уже используется Chess Coach.
6. **Публичная БД:** https://database.lichess.org/#puzzles — задачи объявлены public-domain; `PuzzleId,FEN,Moves,Rating,...,Themes...`, но `FEN` в CSV **предшествует первому подготовительному ходу противника**, а `Moves` начинается с этого хода. **НЕ скачивать** гигантский публичный dataset на компьютер владельца и **не путать CSV-схему** с API `PuzzleAndGame`.
7. **Схема API:** https://github.com/lichess-org/api/blob/master/doc/specs/schemas/PuzzleAndGame.yaml — JSON содержит `game.pgn`, `puzzle.initialPly`, `puzzle.solution` и при наличии `puzzle.fen` / `puzzle.lastMove`. Для batch-API `puzzle.solution` — уже **ходы ответа решающего**, не механически тот же массив, что CSV `Moves` с подготовительным ходом.

**Вывод:** можно реализовать по-настоящему новые тематические задачи через официальный read-only API; текущую историческую базу повторно загружать ради этого не нужно. Мы копируем **удобство и механику**, а не дизайн Lichess, код сайта, полный рейтинговый протокол или Puzzle Storm/Racer.

## 3. Целевой пользовательский сценарий

1. Пользователь нажимает **«Обучение → Решение задач»** либо **«Решать задачу»** на Home. Открывается новый цельный desktop-тренажёр в наших цветах.
2. Видит большую доску, чей ход, режим/тему, сложность, краткое пояснение «Найдите лучший ход», историю последних попыток и текущие показатели (только реальные).
3. Выбирает **«Смешанная тренировка»** или конкретную тему (**связка, вилка, эндшпиль, мат в 2 и т. п.**); сложность **Легче / Обычная / Сложнее** (полная шкала Lichess из 5 значений может быть в меню «Дополнительно»).
4. Получает **одну новую задачу** с Lichess через разрешённый read-only API, либо выбирает «Повторить ошибки» из уже скачанной локальной истории. Если нет сети/токена/разрешения, честная альтернатива: локальные сохранённые задачи.
5. **ЛКМ:** перетаскивает фигуру или нажимает на фигуру и конечную клетку. **ПКМ:** тянет от клетки к клетке и рисует собственную стрелку; ПКМ-клик отмечает клетку. Пометки не делают ход и не используются для оценки ответа.
6. Если ход допустим правилами шахмат, проверяется **пазл-решение**, а не Stockfish. При верном ответе воспроизводится автоматический ответ соперника из решения (если он есть) и пользователь решает следующий ход; при ошибке видит короткую обратную связь и выбор повтора, без преждевременной демонстрации всей линии.
7. По окончании: «Решено / допущена ошибка / с подсказкой / решение показано», короткое пояснение, правильная линия, темы, рейтинг **самой задачи**, ссылка на её источник и кнопка «Следующая задача».
8. Справа либо компактной вкладкой видны **предыдущие задачи** с датой, темой, результатом и возможностью открыть задачу повторно. Можно выбрать «Повторить ошибки», открывая непроработанные попытки.
9. Состояние сохраняется локально, но **не подменяет официальный Lichess рейтинг/историю**. После смены профиля — другой набор истории, без смешения попыток двух аккаунтов.

## 4. Дизайн страницы в Chess Coach, без копирования оформления Lichess

При эталонном широком окне **1672×941, 100%** (и корректной адаптации):

- **Левое стандартное меню Chess Coach** без изменений.
- **Верх:** «Решение задач» + маленькие переключатели источника «Новые Lichess» / «Мои ошибки» / «Сохранённые», ниже «Тема: Смешанная», «Сложность: Обычная». Информационные controls не занимают полэкрана.
- **Центр/основной фокус:** **крупная квадратная доска**, та же цветовая тема/фигуры Chess Coach. Позиция ориентирована по цвету решающего; вспомогательное поле — «Ход белых/чёрных». Никаких видимых спойлеров решения/подсказочных стрелок перед запросом.
- **Компактный левый блок рядом с доской или выдвижные фильтры:** перечень тем по семействам «Общее», «Фаза», «Тактика», «Мат», «Эндшпиль», «Дебюты», «Длина решения». Темы в одном scrollable списке/поиске, не отдельные большие окна.
- **Правая панель:** компактная карточка **«Текущая задача»** (ID/номер, источник, режим, статус, после решения рейтинг и мотив), а ниже **«Предыдущие задачи»** с 5–8 последними результатами (✔, ✖, подсказка, дата, тема, доступный replay).
- **Под доской:** контекстный статус «Найдите лучший ход», «Ход верный», «Попробуйте ещё», «Задача решена», кнопки «Подсказка», «Показать решение», «Повторить», «Следующая задача». Кнопка раскрытия ответа требует подтверждения, не портит историю прежней Lichess-попытки.
- **Небольшие показатели:** рейтинг задач Lichess с датой обновления, количество *локальных* попыток/успехов, отдельная успешность по выбранной теме. Не рисовать произвольные ± баллы и не выдумывать обновление официального рейтинга.

При 1280×720 и Windows 125/150%: квадратная доска остаётся приоритетом, темы скрываются в выпадающий список, история помещается во внутренний scroll / переключаемую вкладку, кнопки доступны, без горизонтального выхода за viewport. Сохраняются размеры и контрастность темно-синей гаммы и фиолетовых CTA. Не создавать дополнительные панели с вертикальным scrolling всей страницы при широком окне, не перегружать длинными пояснениями.

**Внешнее фото Lichess — только референс механики; ни одного требования к идентичным цветам или пиксельному сходству с Lichess.** Зато **настоящие Qt-скриншоты новой страницы** обязательны перед приёмкой.

## 5. Функциональный контракт по устойчивым ID

### PUZ-01 — Режимы, источник и выбор темы

- Режимы: `mix` («Смешанная»), **тематическая тренировка** (один theme ID), «Мои ошибки» и «Сохранённые». В новой сети default `mix`, выбор сохраняется в QSettings для данного пользователя, но не меняет Lichess API activity.
- Для UI первоначально показывать **реальные официальные IDs**, например: `opening`, `middlegame`, `endgame`, `rookEndgame`, `bishopEndgame`, `pawnEndgame`, `knightEndgame`, `queenEndgame`; `pin`, `fork`, `sacrifice`, `skewer`, `discoveredAttack`, `defensiveMove`, `hangingPiece`, `mate`, `mateIn1`, `mateIn2`, `mateIn3`, `promotion`, `underPromotion`, `oneMove`, `short`, `long`. **Перед implementation** проверить действительные angle IDs в Lichess routes/schema/theme catalog; не превращать русские labels в query-ID.
- Поиск тем, категории и логический сброс в «Все темы»; нет необходимости сразу копировать все сотни категорий и экран Puzzle Storm/Racer.
- Difficulty: `easier` / `normal` / `harder` в основных controls; расширенно `easiest` / `hardest`. Это **относительная** настройка официального API, не абсолютное значение «рейтинг 1900».
- Смена темы/аккаунта во время загрузки: cancel/ignore stale; не смешивать очередь старой темы. Если в локальном наборе нет нужных тем — честное `0 задач`, не игнорировать фильтр без уведомления.

### PUZ-02 — Новая задача Lichess: только документированный GET

- Адаптер к `GET /api/puzzle/batch/{angle}` с OAuth `puzzle:read` или `/api/puzzle/next`, через существующую `LichessClient`, credential vault, shared rate-limit/backoff; bounded prefetch по необходимости **1–5 задач**, не 50 по умолчанию. **Никакого массового harvest** и плановых фоновых задач без явного действия. Для API проблем использовать 429, 401/403, 5xx timeout/error/retry по штатной модели; не обходить API лимиты.
- Если текущий OAuth token не имеет `puzzle:read`, UI предлагает стандартное разрешение **после клика пользователя**; без тайной дополнительной авторизации.
- Обычный ответ API может содержать `game.pgn + puzzle.initialPly + puzzle.solution`, не всегда `puzzle.fen`. Нужен source-aware normalizer, восстанавливающий position/FEN из фактического PGN и initialPly и валидирующий `lastMove`, законность всех ходов.
- **Строгая граница форматов:** Lichess public CSV `Moves[0]` = предварительный ход противника; imported puzzle activity в текущем Chess Coach сохраняет исходную FEN/решение с подготовительным первым ходом. API batch `solution[0]` = первый ответ игрока. Не добавлять лишний подготовительный ход к API и не терять его у локального исторического источника. Сделать единый `PuzzlePlayablePosition` с явными `player_to_move_fen` и `expected_user_moves`; unit tests по реальным примерам обоих форматов.
- Нелегальная, повреждённая, неконсистентная позиция — показать `Задача недоступна` и безопасно пропустить, **не** рисовать произвольную стартовую доску и не менять рейтинг.

### PUZ-03 — Жесты доски

- **ЛКМ:** click-click и drag/drop легальных ходов, выбор превращения; никакие premature move не принимаются, когда ход соперника ещё анимируется.
- **ПКМ drag:** toggle собственной стрелки `from→to`; ПКМ click по клетке: toggle круга/заливки клетки. Отмена/удаление: повторный жест или штатная очистка; стрелки **не задают ход** и не вызывают API. Положения стрелок привязаны к текущей puzzle position и очищаются при принятом ходе/смене задачи (без записи в каноническую SQLite), не создают ложных шахматных подсказок.
- Ручные маркеры пользователя и учебные стрелки подсказок разделены, как уже умеет `BoardView`. Перед решением нет engine arrows. Включённая пользовательская ПКМ-аннотация не должна блокировать drag ЛКМ, приводить к лишнему LMB-click или изменению FEN.
- Удерживание/вызов контекстного меню/клик вне доски и high DPI должны быть корректны; без on-line premove в задачах.

### PUZ-04 — Шахматная семантика и жизненный цикл ответа

- Состояния: `LOADING → READY → PLAYER_MOVE → OPPONENT_REPLY → READY → SUCCESS` / `MISTAKE_RETRY` / `REVEALED` / `SKIPPED` / `UNAVAILABLE`. UI state reducer без re-entrancy/race после смены puzzle.
- Проверка с помощью **валидированного сохранённого решения**, а не локального движка: ответы соперника воспроизводятся из source sequence, ход игрока сверяется с соответствующим UCI; при удачном ходе показывать зелёное подтверждение без раннего показа следующего верного хода.
- Специальный случай Lichess `mateIn1`: если в позиции существует альтернативный **легальный мат в один**, считать его решением, даже когда UCI отличается от стандартного `solution[0]`. Не распространять такое произвольное принятие на длинные задачи без доказательства шахматной эквивалентности.
- Illegal drag ничего не меняет. Правильная многоходовая задача не завершается после первого хода пользователя; полноценные `2.Nf3 ... 3.Nd5` и promotions/castling/en passant/black-to-move должны работать.
- Неверный легальный ход: короткое `Не лучший ход. Попробуйте ещё`, отметка ошибки в **локальной** текущей попытке. Предпочтительно вернуть позицию к точке перед неверным ходом; не предлагать движковый анализ неправильной позиции до конца попытки и не раскрывать ответ автоматически.
- `Подсказка`: первый уровень — указывает **исходное поле** следующего нужного хода (без end square), второй по повторному запросу — конечное поле / стрелка, но статус попытки всегда маркируется `с подсказкой` и не считается «чистым» успехом. Не показывать подсказки до клика.
- `Показать решение` требует подтверждения, маркирует результат `решение показано` и переводит в режим просмотра с показом SAN/ходов, без ложного `решено`. Повторить ту же задачу позволяет начать новую **локальную** попытку, предыдущий результат остаётся.
- `Следующая задача` не должна случайно сбрасывать незавершённую попытку: в активном процессе confirm skip, после `SUCCESS/REVEALED` — непосредственно next; ошибка offline/network — оставаться в текущей позиции.

### PUZ-05 — Предыдущие задачи и прозрачная история

- Правая компактная история: последние **5–8** локальных и импортированных попыток с реальным ID, темой, датой, источником, результатом; click открывает этот puzzle в режиме `повторить`, но **не подменяет** прежний исход импортированного результата.
- Кнопка `Вся история` открывает существующую bounded search/filter/pagination history view; она не должна исчезнуть после редизайна. Фильтры: успех / ошибка / пропуск/подсказка (только там, где такие состояния реально известны), дата, тема и источник.
- **Раздельные источники:** `Lichess — официальная попытка (синхронизирована)` и `Chess Coach — локальная попытка`. В одной визуальной ленте их можно упорядочить по датам, но при подсчётах показывать честные знаменатели/лейблы, не считать каждую локальную попытку официальной Lichess.
- Режим `Повторить ошибки`: выбирать только реально сохранённые ошибки текущего аккаунта; при повторном решении исходная неверная запись остаётся неизменной. При отсутствии данных — понятный empty-state и предложение обновить историю Lichess.
- Открытие конкретного puzzle из карточки Home сохраняет `account_id`, `puzzle_id` и правильную ориентацию, запускает решение **без раскрытия ответов**.

### PUZ-06 — Локальная статистика, рейтинг и сохранность данных

- Показать независимо: **официальный рейтинг задач Lichess** (последняя синхронизация, дата), **счётчики локальных занятий** (за текущую сессию / выбранный период) и **исторический Lichess Activity**. Нет клиентского расчёта «прибавилось +15 рейтинга Lichess», потому что `POST puzzle:write` не разрешён.
- Для новых local practice attempts нужна **отдельная аддитивная модель** (`local_puzzle_attempts` или эквивалент в нынешнем modular Sqlite mixin) с ключом account_id/session_id/puzzle_id/attempt_seq/result/hints/time; не изменять `puzzle_attempts`, которая является mirror server activity. Если existing table может обеспечить отдельный source без изменения семантики — документировать доказательство, иначе сделать миграцию с тестом обратной совместимости и backup fixture.
- **Не писать** локальные результаты в серверные Lichess через скрытый endpoint; **не загружать** полный public puzzle CSV. На разрыве связи активное решение должно завершаться **локально** по полученному решению; доставка результата в Lichess **не планируется и не накапливается** на retry queue.
- Для UI периодов и агрегатов все числители/знаменатели scoped по конкретному account/source/theme/date, не считать `0` когда данных нет. Синхронизация старой истории идемпотентна; повторное получение нескольких уже известных puzzle IDs не дублирует server activity.
- Доступный puzzle endpoint для дневной задачи — возможный дополнительный mode, но не обязывает запрашивать его каждый день автоматически.

### PUZ-07 — Fair Play, безопасность и конкурентность

- Решение задач не использует Stockfish / cloud evaluation / GPT во время самого ответа, **никаких PV до завершения**; тактика определяется проверенной canonical solution. Ни hint из движения живой human online партии, ни её FEN не переносятся в puzzle training.
- Если в Chess Coach активна человеческая live online-партия, соблюсти существующий fail-closed engine admission и запрет подсказок по позиции текущей партии. Новый puzzle trainer не должен запускать EngineManager.
- API client, SQLite reads/writes и normalizer heavy PGN выполняются **вне Qt UI thread** с bounds, cancellation/session generation и stale result guard. При уходе в Play, смене аккаунта, выходе или повторном клике «Следующая задача» старый ответ не перезаписывает новую позицию.
- OAuth-токены / PGN / FEN / личные account identifiers не попадут в публичные CI artifacts/логи. Фактическая SQLite пользователя, Dr.Web и Qt на его компьютере — **не трогать**; тесты используют временную SQLite на изолированном Windows runner.
- Не переносить пользовательские стрелки между разными puzzles/account; новый движок или ещё один chess board renderer **не вводить**.

### PUZ-08 — Стабильность прежних сценариев

- Разделы Home, My Games, Review (включая новые ephemeral branches PR #50), Play, Background Operations и синхронизация puzzles сохраняют поведение; новая страница не удаляет `PuzzleHistoryPage` или существующие callbacks без миграционного плана.
- Для старых записей с повреждённым FEN/solution, пустыми themes, неизвестным source, `win=0` и повторением одного puzzle 3 раза — корректная отображаемая история, недоступное replay помечено, приложение не падает.
- UI русскоязычный, навигация та же, высокие DPI без выходов, Qt доступность/keyboard focus в доске, control labels, hints/solution не просачиваются в accessibility description раньше явного раскрытия.
- Режимы Puzzle Storm, Racer и точная серверная модель рейтингов Lichess **отложены**; не создавать неработающие переключатели этих режимов.

## 6. Примеры испытаний до кодинга (обязательные RED фикстуры)

| Тест/данные | Ожидаемый результат |
| --- | --- |
| API `game.pgn + initialPly`, `puzzle.solution[0]` | Игровой ответ игрока появляется первым, **без двойного подготовительного хода** |
| Историческая `puzzle.fen + solution_json` с подготовительным `move[0]` | Подготовительный ход соперника применяется **ровно один раз** |
| `2+` пользовательских хода с промежуточным ответом противника | Не объявлять success на первом ходе, автоматический противник только из решения |
| Три legal actions: ЛКМ drag, click-click, ПКМ from→to и ПКМ click | Ходы/стрелки/кружки независимы, нет duplicate move_intent |
| Неверный легальный ответ → повтор → верная линия | История помнит mistake/hint; не объявлять чистое 100% |
| `mateIn1` два альтернативных мата / длинная задача | Оба правильных `mateIn1` допустимы; на длинной задаче произвольный отклоняющий ход не проходит |
| Смена `pin` на `endgame` при delayed GET; swap account | Старый ответ игнорируется, новая задача/история соответствуют новой теме/аккаунту |
| Lichess `429`, expired token, offline после загрузки и перед первой загрузкой | Прозрачное состояние, backoff, локальный replay работает, нет flood |
| История server `win=0` + локальный retry-success | Историческая неудача остаётся, local success помечен отдельно, рейтинг Lichess не меняется |
| Фоновые операции: auth/sync/engine/FairPlay | Никакого `POST`/Stockfish/чужой SQLite, source counts правильные |
| 0, 1, 1501 локальных попыток; 2 профиля, 20k puzzles synthetic | Bounded pagination, no main-thread freeze, не грузить всё в виджет |
| Закрытие страницы/приложения в процессе GET/сохранения локальной попытки | Нет worker-after-delete, нет duplicate writes, безопасное возвращение |

## План проверок и стоимость CI

**Строго [CC-VERIFY-01](../process/VERIFICATION_PROTOCOL.md): L1 → L2 → один L3 на точном финальном кодовом SHA.** Сначала диагностировать и покрыть источники/математику, затем собирать UI. **Не** повторять 1100+ pytest и ~100 скриншотов после каждой правки QLabel.

### Уровень 1

**После каждого небольшого логического изменения:** `git diff --check`, `python -m compileall -q src/chess_coach/ui/pages/puzzles.py src/chess_coach/board_view.py src/chess_coach/lichess` (только реально изменённые файлы), затем конкретные новые node IDs `python -m pytest -o addopts= -q tests/test_puzzle_training.py::test_official_batch_requires_no_prep_move`, `...::test_history_source_replays_one_prep_move`, `...::test_user_right_drawings_do_not_make_moves`, `...::test_failed_attempt_never_updates_server_activity`, `tests/test_puzzle_api_adapter.py` (пути добавить исполнителю, если этих файлов ещё нет). Начать с RED test-fixture по двум несовместимым source formats, затем GREEN implementation. Изолированный offscreen Qt test только target page/board, не запускать на ПК владельца.

**Расход:** десятки адресных тестов вместо полного набора. Если тест не создан, не выдавать placeholder как существующий; создать конкретный тест с названным контрактом. В кратком отчёте указать измеренную длительность L1, без гарантии минут.

### Уровень 2

**После связанного кода и новых виджетов:** `python -m pytest -o addopts= -q tests/test_puzzle_training.py tests/test_puzzle_api_adapter.py tests/test_board_view.py tests/test_lichess.py tests/test_ui_pages.py tests/test_application_fair_play.py`, плюс `tests/test_window.py` точные сценарии перехода из Home, `tests/test_background_work.py` при изменении cancellation/jobs. Новые integration tests для локального SQLite source split в `tests/test_puzzle_training_store.py`; fake transport для 429/401/token-expiry, никакого реального API.

**Нативная Windows Qt L2:** реальные screenshot PNG в наших цветах:
1. `1672×941` обычная смешанная задача до первого хода (без спойлеров);
2. та же задача с ПКМ-стрелкой и ПКМ-кругом; затем ЛКМ ход без конфликтов;
3. корректный многоходовый ответ и авто-ход соперника; неверный ответ, подсказка, показ решения (разные состояния);
4. выбранный `pin`/`endgame`, пустая тема/offline, история 5–8 задач и replay;
5. `1280×720`, 125% и 150% с реальными Qt bounding rects/доступными CTA; переключение аккаунтов, тем и страниц.

**Обязательный review:** показать настоящие Qt-кадры и таблицу `согласованная механика → фактический кадр/действие → вердикт`; не утверждать «как у Lichess» по одному unit-test. Сохранить sidebar/theme/композицию, не требовать идентичности пикселей/цветов Lichess. Успешные synthetic тесты **не** доказывают реальную работу OAuth на ПК владельца.

**Расход:** один связанный тематический runner, а не каждая микроправка → full Windows. Для Qt/SQLite/Fair Play расширять только нужный набор, записать причину.

### Уровень 3

**Только финальный exact-head** перед передачей на приёмку: один полный Windows pytest, `compileall`, offline-window smoke, native visual matrix 100/125/150 для затронутой страницы + сохранённые обязательные visual-evidence остальных экранов. Подтвердить job status каждого job, **code SHA == CI SHA**, ссылки на полный run и artifact реальных Qt PNG. Нельзя сдавать если L3 `SKIPPED` или `IN PROGRESS`; docs-only commit позже — зафиксировать кодовый и документационный SHA отдельно.

**Что не делать:** не запускать собственный Qt на компьютере владельца до разрешения `R47-SAFE-01`; не использовать рабочую SQLite, живой OAuth token, Dr.Web exclusions, полный puzzle DB download или `puzzle:write`. Не создавать DIST-01. Перед merge всегда требуется явное согласие владельца.

### Триггеры/план затрат

- L1: каждый законченный микроблок — нормализатор, move reducer, gesture, history UI, API transport.
- L2: один раз после связанной работы; повтор только при изменённой архитектурной границе и с объяснением.
- L3: один на final code SHA; повтор если после него менялся Python/resources/tests. Для docs-only не повторять тяжёлый CI.
- Если тесты неожиданно тормозят, диагностировать `pytest --durations=30`, не крутить десятки полных прогонов. Дорогую визуальную матрицу не запускать после изменения одного текста.

## Отчёт Codex и ограничения полномочий

В конце указать: code SHA, branch/PR, краткий diff, реальные L1/L2/L3 команды/результаты, затраты по логам, ссылки native PNG, перечень конкретно поддерживаемых тем/режимов, способ offline fallback, сумму локальных попыток отдельно от импорта, документированный API proof для GET и доказательство отсутствия POST, неустранённые owner gates и новые подтверждённые дефекты с стабильными ID.

**Строгий запрет:** Codex **не выполняет merge**, не меняет основную SQLite владельца и не авторизуется его Lichess от его имени. Пользователь сам принимает результат. Старые дефекты не заводить повторно под новыми ID: привязать к существующему `docs/TECHNICAL_DEBT.md`; новые ошибки текущей работы — `PUZ-01…PUZ-08` в одном реестре/журнале.

**Будущая фаза отдельно:** если владелец захочет, чтобы решения в Chess Coach официально меняли его рейтинг Lichess, предложить отдельное ТЗ на opt-in `puzzle:write` с чёткой семантикой credited/rated/unrated, retry/idempotence и privacy. Не реализовывать в текущем PR.
