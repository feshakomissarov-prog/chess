## 2. C2 [P1] Offer_draw при существующем входящем предложении может стать непреднамеренным согласием на ничью

**Доказательство:** [service_games.py:299–364](https://github.com/feshakomissarov-prog/chess/blob/c2952caa61460dd2f052519e6ab271c291b28106/src/chess_coach/lichess/service_games.py#L299-L364) проверяет `offer_draw` лишь на собственный флаг и pending; **не запрещает offer при подтверждённом opponent draw flag**. [service_games.py:1028–1033](https://github.com/feshakomissarov-prog/chess/blob/c2952caa61460dd2f052519e6ab271c291b28106/src/chess_coach/lichess/service_games.py#L1028-L1033) отправляет один и тот же Lichess `draw/yes` для `offer_draw` и `accept_draw`. Протокол Lichess трактует `draw/yes` как принятие существующего предложения, если оно уже есть. UI обычно показывает правильную кнопку, но прямой API вызов/устаревшая очередь/событие между click и POST обходит это намерение.

**Исправить:** `offer_draw` fail-closed при известном входящем предложении, **также повторно** непосредственно перед transport; никогда автоматически не превращать offer в accept. При race safely reject stale offer и сообщить «соперник предлагает ничью» без стороннего POST. Не нарушать независимость `resign` и разрешённый ответ на incoming offer.

**RED тесты:** в сервисе fresh gameFull→opponent `wdraw/bdraw=True`→`draw(accept=True, accepting_offer=False)`=no POST; fake race opponent offer после reservation, но до выполнения worker; настоящая accept отдельно делает ровно один `draw/yes`; обе стороны цвета, replay, network failure, account switch. Проверить, что **нет непреднамеренного terminal draw**.

### Продуктовый контракт: ДВА УРОВНЯ сохранённой статистики

**Tier A — мгновенная базовая сводка (самый высокий приоритет)**

- Отдельный **маленький, атомарно сохранённый** read model по текущему профилю: число завершённых партий, побед/поражений/ничьих, три последние завершённые партии (результат/соперник/дата/дебют при наличии), необходимые подписи и минимальная история прогресса — **только те поля, которые реально нужны на первом экране**. Не сериализовать сюда целые PGN, позиции и тысячи assessments.
- Сохранять Tier A **сразу после первого успешного получения**, обновлять после релевантных commit; **восстанавливать при следующем запуске до подключения Lichess, тяжёлой аналитики и фоновых синхронизаций**, выбрав persisted account scope. Нет кэша — bounded background query, мгновенные skeleton/card shell без блокировки Qt. Сохранённые значения **не стирать на секунды** при уходе/возврате на Home.
- `show_home()` **только переключает уже существующую страницу** и использует in-memory snapshot/виджеты. Никаких SQLite connect/read, file I/O/JSON parse, fsync, тяжелых пересчётов или join() в GUI event handler. Перепроверка ревизии/диск/кэш — отдельно в background и с coalescing, без гонки account switch.

**Tier B — подробная сохранённая аналитика**

- Независимая версионированная персистентная модель: средняя точность с источниками, покрытие, ошибки/зевки на 100 оценённых ходов, источники оценок, рейтинг задач/тренды, графики/карточки и дополнительные сложные показатели — **только при фактически сохранённых достоверных данных**, без фальшивых нулей/точности.
- Если Tier B уже посчитан и данные не изменились, **показать его сразу вместе с Tier A после перезапуска**. Если Tier B просрочен — показать последнюю сохранённую сводку с деликатным «обновляется» (только для того же аккаунта, с корректной пометкой); затем один **фоновый** источник-ориентированный пересчёт. В любом случае Tier A не теряется и не ждёт Tier B.
- Новые/изменённые записи, завершающиеся партии, новые результаты анализа, обновлённые ratings, исправленные позиции/ревизии → обновлять **только зависимые** read models/карточки. Инкрементальное обновление приветствуется, но если оно рискованно — ровно один coalesced background recompute по затронутому account/scope, с bounded retries/backoff и без блокирования event loop. Если во время закрытия нет изменений, ни Tier A, ни Tier B нельзя «пересчитывать на всякий случай».
- Сохранять результат **по завершении вычисления**, а не только в `closeEvent`. При аварийном завершении или прерванной записи последний подтверждённый snapshot остаётся целым; при штатном закрытии ничего не требует долгого синхронного flush. Корректная атомарность, изоляция разных аккаунтов, schema/formula/source IDs, ограничение размера, чистка и отсутствие чтения чужого профиля.
- Нельзя использовать TTL/time-of-day в качестве единственного invalidation: данные SQLite могут не меняться за часы, а new Lichess archive обнаруживается уже после старта асинхронно. Нужен **доказуемый data fingerprint/revision** на релевантные поля, и отдельная проверка актуальности без задержки первого paint. Исправление C4 (`analysis_jobs`/`game_positions`) часть этой же модели. При ошибки записи cache — отражать диагностический результат и не маскировать его вечным «сверяем аналитику».

### Обязательная диагностика причины именно на 3319 партиях

**Визуальный first paint:** при готовом валидном Tier A/Tier B не показывать бессмысленное «подготавливаем сводку», «сверяем локально сохранённую аналитику», placeholders «—» и прыгающие по высоте карточки. ### 11.2. ПОВЕДЕНИЕ, КОТОРОЕ НУЖНО РЕАЛИЗОВАТЬ (не заменять лозунгом «Tier A/Tier B»)

1. **Стабильный last-known-good для каждого профиля.** Persist полную *компактную* проверенную сводку B отдельно от быстро изменяемого A. Запись нового Tier A, новая партия, background import, job status и новую revision **не должны уничтожать B**, пока не готово корректное новое значение. Не путать `last-good` с резервной копией **того же** revision. Нужны отдельные scope, formula/schema compatibility, признаки freshness/provenance, atomic publish, bounded retention, восстановление при следующем процессе. Сохранять от перезаписи неполными preview/skeleton. Не использовать чужие аккаунты, несовместимую формулу или повреждённый кэш.
2. **Первый полезный paint Home — уже сохранённые данные.** Для ранее успешно рассчитанного профиля показывать **текущий точный count + последние 3 актуальные партии**, а глобальную точность/ошибки/охват и рейтинг задач **с последнего сохранённого достоверного снимка немедленно**, не дожидаясь полного SQL scan или Lichess. Если данные устарели — явно «данные на момент N, обновляется»/точечная ненавязчивая метка рядом с затронутой метрикой; НЕ выдавать старую точность за текущую и не подменять отсутствие оценки нулём. Если puzzle rating не изменялся, его не сбрасывать из-за новой партии. Если валидного B ещё никогда не было, первый расчёт разрешён в фоне с честным статусом, затем persistent save обязателен.
3. **Три последние карточки — идентичность и состав.** После добавления G4 к G1/G2/G3 немедленно показать G4/G1/G2; для **неизменившихся** G1/G2 восстановить их прежнюю точность/ошибки/график по `account + game_id + line_revision/hash + side + source`; у нового G4 показать только достоверную уже сохранённую оценку или честное «не рассчитано/обновляется», не переносить оценку G3. Никаких 3 одинаковых placeholders при наличии валидных сохранённых фактов. Не путать terminal/active и неизвестный цвет.
4. **Пересчёт в фоне действительно завершается и сохраняется.** При source churn/rate-limit повторного query: bounded/debounced scheduler с отменой stale generation, durable publish после стабильного committed snapshot, без бесконечного drop/retry/переписывания B. Разумная отдельная валидность «партии/точность», «последние 3 карточки», «задачи/рейтинг». Если revision изменился прямо во время запроса, помечать данные stale и перепланировать, а не рисовать их как свежие и навсегда пропускать запись. Не блокировать Qt, background workers отключать при shutdown; не ждать **всю** очередь записей ради чтения уже закоммиченных данных.
5. **Переходы должны быть мгновенными.** При Play→Home и обратно `show_home` не делает SQL/диск/JSON/fsync и **не очищает** metrics при неизменившемся профиле. Home может получать тихие обновления данных, но успешный показ не должен превращаться в blank/skeleton при каждом route/account callback. На рестарте заранее восстановить допустимый last-good scope, не требуя живого OAuth/Stockfish/полного archive sync.
6. **Fair Play и сохранность:** при активной игре против человека запрещённое engine-content по-прежнему скрывается. Не разрушать пользовательские PGN/SQLite или credential state; никаких новых вычислений engine в live human. Отображение старого historical snapshot проходит тот же safety gate. Никакой cross-account leakage при быстрых switch/logout/reconnect, нет бесконечного риска stale data после реального изменения формулы/схемы.
