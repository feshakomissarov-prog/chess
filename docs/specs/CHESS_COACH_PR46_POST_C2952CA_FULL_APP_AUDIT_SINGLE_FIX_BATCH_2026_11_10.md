## 2. C2 [P1] Offer_draw при существующем входящем предложении может стать непреднамеренным согласием на ничью

**Доказательство:** [service_games.py:299–364](https://github.com/feshakomissarov-prog/chess/blob/c2952caa61460dd2f052519e6ab271c291b28106/src/chess_coach/lichess/service_games.py#L299-L364) проверяет `offer_draw` лишь на собственный флаг и pending; **не запрещает offer при подтверждённом opponent draw flag**. [service_games.py:1028–1033](https://github.com/feshakomissarov-prog/chess/blob/c2952caa61460dd2f052519e6ab271c291b28106/src/chess_coach/lichess/service_games.py#L1028-L1033) отправляет один и тот же Lichess `draw/yes` для `offer_draw` и `accept_draw`. Протокол Lichess трактует `draw/yes` как принятие существующего предложения, если оно уже есть. UI обычно показывает правильную кнопку, но прямой API вызов/устаревшая очередь/событие между click и POST обходит это намерение.

**Исправить:** `offer_draw` fail-closed при известном входящем предложении, **также повторно** непосредственно перед transport; никогда автоматически не превращать offer в accept. Явное `accept_draw` доступно только при актуальном подтверждённом incoming flag; `decline_draw` аналогично. При race safely reject stale offer и сообщить «соперник предлагает ничью» без стороннего POST. Не нарушать независимость `resign` и разрешённый ответ на incoming offer.

**RED тесты:** в сервисе fresh gameFull→opponent `wdraw/bdraw=True`→`draw(accept=True, accepting_offer=False)`=no POST; fake race opponent offer после reservation, но до выполнения worker; настоящая accept отдельно делает ровно один `draw/yes`; обе стороны цвета, replay, network failure, account switch. Проверить, что **нет непреднамеренного terminal draw**.

**Источник:** [service_games.py:984–1022](https://github.com/feshakomissarov-prog/chess/blob/c2952caa61460dd2f052519e6ab271c291b28106/src/chess_coach/lichess/service_games.py#L984-L1022) создаёт новый worker при каждом `send_move(game_id,uci,request_id)`; в отличие от `_action` и `takeback` не резервирует in-flight ключ и не проверяет повтор того же `request_id`. **Исправить:** atomic request idempotency per account generation + game + pending move/request_id, один POST максимум в условиях concurrency, queued callbacks, reconnect, ambiguous POST. Разрешать следующее новое движение только после надёжного серверного подтверждения линии/другого корректного intent. Не смешать этот ledger с премувом, требующим собственного requestId; отказаться от бесконечного накопления старых IDs. Сохранить существующие исправления N2/N6.

**RED тесты:** два параллельных прямых `send_move` с одинаковым requestId; queued same ID; ошибка timeout/429; late ACK и repeated gameState; новая легальная заявка после confirmed next ply; старое поколение авторизации. Результат: не более одного HTTP POST на один intent, ноль автоматических повторов.

### Продуктовый контракт: ДВА УРОВНЯ сохранённой статистики

**Tier A — мгновенная базовая сводка (самый высокий приоритет)**

- Отдельный **маленький, атомарно сохранённый** read model по текущему профилю: число завершённых партий, побед/поражений/ничьих, три последние завершённые партии (результат/соперник/дата/дебют при наличии), необходимые подписи и минимальная история прогресса — **только те поля, которые реально нужны на первом экране**. Не сериализовать сюда целые PGN, позиции и тысячи assessments.
- Сохранять Tier A **сразу после первого успешного получения**, обновлять после релевантных commit; **восстанавливать при следующем запуске до подключения Lichess, тяжёлой аналитики и фоновых синхронизаций**, выбрав persisted account scope. Нет кэша — bounded background query, мгновенные skeleton/card shell без блокировки Qt. Сохранённые значения **не стирать на секунды** при уходе/возврате на Home.
- \`show_home()\` **только переключает уже существующую страницу** и использует in-memory snapshot/виджеты. Никаких SQLite connect/read, file I/O/JSON parse, fsync, тяжелых пересчётов или join() в GUI event handler. Перепроверка ревизии/диск/кэш — отдельно в background и с coalescing, без гонки account switch.

**Tier B — подробная сохранённая аналитика**

- Независимая версионированная персистентная модель: средняя точность с источниками, покрытие, ошибки/зевки на 100 оценённых ходов, источники оценок, рейтинг задач/тренды, графики/карточки и дополнительные сложные показатели — **только при фактически сохранённых достоверных данных**, без фальшивых нулей/точности.
- Если Tier B уже посчитан и данные не изменились, **показать его сразу вместе с Tier A после перезапуска**. Если Tier B просрочен — показать последнюю сохранённую сводку с деликатным «обновляется» (только для того же аккаунта, с корректной пометкой); затем один **фоновый** источник-ориентированный пересчёт. В любом случае Tier A не теряется и не ждёт Tier B.
- Новые/изменённые записи, завершающиеся партии, новые результаты анализа, обновлённые ratings, исправленные позиции/ревизии → обновлять **только зависимые** read models/карточки. Инкрементальное обновление приветствуется, но если оно рискованно — ровно один coalesced background recompute по затронутому account/scope, с bounded retries/backoff и без блокирования event loop. Если во время закрытия нет изменений, ни Tier A, ни Tier B нельзя «пересчитывать на всякий случай».
- Сохранять результат **по завершении вычисления**, а не только в \`closeEvent\`. При аварийном завершении или прерванной записи последний подтверждённый snapshot остаётся целым; при штатном закрытии ничего не требует долгого синхронного flush. Корректная атомарность, изоляция разных аккаунтов, schema/formula/source IDs, ограничение размера, чистка и отсутствие чтения чужого профиля.
- Нельзя использовать TTL/time-of-day в качестве единственного invalidation: данные SQLite могут не меняться за часы, а new Lichess archive обнаруживается уже после старта асинхронно. Нужен **доказуемый data fingerprint/revision** на релевантные поля, и отдельная проверка актуальности без задержки первого paint. Исправление C4 (\`analysis_jobs\`/\`game_positions\`) часть этой же модели. При ошибки записи cache — отражать диагностический результат и не маскировать его вечным «сверяем аналитику».

### Обязательная диагностика причины именно на 3319 партиях

Codex не должен заявлять «исправлено» на базе одного теста **7.37 ms / empty DB**. До исправления добавить timings *по фазам*, а после снять сопоставимые замеры:

- cold-start before auth, first paint Tier A/Tier B, last 3 games ready, account selection;
- every \`show_home\` after Play / Analysis / Library / 5–10 последовательных переходов, **Qt event-loop max stall** и wall-clock длительность перехода;
- main-thread SQLite wait (включая busy_timeout), JSON file read/parse, cache lookup, widget construction/paint, memory/scope cache hit/miss, revision comparisons;
- cache write result/bytes/OS error/format mismatch/revision mismatch/eviction — **без токенов, логов партий и других персональных данных**;
- background sync no-op vs real changed-game, materialization batches, concurrent SQLite writer, repeated OAuth reconnect, two profiles; определить что именно сбрасывает cache при рестарте на representative dataset.

**Матрица:** clean temporary SQLite (0), 100, **3319**, 5000–10000 synthetic finished games с source-backed и пустыми анализами; первый запуск → успешный расчёт → закрыть → новый отдельный процесс → Tier A и B немедленно → 10× Play↔Home без SQL/диска/агрегата на UI thread; затем одна действительно изменённая партия и одна только метрика → точечная новая ревизия и background update; затем harmless no-op sync → **без** full aggregate; новый аккаунт → no cross-account flashes; offline/429/errors; cache corrupted/too large/permissions denied; in-flight save and worker cancel. Для честной проверки persistent-state **тесты отдельных экземпляров/process и настоящий filesystem**, а не reuse одного Python объекта в одном pytest.

**UX и тестовые пороги:** требование «всегда отзывчивое окно» проверить через реальные Qt timers / native Windows instrumentation. Как **цель производительности**, а не утверждение о существующем результате: warm \`Play → Home\` p95 ≤100 ms, first useful cached Tier A ≤250 ms на согласованном Windows reference profile, no UI-thread stall >100 ms; если на CI разные CPU/DPI, сохранить реальные измерения и пометить hardware-dependent отклонения, не подкручивать/не подменять цифры пустой БД. Подробная аналитика в фоне может завершиться позже; скорость её запроса не должна блокировать UI или мгновенную сводку. Никакого Rust, микросервисов или полного переписывания SQLite без доказанной необходимости.

**Визуальный first paint:** при готовом валидном Tier A/Tier B не показывать бессмысленное «подготавливаем сводку», «сверяем локально сохранённую аналитику», placeholders «—» и прыгающие по высоте карточки. При настоящем cold miss честно дать базовый responsive skeleton с явным состоянием; при partial/missing analysis — «анализа нет», не выдумывать точность.

**Fair Play:** читая историю **завершённых** игр/подготовленные агрегаты, не запускать Lichess preflight и не сбрасывать их только из-за connection status; live человеческие engine-подсказки/активные задачи должны сохранять свои границы, никаких «случайно отобразили текущую engine оценку из кэша». Смена аккаунта не даёт даже кратковременного показа чужих данных.
