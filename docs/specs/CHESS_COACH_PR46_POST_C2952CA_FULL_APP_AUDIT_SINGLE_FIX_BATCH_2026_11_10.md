## 1. C1 [P1] CredentialStore исключение оставляет игровые запросы зависшими без отправки HTTP

**Доказательство исходником:** [service_auth.py:471–476](https://github.com/feshakomissarov-prog/chess/blob/c2952caa61460dd2f052519e6ab271c291b28106/src/chess_coach/lichess/service_auth.py#L471-L476): `operation_token(context)` вызывает `context.credential_store.get()`, который может возбуждать `CredentialStorageError`; это [стандартный контракт WindowsCredentialStore.get в auth.py:61–68](https://github.com/feshakomissarov-prog/chess/blob/c2952caa61460dd2f052519e6ab271c291b28106/src/chess_coach/lichess/auth.py#L61-L68).

- [service_games.py:242–283](https://github.com/feshakomissarov-prog/chess/blob/c2952caa61460dd2f052519e6ab271c291b28106/src/chess_coach/lichess/service_games.py#L242-L283): `takeback.work()` вызывает `operation_token` **до** `try/except`; исключение уходит из worker без `session_takeback_action_completed`, без очистки `_pending_actions`, без разблокировки UI. Это **прямой source-level дефект**, в отличие от теста `get()->None`, который проходит.
- [service_games.py:338–370](https://github.com/feshakomissarov-prog/chess/blob/c2952caa61460dd2f052519e6ab271c291b28106/src/chess_coach/lichess/service_games.py#L338-L370): `_action` переводит pre-transport credential failure в status=-1 и оставляет `awaiting_authoritative_state`, хотя POST точно не отправлен.
- [service_games.py:984–1022](https://github.com/feshakomissarov-prog/chess/blob/c2952caa61460dd2f052519e6ab271c291b28106/src/chess_coach/lichess/service_games.py#L984-L1022): `send_move` переводит это в status=0 (ambiguous); [window.py:7404–7423](https://github.com/feshakomissarov-prog/chess/blob/c2952caa61460dd2f052519e6ab271c291b28106/src/chess_coach/window.py#L7404-L7423) не снимает pending move при status=0.

**Исправить:** для всех команд/ходов единое различение `NOT_SENT` (невозможность получить credential/admission до вызова transport) и `MAYBE_SENT` (после начала сетевого POST). Pre-transport исключения обработать детерминированно: no POST, status local definitive, корректные сигналы UI, освобождение соответствующих reservation и pending, диагностическое сообщение без токена. Не пересылать автоматически запросы с неизвестным исходом. Учитывать одновременный account switch/cancel. В `takeback` гарантировать финализацию через `try/finally`/явную state-machine, а не надеяться на `BackgroundWorkCoordinator` catching exceptions.

**RED тесты:** fake credential store `get()` raises `CredentialStorageError` **после** установки request pending, для `send_move`, `takeback`, `offer_draw`, `resign`, `claim_victory`. Проверить ровно ноль client POST, завершение callback, отсутствие stale pending, доступность дальнейших разрешённых действий после свежего snapshot; проверить комбинацию с 401/429/таймаутом, где реально начатый запрос остаётся ambiguous. Обязательны Qt-window тесты без network.

## 2. C2 [P1] Offer_draw при существующем входящем предложении может стать непреднамеренным согласием на ничью

**Доказательство:** [service_games.py:299–364](https://github.com/feshakomissarov-prog/chess/blob/c2952caa61460dd2f052519e6ab271c291b28106/src/chess_coach/lichess/service_games.py#L299-L364) проверяет `offer_draw` лишь на собственный флаг и pending; **не запрещает offer при подтверждённом opponent draw flag**. [service_games.py:1028–1033](https://github.com/feshakomissarov-prog/chess/blob/c2952caa61460dd2f052519e6ab271c291b28106/src/chess_coach/lichess/service_games.py#L1028-L1033) отправляет один и тот же Lichess `draw/yes` для `offer_draw` и `accept_draw`. Протокол Lichess трактует `draw/yes` как принятие существующего предложения, если оно уже есть. UI обычно показывает правильную кнопку, но прямой API вызов/устаревшая очередь/событие между click и POST обходит это намерение.

**Исправить:** `offer_draw` fail-closed при известном входящем предложении, **также повторно** непосредственно перед transport; никогда автоматически не превращать offer в accept. Явное `accept_draw` доступно только при актуальном подтверждённом incoming flag; `decline_draw` аналогично. При race safely reject stale offer и сообщить «соперник предлагает ничью» без стороннего POST. Не нарушать независимость `resign` и разрешённый ответ на incoming offer.

**RED тесты:** в сервисе fresh gameFull→opponent `wdraw/bdraw=True`→`draw(accept=True, accepting_offer=False)`=no POST; fake race opponent offer после reservation, но до выполнения worker; настоящая accept отдельно делает ровно один `draw/yes`; обе стороны цвета, replay, network failure, account switch. Проверить, что **нет непреднамеренного terminal draw**.

## 3. C3 [P2, strengthening] Прямой send_move не имеет service-level one-shot ledger по request_id

**Источник:** [service_games.py:984–1022](https://github.com/feshakomissarov-prog/chess/blob/c2952caa61460dd2f052519e6ab271c291b28106/src/chess_coach/lichess/service_games.py#L984-L1022) создаёт новый worker при каждом `send_move(game_id,uci,request_id)`; в отличие от `_action` и `takeback` не резервирует in-flight ключ и не проверяет повтор того же `request_id`. UI `session.begin_submission` обычно гасит дубль, но сервису нельзя полагаться только на одну Qt точку вызова.

**Исправить:** atomic request idempotency per account generation + game + pending move/request_id, один POST максимум в условиях concurrency, queued callbacks, reconnect, ambiguous POST. Разрешать следующее новое движение только после надёжного серверного подтверждения линии/другого корректного intent. Не смешать этот ledger с премувом, требующим собственного requestId; отказаться от бесконечного накопления старых IDs. Сохранить существующие исправления N2/N6.

**RED тесты:** два параллельных прямых `send_move` с одинаковым requestId; queued same ID; ошибка timeout/429; late ACK и repeated gameState; новая легальная заявка после confirmed next ply; старое поколение авторизации. Результат: не более одного HTTP POST на один intent, ноль автоматических повторов.
