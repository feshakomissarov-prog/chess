# Chess Coach — M0: детальное ТЗ на игровой интерфейс и шахматную доску

**Версия:** 1.0 — подготовлено для согласования владельцем, **пока не передано Codex в работу**.  
**Статус:** READY FOR REVIEW; после утверждения — задача реализации M0.  
**ОС:** Windows 10/11, 64-bit. **Локальная папка владельца:** `G:\project\chess` (не фиксировать в коде).  
**Технологическое направление:** Python 3.12+, PySide6, python-chess; готовую доску оценить по [BOARD_COMPONENT_REVIEW](../BOARD_COMPONENT_REVIEW.md).  
**Источники:** [PCD](../PCD.md), [PRD](../PRD.md), [ROADMAP](../ROADMAP.md), GitHub Issue #1.

## 1. Цель и нецели

**Цель M0:** разработать настоящую, удобную и визуально аккуратную **офлайн-оболочку шахматного клиента** под Windows. Это не статический мокап: пользователь должен делать ходы, видеть журнал, пользоваться двумя способами перемещения, пометками и предходами (в тестовом режиме), менять настройки и просматривать ранее сыгранные ходы.

**Приёмка:** пользователь лично запускает приложение, проверяет визуальный стиль и типовые манипуляции мышью. Программу спроектировать так, чтобы в M1/M2 добавить Lichess, не переписывая UI и шахматную модель.

**Не реализовывать в M0:** OAuth, сеть и реальный Lichess, поиск/создание приглашений, учётные записи, голос, Stockfish, оценку позиции, GPT, SQLite, аналитику, рейтинг, собственный сервер, сложную систему сохранений, поставку `.exe`. Нет необходимости в звуках; они **опциональны**, их отсутствие не блокирует приёмку.

## 2. Визуальная система и референс

Автор предоставил скриншот классической доски: тёплая светло-бежевая/коричневая клетка, контрастные чёрные и белые **Cburnett-подобные SVG фигуры**, координаты по краям, строгий плоский стиль. Скриншот предоставлен как визуальный ориентир, а не как автоматически лицензированный ассет.

### 2.1. Доска

- Базовые цвета полей: **светлое `#F0D9B5`, тёмное `#B58863`**; близость к скриншоту важнее точного цифрового совпадения.
- Доска квадратная 8×8; отсутствие тяжёлых рамок, 3D, градиентов или шахматных фигур в виде букв/emoji.
- Фигуры чётко различаются по цвету, форме и масштабу; применять SVG с прозрачным фоном, корректно масштабируемые при HiDPI. Классический набор Cburnett предпочтителен, **при подтверждённой лицензии и соблюдении notices**.
- Координаты файлов a–h и горизонталей 1–8 вдоль границ (как на референсе), ориентированы по текущему цвету.
- Подсветка последнего хода — полупрозрачные два поля; выбранная фигура и доступные клетки визуально различимы. Не использовать слишком яркое/агрессивное выделение.
- При шахе можно подсветить короля (не подсказка движка, а шахматный факт).
- Пример стартового положения после запуска. При перевороте доски белые/чёрные меняют нижнюю сторону, но внутренний FEN остаётся прежним.
- Размер доски вычисляется из доступного пространства, не фиксирован пикселями; при изменении окна доска не растягивается по одной оси и не обрезает фигуры.

### 2.2. Оболочка и компоновка

- Верх: название **Chess Coach**; небольшая навигация «Играть», «Мои партии», «Анализ», «Тренировки» (не реализованные разделы явно обозначать как будущие/неактивные, без ложной работоспособности); «Настройки».
- Зона игры: **слева** большая доска; **справа** панель оппонента/статуса, ходов и управления. Для M0 можно использовать адаптивное разделение `QSplitter` с предпочтительным соотношением ~65/35. Размещение справа по умолчанию; в будущем допускается изменение.
- Над доской: имя/метка соперника; под доской: «Вы» или «Локальная партия». Часы не являются обязательными для M0; вместо реальных чисел не рисовать «фальшивые часы».
- Панель ходов прокручивается независимо от доски. Ходы отображаются как номера и пары белых/чёрных: например `1. e4 e5`, `2. Nf3 Nc6`. Выделяется текущий просмотренный ход.
- Кнопки: новая локальная партия (со сбросом после подтверждения), переворот доски, вернуться к текущей позиции, очистить стрелки, настройки. Кнопки будущих Lichess/аналитических функций либо отключены с пояснением, либо отсутствуют.
- Подключение Lichess в M0 честно показано как «Не подключено (будет добавлено позже)».
- Минимальное рекомендуемое окно ~1100×700; на обычном экране 1920×1080 UI должен быть удобен. При меньшем окне допускается сжатие/прокрутка боковой панели без обрезки доски.
- Общие цвета панелей спокойные нейтральные: доска — главный цветовой акцент. Основной UI на русском.

## 3. Управление фигурами: два обязательных способа

### 3.1. Клик → клик

1. Левый клик на **своей фигуре, которой сейчас можно ходить**: выбор, подсветка клетки и возможных ходов.
2. Второй левый клик на допустимой целевой клетке: запрос хода; в M0 локальный контроллер подтверждает ход и обновляет журнал.
3. Второй клик по выбранной фигуре: снять выделение.
4. Клик по другой своей фигуре: изменить выбор.
5. Клик по недопустимой клетке: не менять положение; снять или сохранить выбор последовательно и предсказуемо.
6. Ходы рокировки, взятия на проходе и превращения пешки должны выполняться по правилам.

### 3.2. Drag-and-drop

1. Зажать левую кнопку на фигуре, переместить мышь к целевой клетке, отпустить.
2. Во время движения фигурка визуально следует за курсором (или аналогичная понятная визуализация); исходное поле не создаёт второй «материальной» фигуры.
3. При легальном ходе выполнить его; при недопустимом — вернуть фигуру в исходную клетку, не изменяя FEN/журнал.
4. Перетаскивание за границы доски не удаляет фигуру и не делает ход.
5. Обычный короткий клик **не должен ошибочно считаться drag**; порог движения настроить.
6. При снятии/потере фокуса или Esc незавершённый drag отменяется безопасно.

### 3.3. Превращение

Если пешка достигает последней горизонтали, показывать собственный выбор: ферзь, ладья, слон, конь. Не превращать автоматически в ферзя при обычном ходе. До выбора не зафиксировать движение в модели. Отмена диалога сохраняет исходную позицию.

## 4. Предходы (premove) — обязательный контракт

### 4.1. Семантика

Предход — **условное намерение сыграть ход в будущей позиции**, когда сейчас очередь соперника. Это **не выполненный ход** и не часть PGN до фактического подтверждения.

- Один предход за раз; новый заменяет предыдущий.
- Можно поставить **клик-клик** или **перетаскиванием** своей фигуры, пока ходит соперник.
- На доске предход выделяется отдельной полу-прозрачной стрелкой/цветом, отличной от ручных пометок и последнего хода.
- Предход не меняет реальную доску, turn, FEN, журнал и часы.
- Esc отменяет очередь предхода; также предусмотрен понятный способ отмены через UI.
- После прихода **подтверждённого хода соперника** контроллер повторно проверяет допустимость предхода уже в новой позиции:
  - если допустим — отправляет локальному источнику или, в будущей онлайн-игре, **запрашивает** отправку на сервер; окончательно коммитит его только после подтверждения;
  - если невозможен (например, исходная фигура взята, поле занято по-другому, король под шахом) — молча не применяет, снимает маркер и может показать краткое «Предход отменён: недопустим».
- Смена/сброс партии, переход в режим исторического просмотра, отключение/потеря контекста партии очищают предход безопасно.
- Нельзя запускать фиктивный автоход ИИ/движка для имитации предхода в M0.

### 4.2. Как проверить предход без Lichess в M0

Добавить **явно подписанный локальный тестовый режим** («Проверка предходов»), а не имитацию Lichess:

- Пользователь выбирает свой цвет, например белые. После своего хода белые ожидают.
- Находясь в ожидании чёрных, пользователь ставит белый предход.
- Для проверки есть простой механизм применения **легального хода чёрных вручную** из отдельного списка доступных ходов (либо поле UCI/SAN с валидацией) под надписью «Тестовый ход соперника».
- При применении ход соперника записывается как обычный ход; затем проверяется поставленный белый предход. Тестируется как успешное, так и отменённое выполнение.
- Допустима проверка через unit/integration tests и максимально простой тестовый интерфейс; не загромождать основной экран dev-элементами.
- После подключения Lichess этот «источник хода соперника» должен заменяться сетевыми событиями **без переписывания UI намерений**.

**Необязательные для M0 улучшения:** серия предходов, предход в промоушен с дополнительным выбором, синхронизация звука, визуальные анимации премувов. Поддержка одного обычного предхода — обязательна.

## 5. Ручные графические пометки

- **Правая кнопка мыши + протяжка** между клетками: стрелка из начального поля в конечное.
- **Правый клик без протяжки** по клетке: круг/выделение клетки.
- Повтор того же действия снимает соответствующую пометку (toggle).
- Кнопка «Очистить пометки» удаляет только ручные пометки, не шахматные фигуры и не предход.
- Ручные стрелки не могут становиться «подсказками движка»; никакого автоматического расчёта для них не производится.
- В M0 достаточно одного контрастного, но ненавязчивого цвета стрелок/кругов; горячие клавиши нескольких цветов — позже.
- Отрисовка стрелок и координат не должна нарушать click и drag левой кнопкой.
- При смене позиции ручные пометки можно очищать (выбрать одно предсказуемое правило и зафиксировать). Не сохранять их в PGN на M0.

## 6. История ходов и навигация

- После каждого подтверждённого хода обновить журнал SAN; показать номер хода и кто ходил.
- Автопрокрутка к последнему ходу во время обычной игры.
- Клик по записанному ходу показывает **историческую позицию** (включая допустимые варианты возврата вплоть до начальной). Выбранный ход подсвечен.
- Навигация кнопками `|<`, `<`, `>`, `>|` (начало, шаг назад, шаг вперёд, актуальная позиция); допустимы клавиши ←/→ при фокусе на панели истории.
- **Принцип разделения:** просмотр истории никогда не изменяет фактически сыгранную партию и не удаляет её ходы. В режиме просмотра нельзя отправлять новые ходы; нужно сначала вернуться к актуальной позиции.
- Во время просмотра сохранять подсветку последнего хода выбранного исторического состояния, а не следующего ещё не «достигнутого» хода.
- Новая партия и переключение режима безопасно сбрасывают выделение и предход.

## 7. Настройки M0

В отдельном диалоге «Настройки», с минимумом:
- переворот доски / предпочтительная ориентация;
- показ доступных ходов (вкл/выкл);
- подсветка последнего хода (вкл/выкл);
- визуальные пометки (вкл/выкл) и очистка;
- тема доски: первая версия — **одна согласованная бежево-коричневая по умолчанию**; возможность выбора альтернативы не обязательна;
- звук: **необязателен**; если реализован, в настройках есть тумблер и громкость, по умолчанию можно выключить.

Простые настройки интерфейса допускается хранить локально через `QSettings` (не SQLite, не сервер). После закрытия и повторного запуска они сохраняются. Ошибка/отсутствие настроек приводит к безопасным значениям по умолчанию.

## 8. Архитектурная подготовка к Lichess

Подготовить **тонкие границы**, без реализации API:
- `GameSession` / `GameController` — единственный владелец текущей подтверждённой позиции, списка ходов, статуса/очереди предхода и режима просмотра. За правила отвечает python-chess.
- `BoardView` — только отображает `PositionSnapshot` и генерирует `MoveIntent(from,to,promotion?)`, `PremoveIntent`, `AnnotationIntent`.
- `GameSource` (или иной небольшой интерфейс) — локальный источник подтверждённых ходов в M0, сменяемый сетевым источником позже. Не обязательно вводить сложную hierarchy/DI framework; достаточно ясного контрактного разделения.
- Сетевой сервер в будущих M1/M2 является авторитетом окончательного онлайн-состояния. Виджет **не делает необратимый `board.push` на событии движения мыши до подтверждения**.
- Не хранить отдельные мутируемые `chess.Board` в UI и контроллере одновременно без чёткого синхронизирующего правила. Копии для отрисовки/исторического просмотра должны быть неизменяемыми с точки зрения живой партии.
- Не придумывать Lichess токены, ответы API или «успешные» имитации подключения.

Нужно не разрабатывать всю онлайн-архитектуру, а **избежать очевидной будущей переделки**: в М0 UI не должен быть жёстко привязан к тому, что ходы обоих цветов всегда локальны и мгновенно подтверждаются.

## 9. Поведение вне обычных сценариев

- Нелегальный ход не меняет партию; сообщение должно быть ненавязчивым.
- Нет фигуры / нельзя ходить / текущая позиция историческая — не ломать интерфейс.
- Рокировка, взятие на проходе, превращение, шах, мат, пат корректны в модели; правила не реализовывать вручную, использовать python-chess.
- После мата/ничьей новые ходы нельзя добавлять без запуска новой локальной партии.
- Некорректный импорт FEN в тестовых инструментах не приводит к крэшу (если импорт FEN вообще добавлен).
- Изменение размера окна, DPI/масштаба экрана, переворот доски при наличии стрелок и смена настроек не ломают карту координат.
- Вся чувствительная к времени обработка должна оставаться в основном Qt-потоке только если это лёгкая UI-логика; тяжёлых задач в M0 нет.

## 10. Исследование повторного использования перед написанием кода

Первым шагом реализации провести короткую проверку `leszekhanusz/chess-widgets`: сможет ли виджет быть «чистой» доской под внешним контроллером, допускает ли доработку premove, стрелок и полного выбора promotion без масштабного форка. Изучить не только README, но и `board.py`, `renderer.py` и лицензионные notices SVG.

- Если интеграция реалистична — использовать зависимость/адаптацию с указанием автора и MIT-лицензии кода. Не переносить весь чужой репозиторий.
- Если требуется большой рефакторинг оригинального виджета — остановиться, описать доказанное препятствие и предложить собственный PySide6 `QGraphicsView` или отдельно согласуемую HTML/Chessground-ветку; не выбирать новый стек молча.
- Нельзя включать чужие ассеты/код в финальную сборку без проверки их лицензий и обязательных текстов. Лицензию **нашего** репозитория владелец решает отдельно; это не блокирует личное исследование M0, но блокирует выпуск чужих компонентов без соблюдения условий.

## 11. Доставка и проверки

- Минимальная структура проекта: приложение (`src/` или пакет), тесты, `pyproject.toml` либо `requirements.txt`, инструкции Windows, сведения о сторонних компонентах; избегать десятков пустых директорий.
- Рекомендуемая команда запуска — из корня проекта в `.venv` через `python -m <package>`; конкретное имя пакета выбирает Codex и фиксирует в README.
- CI необязателен в M0; unit tests шахматной логики и минимальная UI smoke-проверка обязательны, где среда позволяет.
- Итог в отдельной ветке + Pull Request, не выполнять merge без владельца. Скриншот рабочего интерфейса в PR желателен, но не заменяет ручную приёмку Windows.
- Codex описывает точные инструкции для владельца: `cd /d G:\project\chess`, создание venv и установку зависимостей/запуск (с учётом PowerShell или cmd — правильно выбрать один вариант; команда `cd /d` предназначена для cmd).
- Не обещать EXE в M0: сначала убедиться, что Python-приложение удобно работает.
