### 1.3. Подтверждённые механики Lichess по первоисточнику

- [Lichess puzzle client `ctrl.ts`](https://raw.githubusercontent.com/lichess-org/lila/master/ui/puzzle/src/ctrl.ts) (изучено 20.11.2026): `sendMove/addNode` сначала создаёт узел и показывает ход; `revertUserMove` для неправильного ответа делает видимый откат примерно через **300 ms**; `applyProgress` различает `fail`, `win`, `good` и автоматически применяет ответ соперника; `autoNext` — **настройка пользователя**, в обычных задачах default может быть OFF, в streak ON. Рейтинговое изменение серверное через `xhr.complete` — **не переносить эту семантику на наше read-only API**.
- [Lichess themes](https://lichess.org/training/themes): группировки открытия/миттельшпиль/эндшпиль, тактика, вилка, связка, незащищённая фигура, маты, финальные комбинации и другие.
- [API authenticated GET batch](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/puzzles/api-puzzle-batch-angle.yaml): `puzzle:read`, выбор angle/difficulty/`nb`, не использовать для массовой выгрузки. Отдельный POST требует `puzzle:write` и меняет официальный рейтинг Lichess.
- [API public GET puzzle by ID](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/puzzles/api-puzzle-id.yaml): одиночная реальная позиция доступна **без OAuth**. Это **минимальный живой online smoke** для Codex без доступа к аккаунту владельца.
- [Lichess Puzzle Streak](https://lichess.org/page/blind-mode-tutorial): серия корректных решений, при ошибке серия сбрасывается; ясный следующий шаг.
- **Сознательное продуктовое отличие:** Chess Coach может включить auto-next **по умолчанию**, хотя на обычном Lichess это настройка. Не объявлять, что на Lichess оно всегда включено; дать пользователю выбор.

Из-за ограничений публичного сайта анонимная автоматическая загрузка страницы `lichess.org/training` не позволяет проверить её полную интерактивность в браузере без активов и логина. Выводы о поведении **обоснованы исходным кодом**, а реальные UX сценарии Chess Coach требуется выполнить независимо.

## 2. Новый пользовательский контракт и экран

### 2.1. Основной поток: «Открыл обучение → сразу задача»

- В обычном обучении отображается **только онлайн-тренировка Lichess**, тема и сложность. В случае существующего безопасного разрешения `puzzle:read` начать асинхронный запрос **сразу при открытии**, без второго клика «Новая задача». Если OAuth отсутствует — один понятный экран `Подключить задачи Lichess` с CTA на отдельный consent; никогда не имитировать задачу Demo.
- Убрать из *основного* source combo «Сохранённые» и автономный fallback. Сохранённые задачи и `Мои ошибки` не удалять из SQLite: доступ к ним из раздела **История → Повтор ошибок** как явно отдельная, **не рейтингованная** ревизия, а не как альтернативный источник ежедневной онлайн-тренировки. Сохранить обратные ссылки с Home/из истории; если пришёл конкретный `puzzle_id`, открыть его в явно отмеченном режиме **«Повтор задачи · без рейтинга»**.
- При отсутствии сети показывать `Не удалось загрузить задачу Lichess · Повторить соединение`. Не подсовывать последнюю сохранённую под видом новой. При отсутствии live OAuth явно показывать причину, не отправлять владельца в ручной GitHub запуск.
- В online-потоке загружать **реальные** темы/сложность, запрещены synthetic/demo fixtures, случайное переключение профиля и автоматическая отправка результатов на Lichess. Ошибка 429 уважает Retry-After, делает умеренный backoff, не зависает UI.
- Профиль и активный puzzle-session изолированы: нельзя продолжить позицию A после смены на B без понятного явного перехода. Прежняя P0 data-attribution защита `_session_account_id` остаётся.

### 2.2. Рекомендуемая композиция 1672×941, текущий стиль

- Верх: `Решение задач`; компактные чипы `Lichess подключён`, `Тема: смешанные`, `Сложность: обычная` и **одна** ясная кнопка/переключатель `Автопереход: ВКЛ/ВЫКЛ`. Список тем не должен отбирать непропорциональную площадь у доски; поисковый фильтр по нажатию, адаптивное раскрытие. Sidebar/общая тема Chess Coach без изменений.
- Центр: крупная квадратная доска, над ней **устойчивый цветной статус игрового процесса** и `Ход белых/чёрных`. Зелёный `Верно!`, красный `Неверный ход — попробуйте ещё`, фиолетовый `Ход соперника`; финальная карточка `Задача решена ✓` или `Ошибка ✕` с конкретным следующим действием; не ограничиваться заменой маленького QLabel внизу.
- Справа: текущая задача (ID, тема, рейтинг самой задачи, только известные факты), **текущая серия** / лучшие серии, **локальный рейтинг Chess Coach** и отдельно `Рейтинг Lichess: 1917 · синхронизирован 11.10.2026` (только если именно эти значения получены от данных — здесь цифры **ПРИМЕР**, не захардкодить). История 5–8 элементов с цветным исходом, временем, темой, clickable replay.
- Под доской: одна компактная строка `Подсказка (0/2)` · `Решение` · `Повторить` · `Следующая задача`, а ниже **постоянная лента последних 10–20 результатов**: зелёные ✓ для чистых решений, красные ✕ для неудачных, нейтральные для skip/unrated; рядом `Серия: 4`, `Решено сегодня: 8 / Ошибок: 2`, **видимый +/− прогресс** по честному локальному рейтингу. Ни строки `Сохраняю в SQLite` вместо победы, ни статусных подсказок, которые исчезают.
- Компактный 1280×720 / 1120×640 / 125–150%: сначала доска, статус и «следующее действие»; информация/история в прокручиваемой боковой карточке; цвета, текст, фокус, кнопки и текущий ход не обрезаются. Отступы минимальны, но читаемость 12–14 px по Qt font metrics.
- Состояние успеха нельзя спутать с ожиданием хода: после конца задачи доска визуально имеет финальную цветную подсветку, а CTA **«Следующая задача»** видна даже при отключённом автопереходе. Задержка записи только в маленьком ненавязчивом бейдже у истории `● Сохраняется…`; ошибка — там же `Не удалось сохранить · Повторить` без закрытия завершённого состояния.

| `SOLVED_WITH_HINT` | `Решено с подсказкой`, без ложной «чистой» победы | отдельно фиксировать использование hint, даже если далее правильные ходы |

| `REVIEW` | `Просмотр хода 2/6 · Вернуться к решению` | колесо/кнопки листают сыгранную часть, без записи дубля попытки; выйти возвращением к текущему состоянию |

Состояния «результат первой попытки» и «попытка понять правильное продолжение» разделены. Не подсчитывать зелёную победу после ошибочного первого ответа, даже если впоследствии задача решена для обучения. При первом неверном легальном ходе **одно** событие FAIL/потеря текущей серии, последующие неправильные ходы не списывают многократно одну и ту же задачу. Ошибки ходов и нелегальные ходы различаются.

## 3. Доска и взаимодействие — детали

### 3.1. ЛКМ, ПКМ, ошибка, продолжение

- Доработать UI адаптер над `BoardView`, **не ломать** исторические игры, premove и аналитику. ЛКМ drag-and-drop и click-click должны работать одинаково, в том числе с promotion picker. ПКМ: drag стрелка, click круг/выделение. Подсказочные и пользовательские аннотации разные слои; пользовательская ПКМ-стрелка не является подсказкой.
- **При легальном, но неправильном ходе** не только менять status QLabel. Сначала показать фигуру на ошибочном поле, подсветить from→to красным/значком ✕, оставить видимой ~350–500 ms, затем плавно откатить; состояние шахматной позиции не должно быть зафиксировано как ответ. Контроллер может иметь transient render-FEN, но авторитетная `PuzzleTrainingState.board` сохраняет правильную позицию.
- При **нелегальном по правилам** ходе фигура возвращается на исходное поле сразу (допустим краткий shake) и появляется `Так ходить нельзя`; нелегальный drag/drop не считается неверным решением и не меняет рейтинг/серию.
- Если ход корректен, **сразу** показать его визуально и текст `✓ Верно`; если есть следующий ответ соперника, отдельным Qt-планировщиком/анимацией выполнить ответ через 350–600 ms и подсветить последнее перемещение; дальше `Ваш ход` и фокус на доске. **Никакого sleep() в GUI thread**. Уместные существующие звуки — опционально, не заставлять пользователя слушать.
- В конце подсветить окончательное правильное поле и показать fullscreen-на-доске? **Нет**: достаточно заметного overlay в пределах области над/под доской; не заслонять фигуры и не прыгать layout. Наряду с оверлеем обязательны текст и aria/accessible label (не только цвет).
- Не давать делать новые ходы во время transient WRONG_FLASH/OPPONENT_REPLY и после завершения без явного `Повторить`/`Просмотр`. **Не молчать**: если игрок пытается двигать фигуру после `SOLVED`, статус: `Эта задача уже завершена. Следующая / Повторить` и фокус на CTA.

### 3.2. Подсказки

- Кнопка `Подсказка` всегда ясна: `Подсказка (1/2)` и тултип «Сначала исходное поле, затем направление хода». После первого клика выделить **исходную клетку** (не стрелкой решения); после второго показать **стрелку** правильного хода; ещё одно нажатие не должно беззвучно ничего не делать — объяснить `Максимум подсказок использован`.
- После любой подсказки результат маркируется `с подсказкой` и не улучшает **чистую** серию/рейтинговый результат; не раскрывать ход в тексте заранее. Разделить help на текущий expected user move, не на полный сценарий.
- `Показать решение` с явным подтверждением; воспроизведение ходов по шагам через колёсико, но `REVEALED` не равно `SOLVED_CLEAN`. После проверки ответов не выводить лучший ход в процессе до user action.

### 3.3. Навигация колесом по ходам

- Использовать **уже существующий** `BoardView.wheel_navigate(int)` и подключить его на странице задач. Функция должна работать и над доской, и через маленькие кнопки `← / →` под ней. Клавиатурные стрелки Left/Right также управляют review, если фокус не в поиске темы/combobox.
- Источник просмотра — **копия доски и позиции из реального puzzle PGN/initialPly** плюс реально уже показанные пользователю ходы/ответы. **НЕЛЬЗЯ раскрывать будущие ходы до завершения**. На стартовой задаче можно листать только известный предыдущий фрагмент партии и назад к puzzle start; если источнику неизвестно историческое PGN, кнопка Previous честно disabled/`История до позиции не сохранена`, никаких фальшивых ходов.
- Каждое событие wheel перемещает ровно **один полуход**, со стабильным debounce; быстрый скролл безопасно ограничен границами. Отображать `Ход 5/9 · 2...Nf6` и подсветку последнего полухода, а текущий момент решения сохраняется отдельно.
- Когда пользователь вошёл в REVIEW до завершения, **не разрешать случайно записывать ход из старой FEN в текущую задачу**: `Вернуться к решению` восстанавливает текущую authoritative FEN, подсказки, время, попытку и счётчики без нового результата. После успеха/ошибки можно просмотреть доступную полную известную линию.
- Проверить mouse wheel/focus при overlay/scroll areas и на 125% DPI; **Qt QScrollArea не должен перехватывать wheel над самой доской**. ПКМ annotations должны переживать review так, как согласовано для текущей позиции; не наследовать стрелки на другой ход.

## 4. Результат, автопереход, следующий puzzle, фокус

- Показ результата **не зависит от записи SQLite или ответа сервера**. В `_finish` нельзя переписывать основной зелёный `Задача решена` статусом «сохраняется». Разделить `gameplay_feedback`, `persistence_feedback`, `network_feedback` и `session_metrics` на отдельные визуальные регионы.
- `Автопереход` — **ВКЛ по умолчанию для новых онлайн-задач** (явно отличается от default обычного Lichess), запоминается в `QSettings` по профилю. После **чистого** решения показать успех минимум 900 ms, затем переключить на готовую следующую задачу; если нет prepared — держать финальный успех и маленький `Загружаем следующую…`. Рекомендуемый диапазон 1100–1700 ms, реализовать один детерминированный default, не случайный.
- После решения **с ошибкой/подсказкой**, а также при раскрытом/пропущенном решении, по умолчанию не убегать автоматически до того, как пользователь увидит причину: **ручной Next** или отдельная настройка `Автопереход после любой задачи` (OFF по умолчанию). При переходе кнопка `Остаться и посмотреть` / явная отмена timer должна срабатывать, если пользователь тронул wheel/review/предыдущие ходы.
- Если авто OFF, показать явный `Следующая задача →` и сохранить победный экран до действий пользователя. По click `Следующая` из любой terminal phase всегда работает; из активной только после подтверждённого пропуска.
- По новой задаче полностью очистить transient overlay/стрелки/цвет предыдущего результата, сбросить timer, актуализировать `turn_label`, доступность кнопок и replay cursor. **Не переиспользовать устаревший callback** после смены темы/аккаунта/закрытия.

## 5. Настоящая отзывчивость: фоновые сохранения и prefetch

### 5.1. Независимые каналы

- **Gameplay UI** синхронно обрабатывает только быстрый reducer и Qt repaint; **persistence service** получает immutable record с `attempt_id, account_id, puzzle_id, session_id, outcome, first_fail/hints, elapsed`; **network service** асинхронно готовит следующий puzzle. Никаких SQLite запросов, HTTP, OAuth или `sleep` из UI handlers.
- Существующий `_save_training_attempt` уже worker, **его не «исправлять» вторым фоновым потоком без доказательства причины**. Удалить зависимость пользовательского успеха от `_attempt_save_completed`, оставить ненавязчивый статус. Если есть искусственное ожидание 2–3 с — показать профилировщик, конкретный stack/frame.
- Минимальная bounded очередь незавершённых writes, idempotent по `attempt_id`, последовательность commit ACK/failed ACK, retry с backoff, *не терять* историю при переходе на новую задачу или закрытии страницы. Если на закрытии pending и нет durable persistence — предупредить пользователя и сохранить без потери данных безопасным механизмом, без UI freeze; проектировать crash-consistency и ограничения очереди; **не создавать незащищённый файл с токенами/личными данными**. Точный уровень durability документировать и протестировать, не обещать надёжность без доказательства.
- После terminal outcome **сразу** разрешить переход к следующей задаче независимо от pending save, а `SAVE_FAILED` не затирает «Победа»; видимый retry в разделе истории/уведомлении. Не дублировать рейтинг/статистику при повторном ACK.
- Кэш подготовленной **одной** следующей online-задачи в памяти для выбранных `account+theme+difficulty`; при success/ошибке или при загрузке текущей prefetch вежливо сделать ≤1 дополнительного `GET`, не получать десятки «про запас». Не отправлять следующий запрос после отмены, при смене профиля или 429, не нарушать rate-limit Lichess.
- Параметры задач/нормализация PGN сохраняются как фактические от Lichess. Сеть недоступна → честно показывать ошибку, никакого скрытого локального фолбэка.

### 5.2. Измеримые нефункциональные критерии

- `move_intent → first visible correct/wrong feedback`: **p95 ≤100 ms** на изолированном Windows Qt runner для серии 40–100 ходов при обычной нагрузке; записать реальное измерение и среднее. Предполагаемая верхняя граница локального repaint, **не время сети**.
- Неверный легальный ход виден в течение 300–500 ms, и это **контролируемая анимация**, а не «лаг»; событие input принято сразу. Противник отвечает спустя 350–600 ms независимо от записи результатов.
- `terminal outcome → visible green/red verdict`: ≤100 ms; `terminal → next prepared puzzle visible`: ≤150 ms после истечения настроенной задержки (при готовом prefetch и живом GUI).
- Отдельно записать latency `sqlite commit` и `GET Lichess`; нет бессмысленного ожидания SQLite ни в ходе решения, ни на следующей задаче. Для внешней сети **не обещать SLA**, оценить реальные медиану/p95 на разрешённом live smoke. В fake transport проверить 50/500/3000 ms DB delay и 100/1200/3000 ms API delay: приложение интерактивно во время этих задержек.
- Если p95 не достигнут — исследовать конкретную причину с trace/stack, не улучшать цифры отключением регрессий, не называть PASS без stopwatch. SQL index не переписывать без замеров.

## 6. Видимый прогресс, рейтинг, серии и честные результаты

### 6.1. Лента результатов и текущая сессия

- По завершении задачи мгновенно добавлять в **UI session history** отдельный слот с цветом/иконкой `✓/✕/–` (при отсутствии SQLite ACK слот метится `pending`, но не исчезает). Последние **20** результатов, текущая серия чистых побед, лучшая серия за сессию, `чисто / с ошибкой / с подсказкой / показано решение / пропущено`.
- Успех с ошибкой **не** является чистым успехом для streak; первая ошибка сбрасывает серию **один раз**. Подсказка лишает чистой победы; результат не фальсифицирует исход, который пользователь реально увидел. Один `attempt_id` → один учтённый результат/изменение rating, повтор истории/перезапуск экрана не дублирует.
- Лента кликабельна: после завершения открывает соответствующий puzzle в `review/unrated`, не вносит новое изменение рейтинга. Итог победы/поражения различим **без необходимости читать таблицу**: цвет + иконка + доступный текст.

### 6.2. Два рейтинга — **никакой лжи об официальном Lichess**

- **Официальный рейтинг Lichess**: только read-only из последней синхронизации, с датой. При решении задачи в Chess Coach **не показывать +N к Lichess**, потому что текущее разрешение `puzzle:read` и GET API не отправляют результат на сервер. [Официальный API](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/puzzles/api-puzzle-batch-angle.yaml) требует отдельного `puzzle:write` для POST рейтингового результата. **Не добавлять его самовольно**.
- Реализовать **отдельный рейтинг практики Chess Coach**, видимый по текущей сессии (и при необходимости сохранённый локально), с честной маркировкой `Рейтинг тренировки CC` и `+12 / −8 за эту задачу`. Нельзя назвать его официальным Lichess и нельзя использовать «1917 → 1929» без явного `CC`.
- До реализации рейтинг-калькулятора (одноразовый choice внутри технического решения, **никаких фальшивых чисел**) определить документированную простую формулу, например Elo-like: `E=1/(1+10^((R_puzzle-R_CC)/400))`, `Δ=round(16*(S−E))`, где `S=1` только clean first-attempt solve, `S=0` при первом неправильном ходе/показе решения/пропуске; использовать рейтинг *реальной задачи* из API, начальный локальный рейтинг — **1500 (явно «начальный рейтинг CC»)**, не брать Lichess как скрытую основу. Задачи с отсутствующим рейтингом, повтор, локальная история и неполный результат — `не рейтингованный`, Δ=0. При hint выбрать жёсткое правило: `S=0` только если задача рейтингована и подсказка сделана до чистого результата; объяснить в UI, не штрафовать дважды. Можно предложить иную формулу **до начала реализации** только при доказанном преимуществе и сохранённой прозрачности. В таблице тестов зафиксировать конкретные пары исход → Δ.
- Изменение локального CC рейтинга фиксировать **не более одного раза** на уникальную первую rated attempt `account_id+puzzle_id` с idempotent database transaction; для следующей попытки puzzle replay Δ=0. Актуальный рейтинг до/после/дельта показываются в RESULT card. Реализация — аддитивная SQLite migration после v27 (если требуется), никакого ALTER с потерей данных. Отдельные учётные записи не перемешивать. UI optimistic delta может показываться сразу с `⏳`, **при save failure** пометка «не сохранено»/retry, при rollback — честная коррекция без двойных побед.
- Если в аккаунте ещё нет данных, явно `Рейтинг тренировки CC: 1500 (стартовый)`, если официальный рейтинг не синхронизирован — `Lichess: нет актуальных данных`; не показывать «+/- N» к чужим данным.
- Полноценная отправка official rating на сервер — **отдельная новая продуктовая задача с явным согласием на puzzle:write**, вне PUZ-UX-03.

## 7. Убрать офлайн-режим из продукта — не удалить данные и тесты

- На входе в «Решение задач» основная кнопка всегда означает **онлайн Lichess**, без системного default `Сохранённые`. Для истории и повторения старых ошибок — отдельная вкладка/переход, пометка `Повтор (не рейтингован)`, не выдавать это за online puzzle.
- **Нельзя** удалить миграцию v27, `puzzles`, `puzzle_attempts`, `local_puzzle_attempts`, импортированные 1500+ исторических задач, read-only backfill, replay из Home, автотесты с фиктивным API или системный `offline_mode`, если он используется другими страницами. Они нужны для целостности/CI/безопасности. Удаляется **только нежелательный пользовательский fallback** из основной тренировки.
- Запрещены пользовательские заглушки: `demo=True` не должен открываться через реальную навигацию; в native screenshots брать live online puzzle из публичного GET для **отдельного** online smoke и fake fixtures только для deterministic CI. Иных «сохранённых демо-задач» при потере сети не отображать.
- Если задача запрошена через старую историю, отдельно и ясно подписать `ПОВТОР ЗАДАЧИ — НЕ ВЛИЯЕТ НА РЕЙТИНГ`. При смене source/theme не перезаписывать старую попытку.

## 8. Обязательный REAL ONLINE UX SMOKE исполнительского агента

Это принципиально **новый gate**, без которого нельзя писать «проверено как на Lichess» или «удобно»; старые Qt synthetic captures **недостаточны**.

### 8.1. Два разных уровня реального онлайн-теста, без владельца

**ONLINE-LIVE-PUBLIC — обязательный и доступный без чужого OAuth:**
1. Использовать разрешённый доступ к Интернету из **изолированной среды агента**, не на пользовательском ПК. Проверить HTTP GET по официальному публичному `/api/puzzle/{id}` на одном документированном ID `0haqU` (из предыдущей официальной fixture), и **ещё 2 разных известных публичных ID**, без перебора диапазонов и массовой выгрузки. Должен быть реальный `200 JSON PuzzleAndGame`, зафиксировать `URL, timestamp, status, id, game.pgn length, solution count`, *не* записывать bearer tokens.
2. Открыть Chess Coach в контролируемом тестовом Windows environment и **пройти эти реальные полученные онлайн-позиции** через настоящий UI (не чисто fake JSON), включая **один неверный легальный ход**, корректный ход, ответ соперника, всю multi-ply последовательность, подсказку, окончание, стрелку ПКМ, wheel history и следующий переход. Снять **видео/GIF 5–15 s или серию consecutive screenshots с timestamps**, а не один static screenshot. Чётко отделять фактически созданные кадры от планируемых.
3. Это **live public API + настоящая UI механика**, но **НЕ** проверка authenticated random-angle batch. В отчёте честно подписать.

**ONLINE-LIVE-OAUTH — желателен как полный пользовательский маршрут, обязателен для утверждения «протестирован онлайн-авторизованный режим»:**
1. Тестовый пользовательский профиль, изолированные токены, consent только `puzzle:read`, без owner credentials; отдельный профиль создаётся/используется **только если разрешён и доступен** (не заводить скрытно дополнительные Lichess аккаунты — учитывать правила сервиса).
2. Пройти 5–10 реальных тематических задач в live GET с состояниями clean/wrong/hint, сменой темы и сложности, без POST и без `puzzle:write`. Сравнить feedback/timings с публичной страницей Lichess/исходным кодом. Проверить отсутствие ожидания SQLite при переходах, смену рейтинга **только у CC**, не официального.
3. **Если нет разрешённого отдельного OAuth и браузер/тестовые данные не позволяют проверить:** выставить `ONLINE-LIVE-OAUTH: BLOCKED (no authorized test credentials)`; **не просить владельца запускать workflow**, не входить в его аккаунт и не притворяться, что fake = live. Public online smoke остаётся обязательным; вопрос живого OAuth — прозрачный продуктовый риск, решение о пользовательском gate за владельцем.

### 8.2. Сценарий живой удобности глазами пользователя

После тестов исполнитель **лично** (в собственной тестовой среде с GUI, если доступна; иначе явно `NOT PERFORMED`) последовательно пройти: открытие тренажёра → первая онлайн задача → 1 верный ход → ожидание ответа → 1 ошибка → откат → 2 правильных → победа → автопереход → следующая тема → hint 1/2 → пропуск → wheel назад/вперёд → история → повтор задачи → потеря сети → восстановление. Обязательный чек-лист с yes/no:
- Без чтения инструкций понятно **чей ход?**
- **Мой ход принят?** Видны фигура/вердикт/ответ соперника?
- **Ошибка была в задаче или ход незаконен?**
- **Задача закончилась?** Где победа/поражение? Что сделать дальше?
- **Сохраняется ли сейчас результат?** Можно ли сразу решать следующую?
- **Какой рейтинг меняется?** Что официально, а что только в CC?
- **Что будет после ошибки сети?** Не подсовали offline/demo?
- **Могу ли я колесом посмотреть предыдущие сделанные ходы?**
- **Какие события отмечены зелёным/красным?** Что означает streak?
- **Есть ли заметная задержка и на каком именно этапе?** Привести trace.

**Если хотя бы один вопрос имеет ответ «нет», не заявлять UX ACCEPTED, даже если 1200+ pytest зелёные.** Исправить до acceptance или ясно выделить blocker. Нельзя выдумывать «я проверил глазами», если нет реальных кадров/интерактивного доступа.
