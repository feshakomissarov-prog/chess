## 2. «Главная» — эталон арт №1

### 2.1 Три карточки верхнего ряда, а не текущий технический dashboard

**Карточка 1 «Всего партий / С оценками»** — размер/позиция как в левом блоке арта: крупное число **завершённых** партий текущего выбранного аккаунта, ниже `С оценками: N` = **уникальные** игры с корректными позиционными score-данными текущей ревизии; под разделителем две видимые компактные строки/бейджа `Stockfish: N` и `Lichess: N` по **своему** источнику. Эти две категории **могут пересекаться** — если пересекаются, не утверждать `Stockfish + Lichess = уникальные оценённые`; tooltip с `N обоих источников`, что считается полной/частичной оценкой, необработанными играми, актуальной версией линии. Никакого «Полный 30 · частичный 953 · мои ходы 168/15605» на карточке. Пример 3309/983/953/30 в арте **не фиксировать в коде**.

**Карточка 2 «Точность»** — главный KPI `NN.N%` как **одна сопоставимая точность игр владельца**. Внизу **два источника** `Lichess: A% (n партий)` и `Stockfish: B% (m партий)` с возможностью увидеть точные определения. Правила: для одной партии брать максимум **один доверенный источник по чётко описанному приоритету** (официальная Lichess accuracy для текущей соответствующей партии, иначе локальный расчёт из её подходящего полного анализа с Lichess-методикой); не складывать и не смешивать проценты как `среднее(среднее Lichess, среднее Stockfish)`; объяснить единицу веса (обычно одна завершённая партия с валидной собственно-сторонней точностью = один вклад). **Официальная** и **локальная по методике Lichess** отличаются меткой provenance и математическим статусом. Не выводить фальшивый `87.1%`, если данных мало/нет: показывать `—` и `Данных пока нет`, либо `87.1% · 123 партии` с подсказкой источников/доверия.

**Карточка 3 «Рейтинг задач»** — сдвинуть в верхний ряд как на арте (не оставлять длинный поток текста отдельной строкой): крупный последний подтверждённый рейтинг, период «последние 90 дней»/доступный интервал, справа красивый мини-график по реальным сохранённым attempts/rating points. Hover по точке: дата, рейтинг, **решено / не решено** в чётко заданном периоде (день/сеанс/отрезок), с tooltip источника. Нет истории = не рисовать придуманный рост, предоставить лаконичный empty state; все существующие входы в «Прогресс»/задачи не терять (возможна кликабельная карточка/ссылка «Подробнее»).

### 2.2 «Последние партии» — 3 длинные горизонтальные карточки

Как на арте: три строки с левого края основной области до почти правого; при размере 1672×941 ориентир **~135–145 px высоты каждая**, отступы ~14 px. **Слева** крупно окрашенное **слово** `Победа`/`Поражение`/`Ничья`, ниже тип/имя соперника, дата/время, контроль `3+2`. **Посередине** русское название дебюта, ниже точность владельца с видимой меткой `Lichess` либо `Stockfish · локально` (или честное `пока нет`). **Правее** компактная таблица **тремя отдельными строками** `Неточности`, `Ошибки`, `Зевки` с маленькими заголовками **Белые/Чёрные** или `Я/Соперник` — не смешивать значения разных сторон. **Справа** мини-график 0/± и оценка по реальной позиции с hover; верх/низ графика без нарисованных заглушек при отсутствии оценок. Все три карточки визуально одинаковой сетки, читаемые, без километра пустой площади. Клик по строке открывает **именно детали той партии** в «Моих партиях» с сохранением возможности «Открыть разбор», не меняет аккаунт/выбор и не запускает Stockfish автоматически.

### 2.3 Показатели, безопасность, фоновая актуальность

`dashboard_snapshot` сейчас разделяет official accuracy и analysed games, а `game_card_metrics` показывает только official accuracy; исправить **read model + источник + UI**, не QSS поверх неверных цифр. `source` и `line_revision` обязательны для всех вычисленных показателей; обновление после готовой Lichess/SF оценки должно инвалидировать нужные кеши без полной загрузки тысяч PGN и без рассинхронизации со сменой аккаунта. Во время человеческой live-партии анализ/графики и скрытые источники **не должны просачиваться** через карточки/tooltip/кеш; сохранить строгий Fair Play fail-closed.

## 3. «Мои партии» — эталон арт №2

- **Верх:** крупный `Мои партии` и одна видимая строка `Поиск по сопернику, дебюту или дате`, справа небольшая кнопка `Фильтры`. Существующие десятки критериев из двух колонок перенести в компактный раскрываемый блок/popup с сохранением функциональности, состояния, клавиатуры, серверной пагинации и debounce. Не оставлять большую пустую форму фильтров всегда развёрнутой.
- **Левый список** ~50–52% рабочей области. Строки умеренной высоты (~72–85 px), каждая: слово результата зелёным/красным/нейтральным, соперник, дата/время, контроль, **русский дебют**. Выбор чётко подсвечен лавандовой рамкой/подложкой как на арте, список скроллится отдельно. Большая тысяча партий не создаёт тысячи QWidget одновременно — SQL paging/virtualize. Пустой список/ошибка загрузки/старый аккаунт — отдельные ясные состояния.
- **Правая деталь** (~48–50%) — карта выбранной партии с визуальной иерархией арта: `Победа` + дата/контроль/дебют; **кто белыми/чёрными, результат 1–0, известный рейтинг если хранится**; компактные отдельные статусы `Stockfish` и `Lichess` (например `Анализ готов`, `Данные ожидаются`, `Официальной точности нет`, `Нет анализа`, `Проверка…`). **Наличие записи на Lichess ≠ наличие серверного анализа**: не делать зелёный `Lichess ✓` от одного факта существования партии.
- **Статистика** — именно **вертикальные строки** как на арте: `Точность`, `Неточности`, `Ошибки`, `Зевки`, `Охват`, опционально `Хорошие`. Чётко указать, кого отражает одиночный счётчик (по умолчанию **я/владелец**), для обеих сторон добавить переключатель `Я / Соперник` или две аккуратные числовые колонки, не смешивая значения. Точность local и official подписана; открыть подробные фазы `Дебют / Миттельшпиль / Эндшпиль` в раскрываемой секции (не превращать верх карточки в таблицу на 30 строк). Нет данных ≠ 0. На старой текущей странице заменить строку `Белые: 45 оценено … точность Б/Ч: н/д …`.
- **График партии** под статистикой, широкий и **читабельный** (не тонкая полоса), реальный ход→оценка белых, источник/мат/неполный coverage, hover с ходом, значение, сторона, смена позиции. Без mock-data в runtime и без автоматического UCI. График не должен путать выражение «кто выиграл» с объективной позицией на конкретном ходу.
- **Низ панели:** ровно различимые действия `Открыть` (открывает сохранённую партию/разбор), `Экспорт PGN` (безопасный экспорт выбранной ревизии), `Анализ Stockfish` (**открывает конфигурацию/управление фоновым пакетом**, а не автоматически переводит в разбор либо тихо анализирует конкретную партию). При необходимости одиночного запуска — отдельно явно названная команда `Поставить эту партию в очередь`, не подменять семантику основной кнопки.
- Сохранить заметки к разным партиям по game_id/line_revision, сохранение с защитой от поздних worker replies, исходный PGN и ревизию, обратный переход, защиту от случайного перезаписывания выбранной линии. Все кнопки — реальные действия и точный текст, не декоративные кнопки.

## 4. «Фоновые операции» — эталон арт №3

**Верхний статус-баннер** ~70–80 px: «Сейчас: …» только **если реально** работает конкретный процесс (например, `Stockfish: анализ партии [без полного публичного ID], ход 23/84`), иначе `Сейчас активных задач нет` или `Приостановлено на время партии`. Показать точное название задания и безопасные кнопки `Пауза/Продолжить` для управляемой очереди и `Обновить` для read-only status. Запретить глобальной кнопке «Пауза» останавливать event stream Lichess с онлайн-ходами.

Ниже **4 горизонтальные карточки** максимально как на арте, каждой — реальное состояние, последняя попытка/последний **успех** и прогресс (если известен знаменатель), причина ожидания:

1. **Синхронизация партий Lichess:** число уже полученных партий, новых, статус полного/incremental импорта, дата последнего обращения и успешной синхронизации. «Все партии загружены» НЕ означает «вся аналитика получена». События одного аккаунта не относятся к другому.
2. **Готовая аналитика Lichess:** сколько **проверено** и сколько реально импортировано с scores/official accuracy, сколько **ожидает проверки**, когда следующая разрешённая проверка, 429/API ограничение/«на сайте анализ есть, через API ещё не подтверждён». Различать `нет анализа`, `не проверено`, `в ожидании`, `ошибка`. Не заказывать серверный анализ автоматически без явного разрешения/поддержки API. Партия, недавно вручную проанализированная на сайте, должна со временем переопрашиваться по корректной политике (не только однажды просканированные ID), без нарушения rate limit. Пример пользователя: 3308 партий, 75 проверено, 15 official accuracy — это **состояние очереди/покрытия**, не обоснование показывать пользователю «всё синхронизировано».
3. **Задачи Lichess:** последняя попытка, последний успех, количество сохранённых попыток, получено новых, текущая синхронизация. Нет данных — честно; нельзя путать попытки с количеством уникальных задач.
4. **Фоновый Stockfish:** в очереди/сделано/ошибки/осталось, текущая партия и прогресс внутри неё, параметры анализа (свёрнуто), реальная длительная очередь, pause/resume/cancel. **Любая активная онлайн-партия, включая AI, приостанавливает тяжёлые фоновые задачи**; после завершения безопасно возобновляет согласно явно включённой настройке. **Stockfish и готовая аналитика не одно и то же**. Для 3300+ партий обеспечить очередь с устойчивостью к перезапуску и ограничением ресурсов.

**Низ:** `Последние события` из коротких записей по-русски с датой/временем: что именно импортировано/запущено/отложено/ошиблось, без секретов и длинных JSON. Служебные `lichess_events · running`, 
`run_id`, `v3`, `source_slug`, сырые даты `2026-...+00:00` — только сворачиваемая диагностика. Progress bar и проценты рисуются **только когда известен общий объём**; если бесконечный/polling поток — честный индикатор текущего статуса, не выдуманные 98%.

## 5. Точность — не просто UI, а расчёт/источники/формулы

**Важный исходный факт по живому PR #44:** в `src/chess_coach/domain/accuracy.py` уже существует **детерминированный локальный** расчёт по методике Lichess с формульной версией `lichess-accuracy-a46b4e6d9d80a100-v2`: cp→Win%, точность хода, game accuracy с volatility-weighted и harmonic means, gate на полную текущую линию/глубину и checkmate. `lichess/game_review.py::load_game_review` уже возвращает `local_game_accuracy` и `local_accuracy_status`. **Не переписывать всё с нуля**: сперва добавить точную трассировку, где `LibraryPage.show_game_detail`, dashboard и GameReview GUI **выводят только official_accuracy**, игнорируя готовый local_game_accuracy. До исправления фазы/метрики проверить сохранённые assessment ряда партий с временной SQLite и правильность gate.

**Авторитетный источник:** Lichess public explainer <https://lichess.org/page/accuracy>, действующий исходник <https://github.com/lichess-org/lila/blob/master/modules/analyse/src/main/AccuracyPercent.scala>, Win% <https://github.com/lichess-org/scalachess/blob/master/core/src/main/scala/eval.scala>. В текущем `AccuracyPercent.scala`: per-move Win% change с exp и uncertainty bonus, game-level = **среднее volatility-weighted и гармонического** (скользящие окна), phase accuracy — по разделению game phases, не арифметическое среднее фаз. На GitHub может меняться версия: зафиксировать exact upstream commit/formula ID и лицензии, сделать golden vectors и отклонение ≤0.1 п.п. для сопоставимых тестовых games. **Никакого слепого копирования AGPL-кода без license review.** Локальный Stockfish не всегда соответствует серверному Stockfish по глубине/версии, поэтому даже методологически идентичные проценты могут различаться; значение назвать `Локальная точность (методика Lichess)`.

**Определение и приоритет:**
- Официальная `Lichess Accuracy` **только** если она реально подтверждена в корректной игре/аккаунте/источнике; если нет — пригодная локальная точность **по актуальному завершённому analysis run** (Stockfish/сохранённые server evals) с явным источником; иначе `Нет рассчитанной точности` + причина (нет позиций, partial, другой line revision, depth неизвестна и т.п.).
- Для сравнения `Lichess vs Stockfish`: показывать **две раздельные агрегированные выборки по своим game IDs**, их численность и provenance, с уточнением, что у одной игры возможны оба анализа. **Общий KPI** считать по **одной стороне игрока, одной партии, одному приоритетному источнику**; не усреднять два средних, не считать двойные игры и не смешивать оценку всех ходов в знаменатель партий.
- **Фазы:** после проверки существующей линии/формулы добавить дебют / миттельшпиль / эндшпиль для каждой подходящей партии с границами фаз по проверяемому `Division`/шахматной модели (не резать механически 1–10 / 11–30 без согласования), повторно применять game accuracy к фазовым ходам и корректному входному score; нет фазы/недостаточно данных — `—`. В материале phase segmentation и sanity по SAN/mate, совпадение sides black/white.
- **Классификация ходов** `хорошие/неточности/ошибки/зевки` остаётся в существующих `move_metrics`/`game_review`, отдельно от accuracy%. Указывать покрытие **ходов соответствующей стороны**, а не смешивать с количеством оценённых позиций; `0 ошибок` показывать лишь если ходов действительно оценено достаточно, иначе `—`.
- **Пересчёт старых партий:** версия формулы, source+engine/options, game_id/account scope, revision/hash, timestamps; bounded SQLite backfill в фоне с resume и дедупликацией, без порчи official fields, настоящих пользовательских PGN и UI-thread stalls.

## 6. Фоновая логика и массовый Stockfish: продуктовый контракт

- Настройки старта: `Анализ Stockfish` **открывает выбор набора/глубины или nodes/hash/CPU и параметров очереди**, а не просмотр партии. В настройках — `Проанализировать все партии без подходящего анализа`, опционально `Только выбранную`, `Повторить ошибки`, `Продолжить очередь`; явное согласие пользователя на долгую задачу и ресурсы (без самопроизвольного бесконечного процесса после установки).
- **Кандидаты на анализ:** завершённые, корректные, поддерживаемые standard-chess линии выбранного аккаунта/набора. Не анализировать повторно, если имеется **совместимый полный (по нужным ходам) актуальный run Lichess** или эквивалентный SF с требуемыми параметрами; если серверное покрытие частично — только недостающие безопасно (если схема поддерживает) либо согласованная полная local обработка, без ложного «Lichess уже всё оценил». Dedup by game_id+revision+source+engine+settings. Доступна оценка объёма очереди до старта и правильное изменение при поступлении новых партий.
- **Режим любой активной игры:** пауза тяжёлых локальных CPU/UCI и фонового backfill/массового HTTP; продолжение только после gameEnd/safety preflight и сохранения state. При игре **против человека** все инструменты analysis/hints скрыты/fail-closed по Fair Play; игровой event stream, часы, отправка ходов и safety-проверка имеют приоритет и **не приостанавливаются** общей кнопкой фонового UI. У AI тоже пауза ради ресурсов по желанию владельца; не путать с отдельным Fair Play требованием.
- Статусы persist на диск, reload после аварии, prevent duplicate queue, pause/resume/cancel, rate-limit 429, ambiguous server result, закрытие/перезапуск, смена аккаунта. Read-only прогресс из **реально хранимого state**. Прогресс CPU/queue worker не открывает автоматически страницу Review, не делает неожиданных переходов и не меняет выбранную партию. Существующий `show_batch_analysis` и `runner.enqueue_missing` переиспользовать и адаптировать под полный охват и долгоживущую очередь; не создавать параллельный engine manager.
- Lichess готовая аналитика: data-refresh pipeline должен обнаруживать **новый** completed site analysis, не считать «проверено 75 из 3308» окончательной синхронизацией; корректная очередь/TTL/recheck старых ID и update card/accuracy после импортов. Уважать официальные API возможности/права пользователя: если серверный Accuracy не доступен по API для отдельного случая — честная причина, а не выдумка. Сохранять старые оценочные run и не подменять источник.
