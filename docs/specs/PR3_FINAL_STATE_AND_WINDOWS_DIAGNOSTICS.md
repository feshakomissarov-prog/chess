## 2. P1 — потеря последнего хода при обратном порядке gameFinish/gameState

### Доказательство по коду

В `src/chess_coach/window.py::_lichess_event` событие `gameFinish` вызывает `session.finish(status,winner)` и сохраняет `session.moves`/PGN. В `_lichess_game_event` следующие `gameFull`/`gameState` просто игнорируются, если у `session.status` уже терминальное значение.

Но `GET /api/stream/event` (глобальные уведомления) и `GET /api/board/game/stream/{gameId}` (игровое состояние) — **разные потоки**, поэтому их события могут быть доставлены в UI в разном порядке.

Сценарий:
1. В Chess Coach есть подтверждённая линия до N-1 полухода.
2. На Lichess игра завершается последним ходом N.
3. Первым в GUI доставляется глобальное `gameFinish`; приложение сохраняет результат и старую линию N-1.
4. Потом доставляется `gameState` с финальным N-м ходом и status `mate`/другим итогом.
5. Текущий обработчик отбрасывает событие → PGN/SQLite **потенциально не содержат последнего хода**. UI при этом может неверно писать «Партия сохранена».

### Требуемое решение

- Состояние «результат партии» **терминальное для доступных действий**, но **не терминальное для дозагрузки подтверждённой серверной линии**.
- Разделить `gameFinish notification` и `final position reconciled`. Не допускать возврата в Active Game при позднем `status=started`.
- Разрешать безопасное уточнение финального списка ходов: принимать только последовательное подтверждённое продолжение текущей истории; при подозрительном расхождении выполнять безопасную сверку свежим серверным состоянием (без бурного polling и вне cooldown 429), а не молча оставлять PGN устаревшим.
- Финальная дата, реальные игроки, победитель, результат, длина PGN и SQLite должны быть согласованы. Пока финальная позиция не подтверждена, интерфейс сообщает «Результат получен, завершаем синхронизацию ходов», а не безусловное «Сохранено».
- Если финальные данные временно недоступны, сохранить частичные подтверждённые данные с явным флагом `final_sync_pending`/эквивалентом, восстановить после reconnect; не удалять партийные данные.
- Не создавать повторные global streams/игровые streams на каждый UI-refresh; уважать 429.

### Тесты (обязательные)

- T1: `gameFinish` **до** последнего `gameState` → финальный ход присутствует в `session.board`, `moves`, `PGN` и SQLite, победитель верный, кнопки игры недоступны.
- T2: `gameState(status=mate)` **до** `gameFinish` → те же данные, одинаковый результат.
- T3: дубли `gameFinish`, запоздавший старый `gameState` и `gameFull` не сокращают историю, не откатывают терминальный результат и не меняют открытую другую партию.
- T4: отсутствие финального game stream / timeout / 429 → корректное `final_sync_pending` и безопасное возобновление, без бесконечных повторов.
- T5: сохранённый PGN включает последний ход, который завершил матом; после повторного сохранения нет дублей, дата и игроки не меняются.
