## RF8-01 · P1: не терять показатели старой Lichess-аналитики при смене v2 → v3

**Подтверждение исходным кодом:**
- `src/chess_coach/lichess/move_metrics.py::METRIC_VERSION` повышен с `cc-move-metrics-v2` до `cc-move-metrics-v3`.
- `src/chess_coach/infrastructure/sqlite/analysis.py::_load_move_metrics` читает **только v3**, `analysis_coverage` (обновлённая SQLite VIEW) считает **только v3**, `src/chess_coach/lichess/statistics.py` использует **только v3** во всех joined показателях ошибок, CPL, фаз и локальной точности.
- Но `count_stale_analysis_metrics`, `materialize_stale_analysis_for_game`, `materialize_stale_analysis_metrics_batch` отбирают исключительно `ar.source='stockfish'`. Ранее сохранённые `lichess-pgn` / `lichess-json` runs со старой v2 после апгрейда **не попадают** в миграцию, даже при валидных CP/mate и текущей линии. `latest_analysis_detail` показывает ephemeral v3 для такого источника, но не записывает (pending=False); Progress/SQLite JOIN ничего не находит.
- Следствие: число анализированных партий по `position_assessments` может остаться прежним, а сводные ошибки/фазы/measured moves для старых источников Lichess стать нулём/н/д. Пользователь ранее жаловался именно на расхождения между 50–70 и ~1000 проанализированных партий.

**Исправить:** единая процедура пересчёта только **derived move_metrics/event projections** для всех пригодных **старых scored runs**, включая `stockfish`, `lichess-pgn` и `lichess-json` (сохраняя физический source, current line_revision/hash, account-scoped read models, сохранённые original `position_assessments`, classifications, PGN и официальный Lichess accuracy). Для Lichess per-move **локальный** показатель точности, считаемый только по Stockfish, не выдумывать: v3 для Lichess должен сохранять честные CP-loss и event coverage без `stockfish-local` маркировки. Review-only и старые revisions не добавлять в текущую статистику; v2 evidence остаётся аудитом. Реализовать одно versioned schema/capability contract, не размывать модель точности, no destructive migration.

**Обязательный тест:** создать настоящую old-format временную SQLite (PR до миграции v20): account A с 2 `lichess-pgn` v2, 2 `lichess-json` v2, 2 `stockfish` v2, включая mate, line/review-only, официальный accuracy-only, другой account B. Сверить до→после через `StatisticsService.summary`, `game_page`, `opening_statistics`, `historical_timeline`, `analysis_coverage.measured_moves`, `latest_analysis_detail`: источник, матовые и CP-классификации/фазы и coverage не теряются, `analysis_games` остаётся distinct scored, local accuracy только stockfish, v2 сохранён, v3 idempotent. Никаких UCI/HTTP/повреждения tokens.

## RF8-02 · P1: пакетный migration worker должен реально выполняться, а не существовать только в tests

**Подтверждение:** `AnalysisStoreMixin.materialize_stale_analysis_metrics_batch(limit=10,cancel_check=...)` реализован, однако **отсутствует его вызов в реальном GUI/application/service**: в `window.py` используется только `materialize_stale_analysis_for_game(game_id)` при открытии **деталей одной партии**, с максимум 5 runs. В `application/dashboard.py`, `lichess/statistics.py` и `ui/analytics_dialogs.py` нет orchestrator, который запускает и продолжает очередь остальных старых игр. `count_stale_analysis_metrics` в UI также не показывается. Следствие: на архиве из тысяч игр общий Progress после перехода на v3 остаётся пустым/неполным, пока владелец не откроет вручную каждую партию. Это не «фоновой пересчёт архива», заявленный в RF7 и необходимый для бизнес-статистики.

**Исправить:** подключить **существующий** bounded batch worker к одному app-owned background coordinator/SQLite writer policy; не создавать второй scheduler, engine service или автономный микросервис. Инициализация после готовности безопасных локальных ресурсов, idle/низкоприоритетный lane (не блокировать live game/ходы/синхронизацию), ограниченная партия и интервал с persisted version checkpoint (v3 existence). После обработки reschedule только при remaining>0, с разумным budget и без busy polling. Stop/cancel при закрытии, account switch или fairness revoke; offline режим допустим для локальных сохранённых данных, но скрытые метрики/матовые угрозы не должны раскрыться во время active/unknown human game. Важно: **сам пересчёт из сохранённых оценок не требует Lichess-сети, PAT или Stockfish**. При изменении версии уже сохранённые данные не портить.
  
Показывать ненавязчивый read-only прогресс `готово N/всего; осталось M` в существующих «Фоновых операциях» / «Прогрессе» (без глобальной перегруженной шапки). Никаких видимых заведомо ложных нулевых KPI: до окончания миграции явно «метрики обновляются: n/N», отдельно `analyzed games` на основе actual CP/mate. На обновлённом account/period/analysis-source cache invalidation и QT events должны приводить к отражению прогресса без пересоздания окна. Сохранить ручную lazy materialization отдельной партии (более высокий приоритет). Важно не направлять прогресс пользователя B на A-аккаунт, даже если миграция выполняется глобально.

**Тесты fake clock/temp DB:** 40–100 старых run, разных источников и аккаунтов; вызов actual MainWindow/UI controller после offline startup, получаем `remaining` уменьшается до 0 **без клика по 100 деталям**, 10/25 budget, cancel→reopen resume без duplicate, account switch/no cross-account counts, human active/safety deny masked UI, 429 Lichess не должен стирать local worker checkpoint, shutdown while in-flight, no UCI/HTTP. Протестировать thread safety на Windows with warnings-as-errors; waitUntil callback с bounded timeout вместо sleep-based SLA.

## RF8-03 · P1: Review выбирает scored run так же, как «Прогресс»

**Подтверждение:** `src/chess_coach/infrastructure/sqlite/analysis.py::latest_analysis_detail` делает `ORDER BY CASE WHEN ar.status='complete' THEN 0 ELSE 1 END, ar.finished_at DESC` **без приоритета наличия CP/mate**. Однако `StatisticsService.summary` в `lichess/statistics.py` уже выбирает ранжирование `ORDER BY CASE WHEN analysis_run_has_position_scores(ar) THEN 0 ELSE 1 END, CASE WHEN status='complete'...`. `lichess/game_review.py::load_game_review` вызывает именно `latest_analysis_detail`. В итоге `complete` с пустой технической оценкой перехватывает настоящий текущий `partial` Stockfish/Lichess scored run: в «Прогрессе» партия анализирована, а в «Разборе» показываются отсутствующие оценки и `н/д`. Старый RF3 предполагал обратное поведение, но в данном методе нет нужной сортировки.

**Исправить:** выбирать один usable scored current-line run с явным deterministic order, предпочтение `has usable current revision CP/mate` > `complete` > fresh finished_at > run_id; при отсутствии scored — сохранить честный `no scored run`/classification-only view, а не замаскировать пустоту. Для очень больших архивов применять indexed bounded query; не загружать все assessments в Python ради сортировки. Отдельные физические источники (Lichess-PGN/JSON vs Stockfish), accuracy provenance и selection tabs не смешивать; загружаемые графики и per-move facts только из одного выбранного run. Уважать user-выбор конкретного run, если workspace его явно поддерживает; текущий автоматический default должен совпасть с read-model Progress.

**Тест:** одна текущая партия с `complete` без CP/mate и `partial` с 2 CP/mate; другой game с двумя scored sources, empty newer complete, stale previous revision, review-only, accuracy-only, аккаунт A/B; `load_game_review().analysis.run_id` должен совпасть с приоритетным usable run из Statistics и иметь непустой graph/accuracy coverage; если ни одного scored — не выдумывать. Добавить Qt-интеграцию `Progress→Library→Review`, Fair Play masking before allow/revoke (никакой запуск Stockfish по клику).
