## 1. Принципы хранения и модель предметной области

### 1.1. Единственная база и несколько сущностей

**Не создавать вторую независимую БД игр!** Уже есть \`src/chess_coach/lichess/repository.py\`, \`games.sqlite3\`, \`games.game_id TEXT PRIMARY KEY\`, \`GameRepository\` и последовательный фоновой writer. **Сохранить таблицу \`games\` и все строки** через миграции, добавить нужные таблицы и индексы. Не заменять работающий онлайн-путь сохранения новым неиспытанным ORM.

Вводим уровни:
1. **Игра** (одна запись, game metadata/result/source).
2. **Подтверждённая версия линии** и **отдельные ходы по полуходам** (\`ply\`): UCI, SAN, clocks, FEN/хэш положения, события изменения линии. Можно хранить исходный \`games.moves\` и PGN ради совместимости, но новая нормализованная история синхронно соответствует им.
3. **Позиции** (\`game_id\`, \`line_revision\`, \`ply\`, полный FEN) как устойчивые точки привязки для будущих заметок, рисунков и движковой оценки; начальная позиция — \`ply=0\`. **Нельзя связывать только по FEN:** повторения и takeback возможны.
4. **Текстовые заметки** к игре/ходу/позиции (редактируемые и принадлежащие пользователю); позже аудио и \`annotation_events\` с таймлайном. Сначала schema + простой текстовый комментарий к позиции; микрофон пока не подключать.
5. **Запуски анализа** и **оценки отдельных позиций**, отдельные от игры и друг от друга; результаты разных движков/лимитов/версий не перезаписывать бездумно.
6. **Классификация ходов** (лучший/хороший/неточность/ошибка/грубая ошибка/неизвестно) с явной версией алгоритма, фазой, игроком и численными метриками.
7. **Импорт и прогресс** по каждому аккаунту/источнику: checkpoint, backfill, инкрементальные курсоры, ошибки, последний успешный импорт.
8. **Личная история шахматных задач** отдельными \`puzzles\`/\`puzzle_attempts\`/\`puzzle_sync_state\`, не в \`games\`.
9. **Агрегированная статистика** — вычисляемая из позиций, классификаций и партий. Допустим индексированный/материализованный кэш \`stats_cache\` с \`analysis_version\` и invalidation; **не вручную увеличиваемые вечные счётчики**.

### 1.2. Эталонная логическая схема

**Codex вправе адаптировать имена таблиц, но обязан сохранить ключи и инварианты:**

| Таблица | Идентификатор и назначение | Главные связи |
|---|---|---|
| \`games\` (существующая) | \`game_id\`; PGN/UCI, source, status, players, result, variant, timestamps, phase boundaries, revision, raw payload checksum | Корневая сущность |
| \`accounts\` | \`account_id\` Lichess / source; canonical username; без OAuth token | Один профиль может иметь много игр |
| \`account_games\` | \`(account_id, game_id)\`, цвет владельца, импорт/сыграна клиентом | Одна Lichess партия может принадлежать двум аккаунтам |
| \`game_moves\` | \`(game_id, line_revision, ply)\` → move UCI/SAN, mover, clock, elapsed, timestamps | FK \`games\`, диапазон \`ply=1..N\` |
| \`game_positions\` | \`(game_id, line_revision, ply)\`, FEN, позиционный uid/хэш | \`ply=0..N\`, FK \`games\` |
| \`game_notes\` | \`note_id\`, \`game_id\`, \`position_uid\` или \`line_revision+ply\`, text, author, created/updated | Несколько заметок к одной позиции |
| \`analysis_runs\` | \`run_id\`, game revision/hash, engine id/version, settings, status/progress, source \`lichess|stockfish\`, timestamps | Версионированный расчёт |
| \`position_evaluations\` | \`(run_id, ply)\` → white_cp или mate, WDL если доступно, depth/nodes, PV, source confidence | FK run/positions; \`ply=0\` допустим |
| \`move_assessments\` | \`(run_id, ply)\` → loss/metric, classification, phase, algorithm_version | Производная от соседних оценок |
| \`sync_jobs\`, \`sync_state\` | \`job_id\`, source, account, mode, since/until/before/checkpoint, status/error/count | Не повторять весь архив |
| \`puzzles\` | \`(source, puzzle_id)\`, FEN, lastMove, solution, difficulty, themes | Публичная задача |
| \`puzzle_attempts\` | стабильный \`attempt_uid\`, account, puzzle, attempted_at_ms, success, source | Все личные попытки, не только последняя |
| \`puzzle_sync_state\` | account, backfill cursor, newer cursor, последняя синхронизация | Отдельный курсор от \`games\` |
| \`stats_cache\` (опционально) | scope/filter/version/source_hash, payload, calculated_at | Восстанавливаемые агрегаты |

**Обязательные правила:** \`FOREIGN KEY\` ON; уникальные индексы; UTC/Unix-ms в одном формате; nullable значения, когда источник не знает; \`source\`, \`source_game_id\` с idempotent \`UPSERT\`; \`line_revision\` и \`game_revision/hash\` при takeback/re-import, не разрушать исторические привязки заметок; \`ON DELETE\` и жизненный цикл данных явно продумать. **Не менять \`games.game_id\` ради красивой схемы**: это совместимость с уже существующими записями. Для локальных игр допустим namespace/UUID без коллизий Lichess id; аккаунт не должен записывать данные другой учётки от своего имени.

**Согласованность:** \`games.moves\` (legacy), \`game_moves\`, \`game_positions\`, \`games.pgn\` должны меняться **в одной атомарной транзакции на одну подтверждённую ревизию**, а не сперва \`games\`, потом потерянные строки \`game_moves\` после крэша. При ещё не завершённом \`final_sync_pending\` не считать результат/линейку финальными. При takeback архивные старые мысли и оценки не уничтожать: предыдущая revision остаётся доступна, текущий анализ получает статус \`stale\` до пересчёта.

**Миграции:** версия \`PRAGMA user_version\`, backup, тест на реальном формате старой схемы через фикстуру, crash/rollback, повторный запуск, сохранение PGN, индексы/производительность. Тестовые файлы — только во временных каталогах. Если таблицы анализа/пазлов пока не нужны, можно добавлять их на своих этапах, **но общую схему, FK и миграционный план документировать до реализации P1**.

## 3. Блок P2 — полный архив Lichess и умная синхронизация

**Официальный API:** \`GET /api/games/user/{username}\`, \`Accept: application/x-ndjson\`. Есть \`since\`/\`until\` в **Unix milliseconds**, \`sort\`, \`max\`, \`finished\`, \`moves\`, \`clocks\`, \`evals\`, \`accuracy\`, \`opening\`, \`division\`, \`pgnInJson\`; некоторые поля могут отсутствовать. Спецификация: https://github.com/lichess-org/api/blob/master/doc/specs/tags/games/api-games-user-username.yaml

1. Первый **явно запрошенный** импорт всех завершённых партий конкретного аккаунта. Подтверждение аккаунта и числа/периода, если доступно; прогресс, остановка, отмена, возобновление.
2. NDJSON читать потоком в worker, память ограничена, запись батчами в транзакциях. **Checkpoint только после успешного COMMIT**. Начальная обратная хронология и старый backfill имеют отдельные курсоры; простое \`since=lastImported\` при незавершённом backfill недопустимо.
3. После завершённого backfill — incremental: запрос по новым датам с небольшим перекрытием, сравнение \`game_id\`/hash/lastMoveAt/result; старые игры не загружать пачкой заново. Поздно появившийся анализ старой партии — отдельное ручное обновление выбранной игры, без бесконечного полного сканирования.
4. Привязка аккаунтов, 429 и \`Retry-After\`/cooldown, ошибки/таймауты, reconnect. Не запускать массовый импорт просто при старте приложения. Не производить реальный сетевой импорт без разрешения владельца.
5. Активные партии \`/api/account/playing\` **уже есть в P0/PR #8**; не реализовывать повторно. Открытие активной игры не является запросом экспортного архива и не должно отправлять pending ход без авторитетного \`gameFull\`. Игры после завершения появляются в библиотеке без дублей.

**Тест P2:** fake NDJSON 0/1/500/10k, pause/resume и два прерывания на разном checkpoint, 429, malformed record, duplicate timestamps, повторный импорт = no duplicates/no full backfill, смена аккаунта, поздний PGN/analysis и полная идентичность UCI/SAN.

## 4. Блок P3 — Stockfish и анализ завершённых партий

**Главное:** показывать **развитие оценки всей партии** и оценивать **свои конкретные решения**. Никогда не анализировать активную собственную онлайн-партию против человека и не показывать оценку/совет во время её игры. Анализатор должен быть полностью отдельным от живой игровой сессии.

### 4.1. Источники

- Если Lichess отдал \`analysis\` и \`accuracy\`, импортировать как \`source=lichess\` и показать источник; отсутствие данных ≠ ноль.
- Если оценок нет, кнопка **«Анализировать Stockfish»** для **завершённой** игры, через \`python-chess.engine\`/UCI, путь к **проверенному** бинарнику и версия, время/depth/nodes, ограничение ресурсов. Фоновый worker с отменой и прогрессом, стабильное закрытие engine даже при исключении.
- Если движок отсутствует, показать инструкцию выбора/установки из проверенного источника, **не скачивать молча**. Статус/состав лицензий GPL, не объявлять распространяемый EXE готовым без аудита.
- Кэш \`(game_id, line_revision/hash, engine version, parameters)\`: открытие старой партии не запускает Stockfish заново; новая линия/takeback инвалидирует расчёт для старой линии, но не удаляет исторический run.

### 4.2. Принципы оценки

- **Единый POV:** оценка \`white_cp\` (+ выгодно белым), \`mate_white\` как отдельное поле; оценку на экране «с точки зрения меня» получать преобразованием, а не переписывать исходные значения.
- **Точки графика привязаны к ply**: до первого хода \`0\`, после первого \`1\`, после второго \`2\` и т. д. При клике на точку — та же позиция в библиотеке.
- Для каждой стороны результат хода = изменение оценки **в пользу/не в пользу игрока, сделавшего этот ход**, сравнение состояния до и после с одинаковым методом анализа/лимитом. Нельзя считать просто \`abs(eval_after - eval_before)\` потерей качества; хороший ход тоже может резко изменить оценку при появлении угроз.
- Mate-счёт **не конвертировать в фиктивные 100000 cp** для точности/среднего CPL. Отдельная шкала/отображение.
- **Accuracy:** официальный % Lichess только если реально пришёл; собственная метрика Chess Coach только с именем, версией, формулой, условиями и предупреждением, что это **не официальный процент Lichess**. Если формула не готова — «Точность недоступна», но график/потери/ошибки могут работать.
- «Неточность», «ошибка», «грубая ошибка» — **не исходный факт** при отсутствии внешней классификации: алгоритм и thresholds документированы, зависят от метрики/WDL/depth, status \`unknown\` при недостатке данных.
- **Дебют/миттельшпиль/эндшпиль:** использовать \`division.middle\`/\`division.end\` от Lichess, если сервер отдал; иначе явно документированный heuristics engine (например material/queen activity, last opening book ply), **не делить автоматически по ходу 10 и 30 без объяснения**. Фаза привязана к ply и version/source; неизвестная фаза = \`unknown\`. Сохранить интерфейс для будущего исправления методики.

### 4.3. Экран одной партии

- График оценки, навигация к выбранной позиции, индикатор глубины/источника.
- Для каждого хода: \`SAN\`, оценка до/после, изменение (с POV текущего игрока), классификация и фаза, лучший движковый вариант **только при разборе завершённой игры**.
- Статистика игры: количество неточностей/ошибок/зевков белых и чёрных; раздельно по фазам; скачки оценок (с заданным порогом и знаком); качество в сравнении с соперником. Показывать \`N evaluated of M plies\`, а не статистику как будто по всей партии, если половина оценок отсутствует.

## 5. Блок P4 — общая статистика / аналитическая витрина

Отдельный экран **«Статистика»** с выбором аккаунта, периода, игры/режима, стороны, контроля, дебюта, соперника, rating band и analysis source/version.

Обязательные показатели **с корректным знаменателем**:
- партий сыграно, выиграно/проиграно/ничьи, по контролю/цвету и периодам;
- rating trend, когда есть ratings и временные отметки; отсутствие рейтинга у AI/casual показывать как \`нет данных\`;
- количество подтверждённых ходов, обработанных движком ходов, coverage %, доля и **частота ошибок на 100 оценённых собственных ходов**;
- отдельно blunders/mistakes/inaccuracies в дебюте, миттельшпиле, эндшпиле, по дебютным ECO/названию, если они есть, и по контролю времени;
- \`evaluation_swing\`: число случаев резкого **падения оценки после собственного хода**, рост/падение оценки со стороны белых для графика; одинаковые единицы/источник/алгоритм и явный порог;
- ACPL или иной показатель качества **только по реально оценённым ходам**, с оговоркой о mate/partial coverage;
- доступная точность Lichess в отдельном столбце и возможная методика Chess Coach рядом, **никогда не усреднять разные источники как один показатель**.

**Реализация:** SQL aggregates/аналитический service поверх \`games + game_moves + assessments\`, без дублируемых «ручных итоговых счетчиков». При производительности 10k+ анализов — \`stats_cache\` с фильтром, algorithm version и explicit invalidate. Графики интерактивны, пользователь может открыть соответствующую игру/ошибочный ply. Отдельный отчёт о пропущенных данных и незавершённом анализе.

**Тест:** по фикстуре 3–10 партий вручную проверить числители/знаменатели, частичный анализ, разные engine versions, нулевые партии, mate/CP, разные аккаунты, переимпорт и invalidation после takeback.

## 6. Блок P5 — личные решённые задачи Lichess

Да, **официальный API позволяет выгрузить историю своих тренировочных задач**.

**Источники:**
- \`GET /api/puzzle/activity\`, OAuth \`puzzle:read\`, NDJSON, обратный порядок; параметры **\`max\`**, **\`before\`**, **\`since\`** (Unix milliseconds). Можно получить весь доступный архив, **постранично по \`before+max\`**. https://github.com/lichess-org/api/blob/master/doc/specs/tags/puzzles/api-puzzle-activity.yaml
- \`GET /api/puzzle/dashboard/{days}\`, OAuth \`puzzle:read\`, общая и тематическая статистика за период. https://github.com/lichess-org/api/blob/master/doc/specs/tags/puzzles/api-puzzle-dashboard-days.yaml
- \`GET /api/puzzle/{id}\` — данные отдельной задачи для повторного просмотра. https://github.com/lichess-org/api/blob/master/doc/specs/tags/puzzles/api-puzzle-id.yaml

**Результат активности** содержит \`date\` (millis), \`win\`, \`puzzle.id\`, \`fen\`, \`lastMove\`, \`rating\`, \`plays\`, \`solution[]\`, \`themes[]\`. **Не додумывать** время решения/количество неверных ходов, если API их не дал. Не путать рейтинг задачи с личным puzzle rating.

**Авторизация:** текущий OAuth \`board:play\` может **не содержать** \`puzzle:read\`. Запросить дополнительное разрешение через стандартный PKCE с явным действием пользователя, без паролей в приложении/логах; если отказал — шахматные онлайн-партии должны продолжать работать. Не перезаписывать работающий токен несовместимым без согласования безопасной модели scopes.

**БД:**
- \`puzzles\` хранит справочник puzzle id/FEN/solution/themes/difficulty;
- \`puzzle_attempts\` хранит **каждую попытку** \`(account_id, puzzle_id, attempt_date_ms)\` или устойчивый \`attempt_uid\`, \`win\`, metadata source. Одна задача может решаться много раз, не уникализировать только по \`puzzle_id\`;
- \`puzzle_sync_state\` хранит отдельный backfill/incremental cursor, 429, checkpoint, progress; список задач пользователя никогда не смешивается с архивом партий;
- по желанию \`puzzle_dashboard_snapshots\` фиксирует момент получения статистики (данные summary Lichess отдельно от пересчитанного локального итога).

**UI:** вкладка «Задачи» — своя история, количество решённых/ошибочных попыток, доля успеха, рейтинг сложности, темы/слабые категории, календарь активности. При выборе — позиция и решение для самостоятельного просмотра/повторной тренировки **офлайн**, не отправлять результат такой локальной тренировки как будто это решение на Lichess. Начать с истории и статистики; полноценный тренажёр — отдельный этап.

**Не требуется скачивать весь публичный банк задач Lichess** (он огромный и не является историей конкретного пользователя). Достаточно своей \`puzzle/activity\` + точечных \`/api/puzzle/{id}\`.

**Тест:** OAuth без puzzle:read и с разрешением; 0/10/10k историй; повторные решения одного puzzle id; \`before+max\` и возобновление; пересечение timestamps; ошибочный puzzle JSON; повторный импорт; ошибочные ответы/приватность; отсутствие изменений live Lichess.

## 7. Нефункциональные требования / ограничения

1. **Только локальный SQLite**, никаких платных серверов или облачной БД. Не передавать голос, партии и токены третьим лицам. Импорт — по команде пользователя.
2. **Безопасность данных:** миграции — backup и rollback, без потери legacy games; SQLite подключение/close/transaction и writer thread корректны. Каталог Windows AppData, не распространять DB/token в git.
3. **Qt:** долгая загрузка NDJSON, анализ Stockfish, перебор 10k игр и статистика не блокируют главный UI; cancel/pause, finite queue, progress, без переполнения памяти.
4. **HTTP 429:** единый cooldown, учёт \`Retry-After\`, без параллельных массовых запросов/автоматических повторах на каждый tick.
5. **Fair play:** если любая собственная игра против человека активна, Stockfish/дебютные оценки/подсказки не должны быть доступны через игровое окно или фоновые операции этого клиента; после завершения — можно. Никакого режима «скрытой подсказки».
6. **Существующий клиент** продолжает ходить/показывать часы/премув/стрелки/takeback, не испытывает лагов из-за импорта, не меняет UX без необходимости. Сохранить корреспонденцию и реальный time control.
7. **Тесты:** Windows Python 3.12 GitHub Actions; локальные pytest-qt offscreen; реальные OAuth/Lichess/массовый архив/движок не использовать в автотестах. Инъекция fake transport/engine. Тестировать Windows offscreen и отдельно живой GUI с разрешения владельца.
8. Не обходить Dr.Web, execution policy или защиту Windows; не скачивать исполняемый движок без согласия. Доработать warning \`actions/checkout@v4\`/\`setup-python@v5\` на современные проверенные версии в отдельном безопасном commit/подблоке.
9. Контроль лицензий \`python-chess\`, \`Stockfish\` GPL, SVG; подготовить THIRD_PARTY_NOTICES/документацию, **не делать инсталлятор** до решения условий распространения.
