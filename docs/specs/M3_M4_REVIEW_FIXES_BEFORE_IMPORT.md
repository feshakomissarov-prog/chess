## A. P0 — исправить Lichess game archive pagination (PR #10)

**Доказательство:** `src/chess_coach/lichess/api.py::stream_user_games` отправляет `before=...` при backfill. Но в **официальном** `GET /api/games/user/{username}` есть **`until` (Unix milliseconds)**, **`before` в этом endpoint НЕ существует**. См. https://github.com/lichess-org/api/blob/master/doc/specs/tags/games/api-games-user-username.yaml . Параметр `before` допустим в **puzzle/activity**, но не здесь. Текущий mock в `test_archive_sync_resumes_backfill...` намеренно реализует неправильный `before`, поэтому тесты проходят.

**Опасность:** сервер может игнорировать неизвестный фильтр → клиент повторно скачивает одну и ту же страницу 1000 игр, не продвигается по реальному архиву, расходует запросы, портит checkpoint/статистику и может упереться в 429.

**Сделать:**
1. Для game export заменить `before` на **`until`**, назвать аргумент `until_ms` или схожим, не путать с `puzzle/activity?before=...`. Проверить `sort=dateDesc` для backfill и `sort=dateAsc` для incremental, а также корректность timestamp относительно фильтра API. `since`/`until` в миллисекундах.
2. Явно запросить **`division=true`**: сейчас `import_archive_record` сохраняет `record['division']`, но клиент вообще не просит это поле, поэтому аналитические фазы обычно `unknown`.
3. Защититься от **same timestamp** на границе страницы: нельзя слепо `oldest-1` или `max_seen` с потерей записей на той же миллисекунде. Использовать overlapping inclusive window + idempotent upsert + набор обработанных id в граничном интервале/допустимое разбиение окон дат. Гарантировать прогресс, finite retry/no progress detection при ошибочных ответах.
4. Разделить **полный backfill cursor** и incremental cursor; не отмечать `backfill_complete=1`, пока действительно не достигнут конец периода/архива. **Не переимпортировать весь архив при повторном запуске**.
5. По возможности `finished=true, ongoing=false` явно и исходные `pgnInJson=true`, `evals=true`, `accuracy=true`, `opening=true`, `clocks=true` с сохранением отсутствующих как null.

**Тесты:** fake transport должен **отклонять любой неизвестный параметр** `before` для games endpoint, моделировать `until`, 2500+ записей, три страницы, дубли на одинаковом миллисекундном времени, отмену на странице 2/перезапуск, 429, empty page, период после первого backfill и повторный импорт без дублей. Проверить, что `division=true` реально присутствует в URL.

## B. P0 — исправить атомарность сохранения архива (PR #9/#10)

**Доказательство:** реальный `MainWindow` запускается из `__main__.py` с `asynchronous_storage=True`; `GameRepository.import_archive_record()` вызывает `self.save_snapshot(...)`, который при async лишь ставит задачу в `ThreadPoolExecutor` и **немедленно возвращает**. Следом в другой SQLite connection выполняются `UPDATE games`, `INSERT account_games` (FK `games`) и продвижение checkpoint. Для **новой** партии строка `games` может ещё не существовать → FK error; либо промежуточные метаданные теряются; при непредсказуемом порядке и ошибке writer checkpoint может уехать вперёд от сохранённой игры.

**Сделать:**
1. Импорт новой игры, нормализованных ходов/позиций, сырого PGN/оценок, account mapping и checkpoint — **в проверяемом порядке** с durable commit. Лучше отдельный метод атомарного archive upsert в Repository, выполняемый в одном writer queue/одной транзакции по записи + checkpoint. Не пытаться решить гонку `sleep(0.1)`; можно использовать ожидаемый Future в worker, но checkpoint только после успешного commit всех необходимых данных.
2. Любая ошибка `save_snapshot` / нормализации / FK / диск / SQLite busy: **не продвигать cursor и не показывать «Синхронизация завершена»**. Не повреждать существующий PGN, заметки, старые revisions.
3. Не пересоздавать `games.pgn` со срезанными оригинальными Lichess комментариями, часами и `[%eval]` при экспорте архивной игры. У нас уже есть `raw_pgn`; экспортировать полноценный оригинал либо документированно восстановить его. Отдельно хранить подлинный PGN и нормализованные UCI/SAN.
4. Уточнить поддержку `chess960` и не-standard variants. Текущий импорт **выбрасывает исключение** на unsupported variant (например Antichess/Crazyhouse), поэтому «полный архив ВСЕХ игр» может стопориться на одной партии. Разрешить сохранить metadata + оригинальный PGN с флагом unsupported/analysis-disabled, **не пропускать навсегда** и не выдавать ложную standard-позицию. Игровой клиент менять не требуется.
5. Account attribution: `games.color` задаётся последним импортировавшим аккаунтом, тогда как `account_games` не хранит color, что ломает статистику, если одна игра присутствует у двух подключённых Lichess-аккаунтов. Хранить owner-specific color/rating в `account_games` или корректном relation; не мутировать смысл старого `games` между аккаунтами.

**Тесты:** `GameRepository(async_writes=True)` + импорт **совершенно новой** игры без ожидания/подкрутки thread scheduling, медленный/падающий writer, проверка FK/account mapping/checkpoint, restart, исходный PGN с [%clk] и [%eval] не потерян, повторный импорт при заметках и анализе, импорт Chess960/unsupported variant без потери сырого PGN, две учётки одной партии.

## C. P0 — pagination новых попыток Puzzle Activity (PR #13)

**Доказательство:** Lichess `GET /api/puzzle/activity` по официальной спецификации **возвращает записи от новых к старым**; документация рекомендует `before` + `max` для страниц. `PuzzleActivitySync.run()` в incremental режиме запрашивает `since=...` и `max=1000`, затем обновляет `since=max_seen` и делает следующий запрос. При >1000 новых попыток получены только **самые новые 1000**, следующие вызовы не видят оставшиеся, что создаёт дыру в истории. Тест `test_puzzle_incremental_sync_pages_more_than_one_page` подменяет ответ **возрастающей** сортировкой, противоречит API.
Спецификация: https://github.com/lichess-org/api/blob/master/doc/specs/tags/puzzles/api-puzzle-activity.yaml .

**Сделать:** реализовать безопасную обработку descending stream: `since=last_success - overlap` как нижняя граница, `before` для последовательного обхода страниц **назад** до нижней границы; сохранять попытки и курсор атомарно, не терять записи с одинаковым date ms и повторные попытки одной задачи, не считать UID puzzle ID; обнаруживать no-progress/429. Обязательно **не поднимать общий incremental high-watermark до окончания всех нужных страниц**, иначе crash создаст дыру.

**Тест:** 2501 нового попытка при page_size=1000 с настоящей **descending** fake API, перезапуск на 2-й странице, одинаковые timestamp, отсутствие дублей, несколько попыток одного puzzle id и отсутствие пропусков.

## D. P1 — безопасность послепартийного Stockfish (PR #11/#13)

**Доказательство:** `MainWindow._start_game_analysis` передаёт `active_human_ids`, а `CompletedGameAnalyzer.analyze` запрещает только `game_id in active_human_game_ids` и статус анализируемой игры. Это позволяет запустить анализ **другой, законченной игры**, пока в этом же приложении идёт активная онлайн-партия с человеком. Это противоречит согласованному консервативному fair-play правилу проекта: **не запускать Stockfish в период любых своих активных онлайн-партий с людьми**.

**Сделать:**
1. На уровне UI **и engine service** блокировать старт любого локального Stockfish, если есть **хотя бы одна подтверждённо активная** человеческая Lichess партия текущего аккаунта (включая фоновую); при уже запущенном анализе и старте новой человеческой партии — отменить/остановить или запретить старт партии с объяснением, согласно безопасной политике. Если пользователь вне Chess Coach играет другую партию на Lichess, локальная карта сессий её не отражает — честно ограничить гарантию, не утверждать «все игры Lichess проверены».
2. Не включать Stockfish/explanations в live board и рядом с текущей позицией, никакого режима обхода.
3. Тест: законченная A + активная человеческая B → запуска engine **нет**, не просто запрет анализа B. После завершения B — возможен. AI партия отдельно по продуктовым правилам.

## E. P1 — кнопка подключения и 429 (PR #8/#13)

**Не ошибка:** при `python.exe -m chess_coach --offline` `MainWindow._disable_online_controls` **намеренно** отключает `connect_button` и все онлайн-действия, локальный GUI не читает OAuth. Если во время Codex была пометка «Офлайн-режим · Lichess отключён», неактивная кнопка **ожидаема**. Если статус «Подключено», кнопка также штатно неактивна, т.к. есть «Отключить».

**Настоящий UX риск:** `_lichess_status` включает Connect только на точных статусах `Не подключено`/`Ошибка подключения`, но при неудачном startup OAuth restore (HTTP 429) сервис выставляет `Ограничение Lichess (429)...`; connect остаётся disabled, даже когда cooldown истечёт, а повторного контролируемого restore может не быть. Обрабатывать 429 как временное состояние с понятным сроком/кнопкой «Повторить после паузы» после истечения лимита, либо корректное backoff восстановление без burst запросов/дублей потоков. **Не разрешать** ручной запрос в течение cooldown. Отдельные статусы «Офлайн», «Подключаемся», «Подключено», «Пауза 429», «Ошибка» и точные доступные действия. Тест 429-restore, expiration, retry one request, success, no duplicate event stream, не испортить OAuth токен.

## F. P1 — статистика и качество данных (PR #12/#13)

1. `StatisticsService.summary` считает **любую** игру без winner при неактивном статусе как **ничью** — aborted/unknownFinish могут попасть в draws. Классифицировать только подтверждённые draw statuses/PGN `1/2-1/2`; cancelled/aborted/unknown — отдельное `unknown/aborted`, не ухудшать W/D/L.
2. `StatisticsService.summary` использует `games.color`, что некорректно для двух разных импортирующих аккаунтов одного game id. Использовать owner-specific `account_games` и фильтрацию account. Показывать срез без выбранного аккаунта как смешанный/ограниченный, а не «моя общая точность» по разным пользователям.
3. `analysis_source` и `finished_at`: выбирать **один конкретный run_id** на игру/ревизию по стабильному ordering, а не JOIN только по `MAX(finished_at)`, во избежание дублирования при равных временных отметках. Mate, частичное покрытие, ACPL, zero games, смешанная official accuracy и Lichess eval без классификаций — честно показывать unknown/coverage.
4. Фазы opening/middlegame/endgame/unknown должны иметь **реальные границы** `division=true` и не становиться по умолчанию `middlegame` при одной известной границе. Отсутствие данных честно обозначать `unknown`.
5. **UI фильтры** представлены только как параметры backend, но не как пользовательские controls (Codex указал NOT IMPLEMENTED). Для приёмки MVP допустимо поставить их в отдельный backlog **с явной пометкой**, но не утверждать «полноценный интерактивный дашборд» без реализации. Минимальный экран вместо одного QMessageBox по возможности с game count/coverage/фазами и источником.
