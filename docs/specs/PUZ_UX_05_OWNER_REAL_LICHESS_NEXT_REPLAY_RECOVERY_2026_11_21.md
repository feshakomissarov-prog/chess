## 1. Инцидент и точная карта фактов

Скриншот 1: Home после PR #55 действительно содержит локальный архив 3327 партий, подтверждённую точность 82,8%, рейтинг задач 1917, графики партий и карточку «Следующая задача» с кнопкой **«Открыть повтор»**. Эти карточки теперь работают, **не переписывать их без причины**. Скриншот 2: владелец нажал на карточку Home; в тренировке показана **начальная шахматная расстановка** и «Ответ Lichess не содержит всех данных задачи»; первая операция не удалась, хотя «Повторить загрузку» иногда переводит к рабочей задаче. Скриншот 3: после решённой задачи отображаются зелёная плитка, сохранение в SQLite, но «Не удалось получить другую задачу для выбранной темы. Повторите загрузку или измените тему». Активная кнопка «Повторить загрузку» не приводит к следующей задаче, даже после нескольких нажатий; флажок автоперехода не спасает. Скриншоты 4–5: выделенный фиолетовый квадрат чекбокса **без видимой галочки**, и чисто решённая задача не переходит дальше. Пожелание: нажатие подсказки/показа ответа **сразу должно показывать результат без вопросов**.

### 1.1. Что подтверждено кодом на main

- **Home preview**: ui/pages/home.py, HomePage._open_puzzle_preview → window.py:3143–3144, show_puzzle_training(account_id, puzzle_id) → window.py:6070–6072, _request_local_training_puzzle(mode="replay") → cached row loop около 6773–6783. После json.loads без соответствующей защиты вызывается **normalize_api_puzzle(payload)**, ожидающий **game + puzzle + initialPly + solution**. У сохранённых/импортированных строк может быть только puzzle/fen/solution, либо устаревшая локальная форма; ошибка ValueError из одного кандидата прерывает весь worker. Эта цепочка **объясняет наблюдаемую надпись**, но точный формат конкретной личной записи неизвестен — Codex обязан подтвердить RED на репрезентативной изолированной fixture, не объявляя просмотренным личный архив.
- **Основной NEXT**: window.py:6455–6464 вызывает LichessClient.get_puzzle_batch(... **count=1**), ui/pages/puzzle_training.py:511–525 до трёх раз просит **тот же batch при дубликате** и затем показывает сообщение «Не удалось получить другую задачу...». Следующий клик снова запускает эту схему. Локальные результаты **НЕ POST-ятся на Lichess**: api.py:479–500 GET с OAuth **puzzle:read**, документация явно отмечает необходимость **puzzle:write для POST**. Поэтому серверный подбор «ещё не решённых на Lichess» не обязан знать о локальном решении Chess Coach; несколько GET могут вернуть одну задачу. Это **конкретный дефект стратегии NEXT**; не сводить решение к повышению retry count.
- **Реальный контракт Lichess:** [официальный GET batch](https://github.com/lichess-org/api/blob/master/doc/specs/tags/puzzles/api-puzzle-batch-angle.yaml) допускает **nb=1..50** и отвечает массивом **puzzles**, [структура batch](https://github.com/lichess-org/api/blob/master/doc/specs/schemas/PuzzleBatchSelect.yaml) содержит **PuzzleAndGame** с game+puzzle, [пример](https://github.com/lichess-org/api/blob/master/doc/specs/examples/puzzles-getMultiplePuzzlesAtOnce.json.yaml); POST batch имеет **отдельный scope puzzle:write**. Существующий клиент уже ограничивает count максимум **5**. **Использовать GET небольшим batch, не добавлять write scope, не публиковать попытки на Lichess.** «Новая» значит не показанная в Chess Coach текущему пользователю, а не обязательно новая для серверного счётчика.
- **Автопереход:** ui/pages/puzzle_training.py:_finish (около 1031–1035) вызывает таймер 1500 мс после чистого успеха; _auto_advance (1323–1328) запускает тот же _next; если тот получает дубликат, автопереход так же заканчивается тупиком. _auto_advance не повторно читает checkbox.isChecked() к моменту срабатывания; это обычное действие пользователя (выключил после решения).
- **Визуал чекбокса:** Qt screenshot владельца: проверяемое состояние выглядит как фиолетовый квадрат без ✓. Нельзя считать его доступным/понятным только потому, что isChecked() меняется.
- **Подсказки:** _hint (около 898–913) уже работает **без QMessageBox**. Окно подтверждения находится в _reveal (около 915–928), в кнопке **«Показать решение»**. Не создавать ложное «исправление» несуществующего диалога _hint: оставить мгновенную подсказку, **убрать подтверждение именно у показа решения**.
- **Риск обычных кликов по плиткам:** _record_first_failure делает красную плитку **до завершения** попытки; _open_session_result (1146–1150) сразу отправляет replay_requested для любого mark кроме нейтрального, а window._replay_puzzle_training (6078–6103) начинает загрузку повтора **без записи или подтверждения незавершённой текущей попытки**. Дополнительно source="lichess" в плитке новой задачи приводит в _request_local_training_puzzle к source_hint="lichess", где текущий код пропускает локально сохранённую попытку и cached replay, предпочитая imported Lichess activity, которой может не быть. Это **доказательные кодовые пути**, но требуют RED-тестов с реальным Qt click, а не обозначения «подтверждённо пользователь видит».
- **Другие видимые UX-пробелы:** set_message после ошибки следующего GET может стилизовать прежний успешный _terminal_verdict как error; _hint не обнуляет серию и не меняет плитку сразу, пока задача ещё не завершена; _navigate_review может показывать инструкцию «выберите фигуру» на завершённой доске. Не распространять на несвязанные системы.

**Цель PUZ-UX-05:** после входа с Home, десяти задач подряд, одного повтора, подсказок и ошибок пользователь **всегда получает либо следующую доступную задачу, либо ясное действие для восстановления**, без вечного круга «Повторить загрузку» и без подмены старой задачи «новой».

## 2. Утверждённая логика и UX, минимальные изменения внешности

### 2.1. Три разных намерения пользователя

**A. «Решать новые задачи»** — основной путь Home → Обучение → сразу одна **новая** тренировка по выбранному аккаунту/теме/сложности. С экрана Home пользователь должен иметь эту явную кнопку и не угадывать, что значит «Открыть повтор». **B. «Повторить сохранённую»** — вторичное, явно подписанное действие из карточки сохранённой задачи, её превью/плитки/истории; загрузка только указанного account+puzzle ID, без rating и без скрытого обращения за новой задачей. **C. «Следующая задача»** — из тренировки после решения/пропуска/показа решения; всегда пытается открыть другой допустимый ID, а не «Повторить».

В карточке Home сохранить существующий preview и стиль; основное действие назвать **«Решать новые задачи»**, вторичное при наличии сохранённой задачи — **«Повторить эту»** (можно компактной текстовой кнопкой). Оба должны открывать корректный экран. Если второе действие нельзя разместить без потери читаемости при 1120×640, оставить основную кнопку и открыть replay через ясный дополнительный link/контекстное действие; **не удалять доступность replay**.

Если запрошен именно replay и в старой локальной строке неполные данные, ошибка должна быть **«Не удалось открыть сохранённую задачу»** с понятным «Решать новые задачи» и «Назад на главную», а не «Ответ Lichess...» для локальной БД. Не показывать стандартную начальную шахматную позицию как реальную задачу при отсутствии загруженного puzzle: placeholder/disabled board + доступные CTA.

### 2.2. Совместимость локального формата Home/replay (PUZ05-01, P1)

Одна безопасная source-aware нормализация **для чтения**, без перезаписи/миграции личной базы:
- API full **game+puzzle** → normalize_api_puzzle; строгая проверка последнего подготовительного хода, допустимых FEN, solution.
- Исторические локальные/imported попытки с **fen+solution** и prep move → existing normalize_activity_puzzle, привязка аккаунта/ID/источника; у legacy схем может быть другая форма — инвентаризировать фактические варианты по репозиторию и synthetic fixture, а не гадать.
- Кэшированная строка с корректным full API JSON → рабочий replay. **Неподходящий один кандидат не должен рушить другие варианты**, особенно когда exact imported/local запись пригодна; пробовать безопасно и строго, с bounded per-row fallback. Никакого «угадывания» шахматной позиции без проверки легальности всей линии.
- При точном выбранном ID не подставлять другой сохранённый ID незаметно. Если нет безопасного воспроизведения — show actionable error и **основной NEW всегда работает независимо**.
- Replay уже решённого puzzle не изменяет local Chess Coach practice rating, session score, Lichess official rating и не создаёт второй rated attempt; существующие PGN/attempts остаются нетронутыми.

### 2.3. NEXT без циклического дубликата (PUZ05-02, PUZ04-03/04, P1)

**Обязательно:** не расширять OAuth до puzzle:write, не делать POST решения, не утверждать пользователю, будто Chess Coach меняет официальный рейтинг Lichess.

Использовать официальный **GET batch с nb до 5**; предпочесть **один** малый запрос на пользовательское намерение NEXT (можно один bounded refresh только при содержательной причине и с соблюдением 429/Retry-After). Из ответа **проверить каждый candidate** (shape, legal chess line, account/theme/difficulty), выбрать первый ID, **не равный текущему и уже показанному в Chess Coach для соответствующего аккаунта/темы/сложности**. Учесть и текущую попытку, и ранее показанные ID в сеансе, и доступную локальную committed историю после перезапуска. Не требовать перебрать полную базу и не грузить 50–100 задач ради одного NEXT.

Излишки валидных уникальных GET candidates можно держать в небольшой подготовленной очереди, привязанной к конкретному credential generation/account/theme/difficulty. При смене фильтра/аккаунта очередь сбрасывается. Попытка не исчезает без ACK, а повторный результат не попадает в новую rated попытку. Применять атомарный current-generation check на GUI; существующие Fair Play/token safety guards **не убирать**.

Если в batch только дубликаты/повреждённые элементы, не делать три **бессмысленных** идентичных запроса по count=1; показать **«Для этой темы сейчас нет другой задачи. Измените тему / Повторить»**. Повтор пользовательский — новый bounded GET; при 429 показать задержку Retry-After и блокировать spam; не зациклить фоновые prefetch и auto-next. Не подменять **новую Lichess** ранее сохранённой локальной головоломкой без явного переключения режима.

Проверить return path от QSignal до обновления GUI: у NEXT и auto-NEXT одинаковый result handling. Один ID не показывается под видом другого, а после серии допустимых результатов одно и то же сообщение не повторяется без причины. Написать локальный test transport, который возвращает **тот же ID в трёх последовательных ответах**, и transport, который возвращает batch вида [duplicate, malformed, new-valid]. Без запроса puzzle:write выбор новой задачи должен работать.

### 2.4. Автопереход и флажок (PUZ05-03/04, P1 UX)

**Контракт toggle:** состояние OFF — пустой чекбокс с контрастной рамкой. ON — **хорошо видимая галочка ✓ внутри фиолетового квадрата** + текст/доступное имя, а не просто залитый квадрат. Использовать кросс-DPI Qt-рисование/QStyle или надёжный локальный SVG/indicator icon без сторонних шрифтов/новых лицензий. Нажатие на квадрат **и на подпись** переключает; tooltip «Только после чистого решения без ошибок/подсказок; ~1,5 с». Пользователь должен понимать ON/OFF даже без цвета; проверить high-contrast/click, курсор и native 100/125/150% screenshots.

По умолчанию новый профиль OFF; уже сохранённый вариант из QSettings **не перезаписывать**. ON при CLEAN SUCCESS ставит единственный timer после видимого зелёного статуса не менее 1500 мс, затем вызывает **ту же рабочую NEXT-логику**. При выключении после решения до timeout таймер останавливается/сверяет isChecked и переход **не происходит**. При включении во время уже завершённого задания — **не надо** внезапно переключать старую задачу; настройка действует для последующих решений. Неверный ход (даже исправленный), подсказка, пропуск, reveal и replay — НЕ автопереходят. При timeout/повторах серверного ID показывается понятный статус и ручная кнопка; нельзя оставлять вечное «Загружаем…».

После ошибки NEXT не стирать/не окрашивать красным вердикт **предыдущего чистого решения**, не очищать его зелёную плитку, серию или сохранённый результат. Network error — **отдельная** строка статуса доставки.

### 2.5. Подсказка и «Показать решение» — без модального вопроса (PUZ05-05, P2 UX)

Кнопка **«Подсказка»**: первый клик — немедленная отметка фигуры/поля, второй клик — немедленная стрелка, **ни одного QMessageBox**. Кнопка **«Показать решение»**: **один клик — сразу** показать правильную линию и конечную позицию, без «Вы уверены?» и без блокирующего окна. Рядом/в tooltip заранее указать «Попытка будет отмечена как показ решения; не чистый результат», но не вводить дополнительную защиту-попап. Действие фиксируется ровно один раз в local outbox, без rating как clean, без автоперехода; доступна единственная NEXT. Просмотр уже открытой линии и повтор без рейтинга работают. **Подтверждение пропуска незавершённой задачи при другой пользовательской операции можно сохранить**, потому что это другое, потенциально разрушительное действие.

### 2.6. Лента результатов, клик и серия (PUZ05-06/07, P1/P2)

Кликабельны только **действительно завершённые и корректно адресуемые** результаты. Красная плитка, возникшая после **первого неправильного хода**, пока пользователь ещё пытается решить, **НЕ должна открывать replay**. У текущей нейтральной/незавершённой плитки cursor обычный, disabled/no handler. При клике на старую завершённую плитку **во время ещё активной новой задачи** — подтверждение «Прервать текущую задачу и открыть повтор?» (не для подсказок); если Yes — оформить пропуск, сохранить один attempt, затем безопасно открыть выбранный replay. Если No — не изменять активную доску/историю. Когда нет активной попытки, открывать replay непосредственно.

Источник записанной в Chess Coach головоломки **source="lichess"** не означает, что она уже есть в Lichess puzzle activity: искать **локальный cache/attempt** по account+ID, соблюдать source metadata и только затем imported history. Не путать отсутствующую серверную активность с локально сохранённым решением. Тестировать: (а) красная плитка после ошибки, до успешного завершения; (б) завершённая зелёная плитка в этом же сеансе, пока нет sync activity; (в) клик старой зелёной при следующей активной задаче; (г) account switch.

Серия CLEAN и плитки: первая ошибка сразу красная и серия 0; первая подсказка сразу жёлтая и серия 0 (без ожидания finish); clean зелёный, skip/reveal серый, после уже случившейся ошибки красный не становится зелёным. Пока идёт попытка, результат не дублируется. Rated attempt и stats после SQLite ACK, повтор unrated. В узком окне лента из **20** плиток 28px + spacing не должна обрезать доску/CTA; допустима компактная адаптация по ширине или ограниченная горизонтальная прокрутка с всегда видимой новейшей плиткой; **не городить большую редизайн-панель**.

### 2.7. Понятный экран при ошибке (PUZ05-08/09, P2)

Когда puzzle не загружен, показать нейтральный placeholder, текст причины, главный CTA: **«Загрузить задачу»** / **«Повторить загрузку»**, вторичные **«Вернуться на главную»** и **«Выбрать другую тему»**, если причина — отсутствие данных. Не выдавать начальную расстановку фигур за настоящую позицию задачи. При долгой загрузке status «Получаю задачу Lichess…» и видимый прогресс; ошибка не должна превращать успех предыдущей задачи в красный. При отсутствии puzzle:read — явное «Подключить задачи Lichess», без скрытого OAuth. При 429 — честный cooldown; при сети недоступна — «Повторить»; после восстановления работать без перезапуска.

В REVIEW после завершения задачи не писать «выберите фигуру» на readonly завершённой доске; подсказывать «Просмотр завершённой задачи · Следующая/Повторить». В READY после возврата колесом предлагать ход именно активной стороны и разрешать реальный ЛКМ. Оставить быстрое удаление пользовательских ПКМ-аннотаций при захвате фигуры; не ломать click-click, drag, hint arrows, scroll history или игровую доску.

## 5. Обязательный human-first acceptance journey (проверка того, что реально нажимают)

Проверить с НАСТОЯЩИМ Qt MainWindow и обычными mouseClick/mousePress/mouseMove/mouseRelease/wheel/клавиатурой, через реальные navigation buttons и worker callbacks. Fake backend допустим для воспроизводимости, но mock-only данные **не заменяют** верификацию реальной формы ответа GET. Обязательно открывать PNG и смотреть UI, а не только trace JSON.

**Journey A — главное меню/сохранённая задача:** Home имеет 3300+ synthetic archive, превью saved puzzle; клик «Решать новые» открывает FEN новой задачи, не initial board; «Повторить эту» по зафиксированному ID загружает историческую FEN и корректную последовательность. Три формы локального puzzle_json: полный API game+puzzle, устаревшая activity форма, повреждённая запись; повреждённая не роняет остальные кандидаты и не уничтожает исходный архив. При невозможном replay — понятная ошибка и рабочий NEW.

**Journey B — 10 заданий подряд:** 1) открыть NEW, сделать ПКМ-стрелку и выделение, взять фигуру ЛКМ — очистка; 2) колесом вернуть историю и продолжить; 3) решить две задачи чисто, увидеть зелёную ленту и серию 2; 4) первая неверная попытка — немедленно красная, затем правильный ход — остаётся красной; 5) нажать подсказку — первая отметка мгновенно, вторая стрелка мгновенно, без popup, жёлтая плитка и reset серии; 6) показать решение одним кликом без popup — серый/красный в зависимости от прежней ошибки; 7) повторить завершённую — без рейтинга и новой плитки; 8) использовать единственную NEXT после каждого завершения и убедиться в **10 разных puzzle ID**, без зависания или вечной ошибки на повторяющемся серверном ID.

**Journey C — специально повторяющийся backend:** fake transport GET возвращает три раза один ID, затем [тот же, валидный новый] внутри batch, затем только duplicate; приложение выбирает новый, не спамит endpoint, при отсутствии кандидата даёт понятный action, ручная retry и смена темы возвращают работоспособность. Проверка сетевых 401, 403, timeout, 429 с Retry-After: видимый статус без потери прежнего green outcome и без скрытого OAuth. Не менять account scope, не потерять попытку при close/leave.

**Journey D — автопереход:** включить галочку → видна ✓; clean-success → 1,5 с видимый verdict → **фактически другой ID**; выключить уже после clean до таймера → не переходит; включить снова во время завершённой задачи → неожиданный auto-next не запускается. После неверной попытки/подсказки/показа решения/повтора → auto-next нет. Профиль B сохраняет свой чекбокс и не наследует A.

**Journey E — плитки и история:** клик красной в текущей ещё не завершённой попытке не открывает replay; клик завершённой старой плитки во время другой активной задачи требует явного подтверждения прерывания/сохранения пропуска; уже завершённая плитка открывает сохранённый локальный replay, даже если Lichess activity ещё пустая. Просмотр ходов и возврат — доска интерактивна только если puzzle READY; после завершения есть понятный статус и NEXT.

**Journey F — закрытие / Home:** после длинной серии обычное окно закрывается с clean runtime shutdown без false-failed test; личные данные не тронуты; Home при 1672×941 без непреднамеренной внутренней прокрутки трёх recent cards, 100/125/150% DPI корректны. Повторный запуск не сбрасывает сохранённую историю и не показывает её как «новую» задачу.

**Live-public boundary:** в тематическом L2 помимо fake GET выполнить разрешённый **read-only публичный GET /api/puzzle/{id}** для заранее известного ID без токена (официальная [схема](https://github.com/lichess-org/api/blob/master/doc/specs/tags/puzzles/api-puzzle-id.yaml)) и пропустить raw JSON через настоящий normalize_api_puzzle; отдельно выполнить GET batch в пределах документированного доступа, **только если можно без личного OAuth/настоящего токена**. Если GitHub network не позволяет — честный **BLOCKED public HTTP**, не выдавать за live proof; тестировать exact documented JSON example из upstream и оставить реальный авторизованный GET владельцу. **Никаких POST puzzle results**, кроме явного нового согласованного продукта в будущем. В trace обозначить actual HTTP vs fixture.

**Владелец лично проверяет:** 10 последовательных задач с собственным разрешением puzzle:read и фактической историей, включая автопереход, Home replay, отрисовку галочки, пояснения и отсутствие вопросов в подсказках. Никакой CI не объявлять доказательством личной авторизованной проверки. До его подтверждения **Draft PR, no merge**; если владелец впоследствии явно распорядится иначе — зафиксировать исключение.
