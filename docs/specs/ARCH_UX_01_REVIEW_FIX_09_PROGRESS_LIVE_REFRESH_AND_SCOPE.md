## RF9-01 — P1: открытый экран «Прогресс» обязан обновлять показатели по мере materialization

**Доказательство по текущему коду:**
- `MainWindow._start_legacy_metrics_batch()` **до** создания фонового worker вызывает `statistics_page._schedule_refresh()`. Это однократный запуск query по старым v2→v3 данным.
- `MainWindow._legacy_metrics_batch_finished()` после успешного `materialize_stale_analysis_metrics_batch` обновляет только `statistics_page.set_metric_migration_status(text)`. Он **не** вызывает `_schedule_refresh()` для открытой Progress-страницы. `_refresh_home_dashboard()` есть только при активной Главной, а `_refresh_background_operations_page()` только для инспектора фоновых операций.
- `StatisticsDialog._refresh_timer` single-shot (250ms); `_query_finished` повторяет запрос только при `_pending_refresh`, но мигратор не выставляет этот флаг. Фоновая обработка 43+ старых runs занимает много пакетов, поэтому исходная выборка может отработать с incomplete/NULL-derived метриками и **остаться такой до ручного переключения фильтра/перехода из вкладки**. Тест `test_application_resumes_bounded_v2_materialization_in_background_and_masks_scope` открывает «Прогресс» **после** завершения 43/43, так что эту проблему не покрывает.

**Требование:** после **каждого результативного батча**, а лучше с разумной 300–1000ms coalescing/по завершению текущей SQL-транзакции, инициировать **реальное обновление активного** Progress read model (summary, phases, historical/openings и coverage) через существующий `StatisticsDialog._schedule_refresh()`/app-owned event, без перерождения страницы, сброса его фильтров/аккаунта/scroll/active tab/выбранной игры. Не запускать тяжёлый query на каждый row, если батчи идут подряд; отсутствие batch progress, cancellation или error не выдают ложный 100%. Выбор по source/fair-play продолжается отдельно. Не создавать второй Qt worker manager/SQL connection global.

**Тест:** synthetic old-format v2 SQLite: 35–60 scored runs всех трёх источников, аккаунт A с `analysis_source='lichess'`, открыть Progress **до** запуска materializer; сделать barrier/delayed batch, убедиться, что первоначальные derived stats `н/д`/partially populated. Разблокировать batch; без ручного изменения фильтра/навигации дождаться внутри **того же** Progress widget, что `assessed_own_moves`/coverage и разрез по фазам соответствуют persisted v3, и label n/N актуален. Проверить full/partial sources, coalescing while query worker running, отсутствуют `PytestUnhandledThreadExceptionWarning`, QApplication remains responsive. Не принимать тест, который проверяет только `label 43/43` и table SQL.

## RF9-02 — P1: у миграционных счётчиков ровно тот аккаунт, что выбран в «Прогрессе»

**Доказательство:**
- `MainWindow._legacy_metrics_account_scope()` всегда читает `self.dashboard_account.currentData()` (это переключатель *Главной*), даже если пользователь сейчас находится в `EmbeddedStatisticsPage` и выбирает **другой** `StatisticsDialog.account.currentData()`.
- Worker/Background Operations возвращает `analysis_metrics_migration_status(account_id=scope)` для Home scope, а `statistics_page.set_metric_migration_status` отображает эти `done/total` прямо в Progress **без коррекции по текущему Progress filter**. Пример: Главная выбрана A с 5 сохранёнными run, в «Прогрессе» выбираем B с 15: показывается **5/5 как будто для B**, хотя контент карточек относится к B.
- `_dashboard_filter_changed()` делает cancel+schedule, но если `_legacy_metrics_complete_revision == game_repository.statistics_revision`, `_schedule_legacy_metrics_batch()` **сразу возвращает**, не обновляя `_legacy_metrics_text`; после переключения Home A→B текст Progress тоже может остаться «A: 5/5».
- В текущем test RF8 есть repository-level assert scoped counts для A/B, но **нет Qt test двух несовпадающих фильтров Home/Progress**. Это не предположение о SQL — это несогласованный UI scope.

**Требование:** migration **engine batch может оставаться глобальным** (обрабатывает все eligible v2, нет ненужных повторных миграций на смене вкладки), но статусы на каждом экране должны строиться по **собственному текущему** account scope: Home/Background Operations — выбранный там profile или подписанный «Все локальные партии»; Progress — `StatisticsDialog.account.currentData()` (включая «Все аккаунты» явным текстом). При переключении фильтра сразу invalidate отображённый старый текст (нейтральное состояние), запустить async bounded count для нового scope с generation guard, обновить label и data snapshot; filter change не должен отменять всю глобальную DB миграцию без надобности. После окончания глобальной миграции повторные выбора аккаунта всё равно корректно показывают `A: n/N`, `B: m/M`; кеш revision shortcut не должен запрещать пересчёт **display** для нового account.

**Тест:** A=5 scored saved games, B=15, общий мигратор завершён, `dashboard_account=A`, `StatisticsDialog.account=B`, toggle B→A→Все при открытом Progress. После каждой смены видимые counts/tooltip/screen reader получают ровно `15/15`, `5/5`, `20/20` (с явным account scope), без отражения другого профиля; late query from previous scope discarded. Затем заново создать queued B rows, продолжить batch, test updated counts for B while Home A. Fail-closed: при revocation не раскрывать ни двигательную статистику, ни per-account derived coverage в UI.
