## 0. Состояние и цель

Владелец **вручную проверил текущую stacked-версию в `--offline`**, все семь сценариев GUI отметил PASS: запуск, локальная доска, исчезновение стрелок после хода, undo/premove, навигация, библиотека/статистика, настройки/закрытие. **Найден реальный UX-дефект:** после первого хода нельзя обычной мышью сделать ход чёрными в «Локальной доске»; BoardView считает ход оппонента временем для premove игрока за белых. В уже готовой цепочке PR #8–#17 **есть**, но в основном пока проверено моками:
- SQLite `games.sqlite3`, миграции, normalized moves/positions/notes;

- `StatisticsService`, пока UI **один QMessageBox со сводкой**, без полноценной панели фильтров;
- puzzle OAuth/activity и локальная статистика.
**Нельзя реализовать эти компоненты второй раз:** задача — сделать безопасным первое настоящее использование, улучшить нужный UX и провести проверяемую приёмку.

**Цель блока:** пользователь может открыть нормальное Chess Coach, подключить Lichess по явному нажатию, пробно импортировать 5–10 завершённых партий, открыть их из локальной SQLite, выбрать официальный Stockfish UCI и после завершения игры получить график и первые честные показатели; затем по отдельному осознанному действию импортировать весь архив и получать инкрементальные обновления. На локальной доске можно свободно двигать обе стороны.

## A. Локальная доска — свободная игра за обе стороны (обязательная UX-правка)

### Проблема

`GameController.apply_move_intent` принимает легальный ход любой стороны. Но `BoardView._is_premove_turn()` при `board.turn != _premove_color` перехватывает мышь как попытку сделать premove за выбранную сторону. При `player_color=white` после 1.e4 чёрную фигуру нельзя двигать обычным click-click или drag.

### Требование

Ввести **два явно различимых режима локальной доски**:
1. **«Свободная доска (за обе стороны)» — по умолчанию** для обычной локальной партии. Пользователь последовательно делает законные ходы белыми и чёрными мышью. Никаких premoves, потому что нет удалённого оппонента; не блокировать чёрные фигуры. Сохранять FEN/историю/undo/стрелки, превращения пешек, рокировку и взятие на проходе.
2. **«Тренировка предходов (мой цвет)»** — существующая симуляция игры за один цвет: разрешить premove за своего игрока на чужом ходе и кнопку тестового хода соперника. Сохранить механизм и тесты, **но не путать его со свободной доской**.

UX: выбор режима при старте локальной партии либо небольшой переключатель в её интерфейсе с понятной подписью. При переключении режима **не обнулять незаметно** уже сыгранную линию; сбрасывать queued premove с явной индикацией. В свободном режиме скрыть/выключить «ПРОВЕРКА ПРЕДХОДОВ», выводить нормальную подпись «Сейчас ход белых/чёрных», убедиться, что нет неверной подсказки «Вы играете белыми». Текущие настройки цвета игрока использовать только в режиме тренировки или отображения, **не как ограничение свободной доски**. Стандартная доска в live Lichess по-прежнему управляется сервером: **настоящий premove в онлайне не сломать**.

**Проверки:** click-click 1.e4 e5 2.Nf3 Nc6, drag для обеих сторон, undo нескольких полуходов, стрелки исчезают после каждого подтверждённого локального хода, поворот доски, история, возврат к позиции; тестовый premove за белых при ходе чёрных остаётся рабочим. Offline Qt test должен получать реальные события BoardView, а не вызывать только `GameController`.

## B. Понятные режимы запуска и безопасное подключение Lichess

- `--offline` оставить **изолированным диагностическим режимом**, без чтения OAuth, live network, пользовательских SQLite и QSettings. Прямо в главном окне — «Офлайн-проверка: реальная библиотека и Lichess недоступны». Кнопка подключения отключена **по определению**. При попытке пользователя открыть реальную библиотеку дать подсказку, как перейти в обычный режим; **не переключать приложение в онлайн тихо**.
- **Обычный режим** `python.exe -m chess_coach` читает постоянную SQLite из пользовательского AppData и может подключаться к Lichess; в нём доступны импорт, активные игры и аккаунт. Для первого live pilot добавить/поддержать `--manual-connect` (или эквивалент): открыть **постоянную пользовательскую библиотеку**, но не делать автоматического OAuth restore, сетевых запросов или восстановления pending intents до явного «Подключить Lichess». Это **не** `--offline`: credential store используется только по явному действию.
- UI-индикация состояний: «Офлайн-проверка», «Не подключено», «Подключение», «Подключено: username», «429 — пауза до ...», «Ошибка + повторить». В начале проверять аккаунт после явной авторизации; не запускать старую pending move/takeback/abort только из-за открытия приложения, сессия по gameFull/server state.
- Учитывать Windows Credential Manager; не печатать/логировать токены, OAuth scopes, пользовательские PGN и приватные пути. Зачистить старые тестовые строки, не менять Dr.Web и `Set-ExecutionPolicy`.
- Нормальный ярлык должен запускать обычный интерфейс без PowerShell, но **запуск через ярлык может восстановить Lichess**. Для тестов пока пользоваться `python.exe` и `--manual-connect` или `--offline`. Не запускать старый ярлык по собственной инициативе.
- Добавить читаемую диагностику «какая SQLite открыта» без раскрытия произвольных приватных файлов (например «Изолированная временная» / «Пользовательская») и путь к данным по явной кнопке. Информация о версии Python/Qt, режиме и статусе для багрепорта.

**Тесты:** фейковый CredentialStore/transport: `--offline` никогда не читает токены и не пишет основную БД, `--manual-connect` использует постоянный профиль но без запросов до нажатия кнопки; после подключение одно, не два потока; 429 и восстановление; запуск с pending intent ничего не отправляет самопроизвольно. CI без live Lichess.

## C. База и подготовка первого реального импорта

1. Использовать только существующую `games.sqlite3` и `GameRepository`, сохранить `games`, normalized history и заметки. Программа должна **не разрушать** старые данные при миграции; backup через SQLite backup API перед миграцией, `PRAGMA integrity_check` на копии, `user_version`, тест восстановления из `.bak` без отключения защиты.
2. На экране аккаунта/архива показать **где будут храниться партии**, число локальных партий, username, время последней успешной синхронизации, стадия backfill, новые/обновлённые/уже имевшиеся, ошибки и доступность продолжения после отмены.
3. **Добавить отдельный безопасный «Пробный импорт последних 5–10 завершённых партий».** Запрос Lichess `GET /api/games/user/{username}`, NDJSON, `max=5` или 10, `finished=true,ongoing=false` и нужные поля. Импортить в ту же локальную БД с атомарным upsert, возможностью открыть PGN, **но НЕ устанавливать `backfill_complete=1` и НЕ перескакивать курсор полного архива**; в журнале явное поле/маркер `pilot_mode` или отдельный журнал. Если эти же игры потом придут при полном backfill, UPSERT без дублей, пользовательские заметки и локальный анализ не затереть.
4. Различать **счётчик полученных записей** и **число новых игр**, показать обе цифры. Повторный пробный импорт 5 игр должен показать 5 просмотренных/0 новых (если данные не изменились). Не вводить случайные лишние live запросы.
5. Кнопка **«Полная первичная выгрузка»** — только после явного подтверждения владельца в приложении. Прогресс, ограничение ресурса/очереди и API rate limit, отмена с durable checkpoint, возобновление, no-progress guard, 429 pause. Кнопка «Обновить новые игры» после завершения backfill — incremental без повторной полной выгрузки. Старые correspondence/поздний analysis — targeted refresh, не обещать бесконечную полноту без сканирования.
6. Обработка ошибок: недействующий токен, пустой архив, aborted/unsupported variant, malformed PGN, sqlite busy, другое имя аккаунта, долгий backfill, повторная игра. Не скрывать `last_error`; не считать «успешно», если worker был отменён/данные не записаны.
7. **Массовый реальный импорт Codex НЕ запускает.** Реальный пилот только в ручных действиях владельца после согласия и backup. Тесты — fake Lichess transport + временная настоящая SQLite.

**Tests:** 0/5/10 тестовых партий пилота, restart/duplicate при переходе в backfill, 500/2501 страниц (большие — fake transport), interruption/crash before COMMIT, one account/two accounts, оригинальный PGN roundtrip, unauthorized/429. Новая интеграция не должна сбрасывать прогресс старых PR #9–#17.

## D. Stockfish — первая реальная оценка завершённых партий

**Код `CompletedGameAnalyzer` и `EvaluationGraph` уже есть. Не переписывать движковый слой с нуля.**

- Экран/настройка **«Движок анализа»**: «Не выбран» или имя/версия UCI, «Указать путь к Stockfish.exe», «Проверить движок» с ограниченным timeout, Nodes/Depth или время на позицию (понятный пресет «Быстро / Обычный / Детально»), Threads/Hash в разумных пределах. Хранить пользовательский путь в QSettings, не в git, не открывать подозрительный файл автоматически.
- Страница с официальным источником: https://stockfishchess.org/download/ или https://github.com/official-stockfish/Stockfish/releases . **Не скачивать и не запускать бинарник без явного согласия**. Для проверки использовать только проверенную пользователем установку. Указать обязательства GPL v3 перед распространением (Stockfish отдельно, лицензия + ссылка на соответствующий исходный код).
- Старт анализа **явно после окончания игры**, в background worker с прогрессом/отменой и кэшем по движку/параметрам/ревизии. В любой активной игре с человеком (включая фоновую сессию аккаунта) engine не запускать; при старте такой игры уже запущенный анализ отменить. Никаких engine evaluation/candidate moves в live board против человека.
- Для графика: `ply=0..N`, + выгодно белым, отдельно mate score, видимое количество оценённых из всех, источник `Lichess` или локальный Stockfish, клик → нужная сохранённая позиция. Не выдавать `accuracy`, которой Lichess не прислал. Если собственная точность не реализована — «нет данных», не рассчитывать подставной 80%.
- После первого ручного пилота на **одной завершённой** партии: validate UCI path and version, bounded analysis, callback cancellation, reopen from cached results **без нового запуска движка**. Не тестировать live engine автоматически.
- Во время P3 не делать автоматического анализа всех импортированных игр и не загружать CPU без явной команды.

## E. Минимальный рабочий экран «Статистика / Анализ» — без полного редизайна

Сейчас `StatisticsService` содержит фильтры и метрики, но GUI показывает главным образом `QMessageBox`; это мало полезно, и верхние вкладки «Анализ» и «Тренировки» отключены. Цель — **простая функциональная аналитическая панель**, а не глобальный дизайн-проект.

- Отдельный экран «Статистика»: селектор аккаунта (или «Все локальные», с предупреждением о смешении данных), период, тип контроля, цвет, результат, дебют/ECO если известен, соперник, анализирован/не анализирован, источник Stockfish/Lichess и **кнопка «Сбросить фильтры»**. Показать W/D/L + unknown/aborted отдельно.
- Сводка: количество партий, ошибки/неточности/зевки (с явной версией алгоритма), на 100 **оценённых собственных ходов** и coverage, средняя потеря CP без матовых псевдо-оценок, колебания оценки и график тренда, распределение по дебюту/миттельшпилю/эндшпилю. Если анализировано только 1 из 200 игр — показать «1/200», а не цифру как будто для всех 200.
- Экран одной партии: дата, участники, цвет, результат, источник, PGN, clickable `EvaluationGraph`, ключевые ошибки и список ходов с переходом в позицию, заметки к ходу. После анализа кнопка «Показать сохранённый результат» — без повторного исполнения Stockfish.
- Содержимое **не пересчитывать синхронно 10k партий при каждом клике**; использовать индексированные SQLite queries, кэш с invalidate при новом analysis/upsert; не блокировать Qt на секунды. Не включать голос и финальный UI-дизайн в эту задачу.
- При отсутствии данных/смешанном аккаунте — честно «нет данных» и объяснение; диалог пустой библиотеки не открывается сам при запуске.
- Фильтры и графики должны **реально работать через UI**, а не оставаться только параметрами `StatisticsService`.

**Tests:** точные fixture числители/знаменатели, 2 аккаунта, aborted/unknown, incomplete eval, mate, изменения движка, кэш; Qt selections/filter navigation; 1000+ игр без фризов. Модульность: UI не вызывает напрямую множество SQL sync запросов на каждый paint.

## F. Личная история задач Lichess — осторожный пилот

Схема `puzzle:read`, `/api/puzzle/activity`, `/api/puzzle/dashboard/{days}` и `puzzle_attempts` в stack уже реализованы. Не переписывать. После успешной проверки архивного импорта:
- Явный отдельный OAuth permission `puzzle:read`, **не заменять** Board token;
- пробная загрузка максимум 5–10 попыток, checkpoint не объявляет полную историю загруженной; отдельное подтверждение на полный backfill;
- локальный экран истории задач и простая статистика по темам/win rate/сложности, если API действительно возвращает поля; один puzzle может иметь несколько attempts;
- повторный пилот без дублей и без утечки токенов/игрового прогресса; никто не делает запросы автоматически при `--offline` или без подтверждения.

**При нехватке времени:** этот блок после D/E и пометить как отдельный reviewable подэтап; не задерживать приёмку базы/Stockfish из-за несущественных косметических задач.

## G. Windows, диагностика аварий, строгая приёмка и Git-границы

- Локальный результат владельца: **7 PASS по `--offline`**, кроме отсутствующего режима ходов за две стороны. Добавить регрессии свободной доски. Не требовать от владельца повторять все тесты из-за каждой мелкой правки.

В CI выполнить Windows Python 3.12 с pytest-qt offscreen, компиляцию и fake offline/init; добавить защищённый ручной smoke и список фактических версий DLL, записывать native error при повторении.

- Перед реальной синхронизацией пользовательской SQLite — согласованный backup и `PRAGMA integrity_check`; **не удалять старые PGN или настоящую базу для теста**. Изменения на копии/fixtures.
- В каждом PR: точное SHA, какие блоки A–G сделаны, перечень тестов, исходная проблема→регрессионный тест→результат, Windows CI PASS/FAIL, интерактивный GUI PASS/FAIL/NOT RUN, Lichess real sync/Stockfish real E2E NOT RUN до разрешения; не заявлять «проверено на данных владельца», если это фейки.

- **Git:** можно сделать один большой Codex job со стадиями A–G внутри; публиковать reviewable PR по логическим блокам поверх последнего PR #17 или обновлять stack с прозрачной историей. **Ничего не мержить, не force push и не менять base PR самовольно.** Перед дальнейшим merge потребуется сохранить актуальные README/PROJECT_STATUS main и составить безопасный порядок #8→...→#17→новые ветки.

### Что намеренно НЕ входит

Полный визуальный редизайн, микрофон/аннотационный timeline, OpenAI API, персональный ИИ-тренер, подсказки движка во время live human game, установщик/публичное распространение. Редизайн обсудить после получения первой реальной аналитики: тогда будет ясно, какие экраны и сценарии действительно нужны.

### Критерий готовности блока

**Пользователь:** может свободно делать ход белыми и чёрными; понимает разницу между офлайн и нормальным режимом; безопасно пробно импортирует собственные 5–10 завершённых партий и видит их после рестарта; может анализировать одну завершённую партию настоящим выбранным Stockfish; видит график и статистику с явным источником и покрытием. Никаких потерь SQLite, подмены accuracy, самопроизвольных live запросов, фризов и скрытых бинарников. Если реальная приёмка пока не проводилась — честно `READY FOR MANUAL PILOT`, а не `DONE`.
