## 0. Продуктовое решение и границы

Программа должна ощущаться как ежедневный личный шахматный кабинет, а не тестовая панель API. Пользователь дважды нажимает на иконку и сразу видит свои партии, текущую игру, прогресс и место последнего разбора, без PowerShell и повторного подключения/импорта.

Владелец утвердил:
- Достаточно ярлыка и устойчивого .cmd/.bat запуска, **EXE собирать сейчас необязательно**; не вводить постоянную пересборку.
- **Тёмная тема обязательна и основная**, светлая не требуется в M4.6. Тёплые медные/золотистые акценты, не зелёный фон.
- Слева вертикальное меню. На игровых и шахматно-аналитических экранах меню **автоматически свёрнуто** до узкой полоски иконок.
- Доска **средняя** по умолчанию, 4 пользовательских размера. Не увеличивать автоматически до гигантской.
- Три содержательные карточки последних партий: точность, свои неточности, ошибки, зевки, подтверждённые сильные ходы, источник и покрытие оценок.
- **Главный сценарий M4.6:** единый экран просмотра И разбора любой завершённой партии: средняя доска, синхронные ходы, интерактивный график с метками качества, статистика белых/чёрных и «Разобрать свои ошибки» с самостоятельным поиском улучшения (подробно §5.1–5.6). Не оставлять базовый просмотр только со списком ходов.
- Продолжение активной партии или ранее прерванного анализа одним действием.
- Шахматные звуки событий (ход/взятие/шах/рокировка/превращение/предход/конец партии), выключение и громкость.
- Масштабирование Windows, сохранение рабочего состояния, единые компоненты, неблокирующие состояния загрузки, без лишней фоновой активности.
- Уведомления — компактные и только по делу; горячие клавиши — инфраструктурный задел, **не приоритет перед мышью**.
- Будущие голос, тренер, уроки, дебюты, упражнения должны встроиться в нынешнюю схему.
- Текущий стек Python 3.12 + PySide6 + SQLite сохранить; **не переписывать на Rust/C# в этом этапе**. Разделить UI/domain, чтобы возможный будущий переход был легче.

**Запрещено:** создавать параллельную новую SQLite, копировать пользовательские PGN в демоданные, показывать выдуманную точность/нулевые ошибки без охвата, запускать Stockfish в live human game, автоматически скачивать программы, запускать полный импорт/анализ из-за простого открытия вкладки, сливать код без review.

## 1. Навигация: пять пунктов + настройки

Ровно пять главных route ID, стабильные идентификаторы без привязки к тексту:
- home — **Главная**: актуальное состояние, продолжить партию или разбор, три последние партии, ключевые показатели.
- play — **Играть**: активные Lichess игры, AI/друг/вызов, локальная доска. Эти действия НЕ занимают главную по отдельной длинной кнопке.
- games — **Мои партии**: архив, поиск, карточки, паспорт, постраничный список, выбор партии для анализа.
- analytics — **Аналитика**: overview, дебюты/фазы, ошибки/динамика/события, массовый анализ.
- puzzles — **Задачи**: локально сохранённые задачи и попытки, статистика и повторное решение, отдельное обновление с Lichess.
- settings — **Настройки**, закрепить в нижней части боковой панели после divider.

Никаких видимых disabled вкладок «Анализ» и «Тренировки» без содержимого. Технические опции «Пробный импорт», full backfill, OAuth, debug, выбор узлов/Hash убрать из основной навигации в «Хранилище / синхронизация» или Advanced Settings, **но сохранить ручной Recovery**. Повторный вход на страницу не выполняет OAuth, engine или sync.

В будущем: puzzles может переименоваться в «Тренировки» при появлении репертуара, эндшпилей и персональных упражнений. M5/M6 получают новые **контекстные вкладки** инспектора доски («Мои мысли», «Аудио», «Тренер»), а не десять постоянных новых пунктов навигации. Будущие элементы до готовности не показывать.

## 3. App shell: строгая геометрия и адаптивность

**Первый запуск:** окно 1360x860 dp на экране, где оно помещается; на маленьком — fit в availableGeometry (не выходить за taskbar). При следующем запуске восстанавливать окно/Maximized и видимое положение. Цель: работать при 1024x700, 1280x720, 1366x768, 1600x900, 1920x1080 на Windows 100%,125%,150%,200%; узкая ширина или ограниченная высота = scroll/flex, не обрезать CTA.

**Sidebar expanded**: ширина ровно **212dp**, фон bg.sidebar, горизонтальный padding12, бренд сверху x≈16, y≈18, 20dp. Навигация с первого ряда на y≈106, затем каждые 48dp: Главная, Играть, Мои партии, Аналитика, Задачи. Каждая интерактивная строка 44dp high, icons 18dp left, текст 14dp. Активный пункт bg.raised с узким 3dp left accent indicator; settings закреплены внизу с divider, не в общей прокрутке. По умолчанию expanded в Home/Games/Analytics/Puzzles при ширине >=1160dp.

**Sidebar collapsed**: ширина ровно **60dp**, только иконки и tooltip с названием, toggle expand вверху; на ALL board screens (игра/локальная/паспорт/задачи) по умолчанию collapsed, чтобы не мешать доске. Не сворачивать/раскрывать заново при каждом ходе/сетевом событии. При окне уже 1160dp sidebar по умолчанию collapsed на любом экране; expand через overlay, без изменения размера доски в процессе перетаскивания фигуры. Ручной override можно запомнить на текущую сессию/route, не навязывать для всех future games.

**Header:** высота **64dp**, справа account status и кнопка меню аккаунта, иконка уведомлений (только если есть польза) и Settings, при активной игре маленькое «К партии». При expanded sidebar бренд только в sidebar, не дублировать. Header divider 1dp; network/color status только по подтверждённому connected и с текстом. Часы онлайн-игры не в header, а вокруг доски.

- x 212..1359, y 0..63: header.

- title y≈86..124, subtitle под ним.

## 4. Главная — шахматный обзор, а не длинный список кнопок

Заголовок «Мой шахматный обзор» 26dp; subtitle «Последние партии, анализ и тренировки» 13dp. Верхние CTA cards (min height96, radius12, padding20, icon20dp, title16, subtitle13):
- если есть подтверждённая активная Lichess партия, primary «**Продолжить партию**» с соперником, своим цветом и состоянием; рядом «Разобрать».
- если активной нет — «**Играть**» и «**Разобрать**», вместо отдельного списка AI/друг/локальная доска. Вторая ведёт к сохранённому разбору или выбору завершённой партии.
- если есть незавершённый разбор, отдельная компактная строка «Продолжить разбор» с соперником, move number, phase и ссылкой. Приоритет у live игры. Нельзя без серверного подтверждения автоматически стартовать/открывать потенциально stale live position.
- Блок «Что нового» не раздувать. Состояние Stockfish (готов/не найден), last sync или прогресс analysis — маленькая nonblocking строка/чип, без специальных главных кнопок full sync.

**4 KPI (каждая height≈96dp; gap 8–12dp):**
1. «Партий»: N (реальный selected account/scope).
2. «Средняя точность»: только true official Lichess accuracy (пример 86,4% **n из N**); для местной без утверждённой формулы — «нет данных», не выдумывать процент.
3. «Разобрано»: N/total games с явным distinction complete/partial. Показывать coverage (assessed own decision pairs), не считать 922 post-move scores эквивалентом 922 classified decisions.
4. «Ошибки»: errors/100 assessed own moves и n; при denominator=0 — «н/д», не «0». Current 90-day profile отдельно от всей исторической истории; фильтр account/clock сохраняет выбор.

### 4.1 Последние партии: 3 реальные информативные карточки

Это **самое заметное изменение макета**, сделанное по просьбе владельца; нельзя оставлять пустые строки, как на наброске.

Сортировать три **последние завершённые** игры по действительной game date, unknown последними. Учитывать account_games.color выбранного аккаунта. Не загружать 3291 PGN в GUI ради трёх.

Каждая карточка: bg.surface, border.subtle 1dp, radius12, padding16dp, minimum height112dp, gap8–12dp.
- СТРОКА 1 (первый ряд): слева результат с маленьким semantic status icon/label («Победа», «Ничья», «Поражение», «Неизвестно»), **имя соперника bold15dp**, затем metadata «Блиц · 3+2 · Белыми/Чёрными · 28 окт». Справа небольшой «Разобрать»/chevron (карточка сама clickable).
- СТРОКА 2: пять показателей **свои**: «Точность», «Неточности», «Ошибки», «Зевки», «Сильные ходы». Число 17–18dp; label 12–13dp. Располагать 5 компактных групп в ряд по flexible grid, min group width≈105dp; при узком пространстве wrap на две строки. Сильные ходы — **только подтверждённые** best/positive moves; не называть любой хороший ход brilliant.
- СТРОКА 3 (необязательная но предпочтительная): source + evaluated own move pairs X/Y и статус «Частичный анализ» / «Готово» / «Нет анализа». Формат: «Lichess · 46/54 своих ходов оценено». Возможен selected Stockfish source, но не смешивать несопоставимые шкалы.
- Если accuracy отсутствует, показывать «—», а не 0%. Если оценки не существуют, counts «—», не 0. Если охват частичный, counts обозначать «найдено ≥2 из 12 оценённых ходов» или аналогично, не утверждать «в партии 2 ошибки» без полного анализа. 0 допустим только при однозначном покрытии конкретного критерия; статус source/version важен.
- Клик на карточку или «Разобрать» = **единый экран завершённой партии §5.1–5.6**, с доской и доступным ранее сохранённым анализом; отдельного «пустого просмотра» больше нет. Вложенное действие не вызывает двойного открытия. Не запускать Stockfish лишь от открытия карточки.
- Пустой архив: «Пока нет сохранённых партий» плюс нормальный путь «Играть»/«Подключить Lichess» без блокирующей повторной авторизации. Есть архив, но нет оценок: показывать игры со значком «Нет анализа», а не пустой блок.

**Текстовый пример только для понимания компоновки, НЕ как фиктивные реальные данные:**
Победа · Соперник — Блиц 3+2, белыми, 28 октября   [Разобрать]
Точность: 86,4% (Lichess) | Неточности: 2 | Ошибки: 1 | Зевки: 0 | Сильные: 3 verified
Охват: 52/52 оценено, Stockfish quick / Lichess только если выбран соответствующий источник.

## 5. Сцена шахматной доски: размер и layout

На всех board screens sidebar collapsed 60dp, header64dp. Две зоны: слева шахматная доска+игроки/часы, справа context inspector. **Доска не занимает весь экран.**

**Размерные пресеты (Settings → Доска):**
- Compact = **400dp** square.
- Medium = **480dp**, DEFAULT.
- Large = **560dp**.
- X-Large = **640dp**, только если действительно влезает.
На маленькой высоте/ширине clamp до доступного max square с минимальным практическим ориентиром 320–360dp, чтобы фигуры не обрезались. Пресет сохраняется (после увеличения окна снова отображать выбранный целевой размер). Не растягивать 480 до 700 при 1920x1080. Сейчас BoardView минимум 440dp, адаптировать sizeHint/minSize так, чтобы Compact=400 действительно работал. Не ломать chess-widgets drag/drop.

**Нормальная геометрия 1360x860dp:**
- sidebar width60;
- body horiz padding24;
- board default 480x480 (центр в левой board column);
- над доской соперник/часы height≈36–40dp;
- под доской игрок/часы height≈36–40dp;
- под ними contextual controls height≈36–40dp: «Перевернуть», «Назад/вперёд», «К текущему ходу», нужные действия.
- gap между доской и правым inspector **20dp**.
- inspector справа width preferred **340dp**, min300, max450, padding16, radius12. Ширина и board вычисляются из свободного пространства; на 1024x700 инспектор может стать drawer BELOW board, а не перекрывать фигуры/часы.
- Не переносить шахматные часы в global header. Автоматическая ориентация за свою сторону — наследовать из M4.5.1, не переписывать.
- При move/premove GUI не занимается долгими SQL, сетью или Stockfish; **нет задержек мыши** ради layout/анимации. Не перерисовывать гигантские pixmap на каждый server ack.

**Inspector tabs** показывать только реально реализованные:
- live human: «Ходы», «Информация», **без Stockfish eval, PV и hint**;
- free local: «Ходы», «Анализ» только по явно включённому и безопасному режиму, «Заметки» если есть;
- finished review/passport: единый **GameReviewWorkspace** §5.1–5.6 с вкладками «Ходы», «Разбор», «События», «Заметки» (если доступно), общим интерактивным графиком и кнопкой «Разобрать свои ошибки»; сведения и оценка в нём всегда связаны с текущим просмотренным ply;
- puzzle: «Задача», «История» и «Объяснение» только когда поддержано.
В M5 добавить «Мои мысли / Аудио» в inspector, в M6 «Спросить тренера». **Не выводить пустые будущие tabs**. Основа data contracts по game_id, line_revision, ply, position UID; никакой второй SQLite.


### 5.1. Центр M4.6 — единый разбор завершённой партии (ОБЯЗАТЕЛЬНО)

**Одно действие = одна рабочая область.** Пользователь открывает завершённую стандартную партию из «Мои партии», последних трёх карточек Главной, статистики/ошибок, истории просмотра или результата анализа — **ВСЕ маршруты ведут в один экран GameReviewWorkspace с одной доской и одним viewmodel**. Старые \`_open_saved_game\` (голая доска/ходы) и \`StatisticsGameDialog\` (отдельный график) должны быть **объединены функционально**, не существовать двумя параллельными копиями статистики. Сохранить экспорт PGN, заметки, выбор позиции, поиск, безопасный возврат к архиву. Реализовать как нормальный route с контекстным Inspector; **не как очередное огромное модальное окно поверх игры**. Любая законченная партия открывается даже при отсутствии анализов; UI корректно говорит «Оценок пока нет» и предлагает **отдельный явный запуск** анализа при безопасном контексте.

**Точная композиция при 1360×860 logical px:** слева sidebar=60dp, header=64dp; body padding 20–24dp. Под компактной шапкой партии (≈48–64dp: игроки, дата, цвет, контроль, результат, открытие) горизонтальный workspace: левая колонка с доской **480×480dp default**, над/под ней имена/ходовые элементы 32–40dp; справа \`ContextInspector\` preferred width **420dp**, min320/max500, gap **20dp**. Инспектор содержит **ходы с бейджами**, выбранную оценку, краткие факты/события, заметки по вкладкам и компактную панель обеих сторон. Под этой областью — **единый интерактивный график ПО ВСЕЙ доступной ширине body**, preferred height **180dp** (min160/max220), а не узкая 400px картинка в отдельном диалоге. Если высота не вмещает, scroll content вертикально: доска НЕ уменьшается только ради графика; у графика остаётся удобная видимая высота. На 1024×700 и при 150–200% DPI инспектор превращается в доступную ниже доски панель/вкладки, график идёт ниже; не обрезать нижние CTA, не менять layout на каждом ходе. \`QSplitter\`/layouts, не \`setGeometry\`.

**Взаимодействие** (одна управляющая величина: \`selected_ply\`, 0..length):
- нажал ход в нотации → доска перестроилась, на графике вертикальный курсор/метка, правая оценка/пояснение/события обновились;
- нажал **точку графика или любое место линии** → выбирается ближайший **реально сохранённый** анализируемый \`ply\` (без интерполяции отсутствующих оценок), доска/нотация/панель синхронизируются;
- нажал «Следующая ошибка»/«Предыдущая ошибка» → прыжок на конкретный ход и подсветка его и источника;
- колесо, мышь, стрелки навигации и «К началу/концу» остаются; просмотр не запускает фонового UCI по одному click/hover;
- \`position_assessments\` привязаны к позиции **после хода ply**, а \`move_metrics.severity\` к **сделанному ходу ply**. На графике значок класса ставить над точкой **после этого хода**, а «Исправить» открывает позицию **до него: ply−1**. На стороне белых/чёрных не путать чей ход и какой счёт оценок;
- открыть завершённую партию и пересмотреть оценки можно **offline**, не делая авторизацию и не повторяя анализ; при подтверждённой живой human-партии engine hints/PV и training-mode по действующей Fair Play policy скрыты/заблокированы также при переходах в другие context windows.

**Никакой новой формулы local accuracy:** пользователь видит источники и степень покрытия, а не фиктивные проценты.

### 5.2. Интерактивный график: точки хороших и плохих ходов

Использовать сохранённые \`analysis_runs\`, \`position_assessments\`, \`move_metrics\`, \`analysis_events\` и \`analysis_alternatives\` с валидным \`game_id + line_revision + line_hash\`; метод \`latest_analysis_detail\` уже собирает часть фактов. Отделить read-only repository adapter/viewmodel от Qt paint; лениво загружать один выбранный game, без всех 3291 PGN. Предпочитать корректный complete run; partial подписывать как partial и не рисовать притворно полный охват. Не использовать stale line revisions или pending/failed job как успешный анализ.

**График:**
- Фон \`bg.surface #1F232A\`, grid \`border.subtle #353A43\`, линия оценки \`accent.primary #C6A477\` 2dp, точки сохранённых позиций радиус 2–3dp, выбранный ply вертикальная светлая пунктирная линия 1dp и кольцо 7dp. Ось X = \`ply 0..N\` (полуходы, нижние подписи «10.», «20.» при достаточной ширине); ось Y = пешки (+/−) **с явной POV-меткой**, default «со стороны белых» как в сохранённых \`white_cp\`, переключатель «с точки зрения моего цвета» может инвертировать знак. Не инвертировать источник самих оценок в БД. \`mate_white\` показывать как «Мат N»/«−Мат N», не превращать mate в выдуманные +10 CP.
- Цветные **и различимые по форме** markers поверх реально классифицированных ходов: «Хороший» (подтверждённый \`severity=good\`, мягкий \`#8EAEC8\`, круг 7dp), «Неточность» (\`#D2AA69\`, контурный ромб 8dp), «Ошибка» (\`#CB916D\`, ромб 9dp), «Зевок» (\`#CF7272\`, треугольник 11dp). Цвета и подписи — семантические; основной фон остаётся тёмным и без зелёной заливки. Метки **unknown/нет сравнимой пары** не называть хорошими и не рисовать как однозначные. Не выдавать нормальные ходы за brilliant.
- Tooltip/всплывающая карточка: «Ход 17... Nf6», собственный цвет/сторона, класс (если подтверждён), исходная оценка и после (только если есть), CP loss (если вычислим), source+budget+coverage. Для неполных данных — «Классификация недоступна», не 0. При сотнях полуходов не рисовать огромные перекрывающиеся кружки: приоритет error/blunder, hover hit area >=14×14dp с выбором ближайшего сохранённого ply, подвижный cursor и доступные keyboard controls; график остаётся интерактивным, не static pixmap.
- Под графиком небольшая легенда (хорошие/неточность/ошибка/зевок/не оценено). Пользователь может скрыть второстепенные бейджи, но **не скрывать все плохие ходы по умолчанию**. Линия не соединяет непрерывно через большие пропуски данных так, как будто анализ всех позиций полный.
- При клике на маркер показать соответствующую позицию **после** совершённого хода; контекстное «Попробовать лучше» открывает **до** хода и упражнение (§5.4).

### 5.3. Сравнение белых и чёрных — никаких вымышленных процентов

В правом Inspector / Game Summary компактная таблица «Белые / Чёрные» (порядок фиксирован, *мой цвет* подчёркнут). Для ОБЕИХ сторон при наличии источников:
- **Точность:** только сохранённый **официальный Lichess accuracy_white/accuracy_black**, независимо для каждой стороны (0–100%, подпись «Lichess»), либо \`— Нет данных\`. Для локального Stockfish **НЕ преобразовывать CP loss в точность процентов**; \`local_accuracy_formula_id\` сейчас отсутствует/unsupported. Если одна сторона имеет точность Lichess, другая нет — показывать именно так.
- **Неточности / Ошибки / Зевки:** отдельно по ходам белых и чёрных из одного совместимого verified \`move_metrics\` + \`severity_policy_version\`; надёжно считать \`mover\` и количество **сравнимых пар оценок ходов** для каждой стороны. Подписать «Охват: 17/31 сравнимых ходов» отдельно у каждой стороны. Если denominator=0, **вместо 0 ошибок показывать «н/д»** (нельзя нулём обозначать невозможность классификации); при частичном охвате честно писать, что это count только на оценённых ходах.
- **Хорошие ходы:** число только \`severity=good\` на сравнимых ходах; **не** называть «блестящие» или «лучшие» без отдельного доказанного критерии. Метрики по умолчанию подсвечивают мой цвет, но обе стороны всегда видимы. Не смешивать official accuracy Lichess и локальные классы с разными provenance без подписи.
- **Связь с графиком:** клик «Зевки: 2» фильтрует markers этого цвета/класса и раскрывает соответствующие ходы, не запускает новый analysis; обе стороны показаны, даже если текущий выбранный аккаунт играл противоположным цветом.
- Информация о выбранном ходе: SAN, кто играл, severity/cp_loss/source, saved top PV если законно доступен и есть, depth/nodes, причём **состояние ошибки ≠ позиционная оценка** (провалены две разные метрики).
- Если source=partial, получены только результаты Lichess одной стороны, нет baseline для первого своего хода, у пользовательского аккаунта поменялся цвет или \`account_id\` относится к другой связке — никаких ложных нулей, double counting или имитации полной точности.

### 5.4. «Разобрать свои ошибки» — лёгкое учебное упражнение уже в M4.6 (НЕ полный M4.7)

**Обязательная кнопка** под summary/над графиком: **«Разобрать мои ошибки»**, с количеством **действительно пригодных** позиций (например «Разобрать мои ошибки · 5»). Если нет подтверждённого цвета игрока/нет сравнимых оценок/партия не завершена/есть активная человеческая партия или неопределённая safety — disabled с понятной причиной. После запуска обычный review график/engine PV должны **скрыться на время попытки**, иначе упражнение сразу даёт ответ.

**Алгоритм:**
1. Построить локальный список из текущего завершённого стандартного game revision: только **мои** ходы с подтверждённым \`severity in {mistake, blunder}\` и достаточным \`ply−1\` board snapshot и сохранённым baseline / legal candidate. \`inaccuracy\` отдельный флажок «Добавить неточности» OFF по умолчанию. Никаких заданий из \`unknown\`, \`partial\` без baseline, нелегального PGN, чужих ходов или событий без сравнимых оценок. Если подходящих мало — показать честное количество.
2. Отправить пользователя **в позицию непосредственно ДО ошибочного хода (ply−1)**, поворот доски за выбранный свой цвет. Показать «Твой ход — найди продолжение лучше, чем сыгранное», счётчик «1 из 5», кнопки «Проверить», «Подсказка» (только по явному запросу), «Пропустить», «Следующая ошибка», «Вернуться к разбору». Не раскрывать исходный ошибочный ход, engine PV, картинку правильной клетки, красный marker или точные CP **пока он думает**. Доска — отдельная **локальная копия позиции**, не online session и не исходный PGN.
3. Пользователь делает **ровно один легальный ход** мышью (или несколькими способами выбора), после чего нажимает «Проверить». Оценивать **улучшение по сравнению с реально сыгранным ходом**. **Не требовать совпадения с первой линией Stockfish**, если подтверждён другой достаточно хороший ход. Безопасный быстрый путь: использовать сохранённый лучший ход из PV \`position_assessments[ply−1]\` как гарантированно предлагаемый кандидат (проверить его легальность и run provenance), плюс сохранённые \`analysis_alternatives\` на ТОЙ ЖЕ pre-move позиции, если действительно имеются и достаточно качественны; при другом кандидатном ходе — по явной кнопке **однократная ограниченная в бюджете проверка реальным Stockfish** (начальный preset ~100k nodes, Hash64 MB, отменяемая, с безопасным fair-play preflight и жизненным циклом analysis job). Не запускать постоянный UCI движок на каждое перемещение фигуры.
4. Для принятия альтернатив нужно **верифицировать**, что кандидат объективно лучше исходной ошибки и остаётся приемлемым относительно baseline (не просто «первый PV другой»). Норматив: использовать существующую версионированную \`move_metrics\` / score comparison на сопоставимых оценках; учесть mate/WDL и выбранную сторону. Точный числовой threshold допуска аналогов выбрать в коротком upfront audit и зафиксировать отдельно как \`acceptance_policy_version\` с тестами (не маскировать неустойчивую low-node оценку уверенностью). При недостаточном budget, несопоставимых run, невозможности safety preflight или неясной позиции — состояние «Не удалось достоверно проверить этот вариант», а **не «Неверно»**.
5. **Fallback первой версии, если MultiPV/сравнение альтернатив слишком сложно:** обязательно работает хотя бы **один законный улучшенный ход** — сохранённый top PV на pre-move позиции. Проверять альтернативы можно позднее; при этом **не считать остальные ходы неправильными без проверки**. GUI явно различает «Найден улучшенный ход», «Нужна дополнительная проверка», «Этот ход не улучшил ситуацию» с evidence source. Не запускать глубокий движок, если отсутствует безопасная проверка (fair play); показать причину и возможность просмотра после игры.
6. После проверки показать «Ты сыграл …, в партии было …; здесь можно было …» с понятным кратким объяснением разницы оценок **только при фактической оценке обоих ходов**. Пользователь выбирает «Повторить без подсказки» или «Следующая ошибка», в конце лёгкий summary «проверено / улучшено / пропущено / не удалось проверить», без фиктивного Elo или «точности обучения».
7. В M4.6 **не делать** FSRS, голосового тренера, отдельного репертуара, человеческого Maia-бота, сложной оценки переноса навыка. Достаточно ephemeral training session на текущем review (или минимального аддитивного persisted state **только если существующего недостаточно**); попытки **не изменяют** архивный PGN, старую классификацию, \`analysis_runs\`, Lichess account или реальные puzzle attempts. Подготовить интерфейс для будущего M4.7, но **не строить его целиком**.

**UX и безопасность:** упражнения только из окончательно завершённых партий; при активной/неизвестной live human игре отключить тренировочные engine hints/PV (fail closed), не копировать текущую онлайн-позицию как «завершённую» и не показывать сохранённый лучший ход из неё. Если местная сеть не работает и нельзя подтвердить отсутствие live human игры, не выдавать движковую помощь обходным способом. Реальный engine worker cancelled/lease/restart корректен, UI не замерзает и не показывает stale result после смены партии/хода/аккаунта.

### 5.5. Что перенимаем у GitHub-проектов (строгий отбор — без переноса кода)

- **[DaisyChess](https://github.com/refaustria/daisychess)**: review с interactive eval graph, ключевыми моментами, переходами по кликам и проверяемым повторным чтением saved run. Берём **концепцию click-to-position и key moments**, не добавляем web server/wasm/новые движки из их архитектуры.
- **[Blitzr](https://github.com/franverona/blitzr)**: ошибка как переход из истории к **самостоятельной попытке найти другой ход**, навигация по missed opportunities. Берём простую кнопку «Разобрать мои ошибки», не копируем целую систему SRS, шахматный репертуар/уроки сейчас.
- **[Opening Trainer](https://github.com/vancoeur/chess-opening-trainer)**: понятная фиксированная боковая навигация, краткий статус изучения, отсутствие технических кнопок на Главной. **Дебютный sparring перенести в отдельный M4.7**, он не входит в M4.6.
- **[Tabia](https://github.com/daxaur/tabia)**: отклик доски и синтезированные/оригинальные короткие звуки при ходах, правые стрелки. У нас уже есть свои board control: не менять premove/safety ради визуальной имитации.

**Не внедрять** чат-LLM, Maia, full SRS, большой Opening Explorer, генератор многоходовых упражнений, ещё один движок, облачное сохранение или вторую SQL базу. Все эти идеи остаются в [M4.7 research](../research/M4_7_TRAINING_ARENA_IDEAS_AND_GITHUB_REFERENCES.md) / M5/M6. Фокус M4.6: **быстро увидеть и понять конкретную завершённую партию, найти свою ошибку и попытаться её исправить**.

### 5.6. Строгая приёмка единого разбора и мини-тренировки

- Fixture завершённой партии с 70 полуходами, смешанными \`good/inaccuracy/mistake/blunder/unknown\`, partial/missing assessments: график по сохранённым точкам, правильное сопоставление \`ply\`, отсечённые пропуски, good/bad метки, переходы из graph/movelist/errors в одну и ту же позицию; «исправить» открывает строго \`ply−1\`. По нажатию графика **0 UCI и 0 Lichess HTTP requests**.
- Две стороны: официальный \`accuracy_white\` есть, \`accuracy_black\` отсутствует — честно отображаются независимо. Каждая сторона имеет свои \`good/inaccuracy/mistake/blunder\` + coverage (0 own comparable => н/д, не 0). Не путать linked account и white/black, не выдумывать local accuracy formula.
- Тренировка: три свои mistake/blunder, один у соперника, один unknown → **3** задачи; без показа best PV/графика до ответа; попытка только legal move; добротная альтернатива engine top1 засчитывается, если verified; неопределённая альтернатива **не помечается неверной**; «пропустить», «попробовать ещё раз», «выход» сохраняют архивный PGN/DB data без изменений.
- Проверка только одной линии без альтернатив: сохранённый best PV есть → минимум 1 рабочее улучшение; отсутствие pre-ply PV/score → «Недостаточно данных», без попытки угадать. 200-полуходная игра остаётся интерактивной, markers не конфликтуют, scroll/hover не тормозит.
- При активной/unknown/429 human party → никакого engine-включения/подсказок, поздних UCI/PV ответов; после ended/reconnect новый preflight, не использовать старый \`safe\`. Переключение завершённой партии/смена selected account/ревизии отменяет старое упражнение и анализ без чужих результатов.
- DPI 100/125/150/200%, окна 1024×700, 1280×720, 1360×860, 1920×1080: доска compact/medium не теряет размер, Inspector/график доступны через прокрутку; keyboard focus, mouse click hit testing на масштабах; tooltip и маркеры видны в dark-v1, no blank white dialogs.
- Открытие из Главной/Мои партии/аналитики/недавно сохранённой заметки всегда один review workspace; пустой архив/нет анализа, partial/failed job и неправильная rev ведут к понятным состояниям без fake metrics. Сохранённый graph не исчезает при просмотре ходов, не пересчитывается автоматически.

## 6. Звуки ходов: простые, оригинальные, без дублей

Технология: Qt QSoundEffect или равнозначный nonblocking локальный WAV player. Asset pack оригинальный либо с подтверждённой лицензией, NOTICE/source, не копировать звуки Lichess, Stockfish или чужого сайта без разрешения. WAV по возможности короткий, mono PCM, заранее preload; нет сетевой загрузки и нет движкового расчёта из звукового обработчика.

| Событие | ID | Характер |
| --- | --- | --- |
| обычный ход | move | мягкий стук деревянной фигуры |
| взятие | capture | более выраженный стук |
| шах | check | короткий отдельный сигнал |
| рокировка | castle | лёгкий двойной стук |
| превращение | promotion | особенный короткий акцент |
| поставлен предход | premove | тихий щелчок |
| окончание игры | game_end | один ненавязчивый сигнал |

Для каждого реально сыгранного/подтверждённого хода **не более одного игрового звука**, priority checkmate/result > promotion > castle > check > capture > ordinary. Свой ход можно озвучить оптимистически сразу после принятия локального намерения, но ACK того же ply НЕ повторяет звук. Ход противника — по authoritative event. Premove placement — тихий щелчок; реальное исполнение — игровой звук, если stream подтверждён. Никаких серий звуков при reconnect, восстановлении, скачивании PGN, прокрутке истории или пересчёте виджетов. History sound OFF by default.

Settings: «Звуки ходов» ON default, «Громкость» 0–100 default 45, «Звуки уведомлений» ON separately, «Звуки при просмотре истории» OFF. Изменения QSettings, missing audio devices/asset fail gracefully. Latency от локального mouse accept до звука ориентир <100ms на нормально нагруженном ПК; не утверждать достижение без ручного E2E. Тесты: no duplicate user ACK, duplicated stream event, reconnect, pending reject, change mute/volume, castle/capture/mate, no sound when scrolling.

## 7. Double-click запуск без EXE и без повторного PowerShell

Создать в корне репозитория понятный launch_chess_coach.cmd; путь определять от расположения скрипта (%~dp0), НЕ жёстко G:\project\chess. Использовать .venv312\Scripts\pythonw.exe (или существующий явно выбранный venv), запускать обычные пользовательские данные, а не режим --offline с временной БД. Для воспроизводимого ручного подключения Lichess можно запускать с --manual-connect. Не выполнять pip install/rebuild каждый старт. Debug launcher отдельный через python.exe, чтобы видеть ошибки.

**Основной комфортный вариант:** один раз создать ярлык Windows Desktop *.lnk на pythonw.exe с Arguments «-m chess_coach --manual-connect», WorkingDirectory=корень репозитория, именем Chess Coach и собственной иконкой. Допустим однократный create_shortcut.ps1 через Windows COM/WSH, **только по явному пользовательскому действию**, не создавать скрыто автозапуск или ярлык из простого запуска приложения. Запуск .cmd может кратко показать консоль, поэтому основной ярлык должен её избегать. Классическая иконка может быть создана как собственный безопасный SVG/ICO resource (без копирования чужих иконок/шрифтов). EXE/инсталлятор/обновлятор пока НЕ делать.

Нужно **single-instance** для одной реальной пользовательской DB/profile: повторный двойной клик активирует открытое окно и не создаёт конкурирующие SQLite writer/UCI/OAuth. Возможен QLocalServer/QLocalSocket или подходящий mutex с восстановлением stale lock; тесты. Если безопасная реализация single-instance пока не готова, не заявлять DONE и блокировать второй writer понятным предупреждением, не рисковать базой.

При отсутствии pythonw/venv — понятная ошибка с инструкцией и лог, а не silent no-op. Уже есть crash.log: писать stack-only диагностику в LOCALAPPDATA/ChessCoach/logs, rotate, НЕ записывать PGN/токены, личные данные и полный URL OAuth. Сначала показывать локальную GUI и сохранённые данные, затем неблокирующая проверка/синхронизация Lichess по ранее разрешённым scopes, без OAuth popup при старте. Не запускать Stockfish, full import или установщик только потому, что открыли программу. First usable paint ориентир 2–3 секунды при умеренном PC, измерить на mock/Windows до утверждения цифры.

## 8. Сохранение рабочего состояния и тихий UX

Хранить в QSettings только небольшой state: размер/позиция/maximized окна, theme dark-v1, sidebar mode, board size preset, board theme, sound enabled/volume, выбранный аккаунт, последний route, последний открытый finished game_id, line revision/hash, viewed ply, selected inspector tab, фильтры. **Не хранить копии PGN/FEN/OAuth токенов в QSettings.**

«Продолжить разбор»: game_id+line_revision+viewed_ply, после перезапуска по совпадающей ревизии открывает тот же ход и место; если PGN обновлён/изменён — показать безопасный fallback на текущую партию, не притворяться что старый ply соответствует новым ходам. Сохранять debounced, не писать state на каждый тик колеса мыши. При смене мониторов убедиться, что restore window intersects availableGeometry.

Аккаунт запоминается локально, токен хранится отдельно как раньше; при истёкшем токене доступ к партиям/задачам остаётся, network помечен «нужна авторизация» без выскакивающего браузера. Любая фоновая синхронизация/анализ имеет короткий inline status и retry (без блокирующих десятков QMessageBox). Лёгкие meaningful notification: анализ завершён/ошибка sync/Stockfish недоступен/результат партии. Маленькая иконка bell и popup <=20 событий возможны, **но не строить отдельную DB и огромный центр уведомлений**, если достаточно inline toast.

Горячие клавиши: Tab/Enter/Escape и существующие колесо/стрелки/отмена предхода. Никакой большой редизайн hotkeys: mouse-first. Любое disabled действие с понятным tooltip «почему недоступно» либо скрыто, если функция ещё не готова.

## 11. Несколько обязательных отрицательных сценариев

1. Нет оценок: accuracy и ошибки = «н/д», а не 0. Сигнал о полной партии Lichess только по positional coverage, own-move pairs отдельно.
2. Один game_id связан с аккаунтами белого и чёрного: card/board owner perspective и сильные ходы корректны; один engine run.
3. Live Lichess human: нет PV/CP, нет преждевременной engine подсказки даже при switch to local board; premove до ACK не мешает.
4. Unknown/expired token: локальная библиотека и задачи доступны, не всплывает OAuth.
5. Размер окна 1024x700, 1280x720, 1366x768 при 150% scaling: все действия доступны через scroll, board не вылезает за область.
6. Double-click на ярлык 2 раза: одна активная GUI, та же SQLite, ни один UCI/Sync не запущен второй раз.
7. Crash до появления GUI: есть понятная диагностика/лог без приватных данных; откат на предыдущую версию не изменил/не удалил SQLite.
8. Смена версии line_revision: «Продолжить разбор» не прыгает в ошибочную позицию.
9. Звуки по одному событию, никакой музыки или перезвука при загрузке PGN, возвращении через колесо.
10. Неактивный/недоступный Stockfish: не возникает некорректный «Запустить анализ»; ссылка к настройкам/установке из M4.5.1 работает.

**Запрет:** не использовать фиктивные скриншотные числа как реальные данные; готовая тема — тёмная, светлая позже; зелёный для смысла, золото для accent; UX мыши важнее горячих клавиш; во время live human game ни один экран не обходит fair-play policy; не затрагивать пользовательские персональные секреты/SQLite без согласованного пилота; в отчёте M4.6 явно назвать НЕ ПРОВЕРЕНО все тесты, которые не запускались на реальном Windows/личной SQLite.
