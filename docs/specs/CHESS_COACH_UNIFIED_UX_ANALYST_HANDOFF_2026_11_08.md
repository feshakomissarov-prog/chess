## 00. СНАЧАЛА ПРОЧИТАТЬ: статус и порядок приоритета

### 00.1. Три класса содержания, не смешивать

- **[NOW / ОБЯЗАТЕЛЬНО В БЛИЖАЙШЕМ UX-ЦИКЛЕ]**: реорганизация существующего интерфейса, разрешённые рабочие страницы, визуальное соответствие, перенос функций, исправление поведения, сохранность всех существующих возможностей, безопасная интеграция с текущим приложением.
- **[NOW — НОВАЯ РАБОЧАЯ ФУНКЦИЯ ПО УТВЕРЖДЁННОМУ КОНТРАКТУ]**: отдельный вложенный экран «Разбор партии» с тройным переключателем, поддержка обычной SAN-нотации и PGN/FEN/файла, ручной редактор, условный автостарт **локального** Stockfish после явного открытия внешнего материала. В актуальном PR часть parse/review/editor уже существует, но не весь новый сценарий. До обещания автоматического запуска требуется code+Fair Play+scheduler аудит.
- **[FUTURE / ПРОДУКТОВАЯ КОНЦЕПЦИЯ — НЕ РЕАЛИЗОВЫВАТЬ КАК РАБОТАЮЩУЮ В ЭТОМ ЦИКЛЕ]**: полный дебютный Explorer/лаборатория, сложная диагностика слабостей, анализ чужого аккаунта и его длинная очередь, новые упражнения и персональный тренер, доказательное отслеживание улучшений после изучения. **Их описание необходимо, чтобы аналитик не сломал будущую информационную архитектуру и чтобы мы смогли впоследствии генерировать картинки.** Но отсутствие алгоритма/контента/API является блокером для активации, а не поводом фальсифицировать данные.

**Предупреждение об особенно важной коллизии:** старые картинки и прежние specs показывают **6 пунктов sidebar**, старые Review/Analysis/Puzzle flow могут предлагать 3 главные карточки или Batch как плитку. **Последнее утверждённое решение — РОВНО ПЯТЬ главных пунктов** («Главная», «Играть», «Анализ», «Обучение», «Прогресс»), а **полный архив «Мои партии» — внутри «Анализ → Разбор партии»**. Четыре карточки на Analysis landing, не три. Это не факультативная косметика. Старые документы используются для выявления пропущенных функций, но **НЕ возвращают старую информационную архитектуру**.

## 01. Словарь и общие продуктовые правила

**GAME** — живой/локальный игровой workspace с одной основной доской. **REVIEW** — общий workspace просмотра одной завершённой или временной внешней партии/позиции; не копия «Моих партий». **PGN** — текст партии с ходами/возможными тегами, не изображение; **SAN** — короткая шахматная запись ходов вроде «1. e4 e5 2. Nf3 Nc6» без заголовков; **FEN** — одна позиция, не сыгранная партия. **ECO** — классификатор дебютов, имя не гарантирует уникальность позиции. **Источник анализа** — saved official Lichess или local Stockfish, их оценки и точности не усредняются как одинаковый алгоритм. **Фон** — единый inspector/очередь операций; **Настройки** — постоянные пользовательские предпочтения.

**Инварианты UX:**
- Один конкретный материал → один Review/Board source и одни шахматные правила. Одни и те же партии не должны существовать в двух независимых архивах.
- Клик карточки выбора режима — только выбор, не создание игры. Клик на строке архива — выбор+детали, не запуск Stockfish. Автоматический анализ для внешнего PGN/FEN разрешается **только после намеренного «Открыть»** и safety-проверки.
- Первичные действия видны без лишних заходов в «Ещё». Редко используемые полезные функции остаются в правильном контексте, а ранее отвергнутые debug UI не возвращаются.
- Ожидание сетевого ответа и подтверждённое действие — разные состояния. Нельзя говорить «Отменено» до ACK; не слать повторный challenge из-за двойного клика.
- «Недоступно/Не оценено/Нет собственных партий/Нет данных» ≠ «0», а «частично проанализировано» ≠ «готово 100%».
- Сразу и честно показывать пользователю источник и охват, особенно в личной статистике и будущих сравнительных графиках.
- Новые разделы не превращаются в pop-up на pop-up. Пользователь видит цельное содержимое текущего route.

### 02.1. Глобальное меню (ровно пять)

| Порядок | Главная кнопка sidebar | Что открывает | Статус в целевой модели |
|---|---|---|---|
| 1 | **Главная** | Персональный четырёхзонный dashboard, последние игры, доступные занятия | Рабочая; существующий путь сохранить |
| 2 | **Играть** | Выбор одного из четырёх режимов, далее GAME | Рабочая; новый layout |
| 3 | **Анализ** | Четыре направляющие карточки 2×2 | Рабочая landing, вложенные маршруты по готовности |
| 4 | **Обучение** | Реально доступные задачи/история; будущие темы WIP | Рабочее существующее не скрывать |
| 5 | **Прогресс** | Подтверждённая статистика и её периоды, без дубля архива | Рабочий существующий путь + будущие метрики WIP |

**«Мои партии» — НЕТ в sidebar**. **«Настройки»** — постоянный отдельный нижний control sidebar (не шестой основной раздел). **«Фон»** — отдельная компактная глобальная кнопка в шапке (не основная вкладка). Подключить/Отключить Lichess, профиль, безопасность — остаются в боковой оболочке по существующим способностям.

### 02.2. Дерево маршрутов

    Главная
      ├─ Недавняя игра → REVIEW(id), напрямую
      ├─ Продолжить живую игру → GAME(id)
      ├─ Следующее занятие → Обучение/действительно доступное упражнение
      └─ Весь прогресс → Прогресс

    Играть
      ├─ Lichess AI → подтверждённое создание → GAME online
      ├─ Друг по ссылке → серверное приглашение → GAME online
      ├─ Вызвать по имени → серверный challenge → GAME online
      ├─ Свободная доска → GAME local
      └─ Продолжить активную игру → GAME(exact id)
    GAME finished → Разобрать → REVIEW(exact finished id)
                  → Вызвать снова → подтверждённое новое приглашение/игра

    Анализ (4 карточки)
      ├─ Разбор партии → вложенная страница [Мои партии | Вставить ходы | Расставить позицию]
      │     ├─ Мои партии → полный утверждённый архив → REVIEW(id)
      │     ├─ PGN / SAN / FEN / .pgn → OPEN → единый REVIEW/позиция → допустимый auto Stockfish
      │     └─ Редактор доски → OPEN → единый REVIEW/позиция → допустимый auto Stockfish
      ├─ Исследование дебютов → сначала legacy статистика; целевая будущая схема:
      │     Обзор всех/моих дебютов → конкретная Дебютная лаборатория
      │     → [позже] Обучение/Практика дебютов
      ├─ Диагностика слабостей → WIP disabled (будущая доказательная карта)
      └─ Подготовка к сопернику → WIP disabled (будущий публичный Lichess username)

    Обучение → доступные реальные задачи/история, позже дебютная практика и повторение
    Прогресс → существующие метрики, позже отслеживание изученных дебютов
    Фон → единый background inspector/queue
    Настройки → Lichess / движок / звуки / экран / лимиты / storage

### 02.3. Владение состоянием и маршрутами

- Sidebar «Анализ» всегда ведёт на **Analysis landing** из четырёх карточек; вложенные экраны имеют breadcrumb «Анализ / Разбор партии» или «Анализ / Исследование дебютов / [Название]» и локальное Back. Не делать открывающиеся панели под landing; вкладка landing **заменяется** полным вложенным workspace.
- При входе «Анализ → Разбор партии» **по умолчанию сразу активен полный архив «Мои партии»**, а не дополнительный экран четырёх плиток выбора источника. Вверху только три компактных переключателя. Первое посещение не требует третьего клика.
- Из Главной, активной закончившейся партии или выбранной строки архива конкретный Review открывается **непосредственно**; пользователь не обязан возвращаться на landing → архив.
- Back из REVIEW восстанавливает источник, выбранный полуход и контекст; Back из вложенного архива — к четырём карточкам Analysis; Back из дебютной лаборатории — к обзору с сохранёнными фильтрами и scroll. При переключении вкладок сохранять черновики PGN/редактора, если это безопасно и не приводит к ложному импорту.
- Отдельные технические внутренние WorkspaceRoute.GAMES/другие старые route IDs могут остаться для совместимости, но **не означают шестой пункт sidebar**; аналитик проверяет route ownership и не ломает события/history/deep links.

## 03. МАНИФЕСТ БУДУЩИХ ВИЗУАЛЬНЫХ ЭТАЛОНОВ

### 03.1. Куда сохранять и как называть

**Владелец пожелал самостоятельно скачивать и переименовывать будущие изображения.** Названия далее назначены заранее и **НЕ означают, что файлы уже существуют**. Единственный корректный процесс:

1. После текстового согласования аналитик/дизайнер генерирует **один конкретный целевой экран** и сообщает владельцу его утверждённое имя из таблицы.
2. Владелец сохраняет **PNG** под этим именем в папке **C:\Users\Михаил\Desktop\Примеры\** (современное название папки в последнем сообщении). **В старых ТЗ исторические изображения лежат в C:\Users\Михаил\Desktop\Пример\ (без «ы»)**. Это НЕ одно и то же имя: перед запуском desktop Codex аналитик должен проверить реальную директорию и не утверждать, что проверил отсутствующее фото.
3. После одобрения изображения владелец сообщает путь/подтверждение. Документ визуального реестра получает статус image APPROVED, размер/версию/фактическое расширение; **имя не меняется самовольно**. При замене концепции — v2, а не незаметная подмена утверждённого изображения.
4. Desktop исполнитель **открывает реальные файлы** на Windows и сравнивает с запущенным Qt интерфейсом. Если Desktop-папка недоступна облачному runner, запросить реальную копию/вложение; не искать «магическую ссылку на локальный путь» в GitHub.
5. Скриншоты не должны содержать настоящие персональные данные, ключи Lichess, реальные токены и экспорт чужих приватных игр. Рендер не равен доказательству backend или математической точности.

**Канонический суффикс:** PNG. Размер-пример исходных предыдущих рендеров **1672×941 (16:9 приблизительно)**; масштаб **не** фиксирован для layout. Для всех скриншотов один узнаваемый текущий тёмно-синий/лавандовый shell и **пять** пунктов sidebar.

## 05. ГЛАВНАЯ: ПЕРСОНАЛЬНАЯ СВОДКА [NOW / СУЩЕСТВУЮЩЕЕ СОХРАНИТЬ]

**Назначение:** «Что происходит с моей игрой и куда удобно перейти прямо сейчас?» Главная **не** является ещё одним архивом, вторым фон-менеджером или крупной дебютной лабораторией. Текущая компоновка в целом устраивает владельца; требуется только совместить с новым shell из пяти пунктов и не потерять безопасные direct links.

**Четыре зоны внутри viewport, без общей длинной вертикальной прокрутки** (старый UX-B1 §B; перед новым редизайном сравнить свежую текущую реализацию):
1. **Личная мини-сводка / «Мой прогресс»**: 2–3 проверенных KPI с датой/источниками/покрытием и небольшой честный тренд; перейти «Весь прогресс» → global «Прогресс». Если нет измерений, показать «Недостаточно данных», не synthetic Elo/accuracy.
2. **«Следующее занятие»**: одно доступное рабочее упражнение/продолжение, CTA «Начать/Продолжить» → общий «Обучение». При отсутствии персонального диагноза предложить нейтральный доступный набор задач, НЕ выдавать за индивидуальную рекомендацию AI.
3. **«Последние партии»**: три компактных реально завершённых game_id, собственный исход/соперник/AI и уровень, цвет, время, контроль, дебют при корректном сопоставлении, краткая реальная аналитика или «Не оценено». Клик или «Разобрать» → конкретный REVIEW **напрямую**, минуя «Анализ → Мои партии». «Все партии» → вложенный **«Анализ → Разбор партии → Мои партии»**, сохраняя фильтры когда это уместно.
4. **Глобальный shell / состояние аккаунта**: sidebar и компактная шапка из §04, не дублировать подключение, настройку и полную очередь в центральных карточках.

**Live games:** при подтверждённой активной сессии предоставить прямое «Вернуться к партии» из шапки или верхнего компактного места, а не вытеснять 3 последние завершённые игры. Наличие активной human-партии маскирует опасные аналитические метрики и подсказки по общему Fair Play.

**Поведение:** быстрые переходы не требуют промежуточных selection pages. При отсутствии связи Lichess локальный кэш/доступные offline функции остаются; неизвестный account scope не подменяется чужим username. Не добавлять пока новый AI trainer/home-avatar/фальшивый учебный план.

### 06.2. Четыре состояния нижней панели

**Normal online game** — две главные области:

**Одна завершённая строка (2–3 компактных строки текста максимум):** Победа/Поражение/Ничья от лица владельца (только если own side known), реальный соперник/AI level либо «Неизвестный соперник», **«Белыми / Чёрными»**, «Моя точность 84% · Lichess»/«Stockfish» **только при valid data** или «Не оценено», дата, контроль, ECO/дебют по подтверждённому источнику. **Не выводить по три ошибки и зевка в строке** — это detail справа. Выбор строки выделяет её и асинхронно грузит panel; late callback чужой записи/аккаунта не перезаписывает текущую.

**Пагинация:** под левым scroll-list в **одной компактной строке** «← / Страница K из M / →»; обе стрелки и номер рядом, disabled на границах. Total matches относится к текущим фильтрам, а «Всего сохранено» наверху — к аккаунту/confirmed scope; подписи не смешивать.

### 10.4. Правая detail panel: каждый элемент

1. **Заголовок/результат:** «Победа / Поражение / Ничья · [соперник]», при наличии authoritatively «Белые [имя] · [1–0/0–1/½–½] · Чёрные [имя]»; мой цвет, дата/контроль, дебют/ECO, реальный источник local/Lichess/AI. Не угадывать владельца из того, что первой ходят белые.
2. **«Моя точность» и «Точность соперника»** — две подписанные величины 0–100% при real valid metric и с отдельными provenance badges («Lichess official», «Stockfish local») и coverage. Если unavailable — «Не оценено». Не смешивать методы/стороны, альтернативный источник можно показать в деталях/tooltip. При неизвестной стороне говорить «Белые/Чёрные».
3. **«Неточности / Ошибки / Зевки»** — компактные 3 пары **Я / Соперник**, реальное покрытие и источник, отсутствие анализа ≠ 0. Уточнять, какие ходы анализировались, не обещать полный охват.
4. **Фазовая точность:** три небольших блока **«Дебют», «Миттельшпиль», «Эндшпиль»** с моей точностью только когда уже вычислена и при правильном phase scope. Не делить одну полную accuracy на три искусственных цифры. Если фазы неизвестны — «Нет данных», не 0.
5. **Компактный advantage graph:** X — ходы/полуходы с честной единицей; Y — **from WHITE perspective** (светлая заливка между 0 и положительной линией — белые, тёмная между 0 и отрицательной — чёрные, независимо от own side), ось ноль видна; **без diamond/triangle/dots на КАЖДОМ ходе**. Не заменять мат ±999 cp, не соединять пропуски/разные sources, указывать X/Y оценённых и source. Hover/click exact ply и keyboard только если safety. Полные error markers/Δ остаются в REVIEW.
6. **Нижние действия:** primary **«Открыть разбор»** (точный выбранный game_id, НЕ автоматически engine), secondary **«Анализ Stockfish»** (явный job по выбранной игре + safety, queued/running/result), **«Экспорт PGN»** (точная линия), компактные **«Заметки»** / «Ещё» только для реально существующих допдействий. «Обновить эту партию с Lichess» — diagnostics/recovery только при подтверждённой ошибке, **не** главный CTA. «Настройки загрузки» → Settings, «Фоновые операции» → глобальная шапка.

**Состояния:** нет партий, нет выбора, нет оценок, partial source, stale details pending, offline/429/sync, активный human match, mismatch account/revision, пропавшая выбранная запись, незавершённая или повреждённая PGN. Любое пустое состояние сохраняет честные game metadata и не выдаёт несуществующее число как 0.

**Реальный source:** ui/pages/library.py::LibraryPage/LibraryRowDelegate, source signal query_requested/open_requested/export_requested/note_requested/analyze_requested/detail_position_requested, GameRepository и window.py::show_saved_games. Нужно переиспользовать и переместить компоненты; не создавать новую SQLite только ради визуальных карточек.

## 11. REVIEW: ЕДИНЫЙ ПРОСМОТР И АНАЛИЗ ПАРТИИ/ПОЗИЦИИ [NOW]

### 11.1. Входы, геометрия, источник

Один текущий **GameReviewWorkspace** для: finished game / выбранной сохранённой игры / last game из Главной / PGN/SAN/FEN text or file / ручного position editor / подтверждённой позиции из «Прогресса». Back source-aware («К игре», «К партиям», «К анализу», где реально уместно), сохранение selected ply и фильтров/scroll предыдущего экрана. При transient FEN нет fictitious opponent, game result или opening accuracy целой сыгранной игры.

**Главные зоны:** большая chess board слева, история ходов №/Белые/Чёрные справа с scroll и navigation beginning/back/forward/end. Подтверждённый source label и выбранный ply/позиция. Вторичные Undo/Reset временного варианта, flip, annotations, экспорт PGN только при фактической возможности. Исходная сохранённая PGN/line revision/notes не меняется от исследования бокового хода.

### 11.2. Без аналитики (кадр UX-12)

Верх: реальное название партии, дата/дебют/score если известны, Back и вторичный «Экспорт PGN». Середина: **две зоны**, без третьей постоянно пустой области. Одна крупная доска и история. Спокойное **«Оценок нет / Анализ ещё не выполнялся»** и одна понятная **«Проанализировать Stockfish»**, если saved game и safety разрешает. При только что открытом внешнем PGN/позиции engine может уже анализировать автоматически; показать queued/running вместо второго start.

**Не выводить:** empty CP graph, фальшивую вертикальную evaluation bar 0.0, три «0 ошибок» как уверенность, основную «Разобрать ошибки (0)», пустую третью колонку. В safety-blocked состоянии UI скрывает прежде сохранённые опасные данные.

### 11.3. С аналитикой (кадр UX-13)

**Одна крупная board** сохраняется, появляются:
- **AdvantageBar**, вертикальная шкала рядом с доской, только при valid eval/safety allowed; orient score consistent white perspective и matte status;
- компактная сводка «Моя точность / Точность соперника», errors/inaccuracies/blunders «Я / Соперник», phase accuracy только с реальными sources/coverage, выбранный ход/SAN/score;
- **ReviewGraph** под доской/в сворачиваемой панели, CP vs **Δ** mode (сохранить переключатель), optional markers **только** по подтверждённым ошибкам, интерактивный click→exact ply; ноль, dark/light fill и mate semantics согласно §10.4;
- доступ к existing **«Ходы / Разбор / События / Заметки»**, critical moments, PGN export, ephemeral branch, реальные Lichess game links;
- **«Разобрать мои ошибки (N)»** только когда N>0 проверенных кандидатов текущей стороны и fresh safety. Нельзя делать упражнения по чужой FEN и назвать «моими».

**Реальный source PR44:** ui/game_review.py содержит GameReviewWorkspace, AdvantageBar, ReviewGraph, CP/Δ mode, error marker toggling, selection, ephemeral undo/reset, упражнение на ошибках, notes/events. Новая визуальная компоновка должна переиспользовать это; нельзя утратить полноценные графики ради упрощения компактного архива.

### 11.4. Границы auto/manual engine и статусы

**Локальный Stockfish запускается:**
- при **явном** «Анализ Stockfish» выбранной партии из архива;
- при **явном** «Проанализировать Stockfish» в Review, если не уже есть актуальный/идущий job;
- **автоматически** лишь при осознанном открытии **внешней** PGN/SAN/FEN или вручную расставленной позиции из §09 (after parse + fresh safety + installed/configured engine + user setting). Это новее старой спецификации, где было «открыть импорт = только view».
- **НЕ** при открытии Analysis landing, перемещении по архиву, hover, выборе табов, открытии GAME local, и **НЕ** как удалённый заказ cloud Lichess analysis.

**State flow:** preflight safety → queued → running (real X/Y if available) → ready/saved or transient result → failed/cancelled/blocked. If no denominator, no arbitrary %. «Остановить» только по supported backend cancel; «Пауза» только если coordinator реально умеет. При активной human Lichess игре либо неизвестной безопасности нет оценки/PV/hints/graph ни в тексте, ни в tooltip/cache/screenreader; engine не запускается. Механизм открытия внешней временной Review не должен создать запись якобы сыгранной собственной игры или смешать с чужим account.

### 11.5. Уже реализованную тренировку своих ошибок сохранить

Текущий GameReviewWorkspace имеет рабочий контекст **«Разобрать мои ошибки»** с действиями «Предыдущая ошибка», «Следующая ошибка», «Проверить», «Подсказка», «Пропустить», «Повторить без подсказки», «Вернуться к разбору». Не удалять этот usable workflow в ожидании будущего единого образовательного движка. Долгосрочно упражнения принадлежат «Обучению», но до реализации нового общего пути старый recovery путь должен быть по-прежнему доступен, без второй независимой проверки и с Fair Play. Результат упражнения не превращать автоматически в глобальное «Освоил навык 100%».
