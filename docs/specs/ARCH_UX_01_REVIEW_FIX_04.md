## RF4-01 · P1 — Progress: историческая лента и дебютные срезы не должны расширять выбранный источник и считать пустые runs

**Подтверждено чтением SHA:**
- `src/chess_coach/lichess/statistics.py::historical_timeline()` строит CTE `chosen` из выбранного источника, но делает `FROM games g JOIN account_games ag ... LEFT JOIN chosen ar ... WHERE` только по account/status/clock/side. При `analysis_source="lichess"` в месячную статистику попадают **все** партии аккаунта, даже Stockfish-only, без оценки и official-accuracy-only. `COUNT(analysis_status)` засчитывает `complete/partial` run **без CP/mate** как analyzed. В результате `personal_profile()["historical_timeline"]` расходится с исправленными `summary(analysis_source="lichess")`, `game_page` и Library; отображение реально используется в `StatisticsDialog` (история по месяцам).
- `opening_statistics()` при указанном источнике фильтрует `ar.source`, но не требует `analysis_run_has_position_scores(ar)`, поэтому classification-only/empty complete этого источника могут попасть в количество `games` и дебютные срезы.
- `game_page()` может выбрать `complete` с 0 scored, если других scores нет, и отдать `analysis_status="complete"`/источник при нулевом `scored_positions`. UI не должен называть это подтверждённым анализом; можно сохранить технический статус отдельно.

**Исправить:** в source-filtered аналитических срезах использовать единый набор **уникальных партий с current-revision scored CP/mate** по `current_scored_analysis_exists`. В `historical_timeline` не включать посторонние игры в отфильтрованную историю; если продуктово нужен исторический *общий* объём, показать его отдельным явно подписанным знаменателем, но не выдавать за фильтрованный набор. Поле `analyzed_games` в месячных строках должно считать только игры с реальными scores, без double count и без review-only. `opening_statistics` должна применять то же правило при выбранном источнике. Для безоценочных runs в `game_page` и UI оставить честное «оценок нет» независимо от технического `complete`; не терять classifications с правильным отдельным label. Источники `lichess-pgn`/`lichess-json` сохранить раздельно в БД, UI `lichess` — их union, param binding и account/color/period safety без SQL injection. При `analysis_source=None` общий historical W/D/L может учитывать все завершённые партии: не сужать его молча только до оценённых.

**Обязательные тесты на временной SQLite:** один аккаунт в одном месяце имеет 2 scored Lichess JSON, 1 scored Lichess PGN, 3 scored Stockfish-only, 2 classification-only Lichess, 1 empty-complete Lichess, 1 official-accuracy-only, 1 stale-line, 1 review-only (плюс соседний месяц/другой аккаунт). Проверить, что для `analysis_source="lichess"` совпадают distinct IDs/count между `search_games`, `summary`, `game_page`, `historical_timeline` и `opening_statistics` в **одном scope**; `historical_timeline.analyzed_games <= games` и равно числу scored Lichess, остальные источники не утекли. Пустой complete в `game_page` не отображается как usable evaluation. Для `analysis_source=None` W/D/L и общий объём остаются прежними; 0/0 имеет честный N/A. Test both white/black and review-only/cross-account, Qt видимые подписи.

## RF4-02 · P1 — исключить обращение statistics worker к уничтоженному QObject при закрытии окна

**Подтверждено не только отчётом Codex, но и полным логом Windows CI #250:** `tests/test_single_instance.py::test_distinct_profiles_can_run_independently` выдаёт `PytestUnhandledThreadExceptionWarning`: поток `chess-coach-statistics`, `src/chess_coach/ui/analytics_dialogs.py` строки около **709/711/713**, последовательно падает `self.loaded.emit`, `self.loaded.emit` в обработчике ошибки и `self.query_finished.emit` в `finally` с **`RuntimeError: Signal source has been deleted`**. Такой сигнал, исходящий из worker с захваченным `self`, небезопасен после разрушения Qt-виджета. `closeEvent` диалога умеет отложить закрытие при живом потоке, но уничтожение родителя/всего приложения обходит эту защиту; аналогичный путь есть у `opening_loaded/opening_finished`.

**Исправить первопричину, не подавлять исключение:** worker должен быть отвязан от времени жизни `StatisticsDialog`/C++ `QObject`; независимый thread-safe job/dispatcher со строго ограниченным жизненным циклом и generation/cancel token, либо безопасное управление ожиданием/остановкой workers при разрушении родителя через уже существующий background coordinator. Нельзя передавать в worker замкнутый Qt emitter диалога, когда объект может уничтожиться. Не выполнять SQL/сетевые операции в GUI thread, не блокировать Qt main loop бессрочным `join`, не ставить `try/except RuntimeError: pass` вокруг emit для маскировки гонки, не отключать warning и не переводить тест в xfail. Сохранить логическую отмену устаревшей выдачи, batch/coalescing, deferred close, смену аккаунтов и один источник данных; обеспечить отсутствие поздних callbacks в удалённую страницу.

**Обязательные тесты:** воспроизводимый barrier-controlled медленный fake `StatisticsService.summary/game_page/personal_profile` и `OpeningMatcher`; пока worker активен, закрыть отдельно dialog, родительское MainWindow, закрыть два профиля (сценарий `test_single_instance.py`), затем освободить barrier. Тесты проверяют отсутствие post-destroy emitter access, несохранение устаревших данных, освобождение worker handles и **ноль `PytestUnhandledThreadExceptionWarning`**. Прогнать релевантные тесты с предупреждениями потоков как errors и полный набор. Если внутри приложения принято ожидание workers на закрытии, оно должно быть ограниченным и безопасным (без zombie/daemon скрытого доступа к Qt).
