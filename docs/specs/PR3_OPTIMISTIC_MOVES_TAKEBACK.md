## 1. Дефект A — визуальный откат фигуры (P0 UX)

### Воспроизведение

В активной партии Lichess перетащить белую пешку e2→e4. На экране она появляется на e4, сразу возвращается на e2, а через 0.5–1 с после подтверждения сервером снова оказывается на e4, часто одновременно с ходом AI.

### Требуемое поведение

- После допустимого `MoveIntent` **немедленно отображать ожидаемое (optimistic) состояние** позиции, включая перемещённую фигуру, взятие, рокировку, en passant, превращение.
- Пока Lichess не подтвердил ход, он **не входит в авторитетную подтверждённую историю, постоянную SQLite-запись и PGN**. Не делать `push()` в authoritative `LichessGameSession.board` до подтверждённого серверного события.
- Одновременно показать ненавязчивый статус «Отправляем ход…» / «Ожидаем подтверждения…»; можно слегка выделить последний ожидаемый ход.
- Когда поток подтверждает тот же ход именно **на ожидаемом ply и префиксе**, заменить ожидаемое состояние подтверждённым **без скачка**; не начинать повторную анимацию уже отображённого хода.
- Если сервер явно отвергает ход, откатить optimistic overlay **один раз** и показать причину; при неоднозначной сетевой ошибке (`timeout` и т.п.) не откатывать/не отправлять автоматически повторно без синхронизации — запросить актуальное серверное состояние.
- Во время pending не разрешать второй обычный ход, не позволять нечаянно поставить premove «сам на себя», не ломать навигацию истории и ориентацию доски.
- Отказоустойчивость: при реконнекте новый серверный `gameFull` должен однозначно разрешать ожидание; дубликат событий не создаёт новую анимацию.
- Optimistic overlay — **производный снимок для рендеринга**, а не второй независимый источник истины. Сохранять разделение `BoardView` / `LichessGameSession`.

### Что исследовать в коде

Проверить цепочку `BoardView.mouseReleaseEvent → _make_interactive_move → MainWindow.on_move_intent → LichessGameSession.begin_submission → LichessService.send_move → _lichess_game_event → _refresh_online`. В частности, рендер сейчас берёт `session.board` (подтверждённую позицию) и `set_position(shown)` обновляет его при pending — это вероятный источник возврата. Не чинить путём «сразу считать ход подтверждённым».

## 2. Дефект B — Lichess takeback (P0 функциональность)

### Официальный API

- `POST /api/board/game/{gameId}/takeback/yes` — **предложить** takeback либо **принять** предложение соперника.
- `POST /api/board/game/{gameId}/takeback/no` — **отклонить** предложение соперника.
- `gameState.wtakeback` / `gameState.btakeback` — необязательные булевы поля, показывают, кто предлагает возврат. Для белого пользователя «предложил соперник» — `btakeback`; для чёрного — `wtakeback`.
- Отсутствующее поле интерпретировать как false при получении **полного актуального** `gameState`; не применять это правило к посторонним event types.
- Авторизация `board:play`.
- Если на сервере takeback запрещён (например, некоторые рейтинговые форматы), UI должен сообщать отказ, не изменять позицию локально.

Официальные исходники:  
https://github.com/lichess-org/api/blob/master/doc/specs/tags/board/api-board-game-gameId-takeback-accept.yaml  
https://github.com/lichess-org/api/blob/master/doc/specs/schemas/GameStateEvent.yaml

### UI

- Кнопка «Предложить вернуть ход» в активной партии, когда это допускает игровой контекст. Отправлять `yes` только по явному действию пользователя; не откатывать позицию после отправки запроса.
- Если пришёл запрос соперника, показать заметное, но ненавязчивое сообщение **«Соперник предлагает вернуть ход»** и кнопки **«Принять» / «Отклонить»**. Эти действия отправляют `yes` / `no` соответственно.
- Показать, что наше предложение ожидает решения соперника; не разрешать бесконечные повторные клики или дубли вызовов.
- В режиме, где сервер запрещает takeback, можно скрывать/отключать предложение или обрабатывать 400/403 с понятным уведомлением. Не утверждать поддержку takeback в любом контроле/rated.
- Если пришёл запрос во время pending move, корректно сериализовать действия и приоритет серверного состояния; не терять уведомление и не создавать конфликтующих локальных ходов.

### После принятия takeback

**Серверный `gameState.moves` может стать короче!** Прежнее правило «отбрасывать все события с более короткой историей как устаревшие» в данном сценарии **некорректно**.

Требуется:
- Отличать **легитимный подтверждённый takeback** от позднего устаревшего event. Не принимать произвольную укороченную историю без доказательств (состояние pending takeback, соответствующие флаги/сигналы, resync через свежий gameFull/stream). Длина ходов сама по себе не критерий свежести.
- Учитывать, что takeback может убирать один или больше полуходов в зависимости от правил Lichess; не зашивать число хода без проверки.
- Сбросить/согласовать `pending_uci`, ожидаемый ply, очередь premove и визуальный optimistic overlay.
- Восстановить позиции, SAN-историю, актуальную очередь хода и часы исключительно из нового подтверждённого серверного состояния.
- **SQLite upsert и PGN должны отражать новую укороченную историю**, а не хранить отменённые ходы; при этом ID партии и дата создания сохраняются.
- После отклонения заявки/обычной следующей серверной новости старая заявка исчезает из UI.
- При reconnect с неизвестным результатом takeback выполнить безопасную повторную синхронизацию до разрешения дальнейшего ввода.

### Дополнительные случаи

- Запрос от соперника при своём и чужом ходе.
- Наша инициатива → соперник принял, отказал или не ответил.
- Отмена/истечение доступности заявки.
- Takeback в партии с Lichess AI, если API разрешает; **не требовать тестирования AI takeback как основного сценария** из-за возможных особенностей/ограничений Lichess. Главный ручной тест — casual-партия с другом.
- Не перепутать `draw` и `takeback`: разные поля и разные endpoints.

## 4. Ручная приёмка Windows

Владельцем уже проверено, что OAuth, партия против AI и базовый сценарий игры с другом доступны, но **не подтверждены** все граничные состояния. Codex должен предоставить следующие шаги и при наличии доступа к аккаунту/Windows выполнить их только с разрешения:

1. Открыть приложение, войти в Lichess.
2. Запустить **casual** игру против AI. Ход e2e4 должен оставаться на e4 без скачка; после серверного ответа всё синхронно.
3. С другом в браузере провести casual-партию; друг предлагает takeback, Chess Coach показывает запрос с кнопками «Принять / Отклонить».
4. Подтвердить takeback; проверить доску, журнал SAN, часы и сохранённый PGN.
5. Отправить предложение возврата из Chess Coach и убедиться, что друг видит его в браузере.
6. Отказать в предложении; позиция остаётся прежней.
7. При возможности проверить разрыв/восстановление соединения, отсутствие дублей и сохранение данных.
8. Повторить обычную игру для проверки premove; стрелки правой кнопкой **не менять**.

Зафиксировать отдельно: `Windows GUI: PASS/FAIL/NOT RUN`, `Lichess AI optimistic move: PASS/FAIL/NOT RUN`, `Lichess friend takeback: PASS/FAIL/NOT RUN`.
