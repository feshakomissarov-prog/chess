## План проверок и стоимость CI

> Этот раздел нельзя опускать. Три уровня из [CC-VERIFY-01](../process/VERIFICATION_PROTOCOL.md) применяются последовательно. Подставить **точные** команды/тесты этой задачи, не оставлять одни общие фразы.

### Уровень 1 — быстрый адресный

- **После чего:** каждая небольшая логическая правка/группа строк до коммита.
- **Команды:** `git diff --check`, `python -m compileall -q <изменённые файлы>`, `python -m pytest -q <tests/test_...py::test_...>`.
- **Если UI:** один целевой Qt/native smoke в безопасном изолированном окружении, только релевантный экран/размер.
- **Решение:** устранить все обнаруженные сбои до L2. Не гонять полный pytest и все DPI на каждую мелкую правку.

### Уровень 2 — тематическая регрессия

- **После чего:** завершён связанный набор исправлений.
- **Команды/сценарии:** `python -m pytest -q <список смежных тестов>`; native screenshots <релевантные размеры и состояния>; явные негативные проверки <перечень>.
- **Решение:** подтвердить корректность всего изменённого модуля, а не только исходного happy path.

### Уровень 3 — полный exact-head CI

- **Когда:** только после завершения реализации, до передачи на финальную приёмку.
- **Проверки:** полный Windows pytest, compileall, offline window smoke, согласованная native visual матрица, другие требования задания на **одном exact HEAD SHA**.
- **Доказательства:** HEAD SHA, GitHub run URL, job-статусы, ссылка на screenshots, результаты пользовательских ручных проверок отдельно.
- **Повтор:** только если после L3 меняются исполняемый код/тесты/ресурсы, либо выявлен дефект. `docs-only` коммит без влияния на код не требует бессмысленного нового полного CI; указать два SHA.
