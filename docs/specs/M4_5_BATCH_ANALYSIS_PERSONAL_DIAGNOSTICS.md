## 0. Продуктовая цель

Использовать уже загруженные личные партии и задачи, чтобы отвечать на вопросы:
- Где у владельца больше всего потерь качества: дебют, миттельшпиль, эндшпиль, определённые позиции и типы решений?
- В каких дебютах (ECO, название, сторона) низкий результат или повторяются конкретные ошибки? Насколько вывод устойчив с учётом количества игр, соперников и контроля времени?
- Сколько реально подтверждённых зевков, ошибок, неточностей, хороших и лучших ходов было *в каждой партии* и во всём архиве?
- Что изменяется со временем, какие характерные позиции служат доказательствами, какова доля проверенных ходов и чего программа пока не знает?

**Конечный пользовательский сценарий:** после единожды явного включения массовой обработки владелец видит счётчики «всего завершённых / с Lichess / со Stockfish / в очереди / частично / ошибок», прогресс и настройки вычислений. Приложение постепенно вычисляет недостающий анализ локально, загружает уже имеющиеся серверные оценки, сохраняет результаты, а статистика обновляется по мере готовности. Прерывание/закрытие не уничтожает прогресс.

**Не считать выполненным:** просто вызвать Stockfish для одной партии, построить усреднённый ACPL или назвать все потери > 200 cp «тактическим зевком». Это уже частично было в M4, а здесь нужна система на весь архив.

## 1. Инвентаризация и неизменяемые границы

Перед новым кодом Codex проверяет текущее состояние `main`:
- `src/chess_coach/lichess/analysis.py::CompletedGameAnalyzer` уже умеет один локальный UCI-анализ и сохраняет `analysis_runs/position_assessments/move_classifications`.
- `src/chess_coach/lichess/repository.py` содержит историю партий, ревизии, `lichess-pgn` оценки, аккаунты, фазовые границы и кэш анализа.
- `src/chess_coach/lichess/statistics.py` уже рассчитывает базовую сводку и фильтры; `window.py` уже показывает отчёты.
- `src/chess_coach/lichess/api.py::stream_user_games` уже запрашивает `evals=true`, `accuracy=true`, `opening=true`, `division=true`.
- PR #26 добавил фоновые синхронизации, но **массовой очереди Stockfish ещё нет**; не дублировать сервис и не делать вторую SQLite.

Собрать «паспорт данных» без личных содержимых в логах:
- Все игры; завершённые; `final_sync_pending`; неподдерживаемый вариант; отсутствующая/некорректная линия; текущая ревизия.
- По каждому `game_id+line_revision+line_hash`: наличие и плотность `lichess-pgn`, локального Stockfish и пользовательских классификаций; число оценённых **собственных** ходов.
- Охват по аккаунтам, цветам, категориям времени, ECO (в т.ч. неизвестным) и датам. Нельзя объявлять «есть анализ», если сохранилась только 1 оценка из 60 ходов.
- Результат — текстовый отчёт со счётчиками/проверенными источниками и тестовый набор синтетических партий. Не загружать личные PGN и SQLite в GitHub/CI/чат.

## 2. Lichess: импорт готового анализа, а не недокументированный массовый заказ

**Важное ограничение:** [официальная публичная API](https://lichess-org.github.io/api/) документирует `GET /game/export/{gameId}`, `GET /api/games/user/{username}` с `evals/accuracy/opening/division` и `GET /api/cloud-eval` для отдельных кэшированных позиций. **Публичный документированный API для массового POST-заказа серверного анализа партий не подтверждён.** Не использовать скрытые веб-эндпоинты, браузерные обходы, автоматические клики и обход ежедневных лимитов. Если в будущем появится документированный официальный метод и будут права/квоты — отдельная согласованная задача.

Реализовать:
- В рамках существующей автосинхронизации сохранять свежие оценки и точность, пришедшие в официальном экспорте.
- Режим **«Проверить появившийся анализ Lichess»** для выбранных старых игр без достаточных `lichess-pgn` оценок: ограниченная очередь `GET /game/export/{gameId}` (или документированного bulk-export), явная настройка частоты/лимита, продолжение, checkpoint, никаких повторных запросов на каждую перерисовку. Не запускать автоматический массовый обход сразу после открытия приложения; только после включения пользователем.
- Отличать «серверный анализ ещё отсутствует» от «ошибка API», «доступно только частично», «запрос запрещён», «устаревшая ревизия». Не превратить отсутствие server eval в бесконечные запросы.
- Сохранять исходную оценку Lichess отдельно от `stockfish`, с source, датой обнаружения, имеющейся глубиной и coverage; официальный `accuracy` хранить отдельно.
- Одно сетевое обращение одновременно во всём Lichess-клиенте, уважать HTTP 429 (минимум рекомендуемая пауза, server Retry-After если длиннее); новые фоновые проверки не мешают ходам/сессии.
- `cloud-eval` — только *кэш* отдельных позиций, не гарантия анализа целой партии; при первом этапе не использовать его для подсчёта полного game coverage и не выдавать за полноценный Lichess server analysis.

## 3. Stockfish: персистентная массовая очередь

Вынести выполнение из одиночной GUI-команды в отдельный queue/service над существующим `CompletedGameAnalyzer`.
- Таблица заданий/состояния (миграция SQLite через `user_version`), уникальность по `account_scope/game_id/line_revision/line_hash/engine_fingerprint/settings_hash` либо обоснованной более узкой идентичности. Одна игра, принадлежащая двум аккаунтам, не должна анализироваться дважды без нужды.
- Статусы `queued/running/complete/partial/paused/cancelled/failed/stale`, время попытки, причина ошибки, количество обработанных позиций, версия/параметры. После crash `running` становится `paused`/возобновляемым.
- Выбор кандидатов: только завершённые стандартные партии, с проверенной линией, без `final_sync_pending`; по умолчанию только игры **без подходящего полного локального запуска**. Наличие Lichess eval не запрещает отдельный Stockfish-анализ, если политика владельца — «локально проверить всё».
- Один явный запуск «Проанализировать недостающие» с опциями: весь архив/диапазон дат, игры без Stockfish/все, CPU threads (начально 1), hash, nodes/depth/time на позицию и фоновый режим; возможность выключить автоматическое продолжение.
- Параллельно *по смыслу*, не безлимитно по ресурсам: **один** управляемый UCI worker и **одна** ограниченная очередь получения готовых Lichess-оценок, сериализованный сетевой API и единый SQLite writer.
- Не пересчитывать кэш при повторном открытии; хранить engine binary fingerprint, depth/nodes, версии алгоритмов. Профили `быстрый` и `подробный` с чётко указанным бюджетом; стоимость вычисления оценить на небольшой синтетической выборке и показать пользователю, без обещаний конкретных часов.
- Пауза, отмена, закрытие приложения и повторный старт не должны оставлять `stockfish.exe` или полузаписанные `complete` runs. Отсутствующий бинарник — понятный статус, без автоскачивания.
- **Fair Play:** если есть активная собственная онлайн-партия с человеком либо неопределённость в проверке безопасности, не запускать и немедленно безопасно останавливать local engine. Проверять при возобновлении/перед каждой игрой/при смене аккаунта/на событиях живой игры; не показывать оценки в live UI. Нельзя ограничиться проверкой только при нажатии «старт».
- Если хотите промежуточную запись оценок — отдельно проектировать atomic partial segments, которые никогда не учитываются как полный и сравнимый analysis run. Допустимо начать с per-game commit, если очередь восстанавливает прогресс хотя бы **между** партиями, не теряет завершённые игры и это явно показано.

## 4. Единая методология шахматных метрик (при сохранении источников)

Версионированный `ClassificationPolicy`: детерминированный, тестируемый без движка.
- Класс/потеря хода считаются со стороны **того, кто ходил**; оценка до/после при сопоставимых условиях, невозможность оценки/неодинаковая глубина → `unknown` или пометка качества. Движковые ошибки/шум и разные поисковые бюджеты не должны автоматически давать ложные зевки.
- `mate` считать отдельным типом исхода/вынужденного матового изменения, **не подставлять фиктивный CP для усреднения CPL**. Учитывать кратность позиций/повторные линии; формулу, пороги и версию фиксировать в документации и данных.
- Детерминированные категории `blunder/mistake/inaccuracy/good`, а **best / сильный ход** — только при верификации best-PV на позиции до хода или другой явно определённой и проверенной методике. «Brilliant»/«гениальный» и «тактический мотив» не присваивать только по CP; официальные Lichess метки не выдавать за рассчитанные Chess Coach.
- Для `lichess-pgn` могут быть оценки позиций, но не PV. Из них можно рассчитать *нашу* классификацию при достаточном coverage с `classification_source=chess-coach-from-lichess-evals` и версией; нельзя заявлять «официальные Lichess зевки» без их данных.
- Не усреднять Lichess/Stockfish как одно число, не смешивать `engine_version/settings/classifier_version` в однородном тренде. При наличии двух запусков показывать оба и явное правило выбранного источника для главной статистики.
- Отдельно оценивать **собственные ходы** и **ходы соперника**, исход игры и rating/context. Показатели `per_game`, `per_100_assessed_own_moves`, `per_100_games` и `coverage` должны иметь разные поля, не делить на все ходы при частичном анализе.
- Результаты, анализ/accuracy, фазы и метки `unknown` — полноценные статусы, не нули.

## 5. Дебюты и этапы партии

- Основа идентификации — имеющиеся `opening_eco/opening_name`, `game_phase_boundaries`; если Lichess неизвестен, показывать `unknown`, не придумывать ECO по одной неточной позиции. Локальная легальная база ECO — опциональная после оценки лицензии/атрибуции.
- Выделять имя/семейство/вариант по доступному проверенному источнику, учитывать транспозиции. Один и тот же дебют за белых и чёрных — **две независимые картины**.
- По дебюту: игры, W/D/L, rating соперника/игрока (если есть), частота, число собственных оценённых ходов, errors per 100, CPL, первые критические позиции и повторяющиеся собственные ошибки. Не объявлять слабостью дебют с 1–2 партиями.
- По фазе: `opening/middlegame/endgame/unknown` с явным источником границ; если Lichess `division` нет, не назначать этапы слепо по «10/30 ходу». Альтернативные собственные эвристики — лишь отдельный версионированный модуль с тестами.
- Дополнительные срезы: контроль времени, период, цвет, диапазон рейтинга и разница рейтингов, длина партии, финальный исход, доступное clock-pressure где реально известен.

## 6. Личная диагностика на нескольких партиях

Страница «Мои шахматные слабости» с **обоснованными гипотезами**, а не диагнозами:
- Группировка по ECO/семейству, фазе, стороне, категории решения, повторяющейся позиции/структуре *там, где метод достоверно существует*. Не выдавать «я часто зеваю вилки» без настоящего детектора вилок и проверенных примеров.
- Для каждого вывода: `N игр`, `N собственных оценённых ходов`, `N ошибок`, `частота`, `coverage`, источник и версия вычислений, диапазон даты, ссылка на **конкретные партии и ply** с доской.
- Минимальная выборка для автоматического ранжирования: предварительно `>=10 анализированных игр` и `>=30 оценённых собственных ходов` *на сегмент*; пороги конфигурируемы и валидируются на фикстурах. Меньше — «недостаточно данных», но подробности доступны.
- Сильный сравнительный сигнал подтверждать контекстом (цвет/контроль/соперники), а не просто плохим W/D/L; выводы формулировать как «наблюдается повышенная частота потерь», не «причина доказана».
- Показывать **сильные стороны** аналогично слабостям, контрольные группы и неизвестные места. Существующую историю Lichess Puzzle Activity показывать отдельно как независимое свидетельство темы, а не автоматически объяснять ею причины игровых ошибок.
- Подготовить машиночитаемые `evidence` записи для будущих упражнений/ИИ-тренера; на данном этапе нет LLM-вызовов и генерации учебных задач.

## 7. Интерфейс и продуктивность

- Новая зона «Анализ архива»: сколько завершённых игр найдено, сколько пригодны, сколько с Lichess/Stockfish/обоими/без оценки, сколько в очереди, сколько ошибочных, сколько новых ходов оценено. Ход обработки, пауза/возобновление/отмена, ограничение нагрузки, видимый отказ и вариант действия.
- «Моя статистика»: обзор W/D/L, качество ходов, динамика, распределение ошибок по фазам, **дебюты с возможностью сортировки**, drill-down к соответствующим партиям/конкретным ходам, фильтры по аккаунту/цвету/контролю/периоду/источнику.
- «Мои слабости»: максимум 3–5 главных находок, рядом формула и N/cоverage, сортировка/переход к исходным позициям, кнопка «Недостаточно данных»/«Не подтверждено» вместо ложной уверенности.
- UX полностью асинхронен; 10k+ партий — bounded pagination/SQL aggregations и кэш с `statistics_revision`, без загрузки всего `game_moves` в Python при каждой смене фильтра.
- Без графиков ради графиков: каждый график должен отвечать на один шахматный вопрос и позволять провалиться к доказательствам.

## 9. Контракт работы Codex: один большой запрос, несколько независимых PR

**Порядок подблоков строго последовательный**. Codex читает `AGENTS.md`, `ROADMAP.md`, этот документ, затем актуальный код. Не просит новый большой документ на каждый подблок:
1. **M4.5-A — Data inventory + contracts.** Аудит имеющихся оценок/владения/ревизий, отчёт о coverage, SQL/fixture tests, версионированные определения состояний; никаких реальных запросов.
2. **M4.5-B — Lichess eval hydration.** Дозагрузка *готовых* оценок по официальному API и контроль позднего появления, bounded/checkpoint/429, fake transport tests; без недокументированных server analysis requests.
3. **M4.5-C — Persistent local engine queue.** Миграция, отбор игр, настройки/ресурсные лимиты, пауза/возобновление/cancel/crash, live-human guard, fake UCI tests. Пользовательская машина/Stockfish executable — отдельная E2E приёмка.
4. **M4.5-D — Reliable classifications and per-game report.** Единый классификатор, best/strong, CP vs mate, версии источников, пред- и постходовые оценки, проверки на синтетических позициях и данных Lichess.
5. **M4.5-E — Opening/phase analytics.** ECO и результаты с чёткими знаменателями, multi-account correctness, рейтинг/цвет/контроль, SQL performance и тесты на 10k+ партий.
6. **M4.5-F — Evidence-based weaknesses + UX.** Гипотезы с N/coverage, примеры/ply, экраны анализа и статистики, подготовленные записи для M5/M6. Без псевдо-тактических меток.
7. **M4.5-G — Stabilization.** Восстановление после сбоя/изменённой линии, проверка ограничений/лицензий, обновление документации, итоговые команды только для контролируемой проверки владельцем.

**Каждый PR:** от свежей базы, ограниченный diff, до слияния полный Windows Python 3.12 CI + fake Lichess/engine + Qt offscreen, `compileall`, тесты миграций, список реально пройденного и НЕ ЗАПУСКАЛОСЬ; без merge/force-push без отдельного решения владельца. После каждого блока можно остановиться и иметь работающее приложение.

## 10. Границы безопасности, качества и критерии финальной приёмки

**Не делать без отдельного разрешения:** запуск на личной SQLite, реальный массовый Stockfish UCI на компьютере владельца, API-потоки на личном OAuth, скрейпинг Lichess, массовый заказ серверных анализов, скачивание engine/model, любые обращения к облачному ИИ. Автотесты — изолированные фикстуры.

**Перед реальными миграциями** владелец отдельно решит об обновлении локальной версии и проверенной SQLite-копии (предыдущий техдолг #5). Личную базу нельзя перезаписывать или удалять, WAL нельзя копировать неконсистентно.

**Acceptance gates:**
- На фикстуре с играми без eval/частично с Lichess/полностью со Stockfish показываются правильные отдельные счётчики игр, позиций, источников и `unknown`.
- Очередь на 0/1/100/10k игр завершает или ставит задачи предсказуемо, повторный запуск не добавляет дубли и не теряет уже завершённые анализы.
- Отмена/закрытие/переход в live human game останавливают движок и не оставляют false-complete runs; reconnect/account switch/неизвестный статус — fail-closed.
- Два источника и разные версии не смешиваются в одном знаменателе без выбранной политики. 50cp потери у белых и чёрных оцениваются симметрично; mate не искажает CPL. Частичный Lichess eval не маскируется под полный.
- Открытия/дебюты/фазы считаются по реальному аккаунту владельца и относятся только к его ходам; одинаковая игра для двух связанных аккаунтов не удваивается в одном выбранном профиле.
- На проверенных синтетических 10–20 партиях суммы W/D/L и меток по каждой фазе/дебюту совпадают с ручным подсчётом; недостаточная выборка даёт «недостаточно данных».
- UI отвечает во время работы очереди; при клике на статистическую находку открывается конкретная партия и правильный ход, без необходимости пересчитывать график.
- Ни один новый механизм не запускает движок в активной человеческой онлайн-партии и не генерирует скрытые OAuth/сетевые операции.
