## 1. P0 приёмки: HOME — СТРОГО НЕ БОЛЕЕ 1 СЕКУНДЫ

**Факт владельца 11.11:** база реального профиля содержит **3321** завершённую партию, последняя наблюдавшаяся сводка: accuracy **82.8%**, puzzle rating **1917**, три последних партии имеют достоверные даты и показатели. Несмотря на неоднократные исправления PR #46, **после запуска приложения, включая запуск после перезагрузки ПК, фактические числовые значения появляются долго**. Значения 3321/82.8%/1917 — историческое наблюдение, не константы, не данные для подмены расчёта и не ожидание после будущих партий.

### 1.1. ЖЁСТКИЙ пользовательский контракт, НЕ P95 и НЕ «целевой SLA»

**Для существующего профиля, у которого статистика уже хотя бы один раз была рассчитана и подтверждённо сохранена:**

- **T0** = первый видимый кадр главного окна Chess Coach в Windows (не конец запуска отдельно вызванного JSON helper). **T1** = момент, когда **видимые Qt widgets Home действительно показывают** числовую завершённую сводку: completed count, accuracy с известным источником, puzzle rating и сохранённые проверенные данные последних трёх партий (если они существовали). **T1 − T0 ≤ 1000 ms.**
- **Каждый проверяемый штатный запуск**, включая холодный после Windows reboot, второй запуск без изменения данных, новую партию между запусками, offline/Lichess not-ready, должен выдержать **≤1.000 секунды** при наличии совместимого ранее рассчитанного сохранённого snapshot. **Один воспроизведённый штатный запуск >1000 ms = FAIL / НЕ ПРИНЯТО.** Не подменять этим p95, среднее, время загрузки одного count или чистое время `cache.load()`.
- Первое появление `3321` при `Точность —`/`Рейтинг —`/`Сверяем…` — **НЕ T1 и НЕ PASS**. Если после мгновенного показа last-good запускается тяжёлый aggregate — допустимо, **но он не имеет права отнимать уже показанные числа**. Если snapshot устарел, отображать последнее подтверждённое значение и возле затронутого блока честное `Сохранено · обновляется` + отметку времени/источника; никогда не выдавать это за актуальный пересчёт.
- **При первом в истории запуске совершенно нового профиля, для которого объективно никогда не существовало рассчитанной сводки**, нельзя выдумывать accuracy/rating; это единственное содержательное исключение из требования мгновенного показа числа — сразу показать честное `Ещё не рассчитано`, синхронизировать/рассчитать в фоне и затем **обязательно** устойчиво сохранить, чтобы второй запуск подпал под ≤1 сек. При существующем профиле с полной историей отсутствие кэша после обновления — ошибка жизненного цикла/миграции, а не обычное «первый запуск».
- Не маскировать нарушение времени splash-экраном, искусственным `show()` после полной базы, фальшивыми текстами или ручной подстановкой данных в тест. Дополнительно измерять `process-start→first useful paint` как диагностическую метрику, но **точкой приёмки** остаётся первое видимое окно.
- При Play↔Home и account selection не очищать хорошую сводку; пользовательский UI не должен замерзать. Отдельный gate **UI loop stall >100 ms = FAIL** для штатного warm-navigation сценария, где всё уже рассчитано.

### 1.2. Обязательная архитектурная проверка, не «положить ещё один JSON»

- Найти **точную** причину промаха на реальном профиле: есть ли B на диске, какой scope/account, версия формулы, какой source revision, когда читается до/после auth, что делает архив sync, пишет ли другой worker, пропускает ли `save_tier_b`, случаются ли повторные перезапуски запросов. Нельзя утверждать RCA только по одному test на пустой БД.
- Нужен **last-known-good с независимым сроком жизни от очередного SQLite revision** и refresh. Не терять B от нового Tier A, no-op UPSERT, затрагивания другого аккаунта, изменений unrelated puzzle/analysis facet. Данные profile scoped, atomic, validated и migration-aware. Неполная запись, сломанный первичный JSON, повреждённая `.previous`, read-only disk и SQLITE_BUSY не должны уронить GUI или уничтожить единственную проверенную копию.
- Чтение/сбор Home на первом показе не блокирует Qt SQL, JSON, HTTP, `future.result()`, file `flush/fsync` или большие вычисления. Можно заранее подготавливать компактный last-good до открытия окна **без искусственного скрытия окна ради заезда в лимит**; правильный путь — сохранять достаточно данных при изменении/закрытии приложения и быстро загружать лёгкий scope. Никаких полных PGN/PV массивов в UI cache.
- Инвалидация отслеживает реальные зависимости и source provenance; разграничить count/последние партии, accuracy, рейтинг задач, метрики отдельных карточек. Если новая партия вошла в последние 3, сохранить данные двух неизменившихся game_id, не приклеивать данные удалённой третьей к новой. Источник, сторона, line revision и точность сверяются.
- Ошибка фонового aggregate не скрывает ранее показанные last-good значения (TD-02). Честно показывать inline-ошибку только у обновления.

### 1.3. Обязательная приёмочная матрица (RED→GREEN)

1. **Реальные ненулевые данные** 3319/3321/3322 и 10 000 synthetic completed games (с ненулевой accuracy и puzzle rating, разными тремя карточками), а также отдельный account B. Не подменять достоверную оценку вымышленными цифрами: seed должен использовать настоящую поддержанную структуру исходников.

## 4. MAT-01: НАГЛЯДНЫЙ МАТЕРИАЛЬНЫЙ БАЛАНС ВО ВРЕМЯ ПАРТИИ

**Новое явное требование владельца:** во время партии виден материал **с точки зрения человека**. Если я за белых и забрал чёрную пешку — **`+1`**; если забрал пешку (+1), а у меня забрали слона (−3), итог **`−2`**. И наоборот для человека за чёрных.

**Формула для стандартных шахмат:** пешка=1, конь=3, слон=3, ладья=5, ферзь=9, король в сумме=0. `white_total = Σ(white pawns/knights/bishops/rooks/queens values on authoritative board)`; `black_total` аналогично; `material_white = white_total − black_total`; `material_player = material_white`, если человек играет белыми, или `−material_white`, если чёрными. **Это разница имеющегося материала, НЕ engine evaluation, НЕ выигрышная вероятность и НЕ обещание стратегического преимущества.**

**UX-контракт:**
- В едином игровом workspace рядом с доской/именами/партией компактно показывать `Материал: +1`, `Материал: −2`, `Материал: 0`, с явной подписью «за вас» или «Белые − Чёрные». Не обозначать как `Stockfish +1.0`; не использовать cp/pawn evaluation, PV, лучшие ходы, подсказки, слабости и т.п.
- Можно дополнить иконками побитых фигур, но без визуального шума и изменения утверждённой сетки. Не требует загрузки Stockfish, не запускает движок вообще; работает офлайн, в локальной партии, против Lichess AI и в **онлайн-партии против человека**, поскольку вычисляется исключительно из подтверждённого расположения фигур и не анализирует качество хода. Все существующие ограничения live engine остаются.
- Обновление **после подтверждённого хода/позиции** и после просмотра исторического ply; не считать speculative premove, ещё не принятый Lichess move или несинхронизированную доску подтверждённым фактом. При reconnection/correction брать authoritative board, сбрасывать устаревшее значение. Смена account/game и смена ориентации доски не должны менять знак для того же человека.
- Для локальной свободной доски за обе стороны — однозначно подписать `Белые − Чёрные`; для завершённой исторической партии можно показывать относительно достоверной стороны игрока. Если сторона не установлена — `Белые − Чёрные` или явное `Сторона неизвестна`, не выдумывать чью-то перспективу.
- Превращение пешки увеличивает на доске стоимость соответствующей фигуры (например pawn→queen = прирост +8 при прочих равных); en-passant, взятие королём, underpromotion, undo, replay, загруженный FEN учитываются корректно. На неизвестной/неподдерживаемой variant position без корректного стандартного board model — честно `н/д`, без ложных цифр. Сумма в середине партии может быть не равна числу побитых фигур в случае произвольного FEN — UI правильно называет её **балансом материала**, а не буквально счётчиком взятий.

**RED→GREEN tests:** стартовая доска 0, белые съели пешку +1, белые пешку +1 и потеряли слона −2, чёрная перспектива меняет знак, конь 3/слон3/ладья5/ферзь9, en passant, underpromotion, takeback, replay, server correction/late packets, abort move, смена стороны/аккаунта/ориентации, local free board vs live human. Stub Stockfish/engine manager обязан подтвердить **0 новых вызовов движка** от MAT-01. Fair Play live-human regression обязателен.

**Цель пользователя:** скачать **один `ChessCoach-Setup.exe`**, установить привычным мастером Windows, увидеть ярлык, открыть и играть. Не ставить Python, pip, venv, Qt, C++ библиотеки или Stockfish вручную. Обновление через понятное уведомление с новой версией и перечнем изменений; удаление/переустановка Windows штатным способом без потери личных данных. Реализация не должна превратиться в десяток регулярно сопровождаемых скриптов и сторонних серверов.

### 6.1. Рекомендуемая небольшая архитектура

- **PyInstaller `onedir`** — приложение, строго фиксированный CPython, PySide6/Qt, python-chess, chess-widgets, keyring, native libs и ресурсные файлы из него же; пользователь **НЕ устанавливает Python отдельно в систему**. Не использовать массовый `pip install` во время setup или после запуска. Не делать `onefile` PyInstaller ради идеи «один EXE»: один файл для человека — это *инсталлятор*, а внутри программы лучше быстро запускаемый, диагностируемый `onedir`.
- **Inno Setup** — один Windows Setup.exe, стандартный ярлык, удалить через «Установленные приложения», один стабильный `AppId` между версиями, штатное обновление поверх имеющейся установки. Предпочтительно установка per-user без обязательного UAC, `Program Files`/per-machine — только при явном выборе.
- **GitHub Releases** (без своего update-server) — опубликованные версии, release notes на русском, установщик и manifest хэшей. CI автоматически собирает на **Windows runner** из утверждённого SHA; staging artifact не считается опубликованным релизом. Добавить release playbook, не создавать GitHub release или публиковать installer без разрешения владельца.
- Первая цель — **Windows x64 10/11**, минимум поддерживаемого Windows/DPI сформулировать после smoke. Никакого обязательного облачного аккаунта или новых серверных служб.

### 6.2. Фиксированные зависимости и гарантия воспроизводимости

- Сейчас `pyproject.toml` использует `version = "0.1.0"`, `chess-widgets==0.5.0`, но `PySide6>=6.10.1,<7`, `python-chess>=1.999,<2`, `keyring>=25,<27` — **диапазоны**, не полностью pinned. Для выпуска создать **release lock** с точными версиями и SHA-256 **всех прямых и транзитивных** зависимостей (включая build tools), и фиксировать CPython patch version/architecture, PySide6/shiboken/Qt, PyInstaller, Inno Setup. `pip --require-hashes` или эквивалентный проверяемый offline wheelhouse; `pip install -e .` в пользовательском установщике запрещён.
- Реальная версия программы должна иметь **единый источник истины** (packaging metadata/build manifest): SemVer, channel stable/beta, commit SHA, build date, schema compatibility, Stockfish version + digest. Одинаково отображается в UI «О программе», filename, Windows install record и release manifest. Не называть CI commit приложением версии `0.1.0` без релизной процедуры.
- Сборка воспроизводима в смысле фиксированных входных артефактов и документированного процесса (bit-for-bit identical необязательно, если PE timestamps и подписи меняются); output installer имеет SHA256, состав/SBOM, проверку оригинального источника.

### 6.3. Stockfish обязательно из НАШЕГО setup, нужной нам версии

- В текущем коде [`engine_manager.py`](https://github.com/feshakomissarov-prog/chess/blob/main/src/chess_coach/engine_manager.py) уже **PINNED** `STOCKFISH_RELEASE="19"`, `STOCKFISH_ASSET="stockfish-windows-x86-64-universal.zip"`, URL official-stockfish `sf_19` и SHA256 **`3c8bf1f9ea66a09350a40df4f632288285ac206d99f33ab5842c408fc30b48a7`**. Проверить их заново на release gate; не заменять автоматически «последним» Stockfish по GitHub search.
- В инсталлятор **включить копию однозначно проверенного Stockfish 19 x86-64 universal** с нужными NNUE/лицензией/атрибуцией, скачать/verify **на CI**, не на машине пользователя (чтобы setup работал OFFLINE). Идентифицировать SHA-256 и официальный source tag, не изменять бинарник без новых digest/source notices.
- После установки Chess Coach **сам находит** встроенный движок по известному относительному пути install dir, **сверяет его версию/hash и UCI `uci/isready`** (без блокировки GUI) и выставляет его как verified default **только если пользователь ещё не выбрал и не проверил собственный Stockfish**. Не перезаписывать существующие `stockfish_path`/`stockfish_verified_path`, ручной engine path и персональные настройки; при сломанном/удалённом bin показать восстановление/repair, а не тайно использовать непроверенный исполняемый файл с PATH. Нужен тест выбора portable/custom path и миграции старой конфигурации.
- При обновлении приложения новая версия движка только после **согласованного обновления release manifest**, а не из-за «появился Stockfish 20». Текущие/старые `analysis_jobs` и `engine_version` не подменять новым движком; источник оценок сохраняется.

### 6.4. Обновления: версии, что нового, явное согласие, безопасная установка

**Минимальный поддерживаемый сценарий в первую очередь:**
1. «Настройки → О программе / Обновления»: `Установлена Chess Coach X.Y.Z`, `Проверить обновления`, и безопасный non-blocking запрос к **официальным GitHub Releases repo**. Показывать `Доступна X.Y.Z`, список изменений на русском (релизные заметки), размер, дату, ссылку на release; канал stable (не draft/prerelease), beta — только opt-in. При offline/429/timeout ошибка **не блокирует игру**. Кэшировать результат/ограничивать частоту.
2. **При нажатии пользователя** `Скачать и установить`: загрузить строго allowlisted release asset по HTTPS, с bounded size/time/retries; проверить `SHA-256` из доверенного манифеста и **подпись издателя или иной независимо проверяемый криптографический источник доверия**. Хэш, полученный с того же полностью скомпрометированного канала без подписи/доверенного ключа, **не является самостоятельной защитой**; release security review обязателен до автоустановки. Не исполнять случайный `.exe` по redirect, из чата, или из пользовательской строки.
3. Проверить совместимость версии/схемы, предупредить о backup/migration; если идёт live human game, challenge, batch analysis или несохранённые данные — **не начинать установку**. Предложить `Позже`. После завершения/закрытия всех workers и SQLite handles отдельный trusted installer заменяет program files, приложение перезапускается; никаких force-kill и overwrite running exe.
4. **Fallback:** если signing/release infrastructure пока не готова, UI честно предлагает `Открыть официальную страницу выпуска` и пользователь **вручную** запускает скачанный setup; никаких фоновых auto-EXE downloads/исполнения без подписи. Это всё равно полноценная управляемая версия приложения с changelog, просто автоматический запуск installer откладывается отдельным разрешением.
5. **Никаких обязательных беззвучных обновлений**. Не требовать GitHub login, PAT/OAuth пользователя, собственного backend, фоновой Windows-службы. Не показывать update popup во время партии; проверять обновления только на безопасных UI entry points.

**Один `AppId`** и корректное upgrade-in-place: установка X.Y.Z → X.Y.(Z+1) не порождает две записи «Установленные приложения», прежний ярлык ведёт на новую версию, версия/изменения обновлены, прежняя пользовательская база открывается корректно.

### 6.5. Удаление, переустановка, сохранность данных

- **Файлы программы** живут только в install dir, **SQLite, PGN, настройки, OAuth/keyring и аналитический cache** только в текущих безопасных пользовательских `QStandardPaths`/AppData locations — **не переносить их в Program Files**, не менять path без миграции. Инсталляция/обновление/удаление **не может** молча уничтожить личный архив.
- Uninstall удаляет бинарники/ярлыки и registration; **личную SQLite/PGN и prefs по умолчанию оставляет**. Отдельное необязательное действие `Удалить мои данные без возможности восстановления` — явный checkbox + отдельное подтверждение, без pre-checked; защищать профили и не удалять произвольные каталоги. Никогда не менять место user data так, чтобы после обновления приложение считало профиль пустым.
- Backup перед migration; проверить возможность rollback **программы и совместимость БД**. Если новая schema делает DB несовместимой со старой программой — предупреждение + recoverable backup/экспорт, запрет молчаливого downgrade; crash mid-update не должен приводить к полупереписанной БД. Старт после failed update либо предыдущий рабочий build, либо понятный repair путь, но не новая пустая база.
- Смена install location, наличие старой разработческой `.venv312`, ручного Stockfish, custom engine path, отсутствие admin прав, non-ASCII Windows account name, антивирус и офлайн — обязательные сценарии.

### 6.6. Лицензии и безопасность — gate до публичного release

`python-chess` — **GPL-3.0-or-later**; Stockfish — **GPL-3.0**, PySide6/Qt — **LGPL/GPL или коммерческая лицензия**; прочие ресурсы/звуки и зависимости имеют отдельные права. До реального бинарного распространения:
- согласовать лицензию **самого Chess Coach** и совместимость с GPL/LGPL (вопрос может потребовать юридической консультации); включить `LICENSE`, third-party notices, доступ к соответствующим исходникам / build instructions конкретного выпуска, исходники Stockfish соответствующего бинарника, required Qt notices/relinking rights, зависимости/SBOM;
- проверить законность redist C++ runtime и включённых аудио/иконок; не включать токены, реальные SQLite, кэш/логи тестового аккаунта, zip-архивы чужих пользовательских партий, signing secrets;
- обсуждать **подпись Windows installer**: неподписанный EXE может показывать SmartScreen warning. Не просить пользователя отключать защиту; если нет сертификата, не обещать «без предупреждений». Не публиковать installer, выдавая green CI за законное/безопасное распространение.
- составить release security checklist и тест update tampering/symlink/zip-slip/rollback. На release asset manifest проверять owner/repo/branch/tag и version monotonicity; не использовать `latest` слепо для pre-release.

### 6.7. Gate фазы B: отдельно мерить стоимость поддержки

**Прежде чем строить автообновлятор, показать владельцу:** 1) сколько весит `onedir`/installer, 2) реальная длительность cold/warm start в сборке (включая Home ≤1 сек), 3) зависимые версии и лицензии, 4) время одного автоматического Windows release CI, 5) что нужно делать человеку на каждый новый выпуск, 6) зачем нужна/не нужна цифровая подпись, 7) как обновление сохраняет реальные данные. **Если всё это становится чрезмерно сложным, выпустить сначала stable portable/Setup + ручное обновление через официальный release, а сложный auto-installer отложить**; без нового long-running service.

**Тестовый маршрут:** чистая Windows без Python и Stockfish → setup offline → запуск с ярлыка → UI version/Stockfish 19 verified → сыграть локальную партию → закрыть → повторно открыть с Home ≤1с → новая версия через setup → проверка неизменной SQLite/PGN и Stockfish/настроек → uninstall → reinstall → те же данные восстановлены → отдельный test с добровольным clear-user-data → fault-injection invalid signature/hash, offline, interrupted download, insufficient disk, interrupted install/migration. Отчёт прикладывает native video/screenshot и manifest версии, не только `installer built`.
