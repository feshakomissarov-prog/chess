**Контекст:** [PROJECT_STATUS.md](../PROJECT_STATUS.md), [PRD](../PRD.md), [ROADMAP](../ROADMAP.md), [AGENTS.md](../../AGENTS.md), [Lichess API research](../LICHESS_API_RESEARCH.md).

## 0. Цель и принцип сдачи

Пользователь хочет **сначала надёжно сохранять все свои партии**, импортировать старую историю Lichess с последующей дозагрузкой лишь новых/изменившихся игр, затем получать графики и оценку качества **завершённых** партий и позже записывать **собственные размышления голосом и нарисованными на доске планами**.

**Не делай «все компоненты за один огромный PR».** Это одно продуктовое ТЗ, но реализация — отдельные небольшие PR с реальными проверками, в таком порядке:

| Этап | Главный результат | Условие приёмки |
|---|---|---|
| **P0 — исправления и надёжность** | Стрелки/круги исчезают после подтверждённого хода, безопасная среда Windows и текущий техдолг | Настоящая и fake-партия, без регрессий |
| **P1 — база/библиотека** | Миграции SQLite без потери текущих PGN; карточки партий и поиск | Существующая база после обновления читается, откатывать не нужно |
| **P2 — архив Lichess и активные игры** | Полная первоначальная загрузка, возобновление и инкрементальная синхронизация; «Активные партии» | Два последовательных импорта не дублируют партии и не скачивают весь архив |
| **P3 — анализ завершённых партий** | Stockfish/UCI и импорт готовых Lichess оценок, график, ошибки, осторожная метрика точности | Анализируем уже завершённые партии, источник оценки ясен |
| **P4 — голос + аннотации по позициям** | Микрофон, сегменты при смене позиции, хронология стрелок и несколько планов, воспроизведение | Повторное открытие партии воспроизводит мысль и визуальный план |
| **P5 — пакет для будущего ИИ-тренера** | Версионированный локальный экспорт: PGN + оценки + транскрипт + стрелки | Данные интерпретируются без угадывания смысла |

Критический принцип: **каждый этап можно оставить в main в рабочем состоянии после отдельной приёмки**. Если большой блок не успевает — остановиться на завершённом PR, документировать остаток, не маскировать незавершённость. Не делать merge самостоятельно. Новые ветки — от актуального `main`.

## 1. Что уже существует — не писать заново

В `src/chess_coach/lichess/repository.py` уже есть SQLite-таблица `games` с `game_id`, `initial_fen`, UCI `moves`, color/opponent/rated/clock/status/winner, `pgn`, игроками, датой и `final_sync_pending`; `GameRepository` умеет читать список, экспортировать PGN, асинхронно последовательно сохранять снимки. **Существующая база** в Windows: `%APPDATA%\ChessCoach\ChessCoach\games.sqlite3` (проверить фактический путь QStandardPaths на рабочей Windows).

Уже работают `chess-widgets`, BoardView/GameController, OAuth PKCE + Windows Credential Manager, потоки Lichess, игра по ссылке/с AI, pending move, premove и takeback, сохранение локальных партий, экраны Home/Game/Result/Review. **Новая БД — это эволюция этой SQLite, не параллельная вторая «база игр».**

В `BoardView`: `_annotation_arrows` и `_annotation_squares` — наборы в памяти. В `set_position()` происходит обновление отображения, но **автоматического clear_annotations() после хода нет**. Это реальный дефект UX, указан владельцем.

**Сохранить:** архитектурные границы, отсутствие доступа к сети из автотестов, выключенный анализ во время онлайн-игры с человеком, ручной правый drag/правый клик для стрелок/кругов, отсутствие изменения чужих установок/Dr.Web.

## 2. P0 — стрелки после каждого хода + технический долг

### 2.1. Исправить исчезновение пометок

**Требование:** сразу после **каждого нового подтверждённого** хода белых или чёрных (включая первый ход белых и ход AI) **очистить с доски все ручные стрелки и выделения клеток**. Не сохранять их на новой позиции. Одинаковый FEN при другом ply — **новое событие**, а не основание оставить стрелки. При takeback/смене ветки/выборе другой партии визуальные пометки предыдущей позиции тоже не должны висеть на новой.

**Когда НЕ очищать:** при приходе дубликата `gameState` с той же подтверждённой линией, refresh часов/статуса, повторной отрисовке, ресайзе, прокрутке истории без изменения подтверждённой игровой линии. Не путать ручную стрелку с синей стрелкой queued premove и подсветкой последнего хода: premove остаётся своей сущностью, очищать только нужное.

**Для P4:** в текущем P0, если нет сохранения аннотаций, **не блокировать очистку попыткой «сначала записать в ещё не существующую таблицу»**. Но уже сейчас предусмотреть единое событие/сигнал `annotation_action` с операцией add/remove/clear и позиционным контекстом, чтобы P4 мог записывать планы *перед* визуальной очисткой. В P4 сохранение обязано завершаться надёжно перед сменой позиции; если аудио выключено, аннотации всё равно должны иметь возможность сохраняться.

**Тесты:** белый ход; чёрный ход; AI; собственный ход/ход друга; дубликат; refresh часов; takeback; отменённый pending; ручные стрелки vs premove. Не чистить стрелки только из-за optimistic overlay, если сервер отверг ход. Если решишь очищать при optimistic UI для отзывчивости, нужна **обязательная возможность восстановить прежние аннотации при отказе сервера** и сохранить правильную привязку.

Настроить Windows GitHub Actions Python 3.12 с `QT_QPA_PLATFORM=offscreen`, install, pytest, compileall, простой import/инициализация Qt без реального Lichess. Убедиться, что GUI smoke не восстанавливает OAuth случайно. При отсутствии CI доступа — `NOT RUN`.
- **Безопасное offline smoke**: явный режим запуска/внедрённый fake transport, не полагаться на временную env в другой Windows-процесс. Режим не должен автоматически читать живые OAuth credentials, открывать глобальный stream или отправлять давно ожидавшие действия.

- Отдельно перед релизом: лицензионные обязанности `python-chess`/Stockfish (GPL), SVG figures, `chess-widgets` (MIT); лицензию всего продукта определяет владелец, не объявлять все зависимости MIT.

## 3. P1 — единая долговременная база и библиотека

### 3.1. Развить SQLite без потери данных

Сохранять `games` и `game_id` существующих партий, ввести версионированные миграции через `PRAGMA user_version` либо таблицу `schema_migrations`; атомарная миграция/транзакция, backup перед опасными миграциями, обновление таблиц без `DROP games`. Миграции повторяемые, идемпотентные. Проверить старую SQLite копию в тестовом каталоге, **не** личную БД владельца для destructive-тестов.

Разделить:
- данные **партии**: источник (`lichess/local/pgn`), id источника, username/id аккаунта владельца (не пароль), уникальность (`source, source_game_id`), начальный FEN/variant, UCI/PGN, игроки, рейтинги при наличии, control, даты начала/окончания, status/result, timestamps, origin, imported/played_with_app, финальная синхронизация;
- данные **пользовательского импорта**: `sync_state` по аккаунту/источнику, окно истории, последний успешный checkpoint, текущая страница/граница, ошибки, дата last success, счетчики; не путать новый курсор и уже обработанный архив;
- данные **анализа**: `analysis_runs` и `position_evaluations` по `game_id + ply + analysis_version`, источник Lichess/local, engine name/version, limits, оценка cp/mate (с указанием POV), PV, статус;
- данные **размышлений**: отдельные `thought_sessions`, `audio_segments`, `annotation_events`, `annotation_snapshots`, `thought_groups`, `transcripts`, привязанные к позиции и при необходимости версии игровой линии.

Не обязательно реализовать таблицы P3/P4 сразу в P1: **описать миграционный план и реализовывать таблицы при начале соответствующего этапа**. Не плодить пустые абстракции и десятки пустых классов. В базе даты в UTC, времена/часы с исходной точностью API; хранить оригинальные данные при доступности и источник каждого вычисленного поля. Пользователь не должен терять уже сыгранные партии из PR #3.

### 3.2. Библиотека «Мои партии»

- Список локально сохранённых завершённых партий, сортировка по дате, фильтры по сопернику, цвету, результату, контролю, источнику, analysed/unanalysed; индикатор количества.
- Открытие партии **без сетевого запроса**: доска, SAN по каждому полуходу, результат/дата/часы, PGN export. Разделить активные игры и завершённые, без самопроизвольного переключения.
- Данные, которые отсутствуют в источнике, показывать как «нет данных», не `0`/выдуманные значения.
- Безопасное хранение: SQLite в QStandardPaths/AppData, права пользователя, резервный экспорт PGN/JSON; не хранить секреты рядом, не коммитить `*.sqlite3`/аудио.
- Не удалять локальные комментарии, аннотации, уже готовый анализ при повторном импорте существующей партии. Разделять `raw source game` и пользовательские дополнения (merge/update).

**Приёмка P1:** старая БД читается; партия играется/завершается и появляется в библиотеке; перезапуск не меняет PGN; повторный upsert не создаёт копию; сбой посреди миграции восстанавливается без потери данных.

## 4. P2 — первый импорт всех игр и инкрементальная синхронизация

**Официальный endpoint:** `GET /api/games/user/{username}`, выбор `Accept: application/x-ndjson`. Документировано: новые сверху (reverse chronological), `since`/`until` как **Unix milliseconds**, `max`, `sort=dateAsc|dateDesc`, `moves`, `clocks`, `evals`, `accuracy`, `opening`, `division`, `finished`, `ongoing`. `accuracy` **только в JSON, когда сервер реально располагает данными**; `evals` могут отсутствовать. Запрашивать только нужные поля; `pgnInJson=true` при необходимости сохранять исходную PGN. Спецификация: https://github.com/lichess-org/api/blob/master/doc/specs/tags/games/api-games-user-username.yaml .

### Первый запуск

- Явная кнопка **«Импортировать архив Lichess»** после OAuth, подтверждение username и права импорта. По умолчанию импортировать **завершённые** партии (`finished=true, ongoing=false`); текущие партии — отдельно через `/api/account/playing` и игровые потоки.
- Потоковая обработка NDJSON построчно без полной загрузки 10 000+ партий в RAM. Ограниченные по количеству игр и/или датам чанки, транзакционное сохранение чанка и **checkpoint только после успешной записи на диск**. Прогресс «импортировано N / диапазон дат / можно отменить», `Pause/Resume/Cancel` без потери импортированных данных.
- У Lichess обратная хронология; **спроектировать восстановление backfill**: отдельно сохранить нижнюю границу уже обработанного старого диапазона/точку resume, не просто `since=lastImported` при незавершённой первой загрузке, иначе старые партии останутся неимпортированными.
- Аккаунт идентифицировать по стабильному Lichess id, а не только отображаемому имени. Один и тот же game_id не дублировать, даже если открыт из онлайн-игры Chess Coach, добавлен импортом или повторно обнаружен при перекрывающемся окне времени. Поддержать случай нескольких Lichess аккаунтов без смешивания атрибуции и без выдуманного владения.
- Ошибка сети/JSON/SQLite/429: не отмечать чанк успешным, корректно возобновлять с checkpoint. Запросы последовательные, не агрессивные; при HTTP 429 соблюдать глобальную паузу **не менее 60 секунд** и Retry-After. Без параллельных массовых запросов.

### Повторная синхронизация

- После полного backfill — **только новые и затронутые игры**: контрольная временная отметка успешного импорта, небольшой безопасный overlap для одинаковых timestamps и запоздавших данных, `upsert` по уникальному id + сравнение поля статуса/хэша ходов/даты, без копирования неизменённых партий.
- Полностью **не перекачивать** архив при каждом запуске. Синхронизировать по кнопке пользователя; автообновление — только после отдельного разрешения/позже. Показывать «Последняя синхронизация», количество новых/обновлённых/пропущенных и ошибку.
- Появившийся **позже серверный анализ** старой партии нельзя обнаружить исключительно через временной диапазон новых игр: разрешить ручное обновление оценки выбранной партии через одноэкспортный endpoint `GET /game/export/{gameId}` или осторожный refresh метаданных небольшого набора; не обещать автоматическую дозагрузку всех поздних оценок без обхода архива.
- Партию без завершения не считать окончательно завершённой, её может обновить live stream/активные партии; `final_sync_pending` не сбрасывать произвольно.

**P2 тесты:** архив из 0, 1, 500 и 10 000 NDJSON партий (фикстуры без real network), частичный backfill → отмена → перезапуск → продолжение, повторный импорт = 0 дублей, overlap timestamps, same game id from two sources, takeback/обновление хода, 429, malformed NDJSON, после crash восстановление checkpoint, отсутствующие `evals`/`accuracy`, приватность и корректность принадлежности нескольким аккаунтам.

## 5. P3 — график и анализ завершённых партий

### 5.1. Выбор источника оценки

- **В первую очередь** использовать уже имеющийся в Lichess `analysis`/`accuracy` у завершённой партии, **если он реально присутствует**. Показать `Источник: Lichess`. Не требовать от Lichess запустить облачный анализ, не выдавать несуществующие `accuracy` за нули.
- Если оценок нет — пользователь нажимает **«Анализировать локально»**. Подключить локальный **Stockfish UCI**, через `python-chess.engine`, выбирать проверенный путь к исполняемому файлу (или безопасную отдельно согласованную установку), версию и лимиты глубины/времени на позицию. Анализ — **только после завершения партии**, в отдельном фоне/процессе, отменяемый, с ограничением CPU/памяти, прогрессом и ошибками. Не скачивать/запускать случайные бинарники из непроверенных источников.
- **Fair Play blocker:** во время любой **своей активной партии Lichess против человека** запретить запуск Stockfish/анализ на связанном клиенте (не только скрыть график): приоритет безопасности перед удобством. Проводить разбор после окончания партии. Проработать корректное различение уже законченной архивной партии и ещё идущей партии.

### 5.2. Что показывает экран анализа

- График оценки по **каждому полуходу (ply)**: centipawns с единой convention (например, положительное = лучше белым), mate отдельно, отметки ключевых моментов. Клик по точке → позиция и SAN в архивной доске, без отправки онлайн-хода.
- Итог: результат, имя соперника, контроль, доступное время и рейтинг, количество ошибок/неточностей/грубых ошибок **только если методика вычисления определена**, список критических ходов. Без «псевдоаналитики».
- **Точность**: если сервер прислал Lichess `accuracy`, показывать как `Точность Lichess` с % каждого игрока. Lichess определяет Accuracy через изменение вероятности победы и агрегирует не простым средним. **Не подставлять среднюю accuracy ходов вместо итогового %**. Если для локальной оценки реализована собственная методика — показывать как `Оценка точности Chess Coach (приближённая)`, документировать формулу/версию/engine/depth и не выдавать за официальный результат Lichess. Можно начать только с CP-графика и «Точность недоступна» до реализации корректной формулы.
- Возможность продолжить анализ или отменить; кэш по `game_id + hash moves/FEN + engine version + settings`; после takeback либо другого изменения истории пересчитать лишь устаревшие позиции/пометить run invalid. Не пересчитывать всю партию при каждом открытии графика.
- Хранить результаты и настройки расчёта локально. Позже их используют M5/ИИ-тренер, но **не вызывать OpenAI API сейчас**.

**P3 тесты:** mate score, POV белые/чёрные, неполные eval, variant unsupported, корреляция eval[ply] и соответствующего хода, отмена worker, падение Stockfish, длинная партия, повторное открытие кэша, отсутствие двигателя, real game AI human fair-play guard.

**Официальные справки:** https://lichess.org/page/accuracy , https://lichess.org/page/fair-play .

## 6. P4 — голос пользователя и стрелки как совместная временная линия размышлений

### 6.1. Общая идея

Нужно сохранять **не просто изображение стрелок**, а последовательность пользовательских мыслей: *какую позицию видел, когда говорил, какие стрелки и выделения добавлял/убирал, какие альтернативные планы показывал, и какая часть аудио этому соответствует*. Это позволит позже посмотреть несколько линий по порядку, а не смешать их в один кадр.

**Нужны две взаимосвязанные оси:**
1. **Позиционная ось** — `game_id`, `line_revision`/branch, `ply`, `fen`, id подтверждённого хода/позиции, сторона хода, серверное время события (когда есть).
2. **Временная ось заметок** — `thought_session_id`, `audio_segment_id`, `annotation_event_id`, monotonic offset/timestamp относительно старта записи, `group_id` (альтернативная идея A/B/C), порядок и продолжительность.

### 6.2. Запись микрофона

- Явное включение владельцем записи, выбор микрофона, разрешения ОС, видимый индикатор, пауза/стоп и graceful handling недоступного устройства. **Записывать только микрофон владельца, не системный звук / звук соперника.**
- **Строгое правило сегментации:** **первое изменение позиции — первый ход белых — уже создаёт границу**, не пропускать его; затем при каждом новом **подтверждённом** изменении позиции (ход игрока либо оппонента) завершить текущий аудиофрагмент и создать следующий. Не резать из-за `gameState`-дубликатов, обновления часов, визуального pending/optimistic, переключения экрана/просмотра архивной истории. Если пользователь включил запись до первого хода — явно сохранить `pre_first_move` вступление либо предложить «Начать с первого хода»; согласовать UX, но **не терять аудио**.
- При takeback возвращается старый ply/FEN, но **мысли того момента нельзя терять**; создать `line_revision` и сохранить аудио/стрелки прежней ветки как историю размышлений, маркируя их как `undone_branch`. Не подвязывать запись лишь по FEN (одинаковые позиции встречаются повторно).
- Захват аудио неблокирующий для UI и игровых потоков; микрофон отказал → игра продолжается. Атомарная запись во временный файл с финализацией, восстановление после аварий, отсутствие пустых/обрезанных «успешных» фрагментов.
- Локальный формат, удобный для пост-обработки (например PCM/WAV и позже сжатие). Метаданные и путь к файлу в SQLite, audio bytes **не хранить в SQLite BLOB без причины**. Изолированный приватный каталог (например в AppData), относительный путь и контроль целостности/размера, не случайные пользовательские пути.
- Расшифровка **после записи** фоново и **по согласию** (предпочтительно локальная модель, отдельная загрузка модели с разрешения владельца). Ошибка распознавания не удаляет аудио. Возможность вручную исправить транскрипт. Не обещать Whisper уже установленным.
- После партии GUI позволяет воспроизвести фрагменты на конкретном ply/линии; оригинальная запись и исправленный текст сосуществуют.

### 6.3. Ручные стрелки/круги и несколько вариантов

- **Визуальная механика не меняется:** правая протяжка — arrow, правый клик — круг/подсветка.
- **На доске стрелки и выделения исчезают при следующем подтверждённом ходе**, но **их сохранённая история остаётся**. Очистка GUI не должна удалять мысль/аннотацию из хранилища.
- Сохранять каждое действие `add/remove/clear` как `annotation_event` с порядком, позиционным контекстом и time offset. При необходимости снапшот набора стрелок/полей на момент смены позиции либо каждые N событий для быстрого replay. Важны `from`/`to`, цвет, стиль и `group_id`; стрелка может быть добавлена и удалена до хода — это всё равно часть рассуждения.
- **Сразу несколько альтернативных планов:** простой UI «Новая идея / Вариант A / Вариант B», можно переименовать `group_id`/название; выбор группы не меняет шахматную позицию и не отправляет UCI. Группы могут существовать одновременно на одной позиции; цвета по группам можно добавить позже, но группировка в данных обязательна. Ручное подтверждение смысла («план атаки», «угроза соперника», «другой расчёт») **опционально**, не приписывать автоматически.
- У каждого аудиофрагмента может быть **много** annotation events и мыслительных групп; одна группа может относиться к нескольким аудиофрагментам. Использовать промежуточные связи при необходимости; не ограничивать «одна стрела на один голос».
- При пересмотре партии: воспроизведение по хронологии в пределах позиции, а не один итоговый слой всех вариантов. Пример: с 0–10 сек план A (e2→e4), с 12–18 сек план B (d2→d4), при комментарии пользователя подсветить соответствующую группу и историю изменения. **Не утверждать, что смысл стрелки автоматически известен**: он понятен из контекста фразы/метки группы.
- Синхронизация UI/SQLite/event writer thread-safe, а ошибки записи видимы. События для непрерывной аннотации нельзя переупорядочить при фоновой записи. При остановленной аудиозаписи стрелки всё равно можно сохранять как самостоятельный комментарий (по настройке).

### 6.4. Минимальный формат данных (ориентир, не строгое имя классов)

```json
{
  "schemaVersion": 1,
  "game": {"source": "lichess", "gameId": "abc12345", "initialFen": "startpos"},
  "position": {"lineRevision": 1, "ply": 17, "fen": "..."},
  "thoughtSession": {"id": "ts1", "recordingEnabled": true},
  "audio": {"segmentId": "a17", "startMs": 0, "endMs": 22100, "transcript": "Я думаю сначала атаковать пешку"},
  "groups": [{"id": "A", "label": "Основной план"}, {"id": "B", "label": "Альтернатива"}],
  "annotationEvents": [
    {"atMs": 1250, "groupId": "A", "action": "add", "kind": "arrow", "from": "e2", "to": "e4"},
    {"atMs": 8200, "groupId": "B", "action": "add", "kind": "arrow", "from": "d2", "to": "d4"},
    {"atMs": 18500, "groupId": "A", "action": "remove", "kind": "arrow", "from": "e2", "to": "e4"}
  ]
}
```

Пример **синтетический**, не настоящий пользовательский экспорт. FEN нельзя оставлять `...` в рабочем файле; хранить полную позицию. Хранить стабильные IDs и UTC/monotonic локально, при воспроизведении для каждой записи приводить time offsets к общей сессии.

## 7. P5 — подготовка данных для будущего ИИ-тренера

**В будущем** ИИ должен получать структурированный пакет, а не «фотографию с кучей линий». Пакет: завершённая партия и UCI/SAN, `game_id/ply/FEN/lineRevision`, результаты и постгейм оценки, последовательность речевых заметок с метками времени, annotation events с group labels, комментарии пользователя. Нужна проверяемая связь: *«на позиции после 9-го хода я в 12:03 произнёс X, нарисовал вариант A и альтернативу B»*.

- При подготовке текста для ИИ делить контекст по позициям и time windows; поддержать воспроизведение и исправление вручную, не смешивать все стрелки в одну вариацию. ИИ должен отличать **изображённую идею пользователя** от **рекомендации движка** и от **реального хода**.
- Экспорт **локально в JSON (versioned) + PGN + относительные пути/манифест аудио**, возможность выгрузить выбранную партию без ключей/секретов. Исходные аудиофайлы включать в ZIP **только по явному выбору** владельца; по умолчанию для будущей модели использовать транскрипт, не оригинальную запись.
- **Никакой автоматической отправки в ChatGPT/OpenAI API**, никаких данных в облако без согласия владельца и понимания стоимости/политики приватности. Реальный ИИ-диалог — отдельный проектный этап после P4.

## 8. Автоматические и ручные проверки, безопасность

- Все unit/Qt tests — `QT_QPA_PLATFORM=offscreen`; отдельные SQLite во временных каталогах и fake transport, без живого Lichess. Тесты не показывают десятки окон, GUI smoke отдельно. При необходимости Windows CI Python 3.12.
- **Миграция и целостность:** старая база, failure halfway, импорт одной игры из живого stream и NDJSON, уникальность, concurrency, export PGN, replay takeback; никаких `DROP` с пользовательскими данными.
- **Импорт:** 10k games memory usage, пауза/возобновление/checkpoint, 429 cooldown, различие отсутствующих eval/accuracy, timestamp millis, фильтр аккаунта, повторный запуск без повторного полного архива.
- **Анализ:** график с известной шкалой/источником, локальный worker, отказ движка, недоступная точность, полная блокировка анализа во время live human game. Engine не подключать незаметно при startup.
- **Голос/стрелки:** первый ход белых; белый/чёрный; быстрые смены позиции и запись аудио без пропусков; дубликат event; takeback и ветви; два плана и одна фраза; смена микрофона; отмена записи; crash; replay в архиве; защищённое удаление по выбору пользователя.
- **Загрузка/ресурсы:** ни один background worker не блокирует GUI или отправляет шахматный ход; все файловые ошибки логируются без токенов/голоса; антивирус и настройки Windows не менять. Windows автообновление окружения, скачивание моделей/движка — только после явного разрешения.
- **Реальные E2E:** только со стороны владельца / явного согласия: импорт небольшой части личных игр, затем полный backfill; чтение из локального архива offline, анализ одной завершённой партии, несколько голосовых сегментов, переигрывание плана; сравнение числа партий с Lichess и проверка дублей.

## 9. Строгие границы реализации

**Включено в большой пул:** база, архив, инкрементальный импорт, активные игры, ручные стрелки и их жизненный цикл, postgame анализ, голос и группы мыслей, технический долг, локальный экспорт для будущей модели.  
**Не включено:** финальный визуальный редизайн, Chess.com интеграция, трансляция аудио собеседника, live-engine подсказки, автоматическая отправка голосовых данных в облако, LLM-тренер с оплатой API, распространение установщика без решения лицензий.

**Если неясны детали UX групп A/B или расчёта своей точности:** выбрать простую, проверяемую реализацию и показать владельцу тестовый сценарий. **Не лгать о доступности официальной точности Lichess у каждой партии и не подменять ею локальный расчёт**.
