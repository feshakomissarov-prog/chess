## Обязательные исправления перед merge

### P0 — идемпотентность Puzzle Activity нарушается при изменении метаданных задачи

**Точное место:** `src/chess_coach/lichess/repository.py::import_puzzle_activities()` (~1039–1100), также `src/chess_coach/lichess/puzzles.py::_key()` (~163). Сейчас `attempt_uid = sha256(username + json.dumps(record,sort_keys=True))`; поле `record.puzzle` входит целиком. **Официальный Lichess `PuzzleActivity` включает `puzzle.plays`, `puzzle.rating`, `themes`, `solution`**, которые могут меняться после решения или уточнения задачи. Источники: [схема Lichess](https://github.com/lichess-org/api/blob/master/doc/specs/schemas/PuzzleActivity.yaml) и [API Activity](https://github.com/lichess-org/api/blob/master/doc/specs/tags/puzzles/api-puzzle-activity.yaml). Таким образом **то же самое решение той же задачи в ту же дату, с тем же win**, но с обновлённым `puzzle.rating` или `plays` приводит к **НОВОМ attempt_uid**, дублированию `puzzle_attempts`, росту ложного `attempts`/win-rate и неверному `new_count` повторного пилота.

**Исправить:** отделить **стабильную идентичность события попытки** от изменяемого содержимого задачи. Ключ должен учитывать `account_id`, `puzzle.id`, `date` (Unix milliseconds), `win` (или явный неподменяемый server attempt id, если официальный API когда-нибудь предоставит), **не** `puzzle.plays/rating/themes/solution/fen`. Если один и тот же puzzle мог быть решён несколько раз в один миллисекундный timestamp с одинаковым результатом, явным образом документировать невозможность различить записи без серверного ID; не придумывать факт отдельной попытки. Применить ту же идентичность в `_expand_boundary/_key`, пилоте, бэкфилле и инкрементальной синхронизации. `puzzles` обновлять свежей metadata, а `puzzle_attempts` — не создавать повторно. **Существующим пользовательским `attempt_uid` нужен аддитивный, резервируемый миграционный путь** с дедупликацией, сохранением ссылок `puzzle_pilot_run_attempts`, counters и пользовательских данных; backup/integrity_check, без удаления личной базы.

**Тесты с настоящей SQLite:** дважды импортировать одну попытку с одинаковыми `account+puzzle.id+date+win`, но `plays: 100→101`, `rating: 1400→1430`, `themes` в другом порядке → `attempts=1`, `new_count=0`, рейтинг задачи обновлён; решить тот же puzzle **в другое время** → отдельная попытка; повторить в другом аккаунте → другой event; pilot→full→incremental без дублей; миграция старой v8 SQLite с двумя ошибочно раздвоенными UID и сохранением связей. Добавить тест `_key` на стабильность при изменении `rating/plays`.

### P0 — статистика полного архива: unbounded SQL `IN (...)` и O(total moves) в памяти

**Точное место:** `src/chess_coach/lichess/statistics.py::StatisticsService.summary()`, ~строки 29–227.

Сейчас:
1. `games = [dict(row) for row in db.execute('SELECT DISTINCT ... FROM games ...')]` **считывает весь выбранный архив** в Python, хотя GUI показывает лишь 100 игр на страницу.
2. `ids = [game['game_id'] for game in games]`, затем `marks = ','.join('?' for _ in ids)`; одновременно несколько SQL `WHERE gm.game_id IN ({marks})` и `analysis_runs ... IN ({marks})` с **одним bind-параметром на каждую партию**.
3. Для `confirmed_moves` делает `move_rows = db.execute(...).fetchall()` **каждого полухода каждой партии**, хотя дальше используется лишь `len(move_rows)`.
4. Аналогично загружает все оценки/классификации в память для вычисления нескольких счётчиков.

**Последствия:** при большом архиве запросы превышают сборко-зависимый лимит SQLite bind variables (`too many SQL variables`) и/или UI получает неприемлемые задержки/потребление памяти, несмотря на фоновую нить. Сценарий «полный архив всех партий» прямо предполагает десятки тысяч партий и миллионы ходов. Нынешний тест `test_statistics_page_is_bounded_for_large_archive` создаёт только **1005** игр и проверяет `game_page`, а `summary` всё ещё полным сканированием. Это не доказательство нормальной масштабируемости.

**Исправить:** выполнить агрегаты **на стороне SQLite с индексами**, через фиксированные bounded CTE / temporary table/подзапрос `filtered_games`, без гигантского списка `IN` и без материализации всех ходов ради `COUNT`; если требуется несколько проходов — chunked ID/temp table и однозначная транзакционная версия `statistics_revision`, чтобы статистика и `game_page` не расходились из-за конкурентного импорта. `rating_trend` ограничить по данным/периоду или downsampling для графика **без потери правильности агрегированных счётчиков**. Сохранить account-specific color/result, источник анализа, coverage, mate as null CP и дубли run IDs.

**Тесты:** реальные временные SQLite со 1005, 35 000+ и при необходимости 50 000 искусственных игр; **можно пометить самый большой как slow/nightly**. Проверить: нет `too many SQL variables`, `confirmed_moves` и ошибки равны известному ground truth, bounded memory и разумное время, UI не блокируется, после добавления игры cache invalidates. Для 35k-50k не обязательно создавать 1.5 млн позиций в каждом PR test, но нужна отдельно проверяемая стресс-нагрузка. Не удалять пользовательскую базу.

### P1 — фильтр GUI «Источник оценки» не ограничивает выборку без дополнительного «С анализом»

**Точное место:** `StatisticsService.summary(..., analysis_source=... , analyzed=None)` и `game_page(...)`. Предикат `ar.source=?` вставлен **только внутрь** `if analyzed in {'yes','no'}`. Поэтому пользователь выбирает в GUI «Источник оценки: Stockfish», оставляя `Анализ: любой` (значение по умолчанию), но список партий, `games` и W/D/L продолжают включать все партии; только отдельные запросы метрик пытаются отбирать `ar.source='stockfish'`. На экране возникает несогласованная выборка.

**Исправить:** явно определить семантику: выбор источника должен однозначно означать `EXISTS completed analysis_runs of selected source for current game revision` (или явно переименовать контрол как «Источник только для метрик» и показать счётчик партий с этим источником); `analyzed=no + analysis_source=X` должен означать «без завершённого анализа **X**», а не «все игры». Нельзя одновременно выдавать общий `games` за количество проанализированных Stockfish партий.

**Тесты:** минимум 4 игры: только Stockfish, только Lichess PGN, оба, ни одного. Проверить `summary` и `game_page` с `analysis_source='stockfish'` и `analyzed=None/yes/no`; результаты, `analysis_games`, W/D/L, coverage и UI списки согласованы. Существующий тест покрывает лишь `analyzed=yes/no` с source, а не default `None`.

### P1 — fair-play: проверка активной human-game перед стартом локального движка неполная

**Точное место:** `MainWindow._start_game_analysis` (~2861) вычисляет `active_human_ids` только из `self.online_sessions`; `CompletedGameAnalyzer.analyze()` блокирует при непустом переданном наборе, но **не проверяет другие активные игры того же аккаунта на Lichess**, если пользователь ещё не открыл их в Chess Coach, либо они начались на другом устройстве. Это не доказывает, что у нас есть live-game: **нет данных** об этом — но не следует заявлять глобальную безопасность.

**Исправить политику консервативно:** до *явного* старта анализа на подключённом Lichess-аккаунте уметь получить актуальный server snapshot `GET /api/account/playing` (список уже реализован) и блокировать анализ при хоть одной active human match, даже не открытой в приложении. Проверка должна выполняться асинхронно, с учётом 429/ошибки сети, без самопроизвольного OAuth; **при неподтверждённом статусе** выбрать честное fail-closed для сетевого режима или явное подтверждение владельца «не играю живую партию» для чисто офлайн-анализа. Исключать явно обозначенные AI/Lichess BOT игры только при доказанной метке. При появлении gameStart event во время анализа stop_event срабатывает — оставить и протестировать. Не отправлять engine подсказки в live board.

**Тест:** законченную партию A можно анализировать только когда `/api/account/playing` пуст, а при активной B (не представленной в `online_sessions`) UCI process не стартует. Сетевая ошибка/429, offline, ручной connect без OAuth, событие gameStart mid-analysis, отмена и ограничение частоты. **Не вызывать настоящий endpoint в CI.**

### P1 — корректное завершение процесса UCI probe и защита от аварий Qt

**Точное место:** `SettingsDialog._finish_engine_probe()` (~798). Выполняется `process.kill()` и сразу `process.deleteLater()` без ожидания `QProcess.finished` и явного подтверждения завершения операционной системы. На Windows kill асинхронен; есть риск предупреждения `QProcess: Destroyed while process is still running` или гонки Qt lifecycle, особенно с уже ранее наблюдавшимися локальными `shiboken6` native failures. **Не утверждать**, что этот участок вызвал предыдущее падение — доказательств нет.

**Исправить:** при `uciok` мягкий `quit\n` и bounded shutdown; при timeout `kill` с надёжным finished/destroyed lifecycle, не уничтожать живой QProcess; Qt сигнал/таймер связывать с жизнью диалога и отменять однократно. Не вызывать блокирующий `waitForFinished` надолго из GUI. Тесты через fake UCI subprocess, отложенный `finished`, быстрый cancel/close, повторный probe, отсутствие Qt warnings/use-after-free. Не отключать Dr.Web, не имитировать «native crash устранён».

### P2 — UX и охват тестирования

- Режим `--manual-connect` использует **постоянную SQLite**: это реальная миграция при запуске. Сохранить backup before mutation, `PRAGMA integrity_check` на копии; в UI не выдавать «безопасно как offline». Скрипт требует `-ConfirmPersistentProfile` и ручную фразу — хорошо.
- В `SettingsDialog` вызов `_apply_analysis_preset()` при конструировании может **перезаписать ранее сохранённый пользовательский `analysis_limit_value`** для nodes, даже если пользователь ничего не менял. Проверить сохранение custom limit через reopen dialog/Cancel/OK; изменить только если воспроизводится.
- Ручной офлайн smoke на **последней ветке #24**, локальный Qt crash — неизвестная причина; использовать **один запуск** с Python 3.12+ в отдельном окружении и остановиться при повторной аварии. В `--offline` Lichess и настоящая БД **недоступны по определению**.
- Начальный реальный пилот 5 завершённых игр + отдельный 5 puzzle attempts и один Stockfish UCI на уже завершённой партии — **NOT RUN**. Ни SQL миграции на реальной SQLite, ни live OAuth не считать прошедшими по одним мокам.
- Не подавать в статистику во время активных матчей движковые оценки, не запускать engine на автоматически выбранных партиях.

## Контроль merge-ready статуса всей stacked цепочки

- На момент аудита **PR #8** `codex/p0-arrow-safety` → `main` GitHub сообщает **`mergeable=false`**, а все последующие PR #9–#24 `mergeable=true` **только относительно своей родительской ветки**.
