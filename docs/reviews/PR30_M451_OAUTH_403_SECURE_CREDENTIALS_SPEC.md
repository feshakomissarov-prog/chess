# PR #30 — OAuth HTTP 403: безопасная диагностика и локальное хранение подключения

**Дата:** 2026-11-02. **Контекст:** draft PR #30, последняя проверенная реализация b326ec36ba02c3b08bfed3e187d27daecf62380b. **Статус:** адресное ТЗ Codex для текущей ветки codex/m45-batch-analysis, не M4.6. PR оставить draft.

## 0. СРОЧНАЯ безопасность — без раскрытого секрета

Владелец случайно опубликовал personal access token в скриншоте/тексте переписки. **Токен скомпрометирован: пользователь должен отозвать его на https://lichess.org/account/oauth/token до других действий.** Никакую часть его значения не переписывать в код, issue, PR, commit, Codex prompt, конфигурацию, тесты, логи или примеры. Codex НЕ должен использовать этот секрет. Новый персональный токен выпускать только при реальной необходимости, с минимальными разрешениями, локально на ПК владельца. Не запрашивать все полномочия. Для Chess Coach по умолчанию предпочтительна существующая безопасная браузерная OAuth PKCE-авторизация.

## 1. Что фактически воспроизведено

- Две попытки восстановления сохранённого OAuth дали в диагностике: event=api_request_failed, http_status=403, mode=account, component=lichess_api; GUI: «Ошибка подключения» и «Lichess запретил действие».
- Владелец удалил только старое сохранённое подключение из Windows Credential Manager штатным WindowsCredentialStore.delete(), повторил браузерную авторизацию. Браузер показал локальную страницу об успешной передаче OAuth callback, но Chess Coach всё равно не подключился, с тем же отказом 403. Значит callback и проверка доступа приложения — РАЗНЫЕ этапы; браузерная страница сама по себе не доказывает вход.
- Исходники: src/chess_coach/lichess/auth.py:authorize_and_store обменивает code на token, затем вызывает GET /api/account и сохраняет токен только если запрос успешен. В lichess/api.py:_error_message для всякого 403 показывается один общий текст без определения стадии. Lichess API docs: https://lichess-org.github.io/api/ — GET /api/account требует аутентификацию, без дополнительных OAuth scopes; полные разрешения не исправляют этот endpoint автоматически.
- Отдельно созданный на сайте персональный PAT не является токеном, автоматически полученным PKCE-процессом Chess Coach, и не должен импортироваться из сообщения пользователя. Никаких утверждений о блокировке аккаунта без серверного доказательства.

## C0 — P0: хранить подключение безопасно, не в GitHub

1. Оставить OAuth 2.0 PKCE основным методом. При запуске штатной версии делать restore из Windows Credential Manager, без ввода каждый раз. Флаг --manual-connect не совершает запросов до клика, но после клика может восстановить сохранённый токен. Не менять прежний ключ WindowsCredentialStore.SERVICE/USER без явной миграции.
2. Лишь после обмена authorization code, успешного GET /api/account и корректного account identity — записать токен в Credential Manager и показать «Подключено». Никогда не писать секреты в Git, QSettings, SQLite, .env, лог, аргумент командной строки, PowerShell history или HTTP dump.
3. При 401 предлагать отдельную явную кнопку переподключения. При 403 не запускать бесконечную повторную OAuth-авторизацию: показать отдельное «Проверка аккаунта отклонена Lichess (HTTP 403)» и кнопку безопасной диагностики. При 429 соблюдать Retry-After.
4. **Обязательно реализовать второй метод подключения через персональный PAT** согласно детальному разделу C0.1 ниже. Два отдельных слота Windows Credential Manager и явный выбор метода; секрет вводится один раз только внутри приложения, никогда не передаётся в GitHub/Codex/логи/командную строку. Скомпрометированный ранее PAT использовать запрещено. Предпочитаемый метод по умолчанию — браузерный PKCE, но ручной ввод НОВОГО PAT должен полноценно работать.
5. У Chess Coach две роли доступа: board:play + challenge:write для игры, puzzle:read — отдельный credential, как сейчас. Никаких «все разрешения» по умолчанию. При 403 сохранять офлайн-доступ к ранее импортированным партиям и задачам, fair-play preflight остаётся fail-closed, batch analysis блокируется.

## C0.1 — ОБЯЗАТЕЛЬНО: два независимых типа подключения в GUI

**Новая согласованная просьба владельца:** два полноценных способа подключения Lichess, доступных на одном понятном экране «Подключить Lichess» / «Настройки → Lichess»:

**A. «Через браузер (OAuth)»** — текущий PKCE-flow. Пользователь нажимает кнопку, подтверждает разрешения в браузере, приложение валидирует GET /api/account и автоматически сохраняет access token в Windows Credential Manager. После перезапуска он восстанавливается автоматически (обычный запуск); в \`--manual-connect\` — только после клика пользователя.

**B. «Через персональный API-токен»** — пользователь на СВОЁМ Windows-ПК открывает https://lichess.org/account/oauth/token , создаёт **НОВЫЙ** минимально привилегированный PAT (НИ В КОЕМ СЛУЧАЕ не тот, который был случайно раскрыт), локально вставляет секрет в **маскированное Qt-поле** \`QLineEdit.EchoMode.Password\`, нажимает «Проверить и сохранить». Приложение отправляет токен только по HTTPS в Lichess через уже существующий штатный \`LichessClient.get_account\`, убеждается в HTTP 200/валидной identity; до этого **не объявляет подключение рабочим**. После проверки пишет секрет только в Windows Credential Manager через \`keyring\` / существующую абстракцию \`WindowsCredentialStore\`. При закрытии/повторном запуске в выбранном режиме токен поднимается **сам** без повторной вставки. Можно удалить локально/заменить через GUI. Внутри приложения токен никогда больше не показывать целиком и не вставлять в буфер обмена.

**Нормативный экран**, в согласованной текущей светлой теме (новую тёмную M4.6 здесь НЕ внедрять):
- Заголовок «Подключение к Lichess», переключатель типа подключения [Через браузер] / [Персональный токен], по умолчанию браузерный OAuth; краткое объяснение разницы/безопасности и ссылка на официальный выпуск PAT.
- Browser mode: кнопка «Подключить через браузер», состояние «Ожидаем подтверждение…» / «Проверяем аккаунт…» / «Подключено» / безопасная ошибка с HTTP status.
- Token mode: скрытое password input «Вставьте новый токен Lichess» (пустое при открытии), «Проверить и сохранить», «Заменить», «Удалить сохранённый токен» только в локальном store; бейдж «Сохранён в Windows Credential Manager» (без показа первых/последних символов токена), аккаунт username только в обычном GUI после проверки; если в настройках нет безопасного backend — **отказаться от сохранения**, НЕ fallback в файл/.env/QSettings.
- Показать реальные нужные разрешения в зависимости от текущих функций: \`board:play\`, \`challenge:write\`, нужные puzzle scopes по существующему отдельному контракту. Переизбыток разрешений НЕ нужен; никакой автогенерации «все права». Проверку required scopes выполнять только с документированным Lichess API, не гадать и не производить мутационные запросы/создавать реальные партии ради теста. При отсутствии полномочий объяснить, какая операция недоступна, а не объявлять валидный account «поломанным». Не копировать секрет в комментарий PR, commit description или stderr.
- Хранить **два независимых credential слота**: существующий \`WindowsCredentialStore.SERVICE = ChessCoach.Lichess\`, \`USER = oauth-access-token\` **сохранить без переименования** (для backwards compatibility); второй, отдельный идентификатор, например \`personal-access-token\`, под тем же OS service. Не перезаписывать OAuth секрет PAT и наоборот. \`QSettings\` допустим ТОЛЬКО для **несекретного enum** \`selected_auth_method = oauth|personal_token\`; аккаунтный selector не должен переиспользовать другой credential неявно. При смене режима — отменить предыдущие background streams/active safety leases, корректно сверить identity нового аккаунта, не объединять личные архивы разных Lichess аккаунтов и не оставлять активные worker threads под старым token.
- **Первый запуск после сохранения PAT** и последующие: выбран personal-token mode → restore проверяет saved PAT → GET /api/account → connection ready → штатный рабочий режим Lichess. \`--manual-connect\` по-прежнему не делает сеть до явного клика, затем вызывает restore выбранного режима. При HTTP 401/403 после restore приложение сообщает причину, сохраняет локальные архивы/задачи и **не** отправляет запросы циклом. Во время любого неизвестного/ошибочного состояния Fair Play engine-analysis fail closed.
- «Отключить» и «Удалить сохранённый токен» должны быть ясно различимы. Для персонального PAT по умолчанию **удалять только локальную копию**, НЕ вызывать серверный revoke автоматически, потому что он мог использоваться где-то ещё; предложить отдельную ссылку «Отозвать токен на Lichess» и предупредить, что удаление из Windows не отзывает полномочия на сервере. Для OAuth при явном отзыве допускается уже существующий \`DELETE /api/token\` при соответствующем UX, но не использовать revoke PAT молча. Смена способа подключения сама по себе не удаляет другой credential.
- **Крайне важная честность о доступе:** токен не публикуется ни в GitHub, ни в ChatGPT и не отправляется Codex как значение. **Но программа Python и любой процесс с достаточно широкими правами того же Windows-пользователя, в том числе локально запущенный агент Codex с доступом к Credential Manager, технически МОГУТ прочитать credential.** Нельзя гарантировать абсолютную недоступность секрета Codex, если дать ему права на ПК/профиль; не заявлять обратное в документации и не пытаться «шифровать» ключом, лежащим рядом. Граница безопасности: не вызывать Codex для получения/чтения реального PAT, не запускать тесты с ним, не логировать; для сильной изоляции нужен отдельный Windows profile/права.
- Ни одного PAT, не прошедшего валидацию аккаунта, не записывать как «подключённый»; если Lichess продолжает отдавать 403 даже на новый PAT, сказать «сервер отклонил проверку аккаунта», а не просить очередной токен. **Второй способ авторизации — полезный fallback UX, но он НЕ гарантирует исправление существующего HTTP 403.**

**Обязательные тесты второго способа:** Qt password field скрыт; fake PAT GET /api/account 200 → store to \`personal-access-token\` and restore after restart без браузера; pre-existing OAuth credential unchanged; switching OAuth↔PAT does not share/overwrite/revoke secrets and cancels old session workers; 401/403 response PAT → not connected / fair-play disabled; 429 respects cooldown; missing keyring → no plaintext fallback; secret strings not in log/QSettings/SQLite/console; manual-connect → zero network before click; local token deletion versus explicit remote revocation; if PAT owner identity differs from OAuth identity, account-specific local history remains separate; avoid background OAuth popup when selected PAT.

## C1 — P0: выяснить, почему GET /api/account отвечает 403

1. Логировать без секретов стадии: oauth_callback_received, oauth_exchange_success/failed, account_check_started, account_check_failed, credential_store_success, connection_ready, restore_started/failed. Для HTTP ошибок: method GET, allowlisted route /api/account, numeric HTTP status, duration, response classification (JSON error vs HTML denial vs other), exception class, correlation ID собственного процесса. Не сохранять response body, URL с query, headers, raw server error text, account name, email, IP, User-Agent full error, персональные данные. Для server JSON допустимо писать только проверенный allowlisted machine-readable error code.
2. Убедиться, что UrlLibTransport и LichessClient.get_account корректно отправляют Authorization: Bearer, GET /api/account, OAuth client ID, PKCE verifier, redirect_uri и content types. Не заменять GET /api/account неавторизованным публичным запросом ради «успешного» входа.
3. 403 может означать отказ сервера/edge protection или отдельную аккаунтную/сетевую политику, но точная причина сейчас НЕ установлена. Разделить серверный отказ и невалидность токена (401), отсутствие scopes и 429. Не просить выпустить десятки токенов, не запускать агрессивные повторы.
4. Экран браузера после callback должен говорить «Код передан Chess Coach, проверку завершит приложение», а не вводить в заблуждение «Авторизация завершена». GUI: понятный этап, статус и кнопка «Открыть обезличенный отчёт». Никаких блокирующих повторяющихся QMessageBox.
5. Если после исправлений Lichess продолжает возвращать 403 на GET /api/account даже с новым корректно выданным PKCE-токеном, зафиксировать sanitized time/status/route/response_type и предложить обращение в Lichess API support. Без обхода правил/ограничений и без передачи настоящего токена.
