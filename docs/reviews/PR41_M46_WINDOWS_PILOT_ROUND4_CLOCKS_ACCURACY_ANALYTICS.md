## R4-01 · P1 · Два отдельных крупных игровых таймера

**Факт:** при игре против Lichess AI с контролем 3+2 игрок не видит удобных часов возле шахматной доски. Код `window.py::_update_clock` (около строки 5913) склеивает время двух цветов в **одном** `clock_label` боковой панели, а когда `white_ms/black_ms` отсутствуют, пишет лишь «Контроль ...» / «Без часов». `LichessGameSession` уже сохраняет серверные `wtime/btime/winc/binc`, `_last_clock_at`. Отсюда решение — не создавать второй источник времени, а корректно отображать сохранённый.

**Нужно:**
1. Два **постоянно видимых** цифровых таймера, у самого поля или рядом с соответствующей шахматной стороной: **противник над доской, владелец под доской**, независимо от переворота белых/чёрных. Сопроводить именем/цветом, явно обозначить чей ход. Минимальная читаемая цифра ~24–32 px на нормальном DPI; активный таймер ярче, пассивный спокойнее, при <30 с заметное предупреждение (цвет + символ, доступный не только по цвету). Пользователю не нужно искать часы в боковой панели.
2. Формат `MM:SS`; при партии >1 часа `H:MM:SS`; для ≤10 секунд допустимы десятые, но не показывать лишние цифры на протяжении всей игры. Явно отражать инкремент `+2` **отдельной маленькой подписью**, не прибавлять его до подтверждённого хода.
3. Источник правды — **Lichess gameFull/gameState**. Между подтверждёнными событиями визуально отсчитывать только часы активного цвета по `time.monotonic()`; остановить локальный тик на статусе finished, paused/unknown/reconnect/awaiting authoritative snapshot/history view (с пояснением «синхронизация», не угадывать новое время). Следующее событие корректирует обе цифры без «скачка в будущее», ложных отрицательных секунд и дублирования прибавки инкремента. В журнале не считать локально рассчитанные секунды авторитетными.
4. Если online game уже стартовала, но `wtime/btime` ещё нет, показывать **«—:— / ожидаем часы Lichess»**, а не обманчивое «Без часов» при выбранном 3+2. Для локальной свободной доски без контроля действительно «Без часов» или скрытые clock cards. При завершённой партии зафиксировать последний известный snapshot.
5. Перерисовка UI каждые 100–250 мс не блокирует сетевой поток и не генерирует лишние Lichess requests; никаких Stockfish/PV в человеческой онлайн-игре. Перестраивать layout с ориентацией и полноэкранной доской, не обрезать поле на 1280×720, 1360×860, 1920×1080/DPI.
6. Тесты (synthetic gameFull/gameState, mock monotonic): белые/чёрные 3+2, flip, инкремент после хода только от authoritative event, paused/reconnect, stale event generation, no-clock, 0:29 и 0:09.9, flag/time expiration, finished; browser and UI clock agree within allowed tick latency. Физический Windows pilot — AI 3+2, белыми и чёрными.

## R4-02 · P1 · Точность, охват и мат: не подменять математические понятия

**Факт со скрина:** в завершённой партии `S: 115/115 позиций`, но сравнительная таблица покрывает только `45/57` собственных ходов и `45/57` ходов соперника; `Точность` и `Сильные` показывают `н/д`. В коде `analysis.py` сохраняет `white_cp=None, mate_white=int` для mate; `move_metrics.py::build_move_facts` присваивает `cp_loss=None` на любом mate-discontinuity и `severity=unknown`. `repository.py` явно не рассчитывает локальную accuracy (это осознанная прежняя защита от выдуманных данных). Официальная Lichess accuracy возможна лишь при наличии серверной метрики.

**Строгая продуктовая позиция:** предложение владельца заменить мат на условные `+10`/`-20`/максимальный cp **ОТКЛОНИТЬ**. `Mate(n)` — отдельный тип шахматной оценки, не число сантипешек; фиктивная конвертация создаст неверный cp-loss, классификацию, графики и высокий процент «охвата». Полнота позиций и полнота **сопоставимых решений** — разные знаменатели. Нельзя доказывать 100% coverage одной подставленной константой.

**Сделать три раздельных показателя:**
- **Официальная точность Lichess** (если получена из JSON с `accuracy` и корректной привязкой game/account) — отдельный источник `L`, без вычислений локально от Stockfish, без заполнения нулём отсутствующих.
- **Точность Chess Coach по Stockfish** — разрабатывать как отдельную **версионированную экспериментальную** метрику на основе `win-chance/WDL` before→after и прозрачной агрегации, согласованной с источником: https://lichess.org/page/accuracy ; она **не называется «официальная точность Lichess»** и не должна показываться, пока формула/валидация/threshold for coverage не пройдены. Если валидировать надёжно в этой итерации невозможно — не выдумывать число; показать `н/д · ожидается корректный расчёт` и дать ниже показатель доли хороших ходов. Подготовить дизайн/запись версии формулы и отдельный feature gate.
- **Доля хороших ходов** — простой показатель `good / analyzed_decisions` с подписанным знаменателем (например `35/45 оценённых`, не `35/57` без объяснения), плюс `coverage 45/57`. При 0 evaluated → `н/д`, не 0%; при частичном покрытии явно `только среди оценённых`. Не называть «точность».

**Обработка мата:**
1. Для каждой позиции хранить typed score `cp | mate | missing`, плюс ply, mover, depth, nodes, engine version, source; терминальные `chess.Board.is_checkmate()`, `is_stalemate()`, `is_game_over()` различать, не путать мат в N из PV с уже случившимся матом.
2. Для переходов cp→mate, mate→mate, mate→cp, cp→cp классификация по отдельной **матовой логике или WDL/win-chance** с доказанным порядком и перспективой ходившего (forced mate found/lost/saved, mate in N decreases/increases, terminal delivery). Если методика не позволяет устойчиво определить качество конкретного хода — `unknown`, но статус позиции **evaluated** остаётся. Не считать mate transition автоматически `blunder`, не рисовать mate как ±1000 cp. Отсутствующий baseline ply0 не чинить копированием значения ply1; нужен достоверный pre-move evaluation.
3. Показывать **две строки покрытия**: `Позиции оценены: 115/115` (mate считается оценкой) и `Решения с сопоставимым качеством: Я 45/57, Соперник 45/57`, с кнопкой информации, объясняющей missing: mate, baseline, depth/source incompatibility, unanalysed. Не обещать 100% без реального полного evidence.
4. **Сильные ходы** не приравнивать к 1-й линии. Нужен самостоятельный `Совпадение с лучшим ходом Stockfish: x/y` (сохранённый verified pre-move PV[0], легальность, engine/run/version, отсечь trivially forced only move при необходимости). Надпись `Сильные` можно заполнять только при отдельной **подтверждённой категории и методике**: первая линия не равна exceptional strong/brilliant. Совпадение PV доступно лишь по реально сохранённому анализу, с denominator PV-known moves; first move of PV at position before, не после.
5. Разные имена и источники в UI: `Точность Lichess: нет данных`, `Точность Chess Coach (эксп.): н/д`, `Хорошие среди оценённых: 35/45`, `Лучший ход движка: x/y`, `Матовые позиции: N`. Фазы игры и свои/чужие оценки — только при наличии достоверных per-phase данных; точность всей партии не делить на три.
6. Проверить сохранённую графику: mate-marker отдельно, cp-линии через мат не соединять, отдельная подпись +M/−M, без кучи перекрывающихся `−M..` в конце графика как на скрине. Скрытие графика/классов при fail-closed preflight.
7. Тесты на synthetic PGN: forced mate, mate in 1/3/7, missed mate, prevented mate, mate→cp, stalemate, missing ply0, multiPV/invalid PV, scored positions vs comparable pairs; source separation, 0/100% boundary, correct denominator, stable SQLite migration/backward compatibility. Никакой реальной БД пользователя.

## R4-04 · P1 · Пользовательские лимиты узлов, в том числе миллион

**Факт:** в SettingsDialog одиночный анализ уже допускает до **100 млн** узлов в `_update_limit_range` и `AnalysisOptions.normalized()`, но `BatchAnalysisDialog.nodes` ограничено **30 000**, а `FastPassOptions.normalized()` тихо обрезает любые превышения до **30 000**. Поэтому при попытке задать **1 000 000** для массового анализа приложение не принимает число (или silently clamps). Вывод: исправить **оба слоя**, а не только QSpinBox.

**Нужно:**
1. Одиночный анализ и массовый анализ согласовать по пользовательским бюджетам. Предлагаемые presets: `Быстрый 20 000`, `Обычный 100 000`, `Подробный 500 000`, `Пользовательский`. При ручном вводе можно задать **1 000 000** и больше до явно документированного разумного предела (например 10 000 000 на позицию в batch, 100 000 000 в одиночном). Никакого silently clamp: либо точное сохранение 1 млн, либо явная ошибка, если конфигурация не поддержана.
2. `BatchAnalysisDialog` принимает `1 000 000`, `FastPassOptions.normalized()` не превращает это в 30 000. Если архитектурно важно отделить fast-pass от deep-pass, внедрить явный `custom/high-budget` режим и **не называть миллион «быстрым»**, сохраняя текущие fast presets и очередь. Нельзя ломать idempotent queue identity/cache key/resume из-за несогласованных параметров.
3. В `Settings → Stockfish` хранить отдельно значение выбранного анализа и выбранный batch budget (или осмысленный общий preset с override), `QSpinBox` c grouping separator `1 000 000`, понятный суффикс `узлов на позицию`, достаточная ширина. Настройки применяются к **новому** запуску, не меняют уже работающую очередь; Resume продолжает именно первоначальный budget, без скрытого перенастроя.
4. Показывать предпросмотр примерной стоимости `N узлов × количество позиций × количество партий` (это оценка вычислительной работы, **не обещание времени исполнения**), и предупреждение для больших лимитов, например 1 млн × 120 позиций × 20 игр. Нельзя автоматически начинать интенсивный batch при смене значения.
5. Лимиты Threads/Hash проверять против UCI и ресурсов устройства; проверить отмену, паузу, preflight перед каждой партией, offline policy, отсутствие CMD окон и stale callbacks.
6. Тест end-to-end fake engine: typed `1_000_000` → dialog read → persisted QSettings → `FastPassOptions` → `AnalysisOptions` → `chess.engine.Limit(nodes=1_000_000)` → queue key/data; negative bounds; select preset then custom, restart/resume, per-game fair play guard.

## R4-05 · P1 · Расширить аналитику из Lichess настолько, насколько данные реально существуют

**Факт:** главная показывает малое `Анализ моих ходов 873/156426` и `Точность Lichess: н/д` при 3301 партии. Это **не доказательство**, что API не работает: в `ui/dashboard.py` `analysis` основан на **локальных complete/partial analysis_runs и move_metrics**, а не на всём архиве; показатель official accuracy по БД `lichess_accuracy_*` отдельно. `lichess/api.py::stream_user_games` уже передаёт `accuracy=true`, `evals=true`, `pgnInJson=true`; **дополнительная процедура `archive.py::refresh_missing_evaluations` получает только PGN** через `export_game_pgn`, который не обязан содержать JSON `accuracy`. Существуют разные покрытия, и UI должен это честно объяснять.

**Проверенные внешние источники:**
- Официальное API https://lichess-org.github.io/api/ : JSON экспорт `GET /game/export/{gameId}` и `GET /api/games/user/{username}`; параметры `accuracy=true`, `evals=true`, `pgnInJson=true` при поддержке, но серверная accuracy/анализ существуют **не у каждой партии**.
- Официальная методика точности https://lichess.org/page/accuracy : она не равна хорошим ходам/всем ходам; расчёт требует полной и сопоставимой позиционной информации.
- API rate limits: https://lichess.org/page/api-tips ; по возможности **один сетевой запрос одновременно**, на 429 обязательная пауза минимум 60 с или корректный больший Retry-After.
- Не считать `/api/cloud-eval` источником **официальной точности конкретной игры**, не использовать `external-engine` для тайного запуска серверного анализа завершённых игр; в API нет обещания произвольно запросить серверную Accuracy для любой завершённой партии.

**Решение:**
1. Развести KPI в сводке: `Партий в архиве 3301`; `Официальная точность Lichess: 0/3301 игр с данными`; `Оценённые решения Stockfish: 873/156426`; `Партий с локальным анализом X/Y`. На tooltip «873 — количество сравнимых собственных решений в локальных сохранённых анализах, а не число партий и не Lichess accuracy». Показать **coverage per source**, а не впечатление «половина данных не подгрузилась».
2. **Автоматически в фоне при нормальном подтверждённом подключении** начинать ограниченную дозагрузку готовых Lichess accuracy/evals для **ранее импортированных завершённых игр, включая давно сохранённые 3301+ партий**. Не ждать ручной кнопки. Дозирование, безопасные условия, видимость и паузы строго по **R4-05A ниже**. Сохранить и ручное действие **«Обновить аналитику Lichess»** для приоритетного запуска/повторной проверки; оно не единственный способ получения данных. **Не** делать все 3301 запроса сразу при старте.
3. Для **конкретного finished Lichess game** использовать JSON export `Accept: application/json`, `accuracy=true`, `evals=true`, `opening=true`; по желанию оставить PGN отдельно. JSON загружать **только через существующий LichessClient, а не scraping/browser**; валидация gameId, account scope, completed status и versioned source. JSON `players.white/black.analysis` и официальные accuracy сохранять независимо от успешного или неуспешного наличия move evals. Не затереть предыдущий verified analysis, если сервер ничего не прислал, не переписывать чужие PGN/SQLite без backup+transaction.
4. Сохранять `accuracy`, `evals`, `pgn source`, `analysis timestamp`, `per-player origin`, confidence/coverage/status; strict account separation and original color mapping. В mixed аккаунте персональные KPI не смешивать. Если нет accuracy на сервере — **`нет серверной оценки`**, не 0 и не «не подключился». На finish AI игры ждать доступности серверного анализа; не пытаться принудительно его получить, если он никогда не появляется.
5. Параллельно предлагать локальный Stockfish **для завершённых игр**, по текущим Fair Play safety preflight/stop and source-labeled pipeline. Не копировать/маскировать локальную accuracy под Lichess. Данные L и S могут сосуществовать, сравнивать coverage и версию, не перезаписывать друг друга и не давать фальшивую официальную accuracy.
6. Тесты synthetic API responses: has accuracy/no evals, evals/no accuracy, neither, partial/mate, wrong account, duplicate/repeated export, stale auth generation, 429/Retry-After, backfill cursor, data merge, no token leakage; dashboard counts source labels; no network in `--offline` or `--manual-connect` before intent, no background auto-analysis during human live.

## R4-05A · P1 · Дополнение владельца: обязательная автоматическая фоновая дозагрузка аналитики старых партий

**Это дополнение к R4-05, не новая фича вне ТЗ. Требование владельца: не искать и не нажимать кнопку для каждой партии.** Если шахматные партии уже были загружены из Lichess, приложение должно само поэтапно проверять, не появились ли на Lichess готовые engine evaluations, официальная accuracy и другие **фактически доступные** метаданные, затем корректно объединять их с локальным архивом. Должен быть виден спокойный статус «что скачивается и откуда». Сохранённые ранее партии — **обязательная** часть backfill, не только новые после установки обновления.

**Исходная ситуация подтверждена кодом на SHA 30d89103:**
- `MainWindow._auto_sync_timer` каждые 10 минут вызывает `_run_background_sync()`, где `sync_archive(background=True)` и синхронизация задач; *это не гарантирует повторную проверку серверного анализа у уже импортированной партии*.
- `ArchiveImporter.refresh_missing_evaluations()` уже умеет выборочно обходить пропуски, но вызывает `client.export_game_pgn` с `Accept: application/x-chess-pgn` и не обеспечивает получение **JSON-only accuracy**. В R4-05 должен появиться JSON export через `LichessClient`.
- `stream_user_games` при первоначальном импорте уже запрашивает `accuracy=true, evals=true`. Но анализ мог появиться **ПОСЛЕ** первой загрузки; необходимо отдельное повторное чтение.

### R4-05A.1 Когда и как запускать без участия пользователя

1. В обычном normal launch **только после успешного восстановления сессии, подтверждения текущей auth generation и рабочего event stream** выполнить фоновый отбор кандидатов. Новые завершённые Lichess партии, позже поступившие в архив, тоже становятся кандидатами; не запускать обработку на каждом событии хода.
2. Первая итерация — максимум **5–10 ранее не проверенных завершённых партий**. Следующие порции по планировщику с небольшим интервалом, устойчивым resume после перезапуска, например дневной лимит **до 25 запросов на отдельные игры по умолчанию**, с возможностью отложить. Не стартовать тысячами GET одновременно. При наличии эффективного пакетного документированного export API допускается читать ограниченные пакеты, но без скрытого неограниченного обхода и с полноценным курсором.
3. Хранить в SQLite **статус и время последней проверки отдельно для accuracy и evals**, приоритеты (новая завершённая; ранее не проверенная; частичная; запрос на повторную проверку), account_id, game_id, line_revision/hash и next_retry_at; состояния `queued/running/has_data/no_server_data/partial/rate_limited/error`. После `no_server_data` повторять **не раньше 7 дней** по умолчанию, не делать бесконечных запросов каждые 10 минут. Не смешивать «отсутствует на сервере» с «не успели скачать/ошибка».
4. Пользователь в «Настройки → Lichess / фоновая синхронизация» видит включённую по умолчанию опцию **«Автоматически дозагружать готовую аналитику завершённых партий»**, может **выключить**, приостановить и возобновить, установить адекватный дневной бюджет. При выключении — никаких запросов на отдельные партии для этого задания; другие согласованные операции остаются независимыми.
5. Если архив пока пуст или нет токена/соединения/доступа к нужному аккаунту, ничего не запрашивать и не блокировать UI. В `--offline` и `--manual-connect` до ручной авторизации — **ноль фоновых сетевых запросов и ноль чтений credential**. При явном Disconnect, logout, revoke, смене account/auth_generation, 401/403, reconnect/неизвестном состоянии и active human Lichess game — **остановить/приостановить worker**, не запускать новый; stale responses не должны дополнять другой аккаунт и не должны раскрывать engine data на экране.

### R4-05A.2 Что именно скачивать и как сопоставлять

6. При запросе **готовой**, уже существующей Lichess-аналитики использовать только **публично документированный** finished-game JSON export через `LichessClient`: `GET /game/export/{gameId}?accuracy=true&evals=true&pgnInJson=true&opening=true&division=true` с корректным Accept и разрешёнными параметрами. Сохранять имеющиеся per-color accuracy, per-ply server scores, открытие/раздел фаз и provenance независимо друг от друга, когда поле действительно существует. Валидация id, completed status, player IDs, colors, account scope, исходного line/hash, schema; никакой передачи PAT в URL/логи.
7. Идентичность партии и line hash не менять только ради metadata update; merge транзакционно, идемпотентно, без дубликатов и без перезаписи Stockfish runs. Отсутствие поля в новом ответе **не стирает старую проверенную оценку**. Если сервер возвращает оценки только для части ходов, сохранять `partial` с честной coverage. При смене line_hash — не приклеивать оценки к чужой последовательности ходов.
8. Источник данных в UI всегда `L · серверная аналитика Lichess` и `S · локальный Stockfish` по отдельности, без присваивания L-accuracy расчётам Chess Coach. После завершения одного пакета освежать главную/аналитику **асинхронно и только для текущего аккаунта/контекста**. Никакая новая оценка не показывается в review/training без **нового полного Fair Play preflight**.

### R4-05A.3 Видимость процесса без надоедливых окон

9. В шапке или рядом с индикатором подключения — компактный неблокирующий статус, например **«Lichess · фоновая аналитика: 7/10 партий»**, и понятный secondary inspector `Фоновые операции` (откуда: Lichess; что: готовые оценки и точность; checked/has accuracy/has evals/no data/errors; обновлено; очередь/пауза/следующая проверка). Без модальных диалогов и без системных всплывающих уведомлений на каждый ход/игру.
10. При 429 показывать **«Lichess ограничил запросы · пауза до ...»** с backoff не меньше 60 секунд и `Retry-After` если больше. При отключении — «Приостановлено: нет соединения», при отсутствии аналитики — «На Lichess готового анализа нет» вместо общего «Н/Д». Ручная кнопка `Проверить сейчас` ставит задачу в очередь и уважает global throttling/Retry-After, **не пробивает** лимиты.
11. Один coordinated Lichess API scheduler на archive/puzzle/backfill/eval retrieval: **не более одного активного HTTP запроса за раз**, с приоритетом авторизации, online game streams и safety preflight. Не конкурировать двумя независимыми burst worker'ами, как это возможно при одновременном вызове `sync_archive(background=True)` и `sync_puzzle_activity_background`; ни нажатие `Проверить`, ни восстановление сети не создаёт параллельный шквал.

### R4-05A.4 Можно ли «заказать серверный анализ» там, где его вообще нет

12. **Разделить скачивание и запрос расчёта.** На текущую дату в **публичной документации Lichess API не выявлен поддерживаемый endpoint для программного заказа серверного computer analysis партии**. В документации `Analysis` указан `GET /api/cloud-eval` (кэш позиции, НЕ серверный анализ конкретной завершённой игры). В исходниках Lichess есть **внутренний веб-маршрут** для запроса анализа, но он **не является публичным контрактом API**. **Запрещено** автоматом вызывать этот веб-маршрут, обходить UI/CSRF/квоты, эмулировать браузер, массово посылать задания на CPU Lichess или выдавать `cloud-eval` за official game accuracy.
13. Если готовой серверной аналитики нет: оставить `no_server_data`, показать человеку **«На Lichess анализ не запрошен или недоступен»** и в карточке завершённой *связанной* игры необязательное действие **«Открыть партию на Lichess для запроса анализа»**. Оно открывает обычную подтверждённую страницу игры только **по клику** пользователя (не запускает POST). Если в будущем Lichess опубликует официальный разрешённый API запроса — отдельное согласование пользователя, проверка квот/разрешений, без фонового автоматического заказа по умолчанию. После того, как пользователь сам запросит анализ на Lichess, автоматический backfill со временем обнаружит готовый результат.
14. Локальный **Stockfish** предлагается как отдельный путь для завершённой игры после актуального preflight, под собственным source label и добровольным запуском; **не стартовать тысячи анализов Stockfish автоматически** вслед за отсутствием готового серверного анализа. Никакого engine во время human online game.

### R4-05A.5 Приёмка и тестирование

15. Детерминированная интеграционная цепочка с **синтетическими 30 сохранёнными завершёнными Lichess играми**: normal login → auto 5–10 запросов → stable JSON accuracy+evals update → home/dashboard reflects source L → приложение закрыли → resume next batch без повторения; отсутствие новых партий не мешает проверке старых. При `no_server_data` повтор до TTL не выполняется. Пользователь не нажимает кнопку для возникновения первых данных.
16. Отдельные fake API случаи: JSON accuracy only, evals only, partial, none, earlier stored L fields, duplicate gameId, account change during request, line revision changed, 401/403/429, stale auth generation, global scheduler with archive/puzzles, recovery from restart, manual pause/opt-out, closed UI; `--manual-connect`/`--offline` no requests; interactive human game suppresses worker; no cross-account/review Fair Play leakage.
17. Проверить, что UI статусы не утверждают «загружено 100%», если 100% лишь **проверено**; separate counters **проверено / получено accuracy / получено evals / отсутствует / ошибка**, реальные timestamp/source. Владелец при ручном прогоне подтверждает, что через несколько минут видит запуск процесса **без нажатия**, но реальные запросы/доступ к личным данным **запрещены в CI**.

**Источники:** публичная документация https://lichess-org.github.io/api/ ; https://lichess.org/page/api-tips ; пользовательский запрос/состояние кода. Отсутствие публичного метода создания серверного анализа обсуждено на https://lichess.org/forum/lichess-feedback/request-game-analysis-through-api ; наличие кнопки на сайте https://lichess.org/forum/lichess-feedback/request-computer-analysis . Не путать веб-функцию сайта с разрешённым автоматическим API.
