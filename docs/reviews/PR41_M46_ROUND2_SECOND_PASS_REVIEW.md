**Outstanding pre-merge P1 (bounded concurrency-hardening):**

1. **Canceled task can still launch a UCI subprocess.** `src/chess_coach/lichess/analysis.py:99–105`: `self.engine_factory(str(path))` is called **before** first `stop_event.is_set()` test. If async safety revoke happens just after worker scheduling and before worker body gets CPU, canceled task can spawn Stockfish briefly; it then notices cancellation and exits without analyzing. Avoid any engine launch after revoked lease: check stop before `engine_factory`, keep the after-spawn check too. Deterministic test injects already-set stop_event with fake engine_factory and asserts it is never called. This is a lifecycle hardening issue, not evidence that scores are shown during active human games.
2. **Persistence cancellation window not fully closed.** `CompletedGameAnalyzer.analyze:167–174` checks stop once **before** `GameRepository.save_analysis()`. The callback can revoke safety while the database commit is in progress; current fake late-success test `tests/test_window.py::test_fair_play_revocation_stops_running_game_analysis_and_discards_late_success` verifies UI ignores late result, but mock worker **does not actually write to SQLite**, so it does **not prove “no stale write”**. Add versioned/cancel-aware transactional commit guard (or reliable rollback/deletion by produced run ID when stop occurs before commit completes) without deleting previously valid runs; test with a deterministic barrier around the repository write. Exact design must avoid DB corruption/data loss. If product policy considers a completed run computed before revoke safe to retain in the database, document that narrower invariant explicitly; **never re-expose results without a new preflight**. Avoid unfounded claim that the race always persists unsafe data; it is a source-visible possible interleaving.
