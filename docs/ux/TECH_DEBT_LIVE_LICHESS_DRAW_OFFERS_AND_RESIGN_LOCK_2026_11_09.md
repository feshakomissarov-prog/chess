## 1. Сценарий, сообщённый владельцем

Реальная партия Chess Coach ↔ Lichess между **двумя людьми**, владелец и друг тестировали разные клиентские стороны:

1. Владелец через Chess Coach отправил другу **предложение ничьей**.
2. Друг **увидел** это предложение со своей стороны.
3. У владельца после отправки **кнопка предложения ничьей стала неактивной и не восстановилась** по мере продолжения партии.
4. Позже возникла **позиция, в которой игроки хотели согласиться на ничью**. Друг отправил **новое предложение ничьей владельцу**, но **Chess Coach у владельца не показал входящее предложение / возможность его принять или отклонить**.
5. Владелец не мог снова предложить ничью из-за заблокированной кнопки; **«Сдаться» также была неактивна** (уточнить точное состояние на обеих сторонах при воспроизведении).
6. Для завершения теста **друг был вынужден сдаться со своей стороны**.

**Недопустимое поведение:** одна отправка предложения ничьей не должна приводить к вечному блокированию управления завершением партии, а входящие актуальные предложения не должны теряться без возможности восстановить authoritative state. Не путать **предложение ничьей**, **заявление ничьей по правилу**, **автоматическую ничью из-за позиции** и **серверное подтверждение результата**.

## 2. Что проверить в коде (предварительная зацепка, НЕ доказанная причина)

В момент записи при выборочном исходном осмотре обнаружены следующие существенные механизмы:

- \`src/chess_coach/window.py::_lichess_session_action_started\` добавляет \`(game_id,command)\` в \`_pending_game_actions\`.
- \`_lichess_session_action_completed\` удаляет pending-запись **только при** status из множества \`{-2,400,401,403,404,422}\`; для остальных случаев ожидается \`_lichess_session_action_reconciled\`.
- \`window.py::_refresh_online\`: если **ЛЮБОЕ** \`(game_id,command)\` осталось в \`_pending_game_actions\`, **одновременно отключаются** \`resign_button\`, \`draw_button\`, \`decline_draw_button\`, \`claim_draw_button\`. Это **подозреваемый механизм** связи «отправил ничью → неактивна даже кнопка сдаться».
- \`src/chess_coach/lichess/session.py::apply_state\` вычисляет \`draw_offered_by_opponent\` по серверным \`wdraw/bdraw\` флагам; нужно подтвердить, что actual stream действительно доставляет соответствующее состояние в UI, и оно не перезаписывается устаревшим/частичным snapshot.
- \`window.py::handle_draw\` выбирает между предложить/принять, основываясь на \`session.draw_offered_by_opponent\`; \`resign_online\` — отдельный endpoint. Проверить, не блокирует ли client-side pending состояние эти независимые команды чрезмерно.
- Проверить инициализацию/восстановление игры, reconnect/resync, смену фокуса/страницы, ACK/HTTP codes, callbacks sequence, cancellation, \`request_id\`/generation fencing, и **как/когда формируется \`action_reconciled\`** для отправленного предложения ничьей.

**Это гипотеза, а не вердикт:** отсутствие event reconcile может быть вызвано адаптером stream, внешней серверной логикой, состоянием кнопок или действительно недоставленным событием. Нельзя «исправить», просто безусловно разблокировав все кнопки, отключив pending/deduplication или отправляя повторные POST без проверки сервера.

## 3. Требуемый результат (контракт будущего исправления)

- **Исходящее предложение:** после успешной отправки показывать понятный статус «Предложение ничьей отправлено»; после ACK, отказа, истечения предложения, хода/изменения статуса и соответствующих правил Lichess UI корректно возвращает доступные действия; **нельзя навечно блокировать resign из-за pending draw offer**.
- **Входящее предложение:** актуальный \`draw_offer\` другого игрока показывается в игровом блоке с **«Принять ничью» / «Отклонить»**, без скрытия в неоткрытой секции; отправка ответа только по осознанному действию пользователя, с подтверждённым серверным результатом.
- **Resign:** во время действительно активной человеческой партии должно оставаться доступным в допустимых состояниях, независимо от истории предложения ничьей. Если сервер запрещает действие или game terminal, показывать честную причину. Не отправлять resign автоматически.
- **При сбое/переподключении:** корректное повторное чтение authoritative Lichess game state, clear stale pending только после достоверного подтверждения и без duplicate POST; не рисовать ложные offers.
- **Состояние игры и Fair Play:** менять только controls/state/reconciliation; не запускать engine/analyse в человеческой живой партии и не ослаблять player/account/generation safety.

## 4. Порядок расследования и тесты следующего этапа

1. **Воспроизвести на двух тестовых Lichess-аккаунтах** в одной live human партии: A отправляет ничью, B видит, B не принимает, оба продолжают ходить, B позднее предлагает ничью, A получает и может принять/отклонить; A может сдаться в любой разрешённый момент. Учесть, что право повторно предложить ничью регулируется условиями сервера; **не требовать повторного предложения раньше, чем его допускает Lichess**.
2. Записать приватно-безопасную временную шкалу событий: outbound action/request-id, game-id в обезличенном виде, status code, action_started/completed/reconciled, \`_pending_game_actions\`, stream \`gameState\`/draw flags, session.status, \`draw_offered_by_opponent\`, состояние и \`enabled/visible\` кнопок. **Никнеймы, токены, тексты PGN и персональные данные в публичный лог не писать.**
3. Проверить: ACK successful but no reconcile, 400/403/429, disconnect/reconnect, stale callback, received offer, rejected offer, timeout/terminal status, параллельный pending move/takeback, switch screen/return to game, новая партия.
4. Unit tests и GUI integration: предложение не блокирует resign навсегда; incoming offer меняет правильные CTA; pending другой команды не приводит к вечному lock; backend не получает лишних повторных запросов; server terminal запрещает действия; после reconnect актуальное состояние восстановлено.
5. Отдельная **ручная GUI приёмка с двумя людьми**, поскольку «входящее предложение не показано» может быть особенностью реального Lichess stream. Если настоящая сеть недоступна CI, использовать mocked event trace, но не объявлять фактическую двухстороннюю игру проверенной.
