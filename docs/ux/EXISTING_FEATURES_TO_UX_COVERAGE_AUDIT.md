### Реальные расхождения нынешней реализации с утверждённым UX

- **После online finish** код сейчас `window.py::_show_result` переключает `screen_stack` на отдельный `ResultPage`. **Требование владельца — удалить автоматический переход**, остаться в игровом workspace; справа только два добавочных primary actions **«Разобрать» / «Вызвать снова»**. Не рисовать summary card/alert/banner и не маскировать полностью доску. Основа source `ResultPage` может стать compatibility adapter, но **UX должен перестать на неё уходить**.
- **Главная сейчас `HomePage(QScrollArea)`** и содержит длинное раскрывающееся «Другие разделы и синхронизация». Будущий утверждённый dashboard без общей прокрутки и шесть навигационных пунктов; технические pilot actions переместить, не потерять.
- **Статистика сейчас большой `StatisticsDialog(QDialog)`**, не постоянная страница Прогресса; **пазлы сейчас `PuzzleHistoryPage` в диалоге**, не Обучение. Переносить без потери фильтров/повторений/выборки/рейтинг-тренда и без дублирования.
- **Историческая `premove_training`** выявлена кодовым аудитом, но **владелец исключил её из UX**. Обычный premove, его отмена и текущие правила исполнения в онлайн-игре обязательно сохраняются.
- **В новой карточке партии уже согласован мини-график**. Заметки сохранить как второстепенные. Обновление конкретной партии не должно конкурировать с фоновой синхронизацией; только диагностический retry/recovery при отдельной неисправной записи. Обязательно safety mask.
- **Существующий `AdvantageBar` УЖЕ РЕАЛИЗОВАН**, хотя по утверждённому UX-A2 его нужно сохранять как вертикальный индикатор оценки. График CP/Δ тоже существует. Это адаптация/preservation, не новая функция с нуля.
- **История и статистика пазлов** требуют входа из «Обучение → Задачи». По решению владельца **детальная переработка Учебного экрана откладывается**: пока может остаться тонкая совместимая страница/переход к нынешнему working puzzle UI.
- **Native rematch Lichess** не подтверждён существующими кодовыми методами. Имеются `challenge_username` и open challenge; поэтому «Вызвать снова» реализовать как **новый challenge тому же сопернику по явному клику** с допустимыми настройками и user consent. Если позже будет документированный серверный механизм предложения рематча, добавить его отдельно; не создавать бесконечную ложную анимацию «ждём приглашение» без event API.

## 2. Что НЕ считать уже реализованным

- **Дальняя подготовка к сопернику** на публичных последних 500 партиях — сохранена [отдельно](../research/OPPONENT_PREPARATION_LONG_TERM_FEATURE.md); **не code feature PR #44**.
- Полноценный интерактивный GPT-шахматный тренер, полноценные темы 263 компетенций, персональные учебные планы, репертуар и новый Opening Explorer — пока **стратегия продукта**, не работающая кнопка.
- Регулярная загрузка новых нерешённых задач Lichess — **не подтверждена** существующим `puzzles.py`; подтверждена синхронизация **истории прошлых попыток**. Не обещать новую задачу из Lichess как гарантированную функцию без API/источника.
- **Rematch event/listener** — не подтверждён кодом; доступен обычный challenge нового матча, если имя соперника известно.
- Не требовать удалять pilot diagnostics и тестовые режимы только ради минималистичного UX; их расположение — Advanced/сервис.

## 3. Утверждённые владельцем решения по спорным функциям — 04.11.2026

1. **Предходы:** действующий обычный premove и отмену оставить без изменений. Отдельную «Тренировку предходов»/тестовый ход соперника **не включать в новый UX**, не создавать для них пункт меню. Это не требование срочно вырезать служебный код.
2. **Пробные загрузки:** пилоты на 5–10 партий или попыток задач **не показывать** в публичных и Advanced-экранах. При этом настоящие синхронизация, checkpoint, ограничители, диагностика, fake-тесты и безопасное восстановление остаются.
3. **Заметки:** оставить второстепенным полем деталей партии/разбора; не превращать в главную функцию. **Обновление одной партии Lichess:** автофон — основной путь. Ручной поштучный refresh не продвигать; доступен лишь как диагностическое восстановление при подтверждённом сбое, в рамках общего rate limiting.
4. **Задачи:** повторное решение, история попыток, просмотр ответа и сброс — сохранить. Отдельную концепцию интерфейса решения задач **проработать позднее**. Не обещать API недоступных новых задач.
5. **Игровые спецкоманды:** «Возврат хода», «Предложить ничью», входящие «Принять/Отклонить», «Сдаться» и прочие применимые команды **на видном месте справа, рядом с ходами**, а не за меню «Ещё». Показывать уместные действия по состоянию, подтверждать необратимые. Утверждённое поведение после finish (ровно две новые главные кнопки) не менять.
6. **Аналитика:** «Критические моменты», фазы, статистика, дебюты, рейтинг-тренды и переходы к позициям сохранить в «Прогрессе» и «Анализе» по контексту.
7. **Звуки:** полный AS-IS контракт раздела 4; остальные согласованные решения UX-B1/UX-A2/UX-GAME-01 остаются.
8. **Общий принцип:** редко используемое нужное — вторично или в настройках; историческое ненужное — не переносить в новый пользовательский интерфейс только ради формального «100% кнопок». Не удалять личные данные, бэкенд-процессы и тесты без отдельной безопасной задачи.

При итоговом UX-ТЗ каждому ID дать `reused/moved/not exposed by owner/technical recovery`, реальный маршрут и проверку. **Эта карта включена в [единое ARCH-UX-01 ТЗ](../specs/ARCH_UX_01_UNIFIED_EXECUTION_SPEC.md); исполнение только после передачи владельцем, не разрешение на merge.**

## 4. Звуки — утверждённое исключение из редизайна

**Чёткое решение владельца:** уже выбранные и встроенные WAV, каталог, набор по умолчанию, выбор между вариантами, настройки, уведомления, просмотр истории, громкость, «Классический 45%», QSettings persistence, порядок вызова звуков и preview **без функциональных изменений**. Разрешён лишь визуальный перенос в удобную страницу «Настройки → Звуки» с проверкой, что весь старый UX работает. Тесты обязаны проверять существующие default IDs, номенклатуру вариантов и retained selections после update и restart; физическую audibility проверить вручную в Windows.
