# Lichess API — исследование для Chess Coach

**Дата:** 2026-10-31. **Статус:** документальное исследование, **не результаты практических API-тестов**.  
**Этап:** M1 (после M0 доски). Официальная спецификация: https://lichess.org/api , исходники https://github.com/lichess-org/api/tree/master/doc/specs .

## 1. Что означает Board API

Board API — интерфейс Lichess для человеческих игроков с обычным аккаунтом, использующих электронную доску или стороннее клиентское ПО. **Chess Coach может быть таким клиентом.** Это не Bot API: бот-аккаунт не требуется и подсказки шахматных движков/ИИ во время партий против человека запрещены.

Документация: https://github.com/lichess-org/api/blob/master/doc/specs/lichess-api.yaml (теги Board и Authentication).

Board API:
- `GET /api/stream/event` — поток уведомлений `gameStart`, `gameFinish`, `challenge`, `challengeCanceled`, `challengeDeclined`; NDJSON, keepalive, **только один глобальный поток на токен**.
- `GET /api/board/game/stream/{gameId}` — поток `gameFull`, `gameState`, `chatLine`, `opponentGone`; первое сообщение `gameFull`, поток закрывается по окончании.
- `POST /api/board/game/{gameId}/move/{move}` — ход в UCI (например, `e2e4`; для превращения суффикс фигуры). `200` подтверждает приём, `400` — отказ; после запроса сверять состояние с потоком.
- Игровые операции: abort/resign/draw и др. — см. Board API.
- `POST /api/board/seek` — поиск случайного соперника; для обычного поиска через Board API только rapid/classical/correspondence. Прямые вызовы, AI и bulk допускают blitz.

## 2. Авторизация

Рекомендуется OAuth2 Authorization Code + PKCE (`S256`) без ввода пароля Lichess в Chess Coach. Токены долгоживущие (ориентир — год) и могут быть отозваны, refresh tokens отсутствуют.

На время разработки *только в защищённой тестовой среде* возможен personal access token, но не хранить его в репозитории, логах и публичных скриншотах. Для будущего приложения — OAuth PKCE, безопасное хранение Windows.

Минимально необходимые scopes проверить по конкретным endpoint: `board:play`, `challenge:write` (вызовы), при необходимости `challenge:read`. Отдельно соблюсти least privilege.

Исходник: https://github.com/lichess-org/api/blob/master/doc/specs/lichess-api.yaml .

## 3. Три способа создавать партии

### A. Открытая ссылка для двух участников: `POST /api/challenge/open`

- API возвращает `id`, общую `url` и **`urlWhite`, `urlBlack`**. Первые два участника, присоединившиеся по приглашению, играют друг с другом. Срок действия по умолчанию — 24 часа.
- Параметры: `rated` (по умолчанию false), `clock.limit` (секунды), `clock.increment` (секунды), `days` (correspondence), `users` (необязательное ограничение двух имён, первое играет белыми), variant и др.
- У этого метода в OpenAPI нет отдельного именованного `unlimited`-варианта запроса, **но официальный пример** без часов возвращает `timeControl: {type: unlimited}`, при `speed: correspondence` и `rated: false`. Это свидетельствует о поддержке открытого приглашения без шахматных часов; полноценное поведение проверки остаётся задачей M1.
- `POST /api/challenge/{challengeId}/accept?color=white|black` — **официальный API принятия входящего вызова**; параметр цвета предназначен именно для открытого приглашения. В M1 проверить, что пользователь Chess Coach, создавший открытый вызов, может тем же обычным аккаунтом присоединиться по `accept`, не открывая браузер. **Статус: API механизмы документированы, вся связка не протестирована.**
- После присоединения обоих участников установить связь с `gameStart` и `gameFull`. Не считать `challenge/open` сам по себе уже начатой партией.
- Если open flow не позволяет сценарий инициатор + друг через browser, альтернативный путь — персональный вызов по нику; автоматическую замену без решения владельца не делать.

Источники:
https://github.com/lichess-org/api/blob/master/doc/specs/tags/challenges/api-challenge-open.yaml
https://github.com/lichess-org/api/blob/master/doc/specs/tags/challenges/api-challenge-challengeId-accept.yaml
https://github.com/lichess-org/api/blob/master/doc/specs/examples/challenges-openEndedChallenge.json.yaml
https://github.com/lichess-org/api/blob/master/doc/specs/schemas/ChallengeOpenJson.yaml

### B. Вызов друга по логину: `POST /api/challenge/{username}`

- Требует авторизации. Параметры `rated`, `color`, `variant`, часы (`clock.limit` + `clock.increment`) либо correspondence `days`, либо **отдельный вариант `unlimited`** без часов.
- Для real-time вызова без `keepAliveStream` срок ожидания принятия около 20 секунд, с `keepAliveStream=true` вызов поддерживается активным до закрытия потока.
- Пример 3+2: `clock.limit=180`, `clock.increment=2`, `rated=false` (или true, если сервер разрешает контекст). Параметр `clock.limit` — **секунды**, не минуты.
- Вызовы допустимы в режиме blitz, в отличие от обычного Board seek.

Источник: https://github.com/lichess-org/api/blob/master/doc/specs/tags/challenges/api-challenge-username.yaml

### C. Игра с Lichess AI: `POST /api/challenge/ai`

Указать `level=1..8`, цвет, по желанию часы. Это игра с компьютером Lichess, не рейтинговая тренировка против обычного соперника. После создания поступает `gameStart`.

Источник: https://github.com/lichess-org/api/blob/master/doc/specs/tags/challenges/api-challenge-ai.yaml

## 4. Рейтинговость и контроль времени: точные ограничения

- `rated=true` означает, что партия должна влиять на рейтинг **если сервер принимает этот сценарий**, но наличие параметра не гарантирует допустимость любой комбинации.
- Прямой вызов с `3+2` поддерживает blitz в Board API (общий запрет быстрого случайного поиска не распространяется на прямые вызовы).
- Для `open` тоже есть `rated` и параметры часов, но необходимо проверить в M1: оба зарегистрированы, требования к режиму/цвету/контролю.
- Для `unlimited` по историческим обсуждениям Lichess рейтинговая игра может быть запрещена или существенно ограничена. **Не обещать rated+unlimited** до реального успешного вызова.
- Три различных режима: **real-time** (часы), **correspondence** (дни на ход), **unlimited** (без часов). Сервер может присваивать `speed=correspondence` игре с `timeControl.type=unlimited`, поэтому не делать вывод о наличии часов по одному полю `speed`.

## 5. Импорт завершённых партий

`GET /api/games/user/{username}` — выгрузка партий в PGN или NDJSON, свежие сначала; есть фильтры `since`, `until`, `vs`, `rated`, `perfType`, `color`, `analysed`. Параметры `moves`, `clocks`, `evals`, `accuracy`, `opening` и др. Содержимое оценки/точности доступно **только если соответствующие данные есть**; локальный Stockfish потребуется отдельно.

Предусмотреть локальный ID источника, устранение дубликатов, дозагрузку по времени и хранение исходного PGN и дополнительных полей при наличии. **Импорт партий, сыгранных вне Chess Coach, не даст голосовых записей задним числом.**

Источник: https://github.com/lichess-org/api/blob/master/doc/specs/tags/games/api-games-user-username.yaml

## 6. Ограничения и безопасность

- Fair Play: **никаких движков, графиков оценки, ассистента GPT и подсказок во время игры против человека**. Даже если UI скрыт, не запускать шахматную помощь в фоновом сервисе активной партии.
- Политика API: не слать лавину запросов; при HTTP 429 приостановить запросы минимум на минуту. Использовать stream вместо частых опросов.
- Игровой источник истины — Lichess. UI передаёт `MoveIntent`; локально он может отображать ожидающее состояние, но подтверждённую игру обновлять по ответу сервера/потоку; premove валидировать заново при приходе хода соперника.
- Не запускать сетевые интеграционные тесты с реальным аккаунтом без решения владельца.
- Разделять локальный архив и сетевой транспорт; потеря связи не должна стирать уже сохранённые игровые события.

Официальная документация по нагрузке: https://lichess.org/page/api-tips .

## 7. Чек-лист M1 — проверки с участием владельца

1. OAuth2 PKCE, чтение профиля, повторный запуск без ввода пароля, отзыв токена.
2. Создать `challenge/open` без часов, `rated=false`; проверить `timeControl.type` и доступные URL, срок жизни.
3. Принять созданный открытый вызов `accept` тем же авторизованным пользователем из клиента; друга попросить перейти по ссылке в браузере. Зафиксировать результаты и порядок.
4. Создать open `3+2`, `rated=false`; затем проверить `rated=true` с двумя зарегистрированными аккаунтами (никакого рейтингового теста без явного согласия владельца).
5. Создать вызов конкретного знакомого по нику: unlimited и `3+2`; проверить `keepAliveStream`.
6. Отследить `gameStart`, `gameFull`, `gameState`; сделать по одному ходу каждым игроком и проверить UCI/счётчик ходов/часы.
7. Протестировать отмену вызова, сдачу, ничью, время, отключение интернета/переподключение.
8. Проверить `challenge/ai` с `level=4`; не путать с локальным Stockfish.
9. Загрузить через API несколько завершённых rated/casual игр пользователя, проверить NDJSON/PGN, даты, данные часов и дедупликацию.
10. Задокументировать точные ответы HTTP, статусы ошибок, ограничения и итог решения. **Не публиковать токены в логах/PR.**

## 8. Рекомендуемая структура реализации M1/M2

- `LichessAuth`: OAuth/токен в защищённом хранилище.
- `LichessClient`: HTTP, ошибки, таймауты, rate limiting.
- `LichessEventStream`: NDJSON, восстановление соединения, только один событийный поток.
- `LichessGameSession`: состояние одной партии по серверным событиям и приёму ходов.
- `ChallengeService`: создание/принятие/отмена/вызов AI.
- `GameRepository`: локальное долговременное хранение отдельно от сетевого клиента.
- `UI Controller/BoardView`: пользовательские намерения → отправка → подтверждение Lichess; никаких Stockfish/LLM на активной доске.

Это **предложение границ**, а не требование создать сразу восемь больших классов. Простота и тестируемость важнее пустых абстракций.

## 9. Вывод

Новый клиент Chess Coach может использовать обычный аккаунт Lichess. Сценарии прямого вызова, 3+2, Lichess AI, потоков ходов и импорта истории документированы. Открытое приглашение и unlimited также имеют соответствующие механизмы API, **но полный сценарий «создатель открытого приглашения присоединяется из собственного клиента, друг через браузер» не был проверен реальной партией**. Это главная техническая точка M1.

## 10. Реализация клиента и незакрытая проверка

Клиентский код в `src/chess_coach/lichess/` реализует OAuth PKCE, Windows Credential Manager (`keyring`), HTTP/NDJSON, серверно-авторитетную сессию партии и SQLite архив. Приложение поддерживает два варианта имён URL из схем/ответов (`urlWhite`/`urlBlack` и `whiteUrl`/`blackUrl`), чтобы несовпадение генераторов OpenAPI не приводило к выдаче неправильной ссылки.

Перед тем как принять open challenge, клиент проверяет возвращённый `timeControl.type`: для безчасового режима требуется `unlimited`, для 3+2 — `clock` с точными параметрами; иначе вызов отменяется и ссылка не показывается. Это fail-closed поведение выбрано из-за расхождения текущего описания OpenAPI (пустой clock назван correspondence) и примера ответа (возвращает `unlimited`). До проверки аккаунтом владельца приложение не гарантирует, что API примет self-accept и ожидаемый режим. Если при реальном вызове сервер вернёт correspondence, основное приглашение по ссылке пока блокируется безопасной ошибкой; тогда нужно проверить документированный вариант `days`/параметризацию unlimited с владельцем, не скрывая correspondence за подписью «без часов».

Статус на момент клиентской реализации: fake-тесты подтверждают PKCE/state, маршруты, проверку тайм-контроля и подтверждённую синхронизацию/сохранение; тестов с реальным Lichess аккаунтом нет. OAuth, само-принятие `challenge/open`, 3+2 часы, AI и game finish остаются `NOT RUN — real Lichess` до ручной приёмки владельцем. Не запускать рейтинговую игру без отдельного согласия.
