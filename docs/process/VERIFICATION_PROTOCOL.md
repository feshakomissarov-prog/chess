# Chess Coach — обязательный регламент проверок и подготовки ТЗ

**Идентификатор:** `CC-VERIFY-01` · **Версия:** 1.0 · **Дата:** 14.11.2026  
**Статус:** постоянное правило проекта после включения в `main`. Действует для Codex, других ИИ-исполнителей, людей и для ChatGPT/других ИИ, составляющих ТЗ на основе репозитория.  
**Корневое включение:** [AGENTS.md](../../AGENTS.md). **Шаблон задания:** [`docs/specs/_TASK_TEMPLATE.md`](../specs/_TASK_TEMPLATE.md).

## 1. Контракт: минимум лишних запусков, максимум доказательств

Для **каждого задания** план тестирования определяется **до реализации**, исходя из масштаба изменений. Нельзя запускать полный Windows pytest + всю visual-матрицу после каждого исправления одной строки или QLabel. Нельзя и объявлять работу готовой, не выполнив полную обязательную приёмку на **финальном SHA**.

Это **трёхуровневый процесс**; порядок обязателен:

| Уровень | Когда | Какие проверки | Решение |
| --- | --- | --- | --- |
| **L1 — быстрый адресный** | После каждого небольшого логического изменения | `git diff --check`; compile изменённых Python-файлов; 1–несколько relevant pytest (точно перечислить paths/node IDs); при UI-правке короткий изолированный Qt smoke **только затронутого элемента и размера окна** | Исправлять дефект здесь; обычно не запускать полный CI |
| **L2 — тематическая регрессия** | После завершения группы связанных исправлений либо изменения layout/API/кэша | Тесты затронутого модуля + смежные границы; минимальная **репрезентативная** native Windows visual-матрица для изменённого экрана, при необходимости 100/125/150% и размеры; проверка негативных сценариев | Доказывает отсутствие регрессий затронутых функций |
| **L3 — полная финальная приёмка** | После завершения работы на **точном final code HEAD** и перед передачей на приёмку/merge; повторить только если после неё изменился исполняемый код/тесты/ресурсы, влияющие на поведение | Полный Windows pytest, `compileall`, native visual-evidence, offline smoke, остальные обязательные задачи конкретного ТЗ; реальное владельческое ручное тестирование — **отдельный gate**, не заменяется CI | Сдавать только с точными SHA, run URL, результатом всех jobs и оставшимися OWNER gates |

**Обязательные исключения:** если изменения затрагивают критичные пересечения (SQLite migration, Fair Play, поток Qt, Lichess state machine, обновления, безопасность), Codex вправе/обязан расширить L1/L2. Причину и ожидаемую стоимость явно указать. Никогда не ослаблять реальные тесты или пользовательские критерии ради скорости. Если узкий тест не воспроизводит дефект — расширить среду обоснованно, а не циклически запускать всю систему.

### Запрещённый цикл

`поправил маленький QLabel → коммит → запускаю 1155 pytest + 98 screenshots → жду 10 минут → новая маленькая правка → снова полный CI`.

### Правильный цикл

`исследую причины и измеряю → L1 быстрый targeted test → объединяю связанные исправления → L2 native smoke по affected states → один финальный L3 exact-head → ревью/приёмка`.

## 2. Экономия времени GitHub Actions

1. **Никаких одновременных бессмысленных прогонов на устаревших SHA:** автопроверки должны иметь `concurrency` и `cancel-in-progress` для одного PR, если старый run уже не нужен; не отменять обязательную финальную проверку в момент приёмки.
2. **Изменения только Markdown** не должны запускать дорогие Windows pytest/visual. Для них нужен отдельный быстрый линтер/проверка ссылок или контрактов ТЗ.
3. Автопроверки при разработке должны быть **быстрыми и информативными**, а полный L3 следует запускать **явно по завершении логической группы изменений**. Если в текущей инфраструктуре GitHub всё ещё запускает L3 на каждый push, это известный **процессный долг**; Codex должен заранее по возможности собирать связанные правки до пуша, не порождать ненужные коммиты/полные прогоны и вынести изменение триггеров workflow отдельной инфраструктурной задачей.
4. Запускать `pytest --durations=30` (или эквивалент, когда приемлемо) при диагностике медленного набора, собирать время по test/visual jobs. Если job/fixture/Qt capture неожиданно тормозит или висит, диагностировать конкретный тест, а не ждать бесконечно.
5. CI, который прошёл для `abc123`, не является evidence для последующих code commits; `docs-only` commit не меняет уже проверенное поведение, но в отчёте **указать обе ревизии** и убедиться, что код не изменился.

## 3. Обязательный раздел в КАЖДОМ новом или изменённом ТЗ

**Автор ТЗ — в том числе ChatGPT в любом новом чате — обязан до сохранения документа открыть корневой `AGENTS.md` и этот файл.** Нельзя полагаться на память предыдущего чата или устное «Codex знает».

Во всех исполняемых `docs/specs/*.md` при создании и значимом изменении разместить ровно один указатель:

`<!-- verification-contract: docs/process/VERIFICATION_PROTOCOL.md -->`

и явный раздел **`## План проверок и стоимость CI`**, содержащий:

- **Уровень 1:** точные узкие тесты/команды для конкретной задачи;
- **Уровень 2:** затронутые экраны, модули, размеры, негативные проверки;
- **Уровень 3:** список финальных обязательных тестов на exact-head SHA;
- **Стоимость/триггеры:** когда запускать каждую ступень; что НЕ повторять после мелкой правки;
- что будет считаться BLOCKED/OWNER ACCEPTANCE; что нельзя доказывать synthetic данными.

Также всегда нужен раздел **`## Критерии приёмки и доказательства`**: таблица/строки `критерий → метод → подтверждение → статус`. Для правок существующего ТЗ обновлять его без создания дублей и сохранять стабильные ID.

Шаблон [`_TASK_TEMPLATE.md`](../specs/_TASK_TEMPLATE.md) использовать как исходную форму, а не как замену техническому содержанию.

### Механическая защита от забывания

- [`scripts/check_spec_contract.py`](../../scripts/check_spec_contract.py) проверяет обязательную ссылку и секции **для всех добавленных/изменённых ТЗ в PR**.
- [`.github/workflows/spec-contract.yml`](../../.github/workflows/spec-contract.yml) запускает проверку отдельно и быстро; ошибка должна **блокировать приёмку документа** до добавления плана.
- Старые архивные ТЗ не переписывать массово. Если исторический документ изменяют как исполняемое ТЗ — он должен получить план и ссылку. Простое копирование одного заголовка без конкретных targeted tests не считается содержательной приёмкой; это остаётся ответственностью ревьюера.

## 4. Технические и пользовательские границы

- Рабочая SQLite, токены, профили Lichess, настройки, Stockfish, Dr.Web/WER и local Qt/pytest на компьютере владельца — **не использовать/не менять без явного разрешения**. После инцидентов с `Qt6Core.dll` локальные нативные запуски запрещены до отдельного решения; использовать изолированный GitHub Windows runner.
- L1/L2 и успешные synthetic-скриншоты **не заменяют** жёстких продуктовых gate: Home ≤1000 мс на ранее сохранённой реальной истории, Fair Play, визуальное совпадение с эталоном, live Lichess.
- Нативные проверки по тем DPI/размерам, которые реально затронуты; не надо каждую мелкую правку гонять во всех комбинациях, но перед финальным L3 обеспечить согласованную матрицу и честно назвать непроверенное.
- Все PR — Draft до решения владельца; не делать merge, release и installer самовольно.
- Для каждой регрессии указывать first bad SHA; прежние замечания не исчезают, не переименовываются и не создаются заново. При повторном ревью проходить **весь утверждённый список**.

## 5. Отчёт и ответственность

В каждом итоговом сообщении Codex:

1. Точный code HEAD, изменённые файлы, тематический объём.
2. **L1**: команды и результаты, длительность (приблизительно по логам).
3. **L2**: команды/runner/скриншоты затронутых состояний.
4. **L3**: один итоговый exact-head run URL и полный PASS/FAIL/NOT RUN; если ещё идёт — `IN PROGRESS`, не «готово».
5. Отдельный список `OWNER ACCEPTANCE REQUIRED`, технический долг и неснятые замечания.
6. Если было больше одного полного прогона: **коротко объяснить причину** и что исправить в L1/L2, чтобы это не повторялось.

Критерий успеха регламента — не обещанное время «30 минут всегда», а отсутствие повторяющегося дорогостоящего CI там, где достаточен targeted test, и сохранение полной доказательной приёмки перед merge.

## 6. Для новых чатов ChatGPT

Данные проекта живут в репозитории, **не в памяти конкретного диалога**. В новом чате ChatGPT необходимо дать ссылку на репозиторий и попросить прочитать `AGENTS.md` + этот контракт **перед подготовкой любого ТЗ**. Готовый текст для однократного добавления в инструкции ChatGPT Project хранится в [`CHATGPT_PROJECT_INSTRUCTIONS.md`](CHATGPT_PROJECT_INSTRUCTIONS.md).

**Ограничение:** один GitHub-файл сам по себе не может программно управлять настройками всех чатов ChatGPT. Для устойчивого поведения вне Codex владелец должен добавить проектную инструкцию (либо повторить ссылку при отсутствии контекста). Валидация ТЗ в GitHub остаётся обязательной страховкой независимо от того, какой чат составил задание.
