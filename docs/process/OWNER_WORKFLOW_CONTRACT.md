# OWNER-WORKFLOW-01 — договорённости владельца о работе ChatGPT и Codex

**Дата:** 20.11.2026 · **Статус:** постоянный регламент после утверждения и merge документационного PR.  
**Адресаты:** ChatGPT/авторы ТЗ, независимый ревьюер, Codex и другие исполнители.  
**Наследование:** корневой [AGENTS.md](../../AGENTS.md) → этот регламент → [CC-VERIFY-01](VERIFICATION_PROTOCOL.md) → действующее ТЗ и утверждённые UX/архитектурные решения. Текущие PR и exact-head код имеют приоритет над устаревшими историческими статусами в markdown.

## 1. Обязательная загрузка контекста перед каждой работой

1. Сначала прочитать **актуальные версии** `AGENTS.md`, `docs/process/OWNER_WORKFLOW_CONTRACT.md`, `docs/process/VERIFICATION_PROTOCOL.md` и `docs/specs/_TASK_TEMPLATE.md` прямо из GitHub соответствующей ветки.
2. Сверить `main`, открытые кодовые и документационные PR, их head SHA, latest review comments, последние дополнения ТЗ и execution log. Сначала отличить уже merged, выполненное в draft, запланированное и историческое.
3. Для задачи читать относящиеся к ней документы, код и тесты; старый текст `AGENTS.md` о «текущем этапе» и старый PR не считаются активным приказом, когда факты GitHub позднее.
4. Если правила конфликтуют, предъявить конкретный конфликт владельцу; не выбирать молча, не ослаблять безопасность, Fair Play или обязательную приёмку.

## 2. ChatGPT: короткий диалог, полные материалы в GitHub

- **По умолчанию ответ владельцу — краткая управленческая выжимка:** решение/статус, существенные блокеры и одно необходимое действие. Избегать длинных отчётов, повторных объяснений, последовательного пересказа тестов и десятков найденных дефектов в чате.
- Полное ТЗ, независимый аудит, реестр замечаний, команды, доказательства, схемы поведения и аргументация живут в соответствующих Markdown-файлах GitHub (ТЗ в `docs/specs/`, журнал в `docs/handoffs/`, нормативные инструкции в `docs/process/`). **Не заменять документ длинным сообщением в чат.**
- После подготовки/ревью владельцу отправлять **готовый короткий текст для Codex** с прямыми ссылками на файл ТЗ в точной ветке/PR, ссылкой на регламент, проверяемым scope, запретом самовольного merge и требованием выполнить всю матрицу. Не копировать содержимое самого ТЗ в чат.
- Дополнительные детали давать по запросу. Если нужно решение владельца (UX, опасные операции, данные, лицензии), назвать варианты и один конкретный вопрос, не скрывать блокер за краткостью.
- Если GitHub запись недоступна, не говорить «сохранено»; указать ограничение и предоставить пригодный для размещения полный документ другим доступным способом. Ничего не обещать выполнить позже без реального запущенного действия.

## 3. ChatGPT: техническое задание должно быть исполнимым, а не общим пожеланием

Автор ТЗ обязан **самостоятельно** проработать предложенную функцию до детально воспроизводимого решения. Codex не должен придумывать продуктовую логику, layout, значения, поведение ошибок или критерии готовности за владельца. Не оставлять фразы «сделать красиво/удобно/как у Lichess» без проверяемого уточнения.

Для **каждого затронутого пользовательского потока** ТЗ содержит:

1. Исходную проблему и наблюдаемое подтверждение; кто пользователь, цель, основной сценарий от входа до результата, в том числе возвращение назад.
2. **Сравнение реальных аналогов:** Lichess и Chess.com как первые ориентиры, другие подходящие проекты при необходимости. Указать источники/даты, как устроены действия, подсказки, результаты и переходы, достоинства/недостатки; отделить проверенный факт от предположения и назвать предпочтительный вариант с причиной. Не копировать чужие исходники, бренд/ассеты или дизайн вопреки лицензии.
3. Утверждённый **конкретный UX-контракт:** экраны, размеры и адаптивность, расположение элементов, все состояния (loading/empty/ready/error/success/retry), кнопки/жесты, подписи, переходы, фокус, scroll, обратная связь, accessibility, 100/125/150% DPI если применимо. Скрин/прототип — дополнение, а не замена тексту.
4. Шахматную/данную семантику: источник истины, FEN/PGN/ход, происхождение оценок и статистик, аккаунт/сессия, idempotency, persistence/migration, worker cancellation/stale callbacks, сеть/429, Fair Play. Отдельно — что **не** входит в задачу.
5. Точную карту реализации: существующие модули/файлы, переиспользуемые интерфейсы, рекомендуемые изменения, недопустимые обходные решения, миграции и зависимости (после проверки лицензии), стабильные ID требований и негативных сценариев.
6. Приёмку **каждого** требования: ожидаемый результат, объективное доказательство (тест, native capture, проверка данных, owner gate), FAIL/BLOCKED, ссылки и exact SHA.
7. План **L1→L2→L3 по CC-VERIFY-01** с узкими командами, конкретными границами и бюджетом CI.

Мелкие технические решения без изменения UX, данных или рисков Codex может принять сам с пояснением. Продуктовую неопределённость нужно разрешить анализом или точечным вопросом владельцу, а не скрытым допущением.

## 4. Ревью: один полный консолидированный проход, а не серия дозированных замечаний

**Главное требование:** при получении работы Codex провести **один максимально полный независимый аудит всей задачи A–Я до передачи замечаний**, а не выдавать только первые найденные 2–3 дефекта и заставлять владельца повторять цикл по старым находкам.

До завершения ревью обязательно:
1. Зафиксировать baseline/main, exact PR head и code SHA. Прочитать **всё действующее ТЗ и его поздние дополнения**, исходный баг-реестр, PR conversation/reviews, изменённые файлы, связанные пути интеграции и existing tests.
2. Создать **матрицу покрытия каждого ID и пользовательского состояния**: feature → утверждённый AC → место в коде → позитивный/негативный сценарий → доступные тесты/скриншоты → evidence → PASS/FAIL/RISK/NOT TESTED. Не проверять только diff: анализировать вызовы, события, данные и переходы до/после изменения.
3. Проходить блоками: пользовательский путь/UX; шахматные правила; данные/SQLite/миграции; Lichess/OAuth/аккаунты/429; асинхронность, гонки, отмена; Fair Play/секреты; производительность; Qt/UI/DPI; ошибки и восстановление; автоматические тесты, CI, актуальность документации и доставка в `main`/локальное окружение. Исключить неприменимые блоки **с объяснением**.
4. Подтвердить найденные дефекты кодом, тестом, наблюдением или артефактом. **Разделить** source-confirmed defect, воспроизводимый bug, UX gap, непроверенный risk и owner-only gate. Не выдавать предположения за найденные баги; не выдавать green CI за доказательство визуальной и реальной пользовательской приёмки.
5. Собрать **весь обнаруженный набор замечаний одной ревизией** в **том же ТЗ** в отдельном разделе независимого ревью либо существующем едином реестре; сохранять ID, приоритет, сценарий воспроизведения, ожидаемое поведение, адресное исправление, RED→GREEN тест, L2 и финальный L3 gate.
6. До сообщения «передать Codex» выполнить последний полный sweep по матрице, ключевым вызовам и устаревшим замечаниям, проверив, что список **не был искусственно разбит**. Передавать один консолидированный пакет в рамках одного текущего PR/цикла.
7. Если часть объектов нельзя проверить (нет артефакта/профиля/инструментов), честно отметить **REVIEW PARTIAL / NOT VERIFIED** и ограничения. Обещать «найдены абсолютно все ошибки» запрещено — цель максимальная полнота, а не ложная гарантия.

**Поздние обнаружения:** обычные пропущенные неблокирующие замечания фиксировать под существующими ID в едином техдолге/следующем согласованном цикле; не заставлять владельца повторять текущий цикл из-за постепенной выдачи старых находок. **Исключение:** безопасность, утрата данных, Fair Play, серьёзный P0/P1 или блокер приёмки немедленно сообщать и исправлять до merge; такие проблемы нельзя умышленно скрывать в техдолге. Новое изменение Codex может породить новую ошибку: проверить её отдельно, не называть это пропущенным прежним дефектом.

## 4а. Соразмерность риску: не искать «экзотику» ради бесконечной приёмки

**Масштаб:** Chess Coach — личное настольное Windows-приложение для нескольких человек. Приёмка должна доказать работоспособность важных сценариев, но не отсутствие всех математически возможных последовательностей потоков, сетевых запросов и состояний. **Это обязательное правило** для всех авторов ТЗ, GPT-чатов, Codex и ревьюеров.

1. **Приоритет:** согласованные AC, реальная игра/тренировка/анализ, удобство UI, правильные шахматные ходы, сохранение и повторное открытие данных, обычное переключение профиля, ожидаемые ошибки сети/OAuth, критичные Fair Play/безопасность. Проверять *затронутые* интеграционные границы, не выдумывать новые требования.
2. **Не заниматься целенаправленной охотой** за искусственными микросекундными race conditions, несколькими одновременными редкими отказами, ротацией токена ровно между emit и Qt-callback, экстремальными последовательностями закрытия/переключения без фактов практического возникновения. Теоретическое `could happen` **не делает сценарий P1**, не требует нового § ТЗ, RED-теста, тематического L2 и полного L3. Не расширять матрицу только ради самого расширения.
3. **Фильтр для каждого нового дефекта:** (а) есть ли правдоподобный путь пользователя или реалистичная внешняя ошибка? (б) какое конкретное последствие для владельца? (в) есть ли наблюдение, воспроизводимый тест либо убедительная кодовая причинная цепочка? (г) соразмерна ли стоимость исправления риску? При отсутствии правдоподобия, доказательств и существенного вреда — максимум короткая строка `RISK / TECH DEBT`, без блокирования merge и без повторного цикла.
4. **Не ослаблять безопасность:** доказанный или убедительно достижимый P0/P1 с утратой/порчей SQLite или PGN, раскрытием OAuth-секрета, смешением аккаунтов/личных записей, нарушением Fair Play, крашем/deadlock или неработающим основным сценарием остаётся блокером. Даже редкую **реально достижимую** тяжёлую ошибку исправлять; но запрещено приписывать тяжесть или воспроизводимость без фактов.
5. **Стоп-условие:** основные утверждённые AC, обязательная тематическая проверка и финальный Windows exact-code-SHA L3 — PASS, подтверждённых/убедительно достижимых P0/P1 нет → **закончить ревью и рекомендовать merge с последующей ручной проверкой владельца**. Не начинать новый «поиск всех следующих гонок» после каждого исправления. Позднюю неблокирующую мелочь — в общий техдолг или следующую *согласованную* задачу, не в новый §17→§18→§19 текущего PR.
6. **Честные границы:** авторизованный OAuth/личный компьютер/база владельца могут оставаться `OWNER ACCEPTANCE PENDING` и быть явно переданы владельцу, не приравнивая их к CI PASS и не запуская из-за них бесконечные кодовые циклы. Одиночный необъяснённый performance outlier без подтверждённого ухудшения обычного сценария — наблюдение, а не автоматический повод переписать подсистему.
7. **Стоимость тестирования:** L1→L2→один финальный L3 по CC-VERIFY-01 остаются обязательными для принятых изменений. **Фильтр риска применяется *до* создания тестового задания**. Не удалять проверки согласованных AC, Fair Play или безопасности ради экономии.

**Полное независимое ревью** = один проход по утверждённому scope, позитивным/реалистичным негативным состояниям и важным затронутым границам. Это **не поиск всех гипотетических interleavings**. Исключение из стоп-условия допускается только с конкретным обоснованием серьёзного риска.

## 5. Пользовательский продукт: онлайн-first, без «офлайн-версии» для владельца

- **Пользовательская концепция строится вокруг Lichess и полноценного онлайн-сценария.** Не проектировать, не рекламировать, не просить владельца тестировать отдельную «офлайн-версию», demo/fallback-задачи или вторую неполную копию приложения. Не отправлять владельцу offline smoke вместо проверки реального UX.
- **Внутреннее изолированное тестирование — другое понятие.** Текущий `--offline`, временная SQLite, fake transport, Qt offscreen и безопасный MainWindow smoke нужны для предотвращения случайных сетевых запросов, OAuth или операций над личными данными в CI; их **не удалять и не объявлять пользовательским режимом**. Внутренние команды имеют право упоминаться в инженерном отчёте, но не навязываются владельцу как «версия для проверки».
- Не удалять локальную шахматную доску/сохранённые данные или архитектурные safety gates без отдельного продуктового ТЗ и согласия. Если неясно, относится ли конкретный старый элемент UI к нежелательному офлайн-продукту или к обязательной локальной функции, сначала предъявить точное различие.
- Для онлайн UX сначала безопасные fake/unit и публичные read-only API там, где допустимо; проверку **авторизованного** Lichess и устройства владельца помечать отдельным owner gate, без скрытого доступа.

## 6. Тесты: минимальная стоимость итераций, не минимальная надёжность

Этот раздел **дополняет, но не отменяет** `CC-VERIFY-01`.

- **L1** после небольших изменений: `git diff --check`, compile изменённых модулей, только новые и прямо затронутые тесты/взаимодействия/негативные случаи. Уже зелёные и не затронутые наборы не запускать повторно в каждом цикле.
- **L2** один тематический прогон после связанного блока: изменённый компонент + **реально затронутые интеграционные границы** (не только тесты файла, поскольку изменения могут ломать аккаунт, SQLite, сигнал или игру). Native Qt только для затронутого экрана/размеров. Зафиксировать конкретный список тестов до реализации.
- **L3** финальный **полный Windows exact-head CI**, compileall, безопасный isolated/offscreen MainWindow smoke, обязательная visual matrix — **один раз перед сдачей**. Это пока обязательный проектный gate. После L3 повторять только при изменении исполняемого поведения/тестов/ресурсов или подтверждённом сбое финального gate; docs-only не повод для полного повтора. Отказ от L3 требует отдельного изменения нормативного регламента и явного решения владельца, а не одностороннего решения исполнителя.
- Не создавать пачки мелких коммитов с дорогостоящим полным CI; использовать cancel-in-progress, при необходимости поправить triggers отдельно, не прятать избыточную стоимость. Сохранять уже собранные evidence на том же code SHA. Если более одного полного L3 — указать реальную причину и как улучшены L1/L2.
- Сокращать **ненужные** тесты, а не приёмочные сценарии/проверки опасных границ. SQLite migrations, Fair Play, auth races, UCI/Qt threading могут потребовать более широкого адресного покрытия.

## 7. Рабочие ветки, доставка и отчёт

1. Нормативные изменения вносить **отдельным документационным PR от `main`**, не коммитить в активный кодовый PR и не делать merge без решения владельца. Пока PR правил не слит, он доступен по branch-specific URL и **не автоматически обязателен** для уже работающего Codex: в текущем задании ему нужно явно передать ссылку на новый документ. После merge использовать ссылку `main`.
2. В новую исполняемую спецификацию включать прямую ссылку на этот контракт и на `CC-VERIFY-01`, поддерживать принятый marker `verification-contract`; новые требования и ревью держать в одном спецификационном файле/реестре без каскада дублей.
3. **К владельцу:** краткое решение/статус и **готовое сообщение для Codex со ссылкой на GitHub ТЗ**; детали в Markdown. **К Codex:** точный branch/SHA, приоритетные ссылки, полный охват, отчёт об доказательствах/блокерах, запрет merge.
4. Ничего не считать завершённым, пока не подтверждены проверяемые критерии. В отчёте различать DONE IN CODE, TESTED IN RUNNER, OWNER ACCEPTANCE PENDING и NOT IMPLEMENTED.
