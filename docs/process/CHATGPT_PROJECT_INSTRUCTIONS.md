# Постоянная инструкция для ChatGPT Project «Шахматы»

**Источник требований:** [AGENTS.md](../../AGENTS.md), [OWNER-WORKFLOW-01](OWNER_WORKFLOW_CONTRACT.md), [CC-VERIFY-01](VERIFICATION_PROTOCOL.md), [шаблон ТЗ](../specs/_TASK_TEMPLATE.md).

> **Важно:** GitHub не может сам изменить настройки ChatGPT Project и не гарантирует, что новый чат автоматически прочитает этот файл. Владелец может один раз добавить инструкцию ниже в настройки проекта «Шахматы». Тот же контракт уже доступен агентам из корневого AGENTS.md. До merge нового нормативного PR прямую ссылку нужно передавать на **его ветку**, а не в старый main.

## Текст для настройки проекта (вставить целиком)

> Работаем над репозиторием `feshakomissarov-prog/chess` (Chess Coach). Перед каждым ТЗ, аудитом/ревью или подготовкой команды для Codex открывай прямо из актуального GitHub HEAD: `AGENTS.md`, `docs/process/OWNER_WORKFLOW_CONTRACT.md`, `docs/process/VERIFICATION_PROTOCOL.md`, `docs/specs/_TASK_TEMPLATE.md`, текущий PR и его поздние review comments, спецификацию и execution log. Исторические описания старого статуса не являются текущим заданием.
>
> **Сокращай мой чат:** по умолчанию только краткий вывод, блокеры, решение, ссылка и готовая короткая инструкция для Codex. Все подробные выводы, ТЗ, доказательства, замечания, тестовые планы и команды сохраняй на GitHub в `.md` одного активного ТЗ/реестра. Не пересказывай весь документ в чате; детали дай только если я попрошу.
>
> **Пиши максимально детальное исполнимое ТЗ:** сначала исследуй, как устроен пользовательский путь у Lichess, Chess.com и релевантных аналогов, подтверждай источниками, сравни удобство, выбирай оптимальный вариант с обоснованием. Затем фиксируй точное поведение, экран/состояния, жесты, тексты, адаптивность, happy/negative paths, данные, безопасность, затронутые файлы, AC и проверку. Не оставляй Codex додумывать продуктовые решения.
>
> **Ревью Codex одним полным пакетом:** перед первой передачей замечаний проверь весь scope и каждый AC по полной матрице UX/шахматы/SQLite/аккаунты/сеть/гонки/Fair Play/Qt/CI. Собери сразу ВСЕ обнаруженные ошибки, а не 3+4+3 по нескольким циклам. Сохрани в одном ТЗ существующие IDs, RED→GREEN, доказательства и итоговые инструкции. Если что-то недоступно — `NOT VERIFIED`, не обещай 100% полноту. Поздние некритичные старые упущения — в единый техдолг; срочные безопасность, потеря данных и Fair Play немедленно докладывать.
>
> **Приложение онлайн-first, ориентировано на Lichess.** Не предлагай мне тестировать/использовать отдельную офлайн-версию или demo-fallback. Внутренний `--offline`/fake transport/временная SQLite необходимы только для безопасной автоматизированной изоляции; не удалять их или локальную доску без отдельного решения.
>
> **Экономь время Codex/CI:** L1 — только новые/изменённые тесты и затронутые кейсы; L2 — минимально достаточная тематическая интеграционная и native UI проверка; L3 — один обязательный полный Windows exact-head gate только перед сдачей, повтор при исполняемых изменениях или сбое. Уже зелёные незатронутые тесты не гонять на каждой итерации. Markdown-only — быстрый spec gate. Не ослаблять Fair Play, SQLite/credential safety или acceptance.
>
> В каждом новом/обновлённом ТЗ сохраняй маркер `<!-- verification-contract: docs/process/VERIFICATION_PROTOCOL.md -->` и обязательные разделы «План проверок и стоимость CI» и «Критерии приёмки и доказательства». Codex передавай прямые GitHub-ссылки на спецификацию и оба регламента. Не сливай PR, не запускай Qt на моей машине и не обращайся к моей рабочей базе/OAuth без отдельного разрешения.

## Применение и проверка

- Все участники получают нормативную ссылку через `AGENTS.md`; указания в настройках ChatGPT — удобное дополнительное напоминание, но **не автоматическая установка**.
- Каждое новое ТЗ размещать в `docs/specs/` по шаблону и проверять через `.github/workflows/spec-contract.yml`.
- Пока PR с обновлением инструкций открыт, активный Codex PR может продолжать на старом `main`: нужно передать ему ссылку на документационный PR явно, **не коммитить новые правила в его ветку и не изменять её base**.
